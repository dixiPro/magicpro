## Что такое связь

Связь — это когда поле записи хранит не значение, а **указатель на другую запись**.

Две ленты:

```
лента "category"                    лента "blog"
id=3  title="Рецепты"               id=41  title="Борщ"
id=7  title="Новости"               id=42  title="Открылся филиал"
```

Статья «Борщ» относится к категории «Рецепты». Записать это можно двумя способами.

**Плохо:** положить в статью строку `"Рецепты"`. Переименуют категорию — статья останется
со старым названием. Появятся две категории с одинаковым именем — станет непонятно, какая
имелась в виду.

**Хорошо:** положить в статью число `3` — идентификатор записи-категории. Переименование
категории на статью не влияет, потому что связь идёт по идентификатору, а не по тексту.

### Уточнение про `uid` и `id`

`uid` — код **ленты** (`blog`, `category`), один на всю ленту целиком. Отдельная запись
опознаётся своим `id`.

Поэтому в поле лежит **`id` записи**, а из какой она ленты — само поле не знает. Это
объявляется в схеме.

## Объявление

К обычному числовому полю добавляются два ключа:

| Ключ  | Обязателен | Назначение                                                                      |
| ----- | ---------- | ------------------------------------------------------------------------------- |
| `ref` | да         | `uid` ленты, на которую ссылается поле                                          |
| `as`  | нет        | Имя, под которым отдаётся сама запись. По умолчанию — `code` без суффикса `_id` |

```json
{
  "fields": [
    { "code": "title", "column": "string_1", "label": "Заголовок" },
    { "code": "category_id", "column": "bigint_1", "label": "Категория", "widget": "select", "ref": "category" },
    { "code": "author_id", "column": "bigint_2", "label": "Автор", "widget": "select", "ref": "user" }
  ]
}
```

Читается так: «в `bigint_1` лежит `id` записи из ленты `category`».

`ref` допустим только на числовых слотах. Лента, указанная в `ref`, должна существовать.

В админке такое поле рисуется выпадающим списком записей указанной ленты. Что показывать в
списке — см. вопрос 5.

## PHP API

### Чтение

```php
$post->category_id;      // 3 — то, что лежит в колонке
$post->category;         // запись категории целиком, или null
$post->category->title;  // «Рецепты»
```

Разделение как в Eloquent: `category_id` — данные, `category` — связанная запись.

### Запись

```php
$post->category_id = 3;
$post->category = $categoryRecord;   // допустимо, положит его id
$post->category_id = null;           // связь снята
```

### Выборка

Фильтр идёт по колонке и пользуется уже существующим индексом — никаких join:

```php
MproHelper::feed('blog')
    ->where('category_id', 3)
    ->where('published', true)
    ->orderBy('mpro.position')
    ->paginate(10);
```

Обратный обход — это тот же самый запрос. Отдельного механизма «все статьи категории» не
нужно: он выражается через `where`.

### Жадная загрузка

```php
MproHelper::feed('blog')->with('category')->get();
```

Без неё вывод списка из тридцати статей с названием категории у каждой даст тридцать
лишних запросов. `with()` собирает все `category_id` списка и достаёт категории **одним**
запросом.

`with()` принимает имя из `as`, а не имя колонки.

## Деревья

Дерево — это ссылка ленты на саму себя:

```json
{ "code": "parent_id", "column": "bigint_5", "label": "Родитель", "ref": "category" }
```

```
id=3  title="Рецепты"    parent_id=null
id=9  title="Супы"       parent_id=3
id=14 title="Борщи"      parent_id=9
```

Один уровень в обе стороны получается сразу и дёшево:

```php
$category->parent;                                           // родитель
MproHelper::feed('category')->where('parent_id', 3)->get();  // прямые дети
```

Обход на произвольную глубину — см. вопрос 1, это единственный нерешённый вопрос,
влияющий на структуру данных.

Защита от цикла: запись не может быть родителем самой себе, и при назначении родителя
проверяется, что назначаемый не находится ниже по ветке.

## Связи «многие ко многим»

Отдельного механизма нет и не будет. Если у статьи должно быть несколько тегов, оператор
создаёт обычную ленту-связку с двумя полями:

```json
{
  "uid": "blog_tag",
  "fields": [
    { "code": "post_id", "column": "bigint_1", "ref": "blog" },
    { "code": "tag_id", "column": "bigint_2", "ref": "tag" }
  ]
}
```

```php
MproHelper::feed('blog_tag')->where('post_id', 41)->with('tag')->get();
```

Движок при этом не знает, что `blog_tag` чем-то особенная. Это обычная лента: те же
индексы, тот же CRUD в админке, то же мягкое удаление, тот же экспорт. Порядок тегов у
статьи — её собственный `position`.

Цена ровно одна: нет `$post->tags()`, ходить надо в два шага.

## Целостность

Ссылки не чистятся автоматически. Удалили категорию — в статьях остался её `id`, ведущий
в никуда. См. вопросы 2 и 3.

Смена `uid` ленты запрещена основным ТЗ. Со ссылками цена ошибки выше: `uid` лежит в `ref`
чужих схем.

### Запрет удаления ленты

В `task18_v5.md` удаление ленты запрещено, если она участвует в связях. Здесь это значит:
нельзя удалить ленту, на которую есть `ref` в схеме любой другой ленты. См. вопрос 4.

## Что убрано и почему

В версиях v2а и v3а был второй механизм — универсальная таблица `feed_relations` со
своими индексами, `attach`/`detach`/`sync`, `whereRelated` и отдельной веткой в `with()`.
Он убран целиком.

**Возможность при этом не потеряна, потеряна только фича.** Связь «многие ко многим»
собирается лентой-связкой из уже существующего — оператором, мышкой, без единой строки
кода в движке.

**Убрана именно сложность.** Вместе с таблицей ушли: три индекса, четыре метода API,
чистка связей при удалении, команда обслуживания висячих строк — и **восемь из девяти**
открытых вопросов предыдущей версии. Показательно, что почти все нерешённые вопросы ТЗ
принадлежали одному этому механизму: сложность была не в задаче, а в конструкции.

Универсальная таблица связей — классическое место, где умирают производительность и
целостность: строковый `uid` в каждой строке, два направления обхода, висячие записи,
никаких внешних ключей.

Если когда-нибудь понадобится сахар `$post->tags()`, его добавляют объявлением в схеме, по
образцу `hasManyThrough`, **не заводя ни одной новой таблицы**:

```json
{ "code": "tags", "through": "blog_tag", "local": "post_id", "far": "tag_id", "feed": "tag" }
```

Хранение не меняется, добавляется только сборка запроса. Поэтому откладывается без риска.

## Вопросы

**1. Дерево на произвольную глубину.** Один уровень работает сам собой. А «все товары в
категории и во всех её подкатегориях»? Варианты:

- не поддерживать — проект пишет обход сам
- рекурсивный обход в движке — просто, но это N запросов на N уровней
- материализованный путь (`/3/9/14/`) в строковом слоте — один запрос `LIKE '/3/%'`, но
  путь надо пересчитывать при переносе ветки, и он занимает слот

Единственный вопрос, меняющий структуру данных. Вводить задним числом дороже, чем сразу.
Моё мнение: если каталог товаров с вложенными категориями в планах есть — берём третий
вариант; если деревья только для меню на два уровня — первый.

**2. Что отдавать при битой ссылке.** Категорию удалили, `category_id` в статьях остался.
`$post->category` — `null` или исключение? Предлагаю `null`: страница со статьёй должна
открыться даже с потерянной категорией, а не падать пятисоткой.

**3. Предупреждать ли при удалении записи, на которую ссылаются.** Удаляем категорию, а на
ней висят сорок статей. Варианты: молча удалить, предупредить и дать удалить, запретить.
Записи удаляются мягко, так что катастрофы нет — `restore()` вернёт всё. Предлагаю
предупреждать, но не запрещать.

**4. Как отвечать на «кто ссылается на эту ленту».** Нужно для запрета удаления ленты из
`task18_v5.md`. Прямой способ — перебрать `schema` всех лент и поискать `ref`. Лент
немного, запрос дешёвый, но он нужен при каждом удалении. Считать на месте или держать
реестр ссылок?

**5. Что показывать в выпадающем списке.** Поле с `ref` рисуется списком записей чужой
ленты — но какое поле показывать оператору? Первый строковый слот? Поле с `code = title`?
Или в `ref`-описании указывать явно, например `"display": "title"`?
