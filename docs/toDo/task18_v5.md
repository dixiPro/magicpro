# ТЗ v5. Модуль «Ленты» (Feeds). Две таблицы

Действующая версия. Связи между лентами — отдельное ТЗ `task18_v2a.md`.
История: `task18.md` → `task18_v2.md` → `task18_v3.md` → `task18_v4.md` → этот файл.

## Цель

Универсальный модуль хранения данных: произвольные сущности (блог, новости, FAQ, отзывы,
сотрудники, вакансии, платежи) без написания нового CRUD.

Главная цель — максимально простой движок, покрывающий 90–95% задач небольших сайтов.

MagicPro не является конструктором баз данных. Это механизм хранения с фиксированной
структурой таблиц и API, внешне похожим на Laravel Query Builder. Разработчик работает с
логическими именами полей, физические колонки скрыты.

Везде, где можно опереться на Laravel, опираемся на Laravel: Eloquent, пагинатор, касты,
Spatie Media Library.

## Структура БД

### Таблица `feeds`

Описание ленты. Метаданные, а не данные — по ней не ищут, поэтому описание полей лежит
одним JSON-столбцом.

| Колонка      | Тип    | Назначение                                |
| ------------ | ------ | ----------------------------------------- |
| `id`         | bigint | Первичный ключ                            |
| `uid`        | string | Код ленты, по нему идёт обращение из кода |
| `title`      | string | Человекочитаемое название                 |
| `schema`     | json   | Описание полей                            |
| `lock`       | bool   | Лента защищена от изменений               |
| `created_at` |        |                                           |
| `updated_at` |        |                                           |

Удаление ленты физическое — см. раздел «Удаление ленты».

**`uid` не редактируется после создания.** Он лежит в `feed_items.feed_uid` и в обеих
колонках таблицы связей; при переименовании всё это осиротеет. Набор символов —
`^[a-z0-9_-]+$`, `UNIQUE`.

**`lock = true` запрещает** правку схемы и удаление ленты.

#### Формат `schema`

Массив, порядок элементов = порядок полей в форме.

```json
{
  "fields": [
    { "code": "title", "column": "string_1", "label": "Заголовок", "widget": "input" },
    { "code": "slug", "column": "string_2", "label": "URL", "widget": "input", "unique": true },
    { "code": "content", "column": "text_1", "label": "Текст", "widget": "textarea" },
    { "code": "published_at", "column": "bigint_2", "label": "Дата", "widget": "date", "cast": "datetime" },
    { "code": "price", "column": "bigint_3", "label": "Цена", "widget": "input", "cast": "money" },
    { "code": "user_id", "column": "bigint_1", "label": "Автор" },
    { "code": "is_new", "column": "bool_1", "label": "Новинка", "widget": "checkbox" }
  ]
}
```

| Ключ     | Обязателен | Назначение                                               |
| -------- | ---------- | -------------------------------------------------------- |
| `code`   | да         | Логическое имя, им пользуется разработчик                |
| `column` | да         | Физическая колонка в `feed_items`                        |
| `label`  | нет        | Подпись в админке, по умолчанию = `code`                 |
| `widget` | нет        | Тип поля в форме, по умолчанию выводится из типа колонки |
| `cast`   | нет        | Преобразование значения при чтении и записи              |
| `unique` | нет        | Значение уникально внутри ленты                          |

`code` подчиняется `^[a-z][a-z0-9_]*$`, уникален внутри ленты и **не может быть словом
`mpro`** — оно зарезервировано под системные атрибуты. Точка в имени невозможна, поэтому
`mpro.` в запросах ни с чем не пересекается.

#### `cast`

Новых физических типов не вводим. Дата и деньги живут в `bigint`, а Eloquent приводит их
на лету:

| `cast`     | Хранится                               | Отдаётся в PHP                 |
| ---------- | -------------------------------------- | ------------------------------ |
| `datetime` | unix timestamp в `bigint`              | `Carbon`                       |
| `money`    | целое в минимальных единицах (копейки) | int, форматирование при выводе |
| нет        | как есть                               | как есть                       |

Такое хранение сортируется и индексируется наравне с обычными числами. Новый физический
тип — это навсегда: он попадает в таблицу, в индексы и в миграции, а каст меняется
правкой JSON.

### Таблица `feed_items`

Хранит данные. Структура фиксированная.

| Колонка                  | Назначение                     |
| ------------------------ | ------------------------------ |
| `id`                     | Первичный ключ                 |
| `feed_uid`               | К какой ленте относится запись |
| `string_1` … `string_10` | Строковые поля                 |
| `text_1` … `text_5`      | Текстовые поля                 |
| `bigint_1` … `bigint_5`  | Числовые поля                  |
| `bool_1` … `bool_5`      | Булевы поля                    |
| `json`                   | Резервное хранилище            |
| `position`               | Позиция внутри `feed_uid`      |
| `visible`                | Показывать запись или нет      |
| `created_at`             |                                |
| `updated_at`             |                                |

#### Правила

- **`bool_*` никогда не `NULL`.** При создании записи все булевы колонки получают `0`.
  Иначе записи, созданные до появления поля, не попадут ни в выборку по `true`, ни по
  `false`.
- **`visible` при создании = `false`.** Редактор сам ставить его в true, после готовности иначе на сайте появятся пустые данные.
- **Незанятые колонки хранятся как `NULL`, а не как пустая строка.** Это важно для проверки
  уникальности: два `NULL` не считаются одинаковыми, две пустые строки — считаются.
- **`position` при создании = `max(position) + 1`** внутри своей ленты. Не ноль — иначе у
  всех новых записей одинаковая позиция.

#### `json` — резервное хранилище

Всё, что не влезло в колонки, кладётся сюда. Колонки нужны для фильтрации и сортировки; то,
что просто хранится и выводится, в `json`.

Фильтровать по содержимому `json` модуль не умеет и не будет: Laravel это позволяет
(`where('json->key', …)`), но SQLite и MySQL ведут себя по-разному, и переносимость
пострадает. Если проекту нужен интерфейс к этим данным — под него пишется своя админка.

#### Видимость и удаление записей

Мягкого удаления нет. Вместо него — колонка `visible`, и два разных, честно названных
действия:

| Что хочет владелец      | Что делает        | Что происходит                             |
| ----------------------- | ----------------- | ------------------------------------------ |
| Временно убрать с сайта | `visible = false` | Запись цела, в админке видна, на сайте нет |
| Убрать навсегда         | Удалить           | Строка и медиафайлы удаляются физически    |

Скрыть и удалить — разные намерения, и они не должны прятаться за одной кнопкой. Корзины,
восстановления и деления на «мягкое/жёсткое» нет: нечего путать и не за чем следить.

#### `visible` не фильтруется автоматически

Движок **не скрывает записи сам**. `visible` — обычная системная колонка, доступная как
`$post->mpro->visible`, а решение принимает шаблон.

Так сделано ради предпросмотра: владелец должен уметь открыть скрытую новость по её адресу
и увидеть, как она будет выглядеть на сайте. Если бы движок молча выбрасывал невидимые
записи из выборок, страница отдавала бы 404 и посмотреть было бы нечего.

**В списках фильтр ставится явно:**

```php
MproHelper::feed('news')
    ->where('mpro.visible', true)
    ->orderBy('mpro.position')
    ->paginate(10);
```

**На странице записи решает блейд:**

```blade
@if( $post->mpro->visible )
    {{-- обычный вывод --}}
@else
    {{-- скрытую видит только администратор, проверка та же, что на сайте --}}
@endif
```

Плата за это — фильтр в списке можно забыть, и черновик уедет на сайт. Взамен
предпросмотр работает без единой строки специального кода.

Удаление необратимо, поэтому оно должно спрашивать подтверждение, а выгрузка ленты
(см. «Экспорт и импорт») перестаёт быть удобством и становится единственной страховкой.

### Медиа

Spatie Media Library. Количество изображений не ограничено. Требует, чтобы запись была
Eloquent-моделью — это и заложено в архитектуру.

### Индексы

Индексируются **все** строковые и числовые колонки. На таблице до десяти тысяч записей и при
редкой записи цена восемнадцати индексов несущественна.

Порядок колонок: сначала равенство, потом сортировка, в конце `id`. `visible` стоит сразу
после `feed_uid`, потому что подставляется в **каждый** запрос сайта — без него индекс
перестаёт покрывать выборку.

| Индекс                                                             | Для чего                                       |
| ------------------------------------------------------------------ | ---------------------------------------------- |
| `(feed_uid, visible, position, id)`                                | Список ленты по порядку — главный запрос сайта |
| `(feed_uid, visible, created_at, id)`                              | Список по дате                                 |
| `(feed_uid, visible, string_1)` … `(feed_uid, visible, string_10)` | Поиск по строковым полям                       |
| `(feed_uid, visible, bigint_1)` … `(feed_uid, visible, bigint_5)`  | Поиск по числовым полям                        |

Текстовые поля не индексируются.

Все индексы **статические, создаются миграцией**. `ALTER TABLE` из админки не делается
никогда.

`id` в конце сортировочных индексов — не про скорость, а про корректность: см. «Пагинация».

### Уникальность значений

вообще не понятно

Флаг `unique` в схеме проверяется **кодом перед записью**, уникальных индексов на колонки
нет.

Причина: слот общий для всех лент. Индекс `UNIQUE (feed_uid, string_2)` заставит быть
уникальным второй строковый слот у всех лент сразу — а другая лента держит там, скажем,
название отдела, и два сотрудника из одного отдела в неё уже не запишутся. Уникальность —
свойство поля конкретной ленты, индекс — свойство колонки таблицы, одно на другое не
ложится. Частичные индексы (`WHERE feed_uid = 'blog'`) MySQL не поддерживает.

Проверка идёт по всем записям ленты, включая скрытые: `visible = false` — это «не
показывать», а не «освободить значение».

## Удаление ленты

Удаление ленты физическое, как и удаление записи. Промежуточных состояний в модуле нет
нигде: скрыть — это `visible`, удалить — это удалить.

### Порядок

1. **Проверка связей.** Если лента участвует в связях с другими лентами — удаление
   запрещено, с перечислением того, что мешает. Это семантика `RESTRICT` из внешних
   ключей.
2. **Проверка `lock`.** При `lock = true` удаление запрещено.
3. **Предложение выгрузить дамп** — с прямой ссылкой на выгрузку.
4. **Подтверждение вводом `uid`.** Оператор вручную набирает код ленты. Кнопку «вы
   уверены?» жмут не глядя, ввод имени — единственный приём, который действительно
   работает; так удаляют репозитории на GitHub.
5. **Удаление** — лента, все её записи, включая скрытые, и все медиафайлы.

### Требования к реализации

Удаление не атомарно: строки в базе, файлы на диске. Поэтому:

- идёт **пачками**, а не одним `DELETE`
- пишется в лог
- **повторный запуск доводит начатое до конца**, если первый упал на середине

Точка проверки связей закладывается сразу, даже пока связей нет. Иначе о ней забудут, и
первая же удалённая лента унесёт с собой чужие данные.

После удаления `uid` освобождается: осиротевших записей не остаётся, унаследовать нечего.

### CRUD записей

Форма строится по `schema`. `widget` берётся из описания поля, если не задан — выводится
из типа колонки: `string` → `input`, `text` → `textarea`, `bool` → `checkbox`,
`bigint` → `input`.

## PHP API

### Пространство имён `mpro`

Единое правило и для свойств, и для запросов:

- **без префикса** — логическое поле ленты
- **с префиксом `mpro.`** — системная колонка

```php
->where('title', 'Статья')        // логическое поле
->where('mpro.id', 15)            // системный id
->orderBy('mpro.position')        // системная позиция
->orderBy('position')             // логическое поле ленты с именем position
```

Без этого правила `orderBy('position')` был бы неоднозначным: слово `position` формально
свободно под логическое поле, но так же называется системная колонка.

`find(15)` по-прежнему ищет по системному `id`.

Системные имена: `mpro.id`, `mpro.position`, `mpro.visible`, `mpro.json`, `mpro.feedUid`,
`mpro.createdAt`, `mpro.updatedAt`.

### Чтение

```php
MproHelper::feed('blog')
```

Возвращает `FeedQuery`. Поддержать: `where()`, `orWhere()`, `whereIn()`, `orderBy()`,
`limit()`, `offset()`, `first()`, `find()`, `get()`, `count()`, `exists()`, `paginate()`.

Обращение к несуществующей ленте — исключение, а не пустая выборка. Опечатка в `uid`
должна быть слышна сразу.

```php
// страница записи: берём независимо от visible, показывать или нет решает блейд
$post = MproHelper::feed('blog')
    ->where('slug', $slug)
    ->first();

// список на сайте: фильтр ставится явно
MproHelper::feed('blog')
    ->where('mpro.visible', true)
    ->paginate(10);
```

Разработчик никогда не работает с `string_1`, `text_3`, `bigint_2` — только с логическими
именами. Преобразование `slug` → `string_2` происходит внутри `FeedQuery` по `schema`
ленты.

### Запись

```php
// создание
$id = MproHelper::feed('blog')->create([
    'title' => 'Привет',
    'slug'  => 'privet',
]);

// изменение по условию
MproHelper::feed('blog')
    ->where('slug', 'privet')
    ->update(['title' => 'Другой заголовок']);

// изменение записи
$post->title = 'Другой заголовок';
$post->save();

// скрыть с сайта, запись цела
$post->mpro->visible = false;
$post->save();

// удалить навсегда, вместе с медиафайлами
$post->delete();
```

Правила записи:

- неуказанные поля сохраняют текущее значение
- поле, которого нет в `schema` ленты — ошибка, а не молчаливое игнорирование
- `position` при создании выставляется автоматически
- `unique` проверяется кодом перед записью

### Получение данных

Запись отдаёт свойства по логическим именам:

```php
$post->title;
$post->slug;
$post->content;
$post->user_id;
```

а не `$post->string_1`.

Системные данные — через `mpro`:

```php
$post->mpro->id;
$post->mpro->position;
$post->mpro->visible;
$post->mpro->json;
$post->mpro->feedUid;
$post->mpro->createdAt;
$post->mpro->updatedAt;
```

Занято только слово `mpro`. Имена `id`, `position`, `json`, `created_at` остаются
свободными под поля ленты.

### Пагинация

Штатный `LengthAwarePaginator`, никаких своих велосипедов.

```php
$posts = MproHelper::feed('blog')
    ->orderBy('mpro.position')
    ->paginate(10);
```

В блейде работает `{{ $posts->links() }}`.

Два требования, без которых пагинация тихо ломается:

1. **Сортировка всегда однозначна.** К любому `orderBy` автоматически добавляется
   `mpro.id` вторым ключом. Иначе при одинаковых значениях одна запись покажется на двух
   страницах, а другая не покажется нигде.
2. **Номер страницы приходит строкой из URL** — приводится к int и зажимается в
   `[1, lastPage]`. Значения `page=abc`, `page=-5`, `page=0` не должны ломать выборку.

Для длинных лент предусмотреть `simplePaginate()` — он не делает второй запрос `COUNT(*)`.

Статья, выводящая ленту, должна иметь `routeParams.getEnable = true`, иначе параметр `page`
до неё не доедет.

## Архитектура

Отдельный неймспейс, а не свалка в `MproHelper`:

| Класс                       | Ответственность                                                                                      |
| --------------------------- | ---------------------------------------------------------------------------------------------------- |
| `Feed`                      | Eloquent-модель ленты, разбор `schema`                                                               |
| `FeedItem`                  | Eloquent-модель записи, подмена имён атрибутов, видимость, Spatie Media                              |
| `FeedQuery`                 | Построитель запросов, **единственное место**, где логические имена превращаются в физические колонки |
| `FeedExport` / `FeedImport` | Выгрузка и загрузка ленты архивом                                                                    |
| `API_Feeds`                 | Командный API для админки, в стиле `AbstractApi`                                                     |

`MproHelper::feed($uid)` — строчка-обёртка над `FeedQuery`, чтобы блейды звали без `use`.

Остальной код о физических колонках не знает.

### Целостность

Внешних ключей не заводим, чистка кодом. Операции удаления редкие, скорость значения не
имеет.

## Не реализовывать
