# ТЗ v2а. Модуль «Ленты». Связи между лентами

Дополнение к `task18_v2.md`. Реализуется после того, как две основные таблицы заработают.

## Цель

Связывать записи разных лент между собой одной универсальной таблицей, не заводя под
каждую пару сущностей свою pivot-таблицу.

Примеры:

- `blog` → `category` — у статьи одна категория
- `blog` → `tags` — у статьи много тегов
- `product` → `category`
- `user` → `roles`
- `payment` → `order`
- `category` → `category` — дерево категорий

## Структура БД

### Таблица `feed_relations`

| Колонка | Назначение |
| --- | --- |
| `id` | Первичный ключ |
| `parent_feed_uid` | Лента родителя |
| `parent_item_id` | Запись родителя |
| `child_feed_uid` | Лента потомка |
| `child_item_id` | Запись потомка |
| `relation` | Имя связи |
| `position` | Порядок потомка внутри связи |
| `created_at` | |

### Индексы

| Индекс | Для чего |
| --- | --- |
| `(parent_feed_uid, parent_item_id, relation, position)` | Прямой обход: теги статьи |
| `(child_feed_uid, child_item_id, relation)` | **Обратный обход: все статьи категории** |
| `(parent_feed_uid, parent_item_id, relation, child_feed_uid, child_item_id)` | Уникальность связи |

Обратный индекс критичен. Без него «все записи в категории» — самый частый запрос
каталога и блога — идёт полным сканом таблицы связей.

## Объявление связей

Связь описывается в `schema` ленты-родителя, рядом с полями:

```json
{
  "fields": [ ... ],
  "relations": [
    { "code": "category", "feed": "category", "type": "one"  },
    { "code": "tags",     "feed": "tag",      "type": "many" }
  ]
}
```

| Ключ | Назначение |
| --- | --- |
| `code` | Имя связи в коде, оно же значение колонки `relation` |
| `feed` | `uid` ленты-потомка |
| `type` | `one` — вернуть запись, `many` — вернуть коллекцию |

Объявление решает две задачи. Во-первых, опечатка `categorys` ловится сразу, а не даёт
молча пустую выборку. Во-вторых, API знает, что возвращать — объект или коллекцию.

## PHP API

### Чтение

```php
$post->category();     // одна запись или null
$post->tags();         // коллекция
$user->roles();
```

Обратный обход — от потомка к родителям:

```php
MproHelper::feed('blog')
    ->whereRelated('category', $categoryId)
    ->where('published', true)
    ->paginate(10);
```

### Жадная загрузка

```php
MproHelper::feed('blog')
    ->with('tags')
    ->paginate(10);
```

Связи грузятся **отдельным запросом**, как это делает Eloquent, а не джойном к основному.
При джойне запись с тремя тегами превращается в три строки, `count()` показывает 3 вместо
1, и пагинация едет. Это требование, а не рекомендация.

### Запись

По образцу Eloquent:

```php
$post->attach('tags', $tagId);
$post->detach('tags', $tagId);
$post->sync('tags', [$id1, $id2, $id3]);   // приводит набор к указанному
```

`position` в связи выставляется как `max + 1`, `sync` расставляет по порядку массива.

## Целостность

Внешних ключей нет, чистка кодом:

- удалили запись — сносятся все связи, где она участвует как родитель или как потомок
- удалили ленту — сносятся все связи, где она участвует любой стороной

Операции редкие, скорость значения не имеет.

## Вопросы по этому ТЗ

Связи — самая скользкая часть модуля, поэтому вопросов больше, и почти каждый меняет
устройство API.

### Направление и симметрия

**1. Кто кому родитель?** В примере `blog` → `category` статья названа родителем, а
категория потомком. Интуитивно обычно наоборот: категория содержит статьи. Это не
придирка к словам — от выбора зависит, в чьей `schema` объявляется связь и какой из двух
индексов окажется горячим.

Предлагаю читать так: **родитель — тот, у кого связь объявлена и от кого её вызывают**.
`$post->tags()` значит, что статья родитель, тег потомок, а `relation = 'tags'`.

**2. Нужен ли обратный обход как метод?** `$category->posts()` — это чтение той же строки
справа налево. Варианты: объявлять обратную связь в `schema` категории отдельно
(`{"code": "posts", "feed": "blog", "type": "many", "inverse": "category"}`), либо не
объявлять и пользоваться только `whereRelated()`. Первое удобнее в блейдах, второе проще
в реализации. Что важнее?

**3. Может ли одна пара лент иметь несколько разных связей?** Например, у статьи есть и
`author`, и `editor`, обе указывают на ленту `user`. Таблица это позволяет — различаются
по `relation`. Подтвердите, что так и задумано, потому что это влияет на уникальный
индекс: уникальна тройка «родитель + relation + потомок», а не пара «родитель + потомок».

### Тип связи и ограничения

**4. Кто следит за `type: one`?** Если связь объявлена как «одна категория», а в таблице
оказалось две строки — что делать: вернуть первую, вернуть ошибку, или не допускать
второй записи при `attach`? Предлагаю третье: `attach` при `type: one` заменяет
существующую связь.

**5. Уникальность связи.** Можно ли привязать один тег к статье дважды? Считаю, что нет —
и это должен обеспечивать уникальный индекс, а не проверка в коде.

**6. Циклы и деревья.** `category` → `category` даёт дерево категорий, и это очень
вероятный сценарий. Тогда возникают вопросы, которых нет у плоских связей: защита от
цикла (A родитель B, B родитель A), обход вверх до корня, обход вниз со всеми уровнями,
ограничение глубины. Нужно ли это в v2а, или дерево пока строим руками через несколько
запросов?

Это, на мой взгляд, главный вопрос ТЗ. Если дерево нужно — стоит сразу решить, храним ли
рядом материализованный путь, иначе «все товары в категории и её подкатегориях» превратится
в рекурсию запросов.

### Сортировка и выборка

**7. По какому `position` сортировать связанные записи?** Их два: `position` в
`feed_relations` (порядок тегов у статьи) и `position` в `feed_items` (порядок тега в
своей ленте). Для тегов обычно нужен первый, для категорий — второй. Предлагаю: по
умолчанию `feed_relations.position`, с возможностью переопределить.

**8. Можно ли фильтровать связанные?** Например, «опубликованные теги статьи»:
`$post->tags()->where('published', true)`. Это значит, что `tags()` возвращает не
коллекцию, а `FeedQuery`, и коллекцию отдаёт только `get()`. Так делает Eloquent, но это
заметно усложняет реализацию. Нужно ли в первой версии?

**9. `whereRelated` по нескольким.** «Статьи, у которых есть теги 1 и 5» — это `AND`,
`INTERSECT` или два `EXISTS`? А «есть хотя бы один из» — `OR`? Нужны ли обе формы, или в
v2а хватит одной связи в фильтре?

### Целостность и эксплуатация

**10. Висячие связи.** Чистку кодом мы приняли, но код может не сработать: упало
исключение, запись удалили напрямую в базе, импорт данных прошёл мимо API. Нужна ли
команда обслуживания, которая находит и сносит связи с несуществующими записями? Без неё
такие строки будут накапливаться незаметно и отдавать `null` в середине коллекции.

**11. Что возвращать при битой связи?** Связь есть, а запись-потомок удалена. Отдавать
`null` в коллекции, молча пропускать, или считать это ошибкой данных?

**12. Смена `uid` ленты.** В основном ТЗ я предложил запретить. Со связями цена ошибки
выше: `uid` лежит в двух колонках `feed_relations`, и при переименовании осиротеет всё.
Это ещё один довод за запрет, но если менять всё же придётся — нужна процедура, которая
обновляет обе таблицы в транзакции.

**13. Нужен ли `relation` в схеме потомка?** Сейчас связь объявлена только у родителя.
Значит, глядя на ленту `tag`, нельзя узнать, кто на неё ссылается — а это нужно, чтобы в
админке предупредить при удалении: «на этот тег ссылаются 43 статьи». Вычислять запросом
по `feed_relations` или дублировать объявление?
