# ТЗ v3. Модуль «Ленты» (Feeds). Две таблицы

Действующая версия. Связи между лентами — отдельное ТЗ `task18_v2a.md`.
История: `task18.md` → `task18_v2.md` → этот файл.

## Цель

Универсальный модуль хранения данных: произвольные сущности (блог, новости, FAQ, отзывы,
сотрудники, вакансии, платежи) без написания нового CRUD.

Главная цель — максимально простой движок, покрывающий 90–95% задач небольших сайтов.

MagicPro не является конструктором баз данных. Это механизм хранения с фиксированной
структурой таблиц и API, внешне похожим на Laravel Query Builder. Разработчик работает с
логическими именами полей, физические колонки скрыты.

Везде, где можно опереться на Laravel, опираемся на Laravel: Eloquent, пагинатор, касты,
SoftDeletes, Spatie Media Library.

## Структура БД

### Таблица `feeds`

Описание ленты. Метаданные, а не данные — по ней не ищут, поэтому описание полей лежит
одним JSON-столбцом.

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `id` | bigint | Первичный ключ |
| `uid` | string | Код ленты, по нему идёт обращение из кода |
| `title` | string | Человекочитаемое название |
| `schema` | json | Описание полей |
| `lock` | bool | Лента защищена от изменений |
| `created_at` | | |
| `updated_at` | | |

**`uid` не редактируется после создания.** Он лежит в `feed_items.feed_uid` и в обеих
колонках таблицы связей; при переименовании всё это осиротеет. Набор символов —
`^[a-z0-9_-]+$`, уникален. `title` меняется свободно.

**`lock = true` закрывает и правку схемы, и удаление ленты.**

#### Формат `schema`

Массив, порядок элементов = порядок полей в форме.

```json
{
  "fields": [
    { "code": "title",        "column": "string_1", "label": "Заголовок",    "widget": "input" },
    { "code": "slug",         "column": "string_2", "label": "URL",          "widget": "input",    "unique": true },
    { "code": "content",      "column": "text_1",   "label": "Текст",        "widget": "textarea" },
    { "code": "published_at", "column": "bigint_2", "label": "Дата",         "widget": "date",     "cast": "datetime" },
    { "code": "price",        "column": "bigint_3", "label": "Цена",         "widget": "input",    "cast": "money" },
    { "code": "user_id",      "column": "bigint_1", "label": "Автор" },
    { "code": "published",    "column": "bool_1",   "label": "Опубликовано", "widget": "checkbox" }
  ]
}
```

| Ключ | Обязателен | Назначение |
| --- | --- | --- |
| `code` | да | Логическое имя, им пользуется разработчик |
| `column` | да | Физическая колонка в `feed_items` |
| `label` | нет | Подпись в админке, по умолчанию = `code` |
| `widget` | нет | Тип поля в форме, по умолчанию выводится из типа колонки |
| `cast` | нет | Преобразование значения при чтении и записи |
| `unique` | нет | Значение уникально внутри ленты |

#### `cast`

Новых физических типов не вводим. Дата и деньги живут в `bigint`, а Eloquent приводит их
на лету:

| `cast` | Хранится | Отдаётся в PHP |
| --- | --- | --- |
| `datetime` | unix timestamp в `bigint` | `Carbon` |
| `money` | целое в минимальных единицах (копейки) | int, форматирование при выводе |
| нет | как есть | как есть |

Такое хранение сортируется и индексируется наравне с обычными числами. Новый физический
тип — это навсегда: он попадает в таблицу, в индексы и в миграции, а каст меняется
правкой JSON.

### Таблица `feed_items`

Хранит данные. Структура фиксированная.

| Колонка | Назначение |
| --- | --- |
| `id` | Первичный ключ |
| `feed_uid` | К какой ленте относится запись |
| `string_1` … `string_10` | Строковые поля |
| `text_1` … `text_5` | Текстовые поля |
| `bigint_1` … `bigint_5` | Числовые поля |
| `bool_1` … `bool_5` | Булевы поля |
| `json` | Резервное хранилище |
| `position` | Позиция внутри `feed_uid` |
| `deleted_at` | Мягкое удаление |
| `created_at` | |
| `updated_at` | |

#### Правила

- **`bool_*` никогда не `NULL`.** При создании записи все булевы колонки получают `0`.
  Иначе записи, созданные до появления поля, не попадут ни в выборку по `true`, ни по
  `false`.
- **`bool_1` — всегда флаг видимости** (`published`, `active`, `visible`). Соглашение
  нужно, чтобы одним составным индексом покрыть главный запрос сайта, а не заводить по
  индексу на каждый из пяти булевых слотов.
- **Незанятые слоты хранятся как `NULL`, а не как пустая строка.** Это важно для проверки
  уникальности: два `NULL` не считаются одинаковыми, две пустые строки — считаются.
- **`position` при создании = `max(position) + 1`** внутри своей ленты. Не ноль — иначе у
  всех новых записей одинаковая позиция.

#### `json` — резервное хранилище

Всё, что не влезло в слоты, кладётся сюда. Колонки нужны для фильтрации и сортировки; то,
что просто хранится и выводится, живёт в `json`.

Фильтровать по содержимому `json` модуль не умеет и не будет: Laravel это позволяет
(`where('json->key', …)`), но SQLite и MySQL ведут себя по-разному, и переносимость
пострадает. Если проекту нужен интерфейс к этим данным — под него пишется своя админка.

#### Мягкое удаление

`deleted_at` и трейт `SoftDeletes`. Данные не пропадают: удалённое из выборок исчезает, но
остаётся в базе и достаётся через `withTrashed()`.

### Медиа

Spatie Media Library. Количество изображений не ограничено. Требует, чтобы запись была
Eloquent-моделью — это и заложено в архитектуру.

### Индексы

Составные, порядок колонок: сначала равенство, потом сортировка, в конце `id`.

`deleted_at` стоит сразу после `feed_uid`, потому что `SoftDeletes` подставляет
`deleted_at IS NULL` в **каждый** запрос — без него индекс перестаёт покрывать выборку.

| Индекс | Для чего |
| --- | --- |
| `(feed_uid, deleted_at, position, id)` | Список ленты по порядку |
| `(feed_uid, deleted_at, bool_1, position, id)` | Список опубликованного — главный запрос сайта |
| `(feed_uid, deleted_at, created_at, id)` | Список по дате |
| `(feed_uid, deleted_at, string_1)` … `(feed_uid, deleted_at, string_3)` | Поиск по строковому полю, например `slug` |
| `(feed_uid, deleted_at, bigint_1)` … `(feed_uid, deleted_at, bigint_3)` | Поиск по числовому полю |

Текстовые поля не индексируются.

`id` в конце сортировочных индексов — не про скорость, а про корректность: см. «Пагинация».

### Уникальность значений

Флаг `unique` в схеме проверяется **кодом перед записью**, уникальных индексов в базе нет.

Причина: слот общий для всех лент. Индекс `UNIQUE (feed_uid, string_2)` заставит быть
уникальным второй строковый слот у всех лент сразу — а другая лента держит там, скажем,
название отдела, и два сотрудника из одного отдела в неё уже не запишутся. Уникальность —
свойство поля конкретной ленты, индекс — свойство колонки таблицы, одно на другое не
ложится. Частичные индексы (`WHERE feed_uid = 'blog'`) MySQL не поддерживает.

Проверка идёт среди неудалённых записей: слот, освобождённый мягким удалением, считается
свободным.

## Админка

Раздел **Ленты**.

- список лент
- создание ленты
- удаление ленты вместе со всеми её записями
- изменение названия
- настройка полей: логическое имя, подпись, виджет
- переключатель `lock`

При `lock = false` оператор распоряжается схемой свободно: переименовал поле — поедет его
собственный CRUD, это его дело. **Данные при правке схемы не трогаются никогда**: ни
очистки колонок, ни переноса значений.

### CRUD записей

Форма строится по `schema`. `widget` берётся из описания поля, если не задан — выводится
из типа колонки: `string` → `input`, `text` → `textarea`, `bool` → `checkbox`,
`bigint` → `input`.

## PHP API

### Чтение

```php
MproHelper::feed('blog')
```

Возвращает `FeedQuery`. Поддержать: `where()`, `orWhere()`, `whereIn()`, `orderBy()`,
`limit()`, `offset()`, `first()`, `find()`, `get()`, `count()`, `exists()`, `paginate()`,
`withTrashed()`.

```php
$post = MproHelper::feed('blog')
    ->where('slug', $slug)
    ->where('published', true)
    ->first();
```

Разработчик никогда не работает с `string_1`, `text_3`, `bigint_2` — только с логическими
именами. Преобразование `slug` → `string_2`, `published` → `bool_1` происходит внутри
`FeedQuery` по `schema` ленты.

### Запись

```php
// создание
$id = MproHelper::feed('blog')->create([
    'title'     => 'Привет',
    'slug'      => 'privet',
    'published' => true,
]);

// изменение по условию
MproHelper::feed('blog')
    ->where('slug', 'privet')
    ->update(['published' => false]);

// изменение записи
$post->title = 'Другой заголовок';
$post->save();

// мягкое удаление и восстановление
$post->delete();
$post->restore();
```

Правила записи:

- неуказанные поля сохраняют текущее значение
- поле, которого нет в `schema` ленты — ошибка, а не молчаливое игнорирование
- `position` при создании выставляется автоматически
- `unique` проверяется кодом перед записью

### Получение данных

Запись отдаёт свойства по логическим именам:

```php
$post->title;
$post->slug;
$post->content;
$post->user_id;
```

а не `$post->string_1`.

Служебные данные вынесены за одно имя, чтобы не отбирать у оператора удобные логические
имена. Занято только слово `mpro`; `id`, `position`, `json`, `created_at` остаются
свободными для полей ленты:

```php
$post->mpro->id;
$post->mpro->position;
$post->mpro->json;
$post->mpro->createdAt;
$post->mpro->updatedAt;
$post->mpro->deletedAt;
$post->mpro->feedUid;
```

### Пагинация

Штатный `LengthAwarePaginator`, никаких своих велосипедов.

```php
$posts = MproHelper::feed('blog')
    ->where('published', true)
    ->orderBy('position')
    ->paginate(10);
```

В блейде работает `{{ $posts->links() }}`.

Два требования, без которых пагинация тихо ломается:

1. **Сортировка всегда однозначна.** К любому `orderBy` автоматически добавляется `id`
   вторым ключом. Иначе при одинаковых `position` одна запись покажется на двух страницах,
   а другая не покажется нигде.
2. **Номер страницы приходит строкой из URL** — приводится к int и зажимается в
   `[1, lastPage]`. Значения `page=abc`, `page=-5`, `page=0` не должны ломать выборку.

Для длинных лент предусмотреть `simplePaginate()` — он не делает второй запрос `COUNT(*)`.

Статья, выводящая ленту, должна иметь `routeParams.getEnable = true`, иначе параметр `page`
до неё не доедет.

## Архитектура

Отдельный неймспейс, а не свалка в `MproHelper`:

| Класс | Ответственность |
| --- | --- |
| `Feed` | Eloquent-модель ленты, разбор `schema` |
| `FeedItem` | Eloquent-модель записи, подмена имён атрибутов, SoftDeletes, Spatie Media |
| `FeedQuery` | Построитель запросов, **единственное место**, где логические имена превращаются в физические колонки |
| `API_Feeds` | Командный API для админки, в стиле `AbstractApi` |

`MproHelper::feed($uid)` — строчка-обёртка над `FeedQuery`, чтобы блейды звали без `use`.

Остальной код о физических колонках не знает.

### Целостность

Внешних ключей не заводим, чистка кодом. При удалении ленты сносятся все её записи.
Операция редкая, скорость значения не имеет.

## Не реализовывать в этой версии

- связи между лентами — отдельное ТЗ `task18_v2a.md`
- фильтрация по содержимому `json`
- динамическое создание SQL-таблиц
- пользовательские типы полей
- миграции структуры
- конструктор схем
- вычисляемые поля
- сложные валидаторы
- мультиязычность данных (интерфейс — да, данные — нет)

## Открытые вопросы

**1. Сколько индексов заводить.** Единственный вопрос из v2, оставшийся без ответа.
Проиндексировать все 10 строковых и 5 числовых слотов — это 15 вторичных индексов на
таблицу: медленнее запись, больше объём. Я заложил первые три слота каждого типа, то есть
соглашение «под поиск занимай первые слоты». Альтернатива — флаг `index` в схеме и
создание индексов по факту, но это `ALTER TABLE` во время работы, а от динамического
изменения структуры мы уходим. **Оставляем первые три?**

**2. Мягкое удаление лент.** Записи теперь удаляются мягко. А сама лента? Сейчас в ТЗ
написано, что удаление ленты сносит её записи насовсем. Если «хранить всё» относится и к
лентам, `deleted_at` нужен и в `feeds`, и тогда удаление ленты — это просто пометка, а
записи остаются нетронутыми.

**3. Чистка корзины.** Мягко удалённые записи копятся вечно и попадают в каждый индекс.
Нужна ли команда, которая физически сносит записи старше N дней? Если да — параметр
хранения общий или задаётся на ленту?

**4. `$post->mpro->id` — так «заковыристее» достаточно?** Плюс варианта в том, что он
резервирует одно имя вместо пяти: `id`, `position`, `json`, `created_at`, `updated_at`
остаются свободны под поля ленты.
