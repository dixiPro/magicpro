# ТЗ v3а. Модуль «Ленты». Связи между лентами

Дополнение к `task18_v5.md`. Реализуется после того, как две основные таблицы заработают.
История: связи в `task18.md` → `task18_v2a.md` → этот файл.

## Что такое связь

Связь — это когда поле записи хранит не значение, а **указатель на другую запись**.

Разберём на блоге. Есть две ленты:

```
лента "category"                    лента "blog"
id=3  title="Рецепты"               id=41  title="Борщ"
id=7  title="Новости"               id=42  title="Открылся филиал"
```

Статья «Борщ» относится к категории «Рецепты». Записать это можно двумя способами.

**Плохо:** положить в статью строку `"Рецепты"`. Переименуют категорию — статья останется
со старым названием. Появятся две категории с одинаковым именем — станет непонятно, какая
имелась в виду.

**Хорошо:** положить в статью число `3` — идентификатор записи-категории. Переименование
категории на статью не влияет, потому что связь идёт по идентификатору, а не по тексту.

### Важное уточнение про `uid`

`uid` — это код **ленты** (`blog`, `category`), один на всю ленту целиком. Отдельная
запись опознаётся своим `id`.

Поэтому в поле лежит **`id` записи**, а из какой она ленты — само поле не знает. Это
объявляется в схеме:

```json
{ "code": "category_id", "column": "bigint_1", "ref": "category", "as": "category" }
```

Читается так: «в первом числовом слоте лежит `id` записи из ленты `category`».

## Два механизма

Сколько ссылок нужно хранить — столько и определяет способ.

| Что нужно | Чем делается | Цена |
| --- | --- | --- |
| **Одна** ссылка: категория, автор, бренд, отдел | `ref` в поле, `id` в `bigint`-слоте | Ноль: слот уже проиндексирован |
| **Много** ссылок: теги, роли, похожие товары | Таблица `feed_relations` | Отдельная таблица, свои индексы, отдельный запрос |

Первый механизм закрывает большинство реальных связей и не стоит ничего. Второй нужен
там, где ссылок несколько и их число заранее неизвестно.

Правило простое: **одна ссылка — поле, много ссылок — таблица связей.**

## Механизм 1. Ссылка в поле

### Объявление

К обычному полю добавляются два ключа:

| Ключ | Назначение |
| --- | --- |
| `ref` | `uid` ленты, на которую ссылается поле |
| `as` | Имя, под которым отдаётся сама запись. По умолчанию — `code` без суффикса `_id` |

```json
{
  "fields": [
    { "code": "title",       "column": "string_1", "label": "Заголовок" },
    { "code": "category_id", "column": "bigint_1", "label": "Категория", "widget": "select", "ref": "category" },
    { "code": "author_id",   "column": "bigint_2", "label": "Автор",     "widget": "select", "ref": "user" }
  ]
}
```

Поле с `ref` рисуется в админке выпадающим списком записей указанной ленты.

### Чтение

```php
$post->category_id;      // 3 — то, что лежит в колонке
$post->category;         // запись категории целиком, или null
$post->category->title;  // «Рецепты»
```

Разделение как в Eloquent: `category_id` — данные, `category` — связанная запись.

### Запись

```php
$post->category_id = 3;
$post->category = $categoryRecord;   // допустимо, положит его id
```

### Выборка

Фильтр идёт по колонке и пользуется существующим индексом — никаких join:

```php
MproHelper::feed('blog')
    ->where('category_id', 3)
    ->where('published', true)
    ->paginate(10);
```

### Жадная загрузка

```php
MproHelper::feed('blog')->with('category')->get();
```

Без неё вывод списка из тридцати статей с названием категории у каждой даст тридцать
лишних запросов. `with()` собирает все `category_id` списка и достаёт категории **одним**
запросом.

## Механизм 2. Таблица связей

Для случаев «много ко многим»: у статьи несколько тегов, у пользователя несколько ролей,
у товара несколько сопутствующих.

### Таблица `feed_relations`

| Колонка | Назначение |
| --- | --- |
| `id` | Первичный ключ |
| `parent_feed_uid` | Лента родителя |
| `parent_item_id` | Запись родителя |
| `child_feed_uid` | Лента потомка |
| `child_item_id` | Запись потомка |
| `relation` | Имя связи |
| `position` | Порядок потомка внутри связи |
| `created_at` | |

**Родитель — тот, у кого связь объявлена и от кого её вызывают.** `$post->tags()` значит:
статья родитель, тег потомок, `relation = 'tags'`.

Пример строк для статьи 41 с тремя тегами:

| parent_feed_uid | parent_item_id | child_feed_uid | child_item_id | relation | position |
| --- | --- | --- | --- | --- | --- |
| blog | 41 | tag | 5 | tags | 1 |
| blog | 41 | tag | 8 | tags | 2 |
| blog | 41 | tag | 12 | tags | 3 |

### Индексы

| Индекс | Для чего |
| --- | --- |
| `(parent_feed_uid, parent_item_id, relation, position)` | Прямой обход: теги статьи |
| `(child_feed_uid, child_item_id, relation)` | **Обратный обход: все статьи с этим тегом** |
| `UNIQUE (parent_feed_uid, parent_item_id, relation, child_feed_uid, child_item_id)` | Один и тот же тег нельзя привязать дважды |

Обратный индекс критичен: без него «все записи с этим тегом» идёт полным сканом таблицы
связей.

Уникальность делается индексом, а не проверкой в коде — здесь, в отличие от `unique` у
полей ленты, колонки не переиспользуются под разные смыслы, поэтому индекс уместен.

### Объявление

В `schema` ленты-родителя, рядом с полями:

```json
{
  "fields": [ … ],
  "relations": [
    { "code": "tags",    "feed": "tag" },
    { "code": "related", "feed": "product" }
  ]
}
```

| Ключ | Назначение |
| --- | --- |
| `code` | Имя связи в коде, оно же значение колонки `relation` |
| `feed` | `uid` ленты-потомка |

Ключа `type` нет: **связь через таблицу всегда «много».** Одиночная ссылка делается полем
с `ref`, для неё отдельная таблица не нужна. Одно правило вместо двух режимов.

Объявление ловит опечатку: `$post->tagz()` падает сразу, а не отдаёт молча пустую
коллекцию.

### Чтение

```php
$post->tags();          // коллекция записей ленты tag
$user->roles();
```

Обратный обход — от потомка к родителям:

```php
MproHelper::feed('blog')
    ->whereRelated('tags', $tagId)
    ->where('published', true)
    ->paginate(10);
```

### Жадная загрузка

```php
MproHelper::feed('blog')->with('tags')->paginate(10);
```

Связи грузятся **отдельным запросом**, а не join к основному. При join статья с тремя
тегами превращается в три строки, `count()` показывает 3 вместо 1, и пагинация едет. Это
требование, а не рекомендация.

### Запись

```php
$post->attach('tags', $tagId);
$post->detach('tags', $tagId);
$post->sync('tags', [$id1, $id2, $id3]);   // приводит набор к указанному
```

`position` выставляется как `max + 1`, `sync` расставляет по порядку массива.

## Деревья

Дерево категорий — это ссылка ленты на саму себя, то есть **механизм 1**, а не таблица
связей:

```json
{ "code": "parent_id", "column": "bigint_5", "ref": "category" }
```

```
id=3  title="Рецепты"    parent_id=null
id=9  title="Супы"       parent_id=3
id=14 title="Борщи"      parent_id=9
```

Один уровень вверх или вниз получается сразу и дёшево:

```php
$category->parent;                                        // родитель
MproHelper::feed('category')->where('parent_id', 3)->get();  // прямые дети
```

Что **не** получается дёшево — «все товары в категории и во всех её подкатегориях».
Такой запрос требует либо рекурсии, либо хранения пути. См. вопрос 3.

## Целостность

Внешних ключей нет, чистка кодом:

- удалили запись — сносятся все строки `feed_relations`, где она участвует любой стороной
- удалили ленту — сносятся все строки, где она участвует любой стороной

Ссылки в полях (`ref`) при этом **не** чистятся автоматически: удалили категорию — в
статьях остался её `id`, ведущий в никуда. См. вопросы 6 и 7.

Смена `uid` ленты запрещена основным ТЗ. Со связями цена ошибки выше: `uid` лежит в двух
колонках `feed_relations` и в `ref` чужих схем.

### Связь с удалением ленты

В `task18_v5.md` удаление ленты запрещено, если она участвует в связях. Проверять надо оба
механизма:

- есть ли строки в `feed_relations` с этой лентой любой стороной
- есть ли в схемах других лент поля с `ref` на неё

## Вопросы

Ни один вопрос предыдущей версии пока не закрыт. Часть из них снялась сама — введение
ссылок в поле убрало режим `type: one` и споры о том, кто следит за его соблюдением.
Осталось девять, и первые три — важные.

### Главные

**1. Нужен ли обратный обход как метод?** `$category->posts()` — это чтение той же строки
справа налево. Варианты: объявлять обратную связь в схеме потомка
(`{ "code": "posts", "feed": "blog", "inverse": "tags" }`), либо не объявлять и
пользоваться только `whereRelated()`. Первое удобнее в блейдах, второе проще в
реализации. И то же самое для ссылок в поле: нужен ли `$category->posts()`, когда связь
живёт в поле статьи?

**2. Фильтрация связанных.** Например, «опубликованные теги статьи»:
`$post->tags()->where('published', true)`. Это значит, что `tags()` возвращает не
коллекцию, а `FeedQuery`, и коллекцию отдаёт только `get()`. Так делает Eloquent, но
реализация заметно усложняется. Нужно ли в первой версии, или `tags()` сразу отдаёт
коллекцию?

**3. Глубина дерева.** Один уровень работает сам собой. А «все товары в категории и во
всех подкатегориях»? Варианты:

- не поддерживать, пусть проект пишет рекурсию сам
- поддерживать рекурсивным обходом — просто, но это N запросов на N уровней
- хранить материализованный путь (`/3/9/14/`) в строковом слоте — один запрос по `LIKE
  '/3/%'`, но путь надо пересчитывать при переносе ветки

Это главный вопрос ТЗ: третий вариант меняет структуру данных, и вводить его задним числом
дороже, чем сразу.

### Поведение

**4. Несколько связей между одной парой лент.** У статьи `author_id` и `editor_id`, обе
ссылаются на ленту `user` — с механизмом 1 это просто два поля, вопросов нет. А через
таблицу связей: `related` и `accessories`, обе на `product`, различаются по `relation`.
Подтвердите, что так и задумано.

**5. Сортировка связанных.** Есть два `position`: в `feed_relations` (порядок тегов у
статьи) и в `feed_items` (порядок тега в своей ленте). Для тегов обычно нужен первый, для
категорий — второй. Предлагаю по умолчанию `feed_relations.position` с возможностью
переопределить.

**6. Что возвращать при битой ссылке?** Категорию удалили, `category_id` в статьях остался.
`$post->category` — `null`, исключение, или запись-заглушка? Для коллекций: пропускать
битые элементы молча или отдавать `null` внутри коллекции?

**7. Чистить ли `ref` при удалении записи.** Удалили категорию — пройтись по всем лентам,
у которых есть `ref` на неё, и обнулить поле? Это дорого и затрагивает чужие данные.
Альтернатива — оставить как есть и жить с вопросом 6. Я склоняюсь ко второму, но тогда
удаление записи, на которую ссылаются, стоит хотя бы предупреждать в админке.

### Эксплуатация

**8. Команда обслуживания.** Висячие строки появятся при любой аккуратности: упало
исключение, запись удалили напрямую в базе, импорт прошёл мимо API. Нужна ли команда,
которая находит и сносит связи с несуществующими записями?

**9. Кто ссылается на ленту.** Чтобы в админке предупредить «на этот тег ссылаются 43
статьи» — и чтобы работал запрет удаления ленты из `task18_v5.md` — нужно уметь отвечать
на вопрос «кто на меня ссылается». Для `feed_relations` это запрос по обратному индексу.
Для `ref` — перебор схем всех лент. Вычислять каждый раз или держать реестр?
