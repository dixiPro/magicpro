# ТЗ. Модуль «Ленты» (Feeds) для MagicPro

## Цель

Создать универсальный модуль хранения данных, позволяющий создавать произвольные сущности
(блог, новости, FAQ, отзывы, сотрудники, вакансии, платежи и т.д.) без написания нового CRUD.

Главная цель — максимально простой движок, покрывающий 90–95% задач небольших сайтов.

## Структура БД

### Таблица `feeds`

Описание ленты.

| Колонка                            | Назначение                                |
| ---------------------------------- | ----------------------------------------- |
| `id`                               | Первичный ключ                            |
| `uid`                              | Код ленты, по нему идёт обращение из кода |
| `title`                            | Человекочитаемое название                 |
| `string_1_code` … `string_10_code` | Логические имена строковых полей          |
| `text_1_code` … `text_5_code`      | Логические имена текстовых полей          |
| `bigint_1_code` … `bigint_5_code`  | Логические имена числовых полей           |
| `bool_1_code` … `bool_5_code`      | Логические имена булевых полей            |
| `created_at`                       |                                           |
| `updated_at`                       |                                           |

Например:

```
string_1_code = title
string_2_code = slug

text_1_code   = content

bigint_1_code = user_id

bool_1_code   = published
```

### Таблица `feed_items`

Хранит данные.

| Колонка                  | Назначение                     |
| ------------------------ | ------------------------------ |
| `id`                     | Первичный ключ                 |
| `feed_uid`               | К какой ленте относится запись |
| `string_1` … `string_10` | Строковые поля                 |
| `text_1` … `text_5`      | Текстовые поля                 |
| `bigint_1` … `bigint_5`  | Числовые поля                  |
| `bool_1` … `bool_5`      | Булевы поля                    |
| `json`                   | Дополнительное поле            |
| `position`               | Позиция внутри `feed_uid`      |
| `created_at`             |                                |
| `updated_at`             |                                |

`json` используется исключительно как дополнительное поле.

### Таблица `feed_relations`

Универсальная таблица связей.

| Колонка           | Назначение           |
| ----------------- | -------------------- |
| `id`              | Первичный ключ       |
| `parent_feed_uid` | Лента родителя       |
| `parent_item_id`  | Запись родителя      |
| `child_feed_uid`  | Лента потомка        |
| `child_item_id`   | Запись потомка       |
| `relation`        | Имя связи            |
| `position`        | Порядок внутри связи |
| `created_at`      |                      |

Примеры:

- `blog` → `category`
- `blog` → `tags`
- `product` → `category`
- `user` → `roles`
- `payment` → `order`

Позволяет строить любые связи между лентами.

### Медиа

Использовать Spatie Media Library. Количество изображений не ограничивается.

### Индексы

- `feed_uid`
- `(feed_uid, position)`
- `feed_uid + string_i`
- `feed_uid + bigint_i`
- `feed_uid + bool_i`

Текстовые поля не индексируются.

## Админка

Раздел **Ленты**.

Возможности:

- список лент
- создание ленты
- удаление
- изменение названия
- настройка полей

Для каждого поля задаётся программное имя. Например: `title`, `slug`, `content`,
`published`, `user_id`.

Типы полей пока фиксированы.

## CRUD

Форма строится автоматически:

- поле с именем `title` — рисуется `input`
- поле с именем `content` — рисуется `textarea`

Позже типы можно расширить.

## PHP API

API максимально похоже на Laravel.

### Получение ленты

```php
MproHelper::feed('blog')
```

Поддержать: `where()`, `orWhere()`, `whereIn()`, `orderBy()`, `limit()`, `offset()`,
`first()`, `find()`, `get()`, `count()`, `exists()`.

### Главное правило

Разработчик никогда не работает с `string_1`, `text_3`, `bigint_2`. Он работает только с
логическими именами.

```php
$post = MproHelper::feed('blog')
    ->where('slug', $slug)
    ->where('published', true)
    ->first();
```

MagicPro автоматически преобразует `slug` и `published` в `string_2` и `bool_1` согласно
описанию ленты.

### Получение данных

Запись должна возвращать свойства по логическим именам:

```php
$post->title;
$post->slug;
$post->content;
$post->user_id;
```

а не `$post->string_1`.

### Связи

Работа должна напоминать Eloquent.

```php
$post->categories();
$product->category();
$user->roles();
```

или

```php
MproHelper::feed('blog')
    ->with('categories')
    ->get();
```

Связи строятся через таблицу `feed_relations`.

### Position

Поле `position` используется только внутри одной ленты.

```sql
WHERE feed_uid = 'blog'
ORDER BY position
```

## Архитектура

Все преобразования — `title` → `string_1`, `slug` → `string_2`, `content` → `text_1`,
`published` → `bool_1` — должны происходить в одном месте (например, `FeedQuery`).

Остальной код не должен знать о физических колонках.

## Основная идея проекта

MagicPro не является конструктором баз данных.

Это универсальный механизм хранения данных с фиксированной структурой таблиц и максимально
удобным API, внешне похожим на Laravel Query Builder.

Разработчик работает с логическими именами полей и связями между сущностями, а внутреннее
отображение на физические колонки полностью скрыто системой.

## Не реализовывать в первой версии

- динамическое создание SQL-таблиц
- пользовательские типы полей
- миграции структуры
- конструктор схем
- вычисляемые поля
- сложные валидаторы

Цель первой версии — простая, быстрая и надёжная реализация универсального CRUD с
поддержкой связей.

## Замечания и вопросы

### Пробелы, которые надо закрыть до начала работы

**1. В ТЗ нет записи данных.** Описано только чтение: `where`, `get`, `first`. Нет
`create()`, `update()`, `save()`, `delete()`. При этом CRUD в админке есть. Значит вопрос:
пишутся ли записи только руками через админку, или из кода тоже? Почти наверняка тоже —
форма обратной связи, регистрация, импорт. Без этого модуль наполовину.

> в тз нет, пропустил

**2. Что происходит при удалении и переназначении поля.** Оператор освободил
`string_2_code` (было `slug`) и потом назначил туда `nickname`. Данные в колонке
`string_2` остались от старого поля — новое поле сразу «родится» с чужими значениями.
Нужно решить: обнулять колонку у всех записей ленты при освобождении слота, или запретить
переиспользование. Я за обнуление, но это разрушающая операция, её надо подтверждать в
админке.

> добавить в feeds поле lock. Если закрыть изменения в админке нет. А так пусть оператор делает что хочет. Ну переименует поле и что? Ну полетит у него CRUD и что? Главное данные не трогать, а так он вырулит.

**3. Индексы для `feed_relations` не описаны.** В разделе «Индексы» только `feed_items`.
Нужны два: прямой `(parent_feed_uid, parent_item_id, relation, position)` и **обратный**
`(child_feed_uid, child_item_id, relation)`. Без обратного `$category->posts()` — то есть
«все записи в категории», самый частый запрос блога — пойдёт полным сканом.

> feed_relations пока слаббо проработана, возможно нужно ее оставить на 2-ю версию

**4. Целостность.** Что при удалении ленты — каскадом сносятся `feed_items` и все
`feed_relations`, где она участвует? Что при удалении записи — чистятся связи? Делать это
внешними ключами БД или кодом? SQLite, MySQL и PostgreSQL все умеют FK, но в SQLite их
надо включать явно.

> Делать руками. скорее всего. Очистка данных операция очень редкая и если она будет идти медленно да и хрен с ним.

**5. Значения по умолчанию для `bool_*`.** Если поле `published` добавили после того, как в
ленте появились записи, у них будет `NULL`, а не `0`. Тогда
`->where('published', false)` их не найдёт, и они пропадут из обеих выборок сразу. Нужно
правило: булево поле при создании записи всегда `0`, никогда `NULL`.

> правильное замечание, принимается

### Вопросы к вам

**6. Что такое `uid`?** Строка вроде `blog` или число? Из `MproHelper::feed('blog')` видно,
что строка. Тогда: уникальна, какой набор символов, и — главное — **можно ли её менять
после создания**? Если да, все `feed_items.feed_uid` и обе колонки в `feed_relations`
осиротеют. Я бы запретил менять `uid`, а `title` пусть меняется свободно.

**7. Мультиязычность.** Мы только что решили этот вопрос для документации. Ленты — это
контент сайта, и он тоже может быть многоязычным. Если переводы понадобятся, решать надо
сейчас: либо колонка `lang` в `feed_items`, либо отдельная лента на язык. Задним числом
это переделывается тяжело.

> нет, это не потянем, мультиязычность интерфейса, но не данных.

**8. Нужны ли служебные типы?** В списке нет даты и нет денег. Дата ложится в `bigint`
(unix timestamp) — сортируется и индексируется. Цена — в `bigint` в копейках. Это стоит
записать в ТЗ явно как соглашение, иначе на каждом сайте будет своё.

> можно подумать добавить еще типов, какие?

**9. Уникальность значений.** Для `slug` она нужна почти всегда. Сейчас индексы
`feed_uid + string_i` неуникальные. Добавлять ли флаг уникальности на поле?

**10. Пагинация.** `limit`/`offset` есть, `paginate()` нет. Для блога нужна почти сразу.
В первой версии можно жить на `count()` + `limit`/`offset`, но лучше решить осознанно.

> да по максиму используем ЛАРАВЕЛjn

### Замечания по архитектуре

**11. Spatie Media Library требует Eloquent-модель.** Трейт `HasMedia` вешается на модель.
Значит запись ленты — это Eloquent-модель `FeedItem` с подменой имён атрибутов, а не
самописный объект поверх Query Builder. Это не плохо, но выбор Spatie фактически
предопределяет архитектуру, и лучше это понимать заранее, чем упереться на середине.

> да по максиму используем ЛАРАВЕЛ

**12. `MproHelper::feed()` — это уже подсистема, а не хелпер.** Тут ровно тот случай, о
котором мы говорили сегодня: `FeedQuery`, `FeedItem`, связи, маппинг — это отдельный
неймспейс, а в `MproHelper` остаётся строчка-обёртка `feed()`, чтобы блейды звали без
`use`. Иначе `MproHelper` окончательно превратится в свалку.

> да можно оформить через АПИ

**13. Описание полей (`*_code`) — это метаданные, а не данные.** 25 колонок в `feeds`
нужны только чтобы хранить имена. Аргумент «фиксированная структура ради индексов» к ним
не относится: `feeds` — маленькая таблица описаний, по ней не ищут. Один JSON-столбец
`schema` дал бы то же самое и рос бы свободно, когда понадобится хранить рядом лейбл,
обязательность, порядок в форме, тип виджета. Это не спор с идеей ТЗ — физические колонки
`feed_items` остаются фиксированными, речь только о таблице описаний.

> да, хорошая идея.

**14. Имена полей надо валидировать.** Уникальность внутри ленты, и запрет на имена,
совпадающие со служебными: `id`, `position`, `json`, `feed_uid`, `created_at`,
`updated_at`. Иначе `$post->id` становится неоднозначным.

> да, можно придумать служебным полям более заковыристые название

**15. `relation` — свободная строка?** Тогда опечатка `categorys` не поймается ничем и
даст молча пустую выборку. Стоит либо завести список допустимых связей в описании ленты,
либо хотя бы приводить к нижнему регистру.

> давай связи проработаем в отдельном ТЗ

**16. Граница применимости.** Стоит записать в ТЗ прямым текстом: если сущности не хватает
10 строк, 5 текстов, 5 чисел и 5 флагов — это не задача для лент, для неё пишется обычная
таблица. Иначе рано или поздно кто-то начнёт складывать два значения в одно поле через
разделитель.

> да ты можешь что угодно писать в инструкции, будут ее выполнять или нет не известно, если бы мне не хватало и нужно было быстро, я скорее всего добавил бы поле в JSON. Ведь поля нужны для поиска, а если они просто как структуризация данных, да пусть в джсон лежат. Опыт показывает, что лучше вовремя чем по феншую. Сделал проект, если он взлетел до небес, тогда может его стоит вообще переписать без маджкПро. А так она выдержит и пару миллионов обращаний в сутки если будет парочка серверов один для баз, второй для бэка.
