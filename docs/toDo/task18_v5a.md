# ТЗ v5а. Модуль «Ленты». Связи

Дополнение к `task18_v5.md`. Реализуется после того, как две основные таблицы заработают.
История: `task18.md` → `task18_v2a.md` → `task18_v3a.md` → `task18_v4a.md` → этот файл.

Версия сведена к минимуму: один механизм, три ключа в описании, ни деревьев, ни таблицы
связей, ни сложных фильтров.

## Что такое связь

Связь — это когда поле записи хранит не значение, а **указатель на другую запись**.

Рецепты, две ленты:

```
лента "recipe_type"          лента "recipe"
id=2  Мясо                   id=222  Котлеты   тип=2
id=3  Рыба                   id=223  Суши      тип=3
```

**Плохо:** положить в рецепт строку `"Мясо"`. Переименуют тип — рецепт останется со старым
названием. Появятся два типа с одинаковым именем — не разобрать, какой имелся в виду.

**Хорошо:** положить в рецепт число `2` — идентификатор записи-типа. Переименование типа на
рецепт не влияет: связь идёт по идентификатору, а не по тексту.

### `uid` и `id`

`uid` — код **ленты** (`recipe`, `recipe_type`), один на всю ленту. Отдельная запись
опознаётся своим `id`.

В поле лежит `id` записи. Из какой она ленты — само поле не знает, это объявляется в схеме.

## Объявление

К обычному числовому полю добавляются три ключа:

| Ключ | Обязателен | Назначение |
| --- | --- | --- |
| `ref` | да | `uid` ленты, откуда берём запись |
| `display` | да | **Колонка** той ленты, которую показываем оператору |
| `as` | нет | Имя, под которым отдаётся сама запись. По умолчанию — `code` без суффикса `_id` |

```json
{
  "fields": [
    { "code": "title",   "column": "string_1", "label": "Название" },
    { "code": "type_id", "column": "bigint_1", "label": "Тип", "widget": "select",
      "ref": "recipe_type", "display": "string_1" }
  ]
}
```

Читается так: «в `bigint_1` лежит `id` записи из ленты `recipe_type`, показываем её
`string_1`».

Куда кладём — известно и без объявления: связь описана внутри схемы той ленты, которой
принадлежит поле.

### Связь цепляется за колонки, а не за имена

Все три конца связи указывают на то, что не переименовывается:

| Конец связи | Чем задан | Почему устойчив |
| --- | --- | --- |
| Куда кладём | `column` своего поля | Физическая колонка |
| Откуда берём | `ref` | `uid` ленты менять запрещено |
| Что показываем | `display` | Физическая колонка чужой ленты |

Оператор волен переименовывать логические имена в любой ленте — связи это не заденет.
Если бы `display` хранил `title`, переименование поля в чужой ленте молча ломало бы
выпадающий список у соседей.

Плата — схема читается чуть хуже: `"display": "string_1"` вместо `"display": "title"`. В
админке это не видно, там показывается `label`.

Одно место остаётся хрупким: если оператор переназначит поле на другой слот, `display`
будет указывать на старую колонку. Но это и так разрушающая операция — данные при смене
слота не переезжают, поле теряет своё содержимое независимо от связей.

Ограничения: `ref` допустим только на числовых слотах, лента из `ref` должна существовать,
колонка из `display` должна быть занята полем в её схеме.

## Админка

Поле с `ref` рисуется выпадающим списком записей чужой ленты. В списке показывается то
поле, которое названо в `display`.

## PHP API

### Чтение

```php
$recipe->type_id;      // 2 — то, что лежит в колонке
$recipe->type;         // запись типа целиком, или null
$recipe->type->title;  // «Мясо»
```

Разделение как в Eloquent: `type_id` — данные, `type` — связанная запись.

### Запись

```php
$recipe->type_id = 2;
$recipe->type    = $typeRecord;   // допустимо, положит его id
$recipe->type_id = null;          // связь снята
```

### Выборка

Фильтр идёт по колонке и пользуется уже существующим индексом, никаких join:

```php
MproHelper::feed('recipe')
    ->where('type_id', 2)
    ->where('published', true)
    ->orderBy('mpro.position')
    ->paginate(10);
```

Обратный обход отдельным механизмом не нужен: «все рецепты этого типа» — это тот же
`where`.

### Жадная загрузка

```php
MproHelper::feed('recipe')->with('type')->get();
```

Без неё список из тридцати рецептов с названием типа у каждого даст тридцать лишних
запросов. `with()` собирает все `type_id` списка и достаёт типы **одним** запросом.

`with()` принимает имя из `as`, а не имя колонки.

## Целостность

Ссылки не чистятся автоматически. Удалили тип — в рецептах остался его `id`, ведущий в
никуда. `$recipe->type` в этом случае отдаёт `null`: страница рецепта должна открыться и с
потерянным типом, а не падать пятисоткой.

Записи удаляются мягко, так что потеря обратима — `restore()` возвращает всё на место.

Смена `uid` ленты запрещена основным ТЗ. Со ссылками цена ошибки выше: `uid` лежит в `ref`
чужих схем.

### Запрет удаления ленты

В `task18_v5.md` удаление ленты запрещено, если она участвует в связях. Здесь это значит:
нельзя удалить ленту, на которую есть `ref` в схеме любой другой ленты.

## Чего в модуле нет

Сознательные ограничения, а не пропуски.

**Деревьев нет.** Ссылка ленты на саму себя технически возможна, но обходов на глубину
(«все записи в категории и во всех подкатегориях») модуль не делает. Это тянет за собой
либо рекурсию запросов, либо хранение материализованного пути — то есть заметное
усложнение ради сценария, которого в наших задачах нет.

**Связей «многие ко многим» нет.** Отдельного механизма не будет. Если у записи должно
быть несколько ссылок, оператор создаёт обычную ленту-связку с двумя полями `ref`:

```json
{
  "uid": "recipe_tag",
  "fields": [
    { "code": "recipe_id", "column": "bigint_1", "ref": "recipe", "display": "string_1" },
    { "code": "tag_id",    "column": "bigint_2", "ref": "tag",    "display": "string_1" }
  ]
}
```

```php
MproHelper::feed('recipe_tag')->where('recipe_id', 222)->with('tag')->get();
```

Движок не знает, что `recipe_tag` чем-то особенная: обычная лента, те же индексы, тот же
CRUD, то же мягкое удаление, тот же экспорт. Цена — нет `$recipe->tags()`, ходить надо в
два шага.

**Сложных фильтров и полнотекстового поиска нет.** Фильтрация — это `where` по
проиндексированной колонке, не более того.

**Универсальной таблицы связей нет.** Она была в версиях v2а и v3а вместе с
`attach`/`detach`/`sync`, `whereRelated`, отдельными индексами и командой обслуживания
висячих строк. Убрана целиком: возможность связывать «многие ко многим» осталась, ушла
только сложность в движке. Показательно, что почти все нерешённые вопросы прошлых версий
принадлежали именно ей.

## Вопросы

**1. Где живёт описание связи.** Сейчас — тремя ключами внутри поля, в схеме своей ленты.
Вы описывали связь четырьмя полями, включая «уид ленты куда кладём» — это имеет смысл,
если связи хранятся отдельным реестром, где все они видны разом. Реестр удобнее для
обзора, но заводит вторую сущность вместо трёх ключей в поле. Я выбрал более простой
вариант; скажите, если нужен реестр.

**2. Предупреждать ли при удалении записи, на которую ссылаются.** Удаляем тип «Мясо», а
на нём висят сорок рецептов. Молча удалить, предупредить и дать удалить, или запретить?
Удаление мягкое, катастрофы нет. Предлагаю предупреждать, но не запрещать.

**3. Как отвечать на «кто ссылается на эту ленту».** Нужно для запрета удаления ленты.
Прямой способ — перебрать `schema` всех лент и поискать `ref`. Лент немного, запрос
дешёвый, но он нужен при каждом удалении. Считать на месте или держать реестр ссылок?
