# ТЗ. Модуль «Ленты» (Feeds). Удаление

Удаление физическое. Корзины, мягкого удаления и восстановления нет.

`visible` — это не удаление. Скрыть и удалить — разные намерения, и они не должны прятаться
за одной кнопкой: скрытая запись занимает своё значение уникального поля, участвует в
проверках и ждёт публикации, удалённой записи просто нет.

Экспорт и импорт — отдельное ТЗ. Резервная копия базы остаётся единственным способом
вернуть удалённое, и админка обязана предупреждать об этом прямым текстом.

## Удаление записи

Запись удаляется из `feed_items` физически, вместе со своими медиафайлами.

Ссылки на неё из других записей обнуляются базой: `link_1` … `link_3` — внешние ключи с
`ON DELETE SET NULL`. Чистить их кодом не нужно.

Перед удалением админка показывает, сколько записей ссылается на эту:

```sql
SELECT COUNT(*) FROM feed_items
WHERE link_1 = :id OR link_2 = :id OR link_3 = :id
```

Удаление при этом не запрещается. Оператор видит последствия и решает сам: пропал рецепт
«Мясо» — у блюд, которые на него ссылались, категория станет пустой, а сами блюда останутся.

`position` соседей не пересчитывается. Дырка в нумерации ничего не ломает: сортировка идёт
по возрастанию `position`, а новая запись получает `max(position) + 1`.

## Очистка ленты

Отдельная команда: удалить все записи ленты, саму ленту и её схему оставить.

Нужна, когда лента наполнялась тестовыми данными или когда содержимое устарело целиком.
Правила те же, что для одиночного удаления: файлы удаляются, ссылки из других лент
обнуляются.

Записи удаляются пачками по 500 штук в транзакции, иначе на большой ленте вырастет журнал
и заблокируется таблица.

## Удаление ленты

Удаляется лента, её схема и все её записи.

**Лента не удаляется, если на её записи ссылаются другие ленты.** Это единственный запрет
в модуле, и он сознательный: обнулить одну ссылку — мелкая потеря, обнулить разом все
категории у всех рецептов — катастрофа, которую оператор заметит через неделю. Сначала
убираются связи, потом удаляется лента.

Проверка перед удалением:

```sql
SELECT EXISTS (
    SELECT 1 FROM feed_items AS src
    JOIN feed_items AS dst ON dst.id IN (src.link_1, src.link_2, src.link_3)
    WHERE dst.feed_id = :feedId AND src.feed_id <> :feedId
)
```

Если ссылки есть, API возвращает ошибку и список лент, которые мешают, — оператору нужно
знать, куда идти.

Ссылки **внутри самой ленты** удалению не мешают: лента-связка ссылается сама на себя, и
уносится целиком.

**Лента с `lock = true` не удаляется.** Флаг защищает схему от изменений, а удаление —
самое сильное изменение из возможных. Сначала снимается блокировка.

Порядок операций — в одной транзакции:

1. Проверка внешних ссылок.
2. Проверка `lock`.
3. Удаление медиафайлов всех записей.
4. Удаление записей пачками.
5. Удаление строки `feeds`.

## Удаление группы

**Группа по умолчанию не удаляется никогда** — она создаётся миграцией и служит домом для
новых лент.

**Непустая группа не удаляется.** Ленты не переезжают в группу по умолчанию автоматически:
молчаливое перемещение чужих данных — худший вид «удобства», оператор потом ищет ленту не
там, где оставил. Сначала ленты переносятся руками, потом группа удаляется.

## Медиа

Файлы удаляются вместе с записью средствами Spatie Media Library — коллекции записи
чистятся до удаления строки, иначе останутся файлы, на которые никто не ссылается.

Метаданные лежат в `data` той же строки и исчезают вместе с ней, отдельной уборки не
требуют.

Если файл удалить мимо API — через медиатеку или руками в файловой системе — метаданные в
`data` останутся и ссылка станет битой. Это то же правило, что при загрузке: медиа меняется
только через API модуля.

## Команды API

| Команда       | Что делает                                | Параметры |
| ------------- | ----------------------------------------- | --------- |
| `deleteItem`  | Удаляет одну запись                       | `id`      |
| `clearFeed`   | Удаляет все записи ленты, ленту оставляет | `feedId`  |
| `deleteFeed`  | Удаляет ленту вместе с записями           | `feedId`  |
| `deleteGroup` | Удаляет пустую группу                     | `groupId` |

Ответ — обычный для слоя `Api`: `status / errorMsg / data / request`. При отказе `errorMsg`
объясняет причину человеческим языком, а `data` содержит то, что мешает удалению: список
ссылающихся лент или количество лент в группе.

## Что происходит со ссылками

| Удаляем      | Ссылки на удалённое | Поведение                          |
| ------------ | ------------------- | ---------------------------------- |
| Запись       | Есть                | `link_N` обнуляется, удаление идёт |
| Записи ленты | Есть                | То же                              |
| Ленту        | Есть снаружи        | Отказ                              |
| Ленту        | Есть только внутри  | Удаление идёт                      |
| Группу       | Есть ленты          | Отказ                              |

## Подтверждение в админке

Удаление ленты и очистка ленты требуют подтверждения вводом `code` ленты — восстановления
нет, и промах мышью не должен стоить содержимого раздела.

Удаление одной записи подтверждается обычным диалогом.

## Журнал

Каждое удаление ленты, группы и очистка ленты пишутся в лог `feeds` через
`MproHelper::addLog`: что удалено, сколько записей, кто и когда. Удаление отдельных записей
не логируется — их слишком много, и смысла в этом нет.

## Чего нет

- **Корзины и восстановления.**
- **Мягкого удаления записей** — для этого есть `visible`.
- **Каскадного удаления связанных записей** — удаление рецепта не трогает блюда.
- **Автоматического переноса лент при удалении группы.**
- **Отмены удаления.**

## Вопросы

**1. Подтверждение вводом `code`** — не слишком ли строго для очистки ленты? Для удаления
ленты выглядит оправданно, для очистки, может быть, хватит обычного диалога.

**2. Размер пачки 500.** Число взято как разумное по умолчанию. Если ленты предполагаются
крупные, стоит вынести его в настройки модуля.

**3. Журнал удалений** — писать в лог `feeds` или в общий журнал админки, если он появится?
