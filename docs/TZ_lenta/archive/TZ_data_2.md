# ТЗ v2. Модуль «Ленты» (Feeds). Структура данных

Содержит только структуру данных и правила их обраотки

## Цель

Универсальный модуль хранения данных, например:

- Новости.
- Рецепты.
- Блог.
- Программа телепередач.
- В этот день были события.
- FAQ.
- Отзывы.
- Сотрудники.
- Вакансии.
- Новинки.

Где структура информации линейна. С простыми внутренними связями.

Главная цель — максимально простой движок, покрывающий множество задач небольших сайтов, без написания нового CRUD.

`MagicPro Lenta` не является конструктором баз данных. Это механизм хранения с фиксированной
структурой таблиц и API, внешне похожим на Laravel Query Builder. Разработчик работает с
логическими именами полей, физические колонки скрыты.

Везде, где можно опереться на Laravel, опираемся на Laravel: Eloquent, пагинатор, касты,
Spatie Media Library.

## Структура БД

### Таблица `feed_group`

Хранит данные. Структура фиксированная.

| Колонка      | Назначение             |
| ------------ | ---------------------- |
| `id`         | Первичный ключ         |
| `title`      | Название группы        |
| `position`   | Порядок вывода в меню  |
| `created_at` |                        |
| `updated_at` |                        |

Группа по умолчанию создаётся миграцией и **не удаляется**: лента без группы существовать
не может, `feeds.group_id` обязателен.

### Таблица `feed_items`

Хранит данные. Структура фиксированная.

| Колонка                  | Назначение                     |
| ------------------------ | ------------------------------ |
| `id`                     | Первичный ключ                 |
| `feed_id`                | К какой ленте относится запись |
| `string_1` … `string_10` | Строковые поля                 |
| `text_1` … `text_5`      | Текстовые поля                 |
| `bigint_1` … `bigint_5`  | Числовые поля                  |
| `date_1` … `date_5`      | Дата и время                   |
| `bool_1` … `bool_5`      | Булевы поля                    |
| `link_1` … `link_5`      | таблицы связей                 |
| `json`                   | Резервное хранилище            |
| `position`               | Позиция внутри `feed_id`       |
| `visible`                | Показывать запись или нет      |
| `created_at`             |                                |
| `updated_at`             |                                |

#### Сущности

`string_1` … `string_10`, `bigint_1` … `bigint_5`, `bool_1` … `bool_5` нужны для хранения и фильтрации.

`text_1` … `text_5` для хранения.

`json` — для резерва, если что то не поместилось в предыдущие колонки

`position` - текущая позиция внутри `feed_id`

`visible` - обрабатывается блейдом и нужна для показа, скрытия информации. Например, владелец добавляет рецепт, что бы на сайте не было в этот момент пустых записей.

#### Правила

- **`bool_*` никогда не `NULL`.** При создании записи все булевы колонки получают `0`.
  Иначе записи, созданные до появления поля, не попадут ни в выборку по `true`, ни по
  `false`.
- **`visible` при создании = `false`.** Редактор сам ставить его в true, после готовности иначе на сайте появятся пустые данные.
- **`Незанятые колонки`** хранятся как `NULL`, а не как пустая строка. Это важно для проверки
  уникальности: два `NULL` не считаются одинаковыми, две пустые строки — считаются.
- **`position` при создании = `max(position) + 1`** внутри своей ленты. Не ноль — иначе у
  всех новых записей одинаковая позиция.

#### `json` — резервное хранилище

Всё, что не влезло в колонки, кладётся сюда. Колонки нужны для фильтрации и сортировки; то,
что просто хранится и выводится, в `json`.

Фильтровать по содержимому `json` модуль не умеет и не будет: Laravel это позволяет
(`where('json->key', …)`), но SQLite и MySQL ведут себя по-разному, и переносимость
пострадает. Если проекту нужен интерфейс к этим данным — под него пишется своя админка.

### Таблица `feeds`

Описание ленты. Метаданные, а не данные — по ней не ищут, поэтому описание полей лежит
одним JSON-столбцом.

| Колонка      | Тип    | Назначение                                |
| ------------ | ------ | ----------------------------------------- |
| `id`         | bigint | Первичный ключ                            |
| `code`       | string | Логическое имя, им пользуется разработчик |
| `title`      | string | Человекочитаемое название                 |
| `schema`     | json   | Описание полей                            |
| `lock`       | bool   | Лента защищена от изменений               |
| `group_id`   | bigint | К какой группе лент принадлежит, обязателен |
| `position`   |        | Позиция внутри группы                     |
| `created_at` |        |                                           |
| `updated_at` |        |                                           |

**`code` уникален среди всех лент** — иначе `feed('news')` не поймёт, какую ленту брать.
Проверяется в админке. В модель это не тащим.

**`lock = true` запрещает** правку схемы.

#### Связи

Без поиска и сложных заморочек.ну Например, рецепты имеют две ленты

Рецепты типы

| id  | Значение |
| --- | -------- |
| 2   | Мясо     |
| 3   | Рыба     |

Рецепты Значения

| id  | Тип | Название |
| --- | --- | -------- |
| 222 | 2   | Котлеты  |
| 223 | 3   | Суши     |

Таким образом в описании связи должнжо быть четыре поля

- Уид ленты откуда берем
- Уид ленты куда кладем
- Поле ленты откуда берем
- Поле ленты куда кладем

#### Формат `schema`

Массив, порядок элементов = порядок полей в форме.

```json
{
  "fields": [
    {
      "column": "string_1",  // физическое поле
      "code": "title", // Мы
      "label": "Заголовок", // Подпись в админке
      "unique": false  // Уникальность внутри ленты
    },

    ],
  "links" [
    { // это для link_1
        "lenta_from_id" : 22, // откуда связь из какой ленты
        "field_from" : "string_1", // из какого поля взять связь
        "field_to" : "string_1", // в какое поле положить
    }

  ]
}
```

| Ключ     | Обязателен | Назначение                                          |
| -------- | ---------- | --------------------------------------------------- |
| `column` | да         | Физическая колонка в `feed_items`                   |
| `code`   | да         | Логическое имя, им пользуется разработчик           |
| `label`  | да         | Подпись в админке                                   |
| `unique` | да         | Значение уникально внутри ленты                     |
| `lines`  | да         | По умолчанию 1, имеет смысл для для текстовых полей |
| `format` | нет        | plain, html. md имеет смысл для текстовых полей     |

`code` подчиняется `^[a-z][a-z0-9_]*$`, уникален внутри ленты и **не может быть словом
`mpro`** — оно зарезервировано под системные атрибуты. Точка в имени невозможна, поэтому
`mpro.` в запросах ни с чем не пересекается.

#### `visible` не фильтруется автоматически

Движок **не скрывает записи сам**. `visible` — обычная системная колонка, доступная как
`$post->mpro->visible`, а решение принимает шаблон.

Так сделано ради предпросмотра: владелец должен уметь открыть скрытую новость по её адресу
и увидеть, как она будет выглядеть на сайте. Если бы движок молча выбрасывал невидимые
записи из выборок, страница отдавала бы 404 и посмотреть было бы нечего.

**В списках фильтр ставится явно:**

```php
MproHelper::feed('news')
    ->where('mpro.visible', true)
    ->orderBy('mpro.position')
    ->paginate(10);
```

**На странице записи решает блейд:**

```blade
@if( $post->mpro->visible )
    {{-- обычный вывод --}}
@else
    @mproauth
        {{-- пользователь админ --}}
        {{-- скрытую видит только администратор, проверка та же, что на сайте --}}
    @endmproauth
@endif
```

Плата за это — фильтр в списке можно забыть, и черновик уедет на сайт. Взамен
предпросмотр работает без единой строки специального кода.

### Медиа

Spatie Media Library. Количество изображений не ограничено. Требует, чтобы запись была
Eloquent-моделью — это и заложено в архитектуру.

### Индексы

Индексируются все строковые, числовые, булевы колонки, колонки даты и колонки связей.
Текстовые поля не индексируются.

Порядок колонок: сначала равенство, потом сортировка, в конце `id`. `visible` стоит сразу
после `feed_id`, потому что подставляется в каждый запрос сайта — без него индекс
перестаёт покрывать выборку.

| Индекс | Для чего |
| --- | --- |
| `(feed_id, visible, position, id)` | Список ленты по порядку — главный запрос сайта |
| `(feed_id, visible, created_at, id)` | Список по дате создания |
| `(feed_id, visible, date_1, id)` … `(feed_id, visible, date_5, id)` | Список и фильтр по датам ленты |
| `(feed_id, visible, string_1)` … `(feed_id, visible, string_10)` | Поиск по строковым полям |
| `(feed_id, visible, bigint_1)` … `(feed_id, visible, bigint_5)` | Поиск по числовым полям |
| `(feed_id, visible, bool_1)` … `(feed_id, visible, bool_5)` | Фильтр по флагам |
| `(feed_id, visible, link_1)` … `(feed_id, visible, link_5)` | Выборка по связи: все рецепты этого типа |

Даты идут с `id` на конце, потому что по ним сортируют: новости по дате публикации,
расписание по времени эфира. У остальных колонок `id` не нужен, там только равенство.

Все индексы **статические, создаются миграцией**. `ALTER TABLE` из админки не делается
никогда.

`id` в конце сортировочных индексов — не про скорость, а про корректность: см. «Пагинация».

### Уникальность значений

Флаг `unique` в схеме проверяется **кодом перед записью**, уникальных индексов на колонки
нет. Проверка идёт по всем записям ленты, включая скрытые: `visible = false` — это «не
показывать», а не «освободить значение».

## Предложение по описанию связи

Раз в базе лежит `id`, из четырёх полей нужны не все, зато не хватает двух других.

```json
"links": [
  {
    "column": "link_1", // куда кладём id
    "code": "type", // логическое имя связи
    "label": "Тип", // подпись в админке
    "feed_id": 22, // из какой ленты берём запись
    "display": "string_1" // какую колонку той ленты показывать в списке
  }
]
```

Что изменилось против исходных четырёх полей:

- **`field_to` не нужен.** Мы кладём `id`, и место для него — `column`. Складывать значение
  чужого поля некуда и незачем.
- **`column` вместо порядка в массиве.** Сейчас какой `link_N` описан, определяется
  позицией элемента — переставили местами, и связи молча уехали на чужие данные.
- **`code` и `label`** — как у обычных полей. Тогда `$recipe->type` читается так же, как
  `$recipe->title`, и админка рисует подпись из одного места.
- **`display` вместо `field_from`** — то же самое, но имя честнее говорит, зачем оно:
  показать оператору в выпадающем списке.

## Вопросы

**1. `feeds.code` уникален среди всех лент?** В тексте про уникальность сказано только про
`code` поля внутри ленты. Для ленты правило другое, и его стоит записать.

**2. `group_id` обязателен?** Может ли лента жить без группы, или перед созданием первой
ленты придётся завести группу «Прочее»?

**3. Сортировка групп.** У `feeds` есть `position` внутри группы, а у самих групп порядка
нет — сортируем по `title` или добавляем `position` и в `feed_group`?
