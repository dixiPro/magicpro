## Назначение

`MagicPro Lenta` — модуль хранения линейных данных небольших сайтов: новости, блог,
рецепты, FAQ, отзывы, сотрудники, вакансии, афиша, справочники, заявки с сайта. Полный
разбор сценариев — в `TZ_cases.md`.

Модуль не является конструктором произвольных баз данных. Структура таблиц фиксирована,
разработчик работает с логическими именами полей, физические колонки скрыты.

Везде, где возможно, используются штатные механизмы Laravel: Eloquent, Query Builder,
casts, paginator, validation, transactions, Spatie Media Library.

## Принцип хранения

Данные делятся на две группы.

**Индексируемые** — те, по которым ищут, фильтруют, сортируют, проверяют уникальность или
строят связи. Лежат в физических колонках: `__string_N`, `__bigint_N`, `__date_N`, `__bool_N`,
`__link_N`.

**Неиндексируемые** — те, которые только хранят, редактируют и показывают. Лежат в
JSON-колонке `__data`. Туда же уходят большие тексты: статьи, описания, программы, код.

Запросы вида `where('__data->content', …)` модуль не поддерживает. Это и даёт одинаковое
поведение на SQLite, MySQL и PostgreSQL.

## Таблица `magicPro_feed_groups`

| Колонка      | Тип      | Назначение      |
| ------------ | -------- | --------------- |
| `id`         | bigint   | Первичный ключ  |
| `title`      | string   | Название группы |
| `position`   | bigint   | Порядок вывода  |
| `created_at` | datetime |                 |
| `updated_at` | datetime |                 |

Миграция создаёт группу по умолчанию. Она не удаляется, используется для новых лент,
может быть переименована. Лента без группы существовать не может.

**Группа с лентами не удаляется.** Сначала ленты переносят в другую группу или удаляют,
потом удаляют группу.

## Таблица `magicPro_feeds`

| Колонка      | Тип      | Назначение                      |
| ------------ | -------- | ------------------------------- |
| `id`         | bigint   | Первичный ключ                  |
| `code`       | string   | Программный код ленты, `UNIQUE` |
| `title`      | string   | Название в админке              |
| `schema`     | json     | Описание полей                  |
| `group_id`   | bigint   | Группа, обязательна             |
| `position`   | bigint   | Позиция внутри группы           |
| `created_at` | datetime |                                 |
| `updated_at` | datetime |                                 |

Версия формата схемы лежит внутри самого JSON (`"version"`), отдельной колонки нет: схема
переносится и копируется целиком, версия должна ехать вместе с ней.

`group_id` — внешний ключ на `magicPro_feed_groups`. База не даст записать ленту в
несуществующую группу и не даст удалить группу, пока в ней есть ленты. Это второй рубеж:
те же проверки остаются и в коде.

### Код ленты

`code` состоит из латинских букв, цифр, дефиса и подчёркивания. Изменить можно, но тогда придётся поправить вызовы в блейдах. На связи это не влияет —
они ссылаются на ленту по `id`.

## Слоты

Дальше по тексту слоты пишутся как `__string_1` … `__string_N`. Значение `N` для каждого типа
задаётся здесь и только здесь.

| Слоты                       | Назначение | `N` |
| --------------------------- | ---------- | --- |
| `__string_1` … `__string_N` | Строки     | 5   |
| `__bigint_1` … `__bigint_N` | Целые      | 3   |
| `__date_1` … `__date_N`     | Дата-время | 3   |
| `__bool_1` … `__bool_N`     | Флаги      | 3   |
| `__link_1` … `__link_N`     | Связи      | 3   |

Числа взяты из `TZ_cases.md`: тридцать сценариев, ни одному не нужно больше. Изменение
количества — это миграция и новые индексы, из админки слоты не добавляются.

## Таблица `magicPro_feed_items`

| Колонка                     | Тип                   | Назначение                             |
| --------------------------- | --------------------- | -------------------------------------- |
| `id`                        | bigint                | Первичный ключ                         |
| `feed_id`                   | bigint                | Лента записи                           |
| `__string_1` … `__string_N` | varchar(255) nullable | Строки для поиска и сортировки         |
| `__bigint_1` … `__bigint_N` | bigint nullable       | Целые числа                            |
| `__date_1` … `__date_N`     | datetime nullable     | Даты и время                           |
| `__bool_1` … `__bool_N`     | boolean not null      | Флаги                                  |
| `__link_1` … `__link_N`     | bigint nullable       | Ссылки на другие `magicPro_feed_items` |
| `__data`                    | json                  | Неиндексируемые данные и тексты        |
| `__position`                | bigint                | Позиция внутри ленты                   |
| `__visible`                 | boolean               | Видимость записи                       |
| `created_at`                | datetime              |                                        |
| `updated_at`                | datetime              |                                        |

Отдельных текстовых колонок нет. Большие тексты живут в `__data` — см. «JSON `__data`».

### Правила при создании записи

- **`__position` = `max(__position) + 1`** внутри своей ленты. Расчёт идёт в транзакции с
  блокировкой строки `magicPro_feeds`: два параллельных запроса иначе дадут одинаковую
  позицию, а это ломает пагинацию — см. «Индексы `magicPro_feed_items`».
- **`__visible` = `false`.** Редактор ставит `true` сам, когда запись готова, иначе на сайте
  появляются пустые заготовки.
- **`__bool_1` … `__bool_N` = `0`.** Колонка `not null`, и `DEFAULT 0` стоит на уровне
  миграции: поля может ещё не быть в схеме, а вставка должна проходить.
- **Незанятые слоты = `NULL`, а не пустая строка.** Два `NULL` считаются разными, две
  пустые строки — одинаковыми, и на этом ломается проверка уникальности.
- **Остальные значения по умолчанию** берутся из настроек поля в схеме.

## Формат `schema`

```json
{
  "version": 1,
  "fields": [],
  "order": []
}
```

`fields` определяет поля в форме. Каждое поле — один объект.
`order` - порядок вывода в списке для редактирования в админке.

```json

  ],

  "fields": [
    {
```

## Логическое имя

`code` поля состоит из латинских букв, цифр, дефиса и подчёркивания, уникален внутри ленты
и не меняется после появления данных.

**Зарезервированные имена.** `code` не начинается с `__` и не равен `id`, `feed_id`,
`created_at`, `updated_at`. Иначе логическое имя в запросе не отличить от настоящей колонки.

Все собственные колонки модуля названы с префикса `__`, поэтому перечислять их не нужно:
добавили слот — правило работает само. Без префикса остались только четыре имени, которые
приносит Laravel, — они и перечислены выше.

### Запрет переименования

**Пока в ленте есть хоть одна запись, поле сохраняет своё имя.** `code` — это то, как
приложение читает значение: переименование молча превращает в ошибку каждый блейд и
контроллер, где стояло старое имя, а сами значения при этом остаются на месте.

Сравнение идёт по колонке: поле, оставшееся на `__string_1`, обязано сохранить `code`. Так
же ловится обходной путь «убрал `title` с `__string_1`, добавил туда же `name`» — для
проверки это одно и то же.

Освободить колонку можно: удаление поля — не переименование. На пустой ленте переименование
разрешено.

**Две дырки, оставленные сознательно.**

Поля внутри `__data` под правило не попадают. Там `code` — это и есть ключ значения в JSON,
и переименование неотличимо от «удалил одно поле, добавил другое». Различить их можно было
бы только по положению в массиве, а это гадание.

Переименование в два сохранения не ловится: убрать поле с `__string_1` одним запросом,
добавить туда новое имя вторым. Обе операции по отдельности законны. Закрыть это можно
только запретом освобождать занятую колонку, пока в ленте есть записи, — такого правила
здесь нет.

## Валидация

`validation` — строка правил Laravel, как в форм-реквестах:

```json
"validation": "required|string|min:4|max:255"
```

Своего формата у модуля нет: строка уходит в штатный валидатор Laravel при сохранении записи через
API. Отдельного ключа `required` нет — это слово в той же строке.

**`unique` правилом Laravel не выражается.** `unique:magicPro_feed_items,__string_2`
проверил бы всю таблицу, а слот общий: у блога там `slug`, у сотрудников — `department`, и
два сотрудника одного отдела перестали бы сохраняться. Поэтому уникальность остаётся отдельным ключом
поля — см. «Уникальность».

## Физические колонки

**`__string_1` … `__string_N`** — `varchar(255)`. Заголовки, slug, коды, короткие значения,
всё, по чему ищут строкой.

**`__bigint_1` … `__bigint_N`** — только целые. Деньги в минимальных единицах: `150000` это
1500.00. Координаты — умноженные на миллион: `55.755819` хранится как `55755819`, множитель
одинаков для всех лент. Дробные значения, по которым не ищут, — в `__data`.

**`__date_1` … `__date_N`** — дата и время, cast `datetime`. Тип один: `datetime`. Отдельного
типа «только дата» нет — время либо используется, либо просто остаётся нулевым.

**`__bool_1` … `__bool_N`** — никогда не `NULL`. Отсутствие значения у старой записи означает
`false`.

**`__link_1` … `__link_N`** — см. «Связи».

## Связи

Каждый `__link_N` содержит `magicPro_feed_items.id`. Связи возможны только между записями модуля
«Ленты»; связи с произвольными таблицами проекта в модуль не входят.

Описание лежит **внутри поля**, а не отдельным массивом:

```json
"relation": {
  "feed_id": 22,
  "display_code": "__string_1"
}
```

`feed_id` — из какой ленты берём запись, `display_code` — её физическая колонка, значение
которой показывается оператору в выпадающем списке.

Колонка, а не `code`, потому что в админке символическое имя от пользователя скрывается, и
связь перестаёт зависеть от того, как поле назвали и переименовали.

Лента указывается по `id`, а не по `code`, потому что `code` разрешено менять — при
переименовании ленты все связи на неё остались бы битыми.

При сохранении проверяется: связанная запись существует, принадлежит указанной ленте, и
колонка `display_code` в той ленте занята полем.

**Кольца запрещены.** Если A ссылается на B, то B не может ссылаться на A, ни напрямую, ни
через цепочку — см. «Удаление».

**Связь всегда «одна запись → одна запись».** Если нужно несколько ссылок одного вида —
несколько авторов, теги — оператор заводит обычную ленту-связку с двумя полями `link`.
Движок про неё ничего особенного не знает.

## JSON `__data`

Все поля, которым не нужна физическая колонка, описываются одним объектом схемы с
`"column": "__data"`. Сами поля лежат в его вложенном массиве `data` и отличаются от обычных
только тем, что вместо `column` у них `type` — см. «Пример описания».

Контейнер используется напрямую: к содержимому обращаются через колонку `__data` модели.
Своего значения в записи он не имеет — в базе лежат только вложенные поля.

В базе хранится плоский объект: ключ — `code` вложенного поля, значение — его содержимое.

```json
{
  "subTitle": "Подзаголовок",
  "email2": "user@example.com",
  "description": "<p>Текст статьи</p>"
}
```

В `__data` запрещены `where`, `orderBy`, `unique` и связи.

### Загрузка

`__data` читается вместе с записью, обычным запросом. Ленивой загрузки нет и отдельного
метода подгрузки тоже: в `__data` лежат метаданные изображений, а миниатюра нужна как раз в
списке — колонку всё равно пришлось бы тянуть почти всегда.

Плата понятна: список тащит и тексты записей. На объёмах, ради которых делается модуль,
это не имеет значения; если у конкретной ленты тексты большие, а список длинный, поля
такой ленты стоит раскладывать иначе.

## Совместимость «колонка ↔ тип»

Одна физическая колонка используется только одним полем схемы.

| Колонка      | Допустимые типы                                                                        |
| ------------ | -------------------------------------------------------------------------------------- |
| `__string_N` | `string`                                                                               |
| `__bigint_N` | `integer`                                                                              |
| `__date_N`   | `datetime`                                                                             |
| `__bool_N`   | `boolean`                                                                              |
| `__link_N`   | `link`                                                                                 |
| `__data`     | `string`, `text`, `integer`, `decimal`, `boolean`, `datetime`, `json`, `code`, `image` |

Проверяется при сохранении схемы.

## Редакторы

У всех полей **text, **bigint в качестве редактирования самый обычный input.

Для текстовых полей доступны `html`, `markdown`, `plain`.

Неизвестный редактор — ошибка сохранения схемы.

**`select` и `textSearch` — не редакторы, а способ выбрать значение.** Они не меняют ни
тип, ни формат хранения, а только ограничивают ввод заранее определёнными значениями:
вместо свободного поля оператор выбирает из списка или ищет по нему.

В описании поля они задаются отдельным ключом `input`, а не `editor`.

## Показ в списке

`showOnList` — показывать ли поле колонкой в списке записей админки. Ключ разрешён и полям
физических колонок, и вложенным полям `__data`.

**Если ключ не указан — поле показывается.** Умолчание одно для всех типов, включая тексты и
изображения.

Так выбрана худшая ситуация из двух. Когда лишнее показывается, оператор видит длинную
простыню и соображает, что часть полей надо убрать. Когда лишнее скрыто по умолчанию, поле
просто не появляется, и понять, что его надо включить, неоткуда.

На вывод на сайте ключ не влияет — там состав полей определяет блейд.

Выключить можно все поля сразу: строка списка остаётся рабочей и без них, у неё есть ручка
перетаскивания и иконка редактирования.

## Порядок в списке

`order` лежит в схеме рядом с `fields` и задаёт, в каком порядке идут колонки списка.

```json
"order": ["img", "__string_1", "subTitle"],
```

Это плоский массив имён. **Имя, начинающееся с `__`, — физическая колонка слота, любое
другое — `code` поля внутри `__data`.** Двусмысленности нет: `code` начинаться с `__` не
может, это запрещено в «Логическом имени».

Строится админкой, не руками на основе "fields": [ { showOnList} ]

## Формат даты в списке

`listFormat` — маска, по которой дата показывается в списке. Ключ есть у полей слотов
`__date_N` и у полей `__data` типа `datetime`.

```json
"listFormat": "y-m-d"
```

Буквы взяты у PHP и означают то же самое, поэтому маску можно без перевода поставить в
блейд:

| Буква | Значение                  |
| ----- | ------------------------- |
| `d`   | День с ведущим нулём      |
| `m`   | Месяц с ведущим нулём     |
| `y`   | Год двумя цифрами         |
| `Y`   | Год четырьмя цифрами      |
| `H`   | Часы, 24-часовые, с нулём |
| `i`   | Минуты с ведущим нулём    |
| `s`   | Секунды с ведущим нулём   |

Остальные символы маски выводятся как есть. Поддерживается только этот набор букв: полный
список PHP тянет за собой названия дней и месяцев, а они у PHP английские.

**Ключа нет — значение показывается так, как лежит в базе**, то есть `2028-01-26 13:33:00`.

Пустое значение даёт пустую ячейку. Значение, которое не разбирается как дата, показывается
как есть: пусть видно, что лежит в поле.

На вывод на сайте `listFormat` не влияет — там формат пишет блейд.

## Форматирование и безопасность

**Значение строковых и текстовых полей сохраняется как введено оператором**

- Никакой автоматической очистки HTML нет;
- Как выводить значение — решает Blade: {{ }} или {!! !!}.

`editor` : html / markdown / plain описывает только интерфейс редактирования, а не правила безопасности или преобразования данных.

Единственное следствие: если вывести введённый HTML через {!! !!}, оператор может вставить и <script>. Но это уже сознательная ответственность разработчика и доверенного оператора, а не задача модуля.

## Видимость

`__visible` не применяется автоматически. Владелец должен
открыть скрытую новость по её адресу и увидеть, как она будет выглядеть. Решение о показе
принимает контроллер или блейд.

Плата — фильтр в списке можно забыть, и черновик уедет на сайт.

## Уникальность

`unique: true` объявляется в описании поля и разрешён только для полей физических колонок. Проверка идёт по всем записям
ленты, включая скрытые: `__visible = false` означает «не показывать», а не «освободить
значение».

Проверка и запись выполняются в транзакции с блокировкой строки `magicPro_feeds`.

Уникальных индексов на слоты **нет**: слот общий для всех лент, и `UNIQUE (feed_id,
__string_2)` заставил бы быть уникальным второй строковый слот везде — а другая лента держит
там название отдела, и два сотрудника из одного отдела туда уже не запишутся.

Настоящий уникальный индекс есть только у `magicPro_feeds.code`.

## Индексы `magicPro_feed_items`

Все индексы перечислены явно. Они статические, создаются миграцией, админка никогда не
делает `ALTER TABLE`.

| №   | Индекс                                           | Для чего                               |
| --- | ------------------------------------------------ | -------------------------------------- |
| 1   | `(feed_id, __visible, __position, id)`           | Главный список ленты, ручной порядок   |
| 2   | `(feed_id, __visible, created_at, id)`           | Список по дате создания                |
| 3   | `(feed_id, __visible, __date_1, id)`             | Список и фильтр по первой дате         |
| 4   | `(feed_id, __visible, __date_2, id)`             | То же по второй дате                   |
| 5   | `(feed_id, __visible, __date_3, id)`             | То же по третьей дате                  |
| 6   | `(feed_id, __visible, __link_1, __position, id)` | Все записи с первой связью, по порядку |
| 7   | `(feed_id, __visible, __link_2, __position, id)` | То же по второй связи                  |
| 8   | `(feed_id, __visible, __link_3, __position, id)` | То же по третьей связи                 |
| 9   | `(feed_id, __visible, __bool_1, __position, id)` | Список по первому флагу, по порядку    |
| 10  | `(feed_id, __visible, __bool_2, __position, id)` | То же по второму флагу                 |
| 11  | `(feed_id, __visible, __bool_3, __position, id)` | То же по третьему флагу                |
| 12  | `(feed_id, __string_1)`                          | Поиск записи по первой строке          |
| 13  | `(feed_id, __string_2)`                          | Поиск по второй строке                 |
| 14  | `(feed_id, __string_3)`                          | Поиск по третьей строке                |
| 15  | `(feed_id, __string_4)`                          | Поиск по четвёртой строке              |
| 16  | `(feed_id, __string_5)`                          | Поиск по пятой строке                  |
| 17  | `(feed_id, __bigint_1)`                          | Поиск записи по первому числу          |
| 18  | `(feed_id, __bigint_2)`                          | Поиск по второму числу                 |
| 19  | `(feed_id, __bigint_3)`                          | Поиск по третьему числу                |

Итого 19 индексов.

### Почему именно так

**Порядок колонок: `feed_id`, потом равенство, потом сортировка, в конце `id`.** Составной
индекс читается слева направо, пропускать колонки нельзя: если в индексе
`(feed_id, __visible, __date_1)` не задать `__visible`, до `__date_1` база не доберётся и пойдёт
читать таблицу.

**`id` в конце сортировочных — не про скорость, а про корректность.** При одинаковых
значениях `__position` или `__date_1` порядок строк не определён, и на границе страниц одна
запись покажется дважды, а другая не покажется нигде. `id` делает порядок однозначным.

**`__visible` стоит только в списковых индексах (1–11).** Поиск конкретной записи идёт без
него: запись по адресу берётся независимо от видимости, иначе не работает предпросмотр
черновика. Поставь `__visible` вторым в поисковом индексе — и при запросе без него база до
`__string_2` не дойдёт.

**Булевы и связи — всегда вместе с сортировкой.** Голый `(feed_id, __visible, __bool_1)`
отберёт строки, но сортировать их придётся в памяти. С `__position` следом «первые десять
оплаченных» читаются как десять строк, а не как двести с последующей сортировкой.

**Строковые и числовые индексы — без сортировки.** По ним ищут конкретную запись по
равенству: slug, артикул, номер документа. Сортировать по ним незачем, поэтому `__position`
и `id` в них не нужны.

**`__data` не индексируется вовсе** — по ней запрещены `where` и `orderBy`.

**По `__link_1` … `__link_N` идёт проверка «на эту запись ещё ссылаются».** Индексы 6–8 для неё
не годятся: они начинаются с `feed_id`, а ищут по самой колонке, через `OR` по всем трём
слотам, и ленту при этом не знают.

**Индексы не зависят от схемы ленты.** Слот `__string_2` у блога хранит `slug`, у сотрудников
— отдел; индекс один и тот же и работает для обоих. Поэтому список фиксирован и не растёт
при появлении новых лент.

## Индексы `magicPro_feeds`

| №   | Индекс                     | Для чего                                     |
| --- | -------------------------- | -------------------------------------------- |
| 1   | `UNIQUE (code)`            | Поиск ленты по коду и запрет двух одинаковых |
| 2   | `(group_id, position, id)` | Список лент группы по порядку в админке      |

**`UNIQUE (code)`** — единственный настоящий уникальный индекс во всём модуле. По нему
работает обращение к ленте из кода, и он же не даёт завести вторую ленту с тем же кодом.
Проверка в админке остаётся, но последнее слово за базой.

**`(group_id, position, id)`** обслуживает главный экран админки: группы, внутри каждой —
свои ленты в заданном порядке. Он же покрывает внешний ключ `group_id`, потому что стоит
первой колонкой.

`title` и `schema` не индексируются: по названию не ищут, а схема — JSON.

## Индексы `magicPro_feed_groups`

| №   | Индекс           | Для чего                         |
| --- | ---------------- | -------------------------------- |
| 1   | `(position, id)` | Вывод групп по заданному порядку |

Таблица маленькая — обычно единицы строк, — и других запросов к ней нет: группы всегда
читаются целиком и всегда по порядку. `id` в конце по той же причине, что и везде: при
одинаковых `__position` порядок иначе не определён.

Уникального индекса на `title` нет. Две группы с одинаковым названием ничего не ломают,
а запрет — вопрос админки, а не базы.

## Медиа

Файлы хранит Spatie Media Library, количество не ограничено. Она требует, чтобы запись была
Eloquent-моделью — это в архитектуру заложено.

### Установка Spatie

Зависимость пакета, `packages/dixipro/magicpro/composer.json`, секция `require`:

```json
"spatie/laravel-medialibrary": "^11.0"
```

Обновить проект, из корня:

```bash
composer update dixipro/magicpro
php artisan vendor:publish --tag=medialibrary-migrations
```

Выполнить опубликованную миграцию — она создаёт таблицу `media`:

```bash
php artisan migrate --path=database/migrations/2026_08_04_090345_create_media_table.php
```

Имя файла подставить настоящее, из `database/migrations/`: дату в начало имени ставит
`vendor:publish`. Без `--path` выполнятся все неприменённые миграции.

Модель записи подключает библиотеку двумя строками:

```php
class FeedItem extends Model implements HasMedia
{
    use InteractsWithMedia;
```

Без них методы `addMedia()`, `getMedia()` и `clearMediaCollection()` у модели не появятся.

**Порядок обработчиков `deleting` важен.** Spatie вешает свой обработчик и в нём удаляет
файлы. Если он сработает раньше проверки «на запись ссылаются», файлы исчезнут у записи,
которую удалять было нельзя. Значит либо проверка регистрируется раньше обработчика Spatie,
либо удаление идёт отдельным методом модуля: сначала проверка ссылок, потом очистка
коллекций, потом удаление строки.

Метаданные файла лежат в `__data` под `code` поля: `url`, `size`, `mime`, `x`, `y`, а рядом
то, что заполняет оператор, например `alt`. Само поле описывается в схеме типом `image`.

**Одно поле — одно изображение.** При загрузке коллекция поля очищается, старый файл
удаляется. Галереи нет: нужно десять картинок — заводится десять полей.

**Пока только изображения.** Документы и видео — позже, отдельным типом поля.

**Медиа меняется только через API модуля.** Если файл удалить или заменить мимо него —
через саму Spatie или через медиатеку — метаданные в `__data` об этом не узнают и ссылка
останется битой.

Загрузка после создания записи:

```php
/**
 * Загружает изображение в поле записи и сохраняет его метаданные.
 * Существующие пользовательские данные поля, например alt, сохраняются.
 * Обработки ошибок нет, вызов стоит завернуть в try/catch.
 * На этапе ТЗ уточняем только важные моменты.
 */
public function loadImage(string $code, int $id, $file): FeedItem
{
    // Получаем запись ленты.
    $item = FeedItem::findOrFail($id);

    // В поле хранится одно изображение — старое удаляем.
    $item->clearMediaCollection($code);

    // Сохраняем файл в коллекцию с именем поля.
    $media = $item
        ->addMedia($file)
        ->toMediaCollection($code);

    // Получаем размеры изображения.
    [$width, $height] = getimagesize($media->getPath());

    $data = $item->__data ?? [];

    // Обновляем только метаданные файла, не затирая alt и другие свойства.
    $data[$code] = array_merge($data[$code] ?? [], [
        'url'  => $media->getUrl(),
        'size' => $media->size,
        'mime' => $media->mime_type,
        'x'    => $width,
        'y'    => $height,
    ]);

    // Сохраняем обновлённый JSON.
    $item->__data = $data;
    $item->save();

    return $item;
}
```

## Удаление

Удаление физическое. Корзины, мягкого удаления и восстановления нет. `__visible` — это не
удаление, а скрытие.

### Главное правило

**Запись, на которую кто-то ссылается через `link`, не удаляется.** Сначала снимается
ссылка, потом удаляется запись.

Проверка «кто ссылается»:

```sql
SELECT * FROM magicPro_feed_items
WHERE __link_1 = :id OR __link_2 = :id OR __link_3 = :id
```

**Скорость удаления не важна.** Операция редкая, объёмы небольшие. Отдельных индексов под
эту проверку не заводим и время её выполнения не оптимизируем.

### Удалить запись

1. Оператор нажимает корзинку.
2. Проверяем, кто ссылается на запись.
3. Никто — подтверждение, удаляем запись вместе с её файлами.
4. Кто-то ссылается — открывается окно со списком ссылающихся записей, у каждой своя
   корзинка.

Окно рекурсивное: удаление записи из списка идёт по тем же правилам и может открыть
следующий список. Оператор спускается по цепочке до записей, которые никто не держит, и
разбирает её снизу вверх.

`__position` соседей не пересчитывается: дырка в нумерации ничего не ломает, новая запись
получает `max(__position) + 1`.

### Групповое удаление записей

Рядом с каждой записью чекбокс, есть «выбрать все». После подтверждения удаляются все
отмеченные записи, на которые никто не ссылается.

В конце выводится список тех, кого удалить не удалось, с указанием, кто их держит.

### Очистка ленты

Удаляются данные, описание ленты остаётся.

Проход по записям: удаляем все, на которые никто не ссылается. Проход повторяется, пока за
него удалилась хоть одна запись.

Повтор нужен из-за цепочек: пока жива запись C, нельзя удалить B, которая на неё
ссылается, а пока жива B — нельзя A. Первый проход снимает C, второй B, третий A. Когда
очередной проход не удалил ничего, работа закончена.

В ленте остаётся только то, что держат ссылки из других лент.

### Удаление ленты

То же самое, что очистка, плюс последний шаг:

1. Проходами удаляем все записи, которые никто не держит.
2. Смотрим, осталось ли что-нибудь.
3. Записей нет — удаляем описание ленты, ленты больше не существует.
4. Записи остались — описание остаётся, лента продолжает жить с остатком.

### Файлы

Файлы записи удаляются вместе с ней средствами Spatie Media Library — коллекции чистятся
до удаления строки, иначе на диске останутся файлы, на которые никто не ссылается.

Метаданные лежат в `__data` той же строки и исчезают вместе с ней.

### Взаимные ссылки запрещены

**Связи не должны образовывать кольцо.** Если A ссылается на B, то B не может ссылаться на
A — ни напрямую, ни через цепочку C, D и так далее.

Без этого запрета обе записи становятся вечными: каждая держит другую, ни одна не
удаляется, проходы очистки на них останавливаются, и рекурсивное окно водит оператора по
кругу. Удалить их можно было бы только правкой записи, то есть в обход всей механики
удаления.

Проверка выполняется при сохранении записи: если новая связь замыкает кольцо, запись не
сохраняется и оператор получает ошибку с указанием, через какие записи идёт кольцо.

## Чего в модуле нет

Сознательные ограничения, а не пропуски.

- **Мягкого удаления записей** — есть `__visible`. Скрыть и удалить это разные намерения,
  и они не должны прятаться за одной кнопкой.
- **Деревьев** — обхода на произвольную глубину модуль не делает.
- **Связей «многие ко многим»** — собираются лентой-связкой.
- **Фильтрации и сортировки по `__data`**.
- **Полнотекстового поиска и сложных фильтров.**
- **Галерей** — одно поле хранит одно изображение.
- **Файлов и видео** — на этом этапе только изображения.
- **Мультиязычности данных** — интерфейс да, данные нет.
- **Динамического изменения структуры таблиц.**

## CRUD

Источник истины по CRUD. Если в других разделах есть расхождение по доступу к данным —
верна эта часть.

CRUD лент использует модели Laravel и Eloquent.

В таблице `magicPro_feed_items` данные физически хранятся в универсальных колонках:

```text
__string_1
__string_2
__bigint_1
__date_1
__bool_1
__link_1
__data
```

В коде приложения используются логические имена `code`, заданные в `magicPro_feeds.schema`.

Например:

```text
name    → __string_1
price   → __bigint_1
content → __data['content']
```

Физические имена слотов нужны только внутреннему коду модуля.

### Контекст ленты

Соответствие логических имён физическим колонкам зависит от конкретной ленты. Поэтому запросы с логическими именами выполняются через связь `Feed::items()`:

```php
$feed = Feed::where('code', 'Users')->firstOrFail();

$items = $feed->items()
    ->where('name', 'Вася')
    ->get();
```

Связь передаёт в `FeedItemBuilder` схему этой ленты и автоматически добавляет условие:

```php
where('feed_id', $feed->id)
```

Прямой запрос:

```php
FeedItem::query()
```

не имеет контекста конкретной ленты, поэтому логические имена в нём не используются. Внутренний код модуля может обращаться через него к физическим и системным колонкам.

### `FeedItemBuilder`

Модель `FeedItem` использует собственный Eloquent Builder:

```php
public function newEloquentBuilder($query)
{
    return new FeedItemBuilder($query);
}
```

`FeedItemBuilder` получает из схемы массив соответствий:

```php
[
    'name'  => '__string_1',
    'price' => '__bigint_1',
    'date'  => '__date_1',
]
```

и заменяет логические имена физическими перед передачей запроса стандартному Eloquent Builder.

Поддерживаются обычные операции Eloquent над колонками:

```php
where()
orWhere()
whereIn()
whereNotIn()
whereNull()
whereNotNull()
orderBy()
value()
pluck()
```

Вложенные условия используют тот же контекст:

```php
$items = $feed->items()
    ->where(function ($query) {
        $query
            ->where('name', 'Вася')
            ->orWhere('name', 'Петя');
    })
    ->get();
```

После преобразования выполняется запрос по физической колонке:

```php
FeedItem::query()
    ->where('feed_id', $feed->id)
    ->where(function ($query) {
        $query
            ->where('__string_1', 'Вася')
            ->orWhere('__string_1', 'Петя');
    })
    ->get();
```

Поля из `__data` нельзя использовать в `where`, `orderBy`, `unique`, `value` и `pluck`.

Попытка выполнить такой запрос считается ошибкой:

```php
$feed->items()
    ->where('content', 'Текст')
    ->get();
```

Неизвестное логическое имя также вызывает ошибку, а не передаётся в базу как имя колонки.

### Чтение значений

Загруженная модель `FeedItem` получает схему своей ленты и позволяет читать значения по логическим именам:

```php
$item = $feed->items()->findOrFail($id);

$name = $item->name;
$price = $item->price;
$content = $item->content;
```

Фактически значения берутся из:

```php
$item->__string_1;
$item->__bigint_1;
$item->__data['content'];
```

Системные поля доступны под своими настоящими именами:

```php
$item->id;
$item->feed_id;
$item->__position;
$item->__visible;
$item->created_at;
$item->updated_at;
```

### Изменение значений

Логические имена поддерживаются при обычном присваивании:

```php
$item = $feed->items()->findOrFail($id);

$item->name = 'Петя';
$item->price = 1500;
$item->content = '<h2>Описание</h2>';

$item->save();
```

Физически будут изменены:

```text
__string_1
__bigint_1
__data['content']
```

Изменение одного поля внутри `__data` не должно удалять остальные значения JSON.

Например, изменение `content` сохраняет `subTitle`, `description`, `userPhoto` и другие поля записи.

### Создание записи

Запись создаётся через связь ленты:

```php
$item = $feed->items()->create([
    'name'      => 'Вася',
    'price'     => 1000,
    'content'   => '<h2>Описание</h2>',
    '__visible' => false,
]);
```

Связь автоматически устанавливает:

```php
'feed_id' => $feed->id
```

Перед сохранением логические имена преобразуются в физические колонки:

```php
[
    '__string_1' => 'Вася',
    '__bigint_1' => 1000,
    '__data' => [
        'content' => '<h2>Описание</h2>',
    ],
    '__visible' => false,
]
```

Значения `__position`, `__visible`, булевых слотов и значения по умолчанию устанавливаются по правилам создания записи, описанным выше.

### Обновление записи

Обновление поддерживает логические имена:

```php
$item = $feed->items()->findOrFail($id);

$item->update([
    'name'    => 'Петя',
    'price'   => 1500,
    'content' => '<h2>Новое описание</h2>',
]);
```

Допускается массовое обновление выбранных записей:

```php
$feed->items()
    ->where('price', '<', 1000)
    ->update([
        'hasDiscount' => true,
    ]);
```

Перед выполнением запроса имена в условиях и обновляемых данных преобразуются в физические колонки.

При массовом обновлении полей `__data` модуль должен сначала загрузить записи и изменить JSON каждой записи отдельно. Обычный SQL `update` для вложенных полей `__data` не используется.

### Сортировка и пагинация

Логическое имя можно использовать в сортировке:

```php
$items = $feed->items()
    ->orderBy('name')
    ->paginate(20);
```

Фактически используется:

```php
orderBy('__string_1')
```

Для однозначного порядка при пагинации CRUD добавляет сортировку по `id`, если она не была указана явно:

```php
$items = $feed->items()
    ->orderBy('name')
    ->orderBy('id')
    ->paginate(20);
```

Для обратной сортировки:

```php
$items = $feed->items()
    ->orderByDesc('date')
    ->orderByDesc('id')
    ->paginate(20);
```

Наличие `id` в индексе помогает выполнить такой запрос, но само по себе не задаёт порядок — `id` должен присутствовать в `ORDER BY`.

### Валидация и значения по умолчанию

Замена логических имён физическими не выполняет валидацию.

При сохранении через API модуля отдельно выполняются:

- проверка правил `validation`;
- проверка `unique`;
- применение значений `default`;
- проверка связей;
- обработка изображений;
- установка системных значений.

`FeedItemBuilder` отвечает только за преобразование запросов.

Модель `FeedItem` отвечает за чтение и запись значений по логическим именам.

API CRUD отвечает за правила сохранения записи.

### HTML и преобразование данных

CRUD сохраняет строковые и текстовые значения без очистки и преобразования:

```php
$item->title = '<h2>Заголовок</h2>';
```

В базе сохраняется именно переданная строка.

Ключ `editor` определяет интерфейс редактирования в админке, но не изменяет правила хранения.

Очистка HTML может выполняться отдельной командой или кнопкой админки. Автоматическая очистка на текущем этапе не производится.

Способ вывода определяет приложение:

```blade
{{ $item->title }}
```

или:

```blade
{!! $item->title !!}
```
