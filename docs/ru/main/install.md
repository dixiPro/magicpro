# Установка: что происходит и когда

Документ описывает установку так, как она идёт на самом деле: кто что создаёт, в
каком порядке и что остаётся несделанным, если шаг пропустили. Разбор известных
дефектов установки — в `docs/toDo/TZ_install.md`, здесь только фактическая
картина.

По `Readme.md` установка выглядит так:

```bash
composer require dixipro/magicpro
php artisan migrate
(sudo crontab -u www-data -l 2>/dev/null; echo "* * * * * cd $(pwd) && /usr/bin/php artisan schedule:run >> /dev/null 2>&1") | sort -u | sudo crontab -u www-data -
```

Затем открыть `/a_dmin`.

Четыре команды, но работу делают не они: каталоги, файлы статей и ассеты
появляются при первом заходе в админку. До этого захода на диске нет ничего.

## 1. composer require

Пакет подключается как обычная зависимость. В разработке — path-репозиторий с
симлинком: `vendor/dixipro/magicpro` указывает на `packages/dixipro/magicpro`.

`package:discover` находит провайдер по `extra.laravel.providers` в
`composer.json` пакета, регистрировать руками ничего не нужно.

В автозагрузку попадает и то, чего ещё нет:

```json
"MagicProControllers\\": "../../../storage/dataMagicPro/controller/"
```

Каталога на этот момент не существует, и это нормально: psr-4 сопоставляет
префикс каталогу лениво, отсутствие проверяется только при попытке загрузить
класс.

Composer ничего не создаёт: ни каталогов, ни таблиц. Файлов на диске после этого
шага не прибавляется.

В пакете лежит `src/Installer/InstallCommand.php` с сигнатурой
`magicpro:install`, но команда нигде не регистрируется — ни `commands()` в
провайдере, ни автозагрузки консольных команд. Вызвать её нельзя, в первой же
строке файла написано «не используется, перенёс в старт админки».

## 2. Любой следующий запрос: провайдер

Дальше всё, что делает MagicPro, начинается с `MagicServiceProvider`. Он
отрабатывает на каждый запрос и на каждую artisan-команду, включая саму
`migrate`.

`register()` — раньше всего остального:

1. `MagicGlobals::register()` читает `storage/app/private/magic/mproLocalIni.php`.
   Файла нет — он создаётся из умолчаний схемы `src/Config/magicSchema.php`. Это
   первое, что MagicPro пишет на диск, и происходит оно само.
2. Определяются константы: `MAGIC_DATA_DIR` (`storage/dataMagicPro`),
   `MAGIC_VIEW_DIR`, `MAGIC_CONTROLLER_DIR`, `VENDOR_FROM`, `VENDOR_PUBLIC`,
   `STATIC_HTML_CREATE_DIR`, `MAGIC_FILE_ROLES`, `ART_NAME_404`. Часть считается
   из настроек, поэтому порядок «сперва `$INI`, потом константы» обязателен.
3. `MagicLang::loadLocale()` поднимает словарь по `LANGUAGE`.

`boot()` — всё остальное:

- `loadViewsFrom(MAGIC_VIEW_DIR, 'magic')` — пространство `magic::`. Каталога
  может не быть, Laravel на это не жалуется: он просто не найдёт вьюху, когда её
  попросят;
- маршруты админки из `admin/web.php` под middleware `web`, вьюхи админки как
  `magicAdmin::`;
- `loadMigrationsFrom(__DIR__ . '/../database/migrations')` — миграции пакета
  видны artisan без публикации;
- guard `magic` и провайдер `magic_users` поверх модели `MagicProUser`, алиас
  middleware `magic.auth`, blade-директива `@mproauth`;
- алиасы `Feed` и `FeedItem`, чтобы блейды писали короткие имена;
- расписание через `callAfterResolving(Schedule::class, …)`;
- маршруты MCP-сервера из `src/Mcp/ai.php`;
- медиатеке подменяется генератор путей, но только если он стандартный.

## 3. php artisan migrate

Восемь миграций пакета. Префиксов с датой у них нет, порядок — по имени файла.

| Файл | Что создаёт |
| --- | --- |
| `create_magicPro_articles_table.php` | таблицу `articles` и три статьи |
| `create_magicPro_users_table.php` | `magicPro_users` и администратора |
| `create_magicPro_lenta_0_feed_groups_table.php` | группы лент |
| `create_magicPro_lenta_1_feeds_table.php` | ленты |
| `create_magicPro_lenta_2_feed_items_table.php` | записи лент |
| `create_magicPro_mail_messages_table.php` | очередь и историю писем |
| `create_magicPro_email_addresses_table.php` | адреса и их состояние |
| `create_magicPro_events_table.php` | события |

### Статьи

Таблица называется `articles`, без префикса пакета. Вместе с ней вставляются три
записи:

| id | name | Что это |
| --- | --- | --- |
| 1 | `root` | корень дерева, `parentId = 0`, имя защищено от изменения |
| 2 | `error404` | страница, которой отвечает роутер на ненайденный адрес |
| 3 | `index` | главная, единственная с `isRoute = true` |

Создание таблицы и вставка этих трёх строк лежат внутри одного условия:

```php
if (!Schema::hasTable('articles')) { … }
```

Если таблица `articles` в проекте уже была — от хост-приложения или от прошлой
установки, — миграция не вставит ничего и всё равно отметится выполненной. Сайт
останется без корня, и ниоткуда это не видно.

### Администратор

Заводится не сидером, а самой миграцией `create_magicPro_users_table.php`, и
интерактивно:

```php
$email    = readline('Enter admin email: ');
$password = readline('Enter password: ');
```

Пароль хешируется, роль ставится `admin`, а введённые email и пароль печатаются
в консоль открытым текстом — чтобы не потерялись при установке. Там же
подсказка открыть `/a_dmin`.

Отсюда следуют три вещи, о которых надо знать заранее:

- **Миграция ждёт человека.** В неинтерактивном запуске — `migrate --force` из
  скрипта, деплой, CI, `composer setup` из корневого `composer.json` — `readline()`
  вернёт пустую строку, и админ создастся с пустым email и пустым паролем.
- **Нужно расширение readline.** Без него функции нет и миграция падает на
  середине.
- **`migrate:fresh` спросит заново**, а откат `down()` роняет таблицу вместе со
  всеми администраторами.

Сидер `database/seeders/UserSeeder.php` к админке отношения не имеет: он делает
двести пользователей `App\Models\User` хост-приложения и запускается вручную,
для тестов.

## 4. Крон

Строка из `Readme.md` кладёт в crontab пользователя `www-data` запуск
`schedule:run` раз в минуту. `sort -u` не даёт строке задвоиться, уже стоящие
задачи остаются.

В расписании две задачи: `Heartbeat` — отметка живого крона, и `sendQueue` —
разбор очереди писем. Без крона письма из очереди не уходят, а `/a_dmin`
показывает, что планировщик не настроен. На остальное отсутствие крона не влияет:
страницы работают.

## 5. Первый заход на /a_dmin

Здесь и происходит установка.

Маршрут объявлен без `magic.auth`:

```php
Route::get('/a_dmin', [AdminController::class, 'index'])->name('magic.a_dmin');
```

Значит шаги установки выполняются до всякой проверки прав — форму входа рисует
уже шаблон, поверх готового результата. За `magic.auth` стоят POST-API, а не
GET-страницы админки.

Порядок такой:

1. Берётся общая блокировка `magicpro:install` на 60 секунд, ожидание — 5. Не
   дождались (установку прямо сейчас делает сосед) — список шагов возвращается
   пустым, страница просто ничего не покажет в диагностике.
2. Четыре шага подряд, каждый в своём `try`: упавший не мешает следующим.
3. Ошибка шага пишется строкой на экран и целиком в `storage/logs/install.log`.

### Шаги

| Шаг | Что проверяет | Что делает |
| --- | --- | --- |
| `installDataDir` | существует ли `storage/dataMagicPro` | создаёт каталог, пишет и удаляет тестовый файл, зовёт `regenerateAll` |
| `installVendorPublic` | `version.txt` в `public/vendor/dixipro/magicpro` против `MAGIC_VERSION` | копирует `readyBundle`, записывает версию |
| `installUploadDir` | существует ли `public/{PUBLIC_UPLOAD_DIR}` | создаёт каталог |
| `installStorageLink` | есть ли `public/storage` | ставит симлинк на `storage/app/public` |

`regenerateAll` (`API_ArticlesPostController`) проходит по всем статьям и для
каждой зовёт `createMpro`: пишет блейд в `storage/dataMagicPro/view/имя.blade.php`
и, если у статьи включён `useController`, контроллер в
`storage/dataMagicPro/controller/имя.php`. Каталоги создаёт не билдер, а
`MagicFile::saveToFile()` — она поднимает каталог под файлом перед записью.
Поэтому `view/` и `controller/` появляются вместе с первым записанным файлом.

Второй шаг — единственный, где хранится отметка о проделанном: по скопированным
файлам версию не узнать, спросить не у кого. Остальные шаги смотрят на результат.

### Что ещё показывает страница

- **Обработка изображений** — есть ли `cwebp`, `vips` и расширение `gd`.
  Проверяется по коду возврата, а не по выводу. Нет утилиты — рядом печатается
  команда установки.
- **Планировщик** — свежесть отметки `Heartbeat`, порог 120 секунд. Крон не
  тикает — под строкой печатается готовая команда установки крона.

Обе проверки ничего не чинят, только сообщают.

### Вход

Форма шаблона шлёт POST на `/a_dmin/login`, `AuthController` пускает через guard
`magic`. После входа шаблон рисует меню, до входа — только форму. Диагностика
установки при этом отработала в любом случае.

## Что появилось на диске

| Путь | Кто создал | Когда |
| --- | --- | --- |
| `storage/app/private/magic/mproLocalIni.php` | `MagicGlobals` | первый же запрос или artisan-команда |
| `storage/dataMagicPro/view/` | `MagicFile::saveToFile` при генерации статей | первый заход на `/a_dmin` |
| `storage/dataMagicPro/controller/` | там же | появляется, только если есть статья с контроллером |
| `public/vendor/dixipro/magicpro/` | `installVendorPublic` | первый заход на `/a_dmin` |
| `public/{PUBLIC_UPLOAD_DIR}` | `installUploadDir` | то же |
| `public/storage` | `installStorageLink` | то же |
| `storage/app/private/magic/heartbeat.txt` | `Heartbeat` | первая минута живого крона |
| `storage/logs/install.log` | `stepFailed` | только при ошибке шага |

Ассеты админки берутся из `readyBundle` — собранный фронт едет в пакете, `npm run
build` при установке не нужен. Блейды админки просят их явным адресом:
`@vite('admin/js/…', 'vendor/dixipro/magicpro')`, и путь совпадает с
`VENDOR_PUBLIC`. Вызовы `Vite::useBuildDirectory('vendor/magicpro')` и
`publishes([… => public_path('vendor/magicpro')], 'magicpro-assets')` в провайдере
указывают на другой каталог и ни на что не влияют: второй аргумент `@vite`
перебивает первое, а публикацией никто не пользуется.

## Где установка может остановиться незаметно

Собрано в одном месте: всё это не бросает ошибок и выглядит как удачная
установка.

- **Каталог `storage/dataMagicPro` уже существует.** Шаг считает работу
  сделанной, `regenerateAll` не зовётся, вьюх нет. Само не починится: каталог
  остаётся и после сбоя. Подробно — `docs/toDo/TZ_install.md`.
- **Таблица `articles` уже была.** Статьи не засеялись, генерировать нечего,
  `regenerateAll` возвращает успех.
- **`migrate` прогнали неинтерактивно.** Администратор создан с пустыми email и
  паролем.
- **Каталоги создал root.** Всё дальнейшее пишет веб-сервер, и пишет он в чужой
  каталог. По `Readme.md` после установки положено сделать
  `sudo chown -R :www-data storage/dataMagicPro`.
- **Не дождались блокировки.** Диагностика на странице пуста, и это выглядит как
  «проверок нет», а не как «проверки не выполнялись».

Быстрая проверка после установки: в `storage/dataMagicPro/view/` должно лежать по
блейду на каждую статью — после чистой миграции это `root.blade.php`,
`error404.blade.php` и `index.blade.php`. Если их нет, помогает ссылка
«Перегенерировать статьи» на `/a_dmin/setup`: она дёргает тот же `regenerateAll`.
