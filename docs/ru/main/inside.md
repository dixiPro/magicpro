# Центральный модуль: как устроено

Документ для того, кто правит сам движок. Как писать страницы — в `use.md`.

## Структура данных

Одна таблица — `magicPro_articles`. Всё остальное движок держит файлами.

| Колонка                    | Тип                        | Назначение                       |
| -------------------------- | -------------------------- | -------------------------------- |
| `id`                       | bigint                     | первичный ключ                   |
| `parentId`                 | integer, default 0, индекс | родитель; у корня `0`            |
| `npp`                      | integer, default 0         | номер по порядку у родителя      |
| `name`                     | string, индекс             | имя, оно же маршрут              |
| `title`                    | string, default `''`       | заголовок                        |
| `controller`               | text nullable              | исходник контроллера             |
| `body`                     | text nullable              | исходник блейда                  |
| `templateName`             | string, default `''`       | не используется                  |
| `directory`                | boolean, default 0         | признак, что есть дети           |
| `menuOn`                   | boolean, default 0         | участвует в меню                 |
| `isRoute`                  | boolean, default 0         | опубликована маршрутом           |
| `routeParams`              | text nullable              | параметры маршрута, JSON строкой |
| `created_at`, `updated_at` | datetime                   |                                  |

Внешних ключей нет: дерево держится на `parentId`, целостность — на коде.
`routeParams` лежит текстом, а не json-колонкой, — модель разбирает его сама.

Тела статей в базе, а их рабочие копии на диске: блейд в
`storage/dataMagicPro/view/{name}.blade.php`, контроллер в
`storage/dataMagicPro/controller/{name}.php`. База — источник истины, файлы
перегенерируются из неё.

Настройки в этой таблице не лежат: они в файле, см. «Настройки».

## Путь запроса

1. `admin/web.php` регистрирует маршруты админки и в самом конце catch-all.
2. Catch-all уходит в `MagicProSrc\Routing\DynamicRouteHandler::handle()`.
3. Тот зовёт `checkFirts()`, а всё, что оттуда вылетело, ловит и отдаёт 404.

`checkFirts()` по шагам:

- берёт первый сегмент адреса; сегментов нет — статья `index`;
- разворачивает точку: в имени есть `.` — она меняется на `___`, нет — наоборот.
  Так адреса вида `/robots.txt` доходят до статьи `robots___txt`. Направление
  менять нельзя, не проверив оба;
- проверяет имя — только латинские буквы, цифры, дефис и подчёркивание — и ищет
  статью по `name`;
- нет статьи, нет `isRoute`, `adminOnly` без входа в админку — исключение;
- `postEnable` — забирает `$request->post()` и разбор GET пропускает целиком,
  иначе идёт в `checkRout()` за параметрами;
- собирает `$Env` и отдаёт либо вью, либо контроллер.

Развилка последнего шага буквально такая:

```php
if (array_key_exists('useController', $routeParams) && !$routeParams['useController']) {
    return view($view, ['Env' => $env, 'Get' => $res, 'Post' => $postParams]);
}
```

То есть вью рендерится, только когда ключ есть и он `false`. Ключа нет вовсе —
пойдёт попытка вызвать контроллер `\MagicProControllers\{name}`. В контроллерной
ветке `$Env` дополнительно кладётся в `$request->attributes`.

Ошибки наружу не выходят: `handle()` ловит `\Throwable` и рендерит статью
`ART_NAME_404` с кодом 404, передавая в неё `message`, `file` и `line`
исключения. Удобно при разработке, но на бою эта статья не должна их печатать.

Маршруты, которым до catch-all доходить нельзя, перечисляются в `EXCLUDED_ROUTES`.

## Откуда берутся вью и контроллеры

Регистрация в `MagicServiceProvider`:

```php
$this->loadViewsFrom(MAGIC_VIEW_DIR, 'magic');       // magic::имя
Blade::anonymousComponentPath(MAGIC_VIEW_DIR, 'magic');   // <x-magic::имя />
Blade::componentNamespace('MagicProControllers', 'magic'); // <x-magic::Имя />
```

Сами файлы пишет `MagicProBuilder` (`admin/controller/MagicProBuilder.php`), две
функции:

- `createMpro($article)` — сперва зовёт `deleteMpro()`, потом всегда пишет блейд,
  а контроллер только если его текст непустой и `useController` включён.
  Записанный контроллер тут же проверяется `php -l`; не прошёл — исключение, и
  сохранение статьи падает целиком;
- `deleteMpro($article)` — сносит оба файла статьи.

Отсюда правило: генерированное в `storage/dataMagicPro/` правится только через
статью.

## Сохранение статьи

`API_ArticlesPostController`, `POST /a_dmin/api/articles`, за `magic.auth`.
Команды:

| Команда                                                   | Что делает                |
| --------------------------------------------------------- | ------------------------- |
| `getById`, `articleByName`                                | статья целиком            |
| `getParents`, `getChildrens`, `getBrothers`, `makeHeTree` | обход дерева              |
| `createNew`, `saveById`, `deleteById`, `copyRec`          | правка                    |
| `move`                                                    | перенос и порядок         |
| `regenerateAll`                                           | перегенерация всех файлов |
| `search`                                                  | поиск                     |
| `getDefaultController`, `getDefaultLiveWareController`    | заготовки для «лампочки»  |

Позицией в дереве владеет `move`, и только он: `saveById` выбрасывает из данных
`parentId` и `npp`, чтобы обычное сохранение их не сдвинуло. `move` перенумеровывает
`npp` у соседей и поддерживает флаг `directory` у обоих родителей, всё внутри
`DB::transaction`.

Поэтому сохранение статьи — не запись строки: это ещё и генерация файлов, и
пересчёт дерева. Прямой `UPDATE` рассинхронит базу с диском.

## Настройки

Настройки живут в трёх местах, и это разные вещи:

| Файл                                         | Что в нём                                                        |
| -------------------------------------------- | ---------------------------------------------------------------- |
| `src/Config/magicSchema.php`                 | описание параметров: какие бывают, какого типа, что по умолчанию |
| `storage/app/private/magic/mproLocalIni.php` | значения этой установки                                          |
| `src/Config/MagicGlobals.php`                | загрузка, проверка, сохранение и константы                       |

### Схема

`magicSchema.php` возвращает массив «имя параметра → описание»:

```php
'LANGUAGE' => [
    'label'   => 'language',   // ключ словаря, не текст
    'type'    => 'list',
    'values'  => ['ru', 'en'],
    'default' => 'ru',
    'mutable' => true,         // false — оператор поменять не сможет
],
```

`label` — это **ключ** из `lang/{locale}/messages.php`, а не готовая подпись.
Экран Setup подставляет его через `MagicLang::getMsg()`, и неизвестный ключ даёт
пустую подпись.

`mutable => false` означает, что при сохранении значение принудительно вернётся к
`default`, чем бы его ни пытались заменить.

### Типы параметров

| Тип         | Значение                       | Чем правится                    | Что проверяется                    |
| ----------- | ------------------------------ | ------------------------------- | ---------------------------------- |
| `string`    | строка                         | поле ввода                      | что это строка                     |
| `localpath` | путь от корня проекта          | поле ввода                      | строка, непустая                   |
| `boolean`   | флаг                           | переключатель                   | что это bool                       |
| `integer`   | целое число                    | поле-счётчик                    | целое, границы `min` и `max`       |
| `list`      | одно из готовых значений       | выпадающий список               | вхождение в `values`               |
| `array`     | список строк                   | список со строками и корзинками | что это массив                     |
| `group`     | контейнер вложенных параметров | те же поля внутри               | массив, каждое поле по своей схеме |

У `integer` границы задаются `min` и `max`, у `list` — обязательный `values`.
Браузер только подсказывает, проверяет всё равно сервер.

### Группа

Когда параметров по одной теме несколько, они складываются в контейнер:

```php
'RESIZE' => [
    'label'   => 'resize_params',
    'type'    => 'group',
    'data'    => [
        'MAX_RESIZE' => [
            'label'   => 'image_max_size',
            'type'    => 'integer',
            'min'     => 10,
            'max'     => 1000,
            'default' => 1000,
            'mutable' => true,
        ],
        'RESIZE_FORMAT' => [
            'label'   => 'image_resize_format',
            'type'    => 'list',
            'values'  => ['webp', 'avif', 'jpg', 'png'],
            'default' => 'webp',
            'mutable' => true,
        ],
    ],
],
```

В файле значений группа лежит вложенным массивом, читается целиком:

```php
MagicGlobals::$INI['RESIZE']['MAX_RESIZE'];

// или весь набор сразу
$resize = MagicGlobals::$INI['RESIZE'];   // ['MAX_RESIZE' => 1000, 'RESIZE_FORMAT' => 'webp', …]
```

Вложенность одноуровневая: группа внутри группы не предусмотрена. Умолчания,
подстановка `default` немутабельным и проверка типов идут вглубь автоматически, а
на экране группа сворачивается так же, как `array`.

### Файл значений

`mproLocalIni.php` — обычный php-массив, который возвращается через `return`.
Пишется машиной, руками его править не предполагается:

```php
<?php return array (
  'LANGUAGE' => 'en',
  'PUBLIC_UPLOAD_DIR' => '/design',
  'EXCLUDED_ROUTES' => array ( 0 => 'livewire', ... ),
);
```

Лежит в `storage/app/private/`, то есть наружу не отдаётся и в репозиторий не
попадает: у каждой установки он свой.

### Как это работает

1. `MagicServiceProvider::register()` зовёт `MagicGlobals::register()`.
2. Тот первым делом читает настройки: `loadLocal()`. Файла нет — он создаётся из
   умолчаний схемы (`saveDefaultIniFile()`), так что после установки система
   поднимается сама.
3. Значения кладутся в `MagicGlobals::$INI` — статический массив, доступный
   отовсюду как `MagicGlobals::$INI['LANGUAGE']`.
4. Дальше в том же методе определяются константы `MAGIC_DATA_DIR`,
   `MAGIC_VIEW_DIR`, `MAGIC_CONTROLLER_DIR`, `MAGIC_FILE_ROLES` и прочие. Часть
   из них считается на основе настроек, поэтому порядок важен: сперва `$INI`,
   потом константы.

Файл читается на каждый запрос, никакого кеша поверх него нет.

### Сохранение и сброс

Экран Setup работает через `API_Setup`:

- `getParamsAttr` — отдаёт схему с переведёнными подписями;
- `getIniParams` — текущие значения;
- `saveIniParams` → `MagicGlobals::saveIniFile()` — проверяет типы
  (`validate()`), подставляет `default` немутабельным, пишет файл через
  `var_export`;
- `restoreParams` — **удаляет файл целиком**. Отдельного сброса одного параметра
  нет: при следующем старте файл соберётся из умолчаний схемы.

`validate()` бросает исключение на неизвестный ключ и на неподходящий тип, так
что кривой запрос до файла не доедет.

### Кто какие настройки читает

| Параметр            | Где используется                                                                 |
| ------------------- | -------------------------------------------------------------------------------- |
| `LANGUAGE`          | `MagicServiceProvider` → `MagicLang::loadLocale()`, `MproHelper`                 |
| `EXCLUDED_ROUTES`   | `admin/web.php`, исключения для catch-all маршрута                               |
| `ENABLE_URL_PARAMS` | `Routing/DynamicRouteHandler.php`, разрешённые utm-параметры                     |
| `PUBLIC_UPLOAD_DIR` | `AdminController`, `API_FileManagerPostController`, константа `MAGIC_FILE_ROLES` |
| `STATIC_HTML_DIR`   | `API_Setup`, генерация статических страниц                                       |
| `RENDER_URL`        | дополнительные адреса для генерации статики                                      |
| `RESIZE`            | пока нигде: группа заведена под ресайз изображений, код появится позже           |

### Добавить новый параметр

1. Описать его в `magicSchema.php`.
2. Завести ключ подписи в `lang/ru/messages.php` и `lang/en/messages.php`.
3. Читать через `MagicGlobals::$INI['ИМЯ']`.

`mproLocalIni.php` трогать не надо: недостающий ключ подставляется из умолчания
схемы при первом же сохранении настроек. До этого момента его в файле нет,
поэтому в коде, который читает параметр сразу после обновления, безопаснее писать
`MagicGlobals::$INI['ИМЯ'] ?? 'умолчание'`.

## Вход в админку

`admin/controller/AdminController.php` — четыре метода, все за `magic.auth`.

| Маршрут                  | Метод        | Что делает                            |
| ------------------------ | ------------ | ------------------------------------- |
| `/a_dmin`                | `index`      | главная админки, она же самоустановка |
| `/a_dmin/artList`        | `artList`    | список статей                         |
| `/a_dmin/adminList`      | `adminList`  | список администраторов                |
| `/a_dmin/api/clearCache` | `clearCache` | пять artisan-команд очистки           |
| `/a_dmin/api/testWrite`  | `testWrite`  | проверка прав на запись               |

### index — самоустановка

Открытие `/a_dmin` — не просто страница. При заходе проверяется и при нужде
чинится состояние установки:

1. нет `MAGIC_DATA_DIR` — создаётся, туда пишется и удаляется тестовый файл, а
   затем перегенерируются все статьи (`regenerateAll`), потому что вьюхи и
   контроллеры лежали именно там;
2. нет `VENDOR_PUBLIC` или в нём другая версия (`version.txt` против
   `MAGIC_VERSION`) — из `VENDOR_FROM` копируется `readyBundle`, версия
   записывается. Так обновление пакета доезжает до `public/vendor` без ручной
   команды;
3. нет каталога загрузок `PUBLIC_UPLOAD_DIR` — создаётся;
4. нет ссылки `public/storage` — создаётся симлинком.

Ошибки не бросаются наружу: всё, что случилось, копится строками и выводится
списком на самой странице. Поэтому сломанная установка выглядит как список
сообщений, а не как белый экран.

Каждый шаг делается только когда чего-то не хватает, так что обычный заход не
делает ничего.

**Проверка внешних утилит** — `cwebp`, `libvips` и прочее, чем режутся
изображения, — живёт здесь же. Страница и так отвечает на вопрос «всё ли на
месте», её открывают первой, и результат виден сразу.

### testWrite

Идёт по `MAGIC_FILE_ROLES` — это список каталогов с описаниями, собранный в
`MagicGlobals`. Для каждого: создать каталог, если нет, записать файл, удалить.
Результат кладётся в тот же массив (`ok` или текст ошибки с названием операции) и
уезжает во flash-сессию `testWriteStatus`.

### clearCache

`cache:clear`, `config:clear`, `route:clear`, `view:clear`, `event:clear` через
`Artisan::call`. Коды возврата уходят во flash `clearCacheStatus`. Важно, что
команды выполняет веб-сервер: файлы кеша принадлежат ему же, и чужих владельцев
не появляется.

| `/a_dmin`                | `index`      | главная, она же самоустановка и диагностика |

### index — самоустановка

Заход на `/a_dmin` чинит установку, чтобы после `composer install` не надо было
ничего делать руками. Четыре шага, каждый смотрит сам, нужно ли что-то делать:

1. нет `MAGIC_DATA_DIR` — создаётся, туда пишется и удаляется тестовый файл, а
   затем перегенерируются все статьи: вьюхи и контроллеры лежали именно там;
2. нет `VENDOR_PUBLIC` или в нём другая версия (`version.txt` против
   `MAGIC_VERSION`) — из `VENDOR_FROM` копируется `readyBundle` и пишется версия.
   Так обновление пакета доезжает до `public/vendor` без ручной команды;
3. нет каталога загрузок `PUBLIC_UPLOAD_DIR` — создаётся;
4. нет ссылки `public/storage` — создаётся симлинком. Без неё не отдаются ни
   загруженные файлы, ни кеш производных картинок, а ломается она молча, например
   при переносе проекта.

Всё под общей блокировкой `magicpro:install` на 60 секунд: иначе два
администратора, зашедших одновременно, вдвоём полезут копировать каталоги. Не
дождались за 5 секунд — установку делает сосед, повторять незачем.

У каждого шага свой `try`: упавшая перегенерация статей не должна оставить
каталог загрузок несозданным. Упавший шаг пишется в лог `install` целиком, а на
экран уходит строкой.

Проверки идут на каждый заход, без кеша. Кеш здесь сохраняет прошлое положение дел
и показывает его как нынешнее, а страница нужна ровно для обратного.

### Диагностика утилит

`imageTools()` спрашивает версии у `cwebp` и `vips` и смотрит расширение `gd`.
Результат — по коду возврата, а не по выводу: `vips: not found` приходит текстом и
выглядит как удачный ответ. Рядом с крестом печатается команда установки, иначе
крест ничего не сообщает.

### Статус планировщика

Крон живёт снаружи и о себе не сообщает. Поэтому в расписании стоит
`MagicProSrc\Scheduling\Heartbeat`: раз в минуту он переписывает
`storage/app/private/magic/heartbeat.txt`. Больше он ни для чего не нужен, но
остальные задачи следов не оставляют — пустая очередь писем молчит ровно так же,
как мёртвый крон.

`AdminController::cron()` смотрит `filemtime` этого файла, а не то, что внутри:
так проверка не зависит от формата записи. Путь берётся из `Heartbeat::FILE`,
порог — константа `CRON_MAX_AGE`, 120 секунд.

| Что на диске              | Что на экране                                          |
| ------------------------- | ------------------------------------------------------ |
| файла нет                 | «Крон не настроен: планировщик не запускался ни разу.» |
| отметка старше 120 секунд | «Крон не работает. Последняя отметка: …»               |
| отметка свежая            | «работает, последняя отметка: …»                       |

В первых двух случаях ниже печатается готовая команда установки крона — та же, что
в `Readme.md`, с подставленным `base_path()` и с `php` по полному пути: у крона
своего `PATH` почти нет. При живом кроне команда не показывается.

Строка отвечает только за то, тикает ли планировщик. Уходят ли письма из очереди,
она не знает.

## Расписание

`MagicProSrc\Scheduling\MagicProSchedule::register()`, подключается из
`MagicServiceProvider` через `Schedule::class`. Две задачи, обе ежеминутно:
