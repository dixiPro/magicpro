# Вёрстка сайта

Правила для Blade статей, шаблонов и компонентов. Маршруты и PHP-контроллеры
описаны в [руководстве по сайту](use.md).

## Статьи

### Общие правила

- не меняй смысл исходного текста и не добавляй факты от себя;
- используй стили Bootstrap 5, если он подключён шаблоном сайта;
  наличие Bootstrap в админке само по себе не подключает его к публичной странице;

Всё, что можно в блейдах Laravel, можно и здесь. Этот файл — не пересказ
документации Laravel, а то, что специфично для MagicPro и то, обо что легко
споткнуться.

### Роли статьи

Статья хранит Blade и при необходимости контроллер. Её роль определяется
настройками и способом подключения.

| Роль                    | Как выглядит                                 | Как подключается                                |
| ----------------------- | -------------------------------------------- | ----------------------------------------------- |
| Страница                | `@extends` + `@section('content')`           | маршрутом, `isRoute`                            |
| include                 | голая разметка, переменные приходят снаружи  | `@include('magic::имя', [...])`                 |
| Компонент               | `@props([...])` первой строкой               | `<x-magic::компонент …>`                        |
| Шаблон                  | `<html>`, шапка, подвал, `@yield('content')` | `@extends('magic::шаблон')`                     |
| Страница с контроллером | Blade и класс на основе `MagicController` | Маршрут с `isRoute` и `useController` |
| helper                  | только контроллер: класс со своими методами  | `app(\MagicProControllers\имя::class)->метод()` |

#### Страница

Статья с включённым `isRoute` открывается по адресу `/<имя>`. Какие параметры
адрес принимает — `routeParams`, см. [маршрут статьи](use.md#маршрут-статьи).

```blade
@extends('magic::main')

@section('title', $Env['title'])

@section('content')
    <h1>{{ $Env['title'] }}</h1>
@endsection
```

В блейде страницы есть `$Env` и `$Get`, при `postEnable` — `$Post` (с
контроллером его отдаёт в блейд сам контроллер). Нужны данные из базы или ленты
— их готовит контроллер статьи, а не `@php` на полэкрана.

#### include

Голая разметка без `@props`: шапка, подвал, блок контактов. Переменные приходят
снаружи:

```blade
@include('magic::contactsBlock', ['phone' => $phone])
```

Blade статьи `contactsBlock`:

```blade
<p>{{ $phone }}</p>
```

include и компонент решают одну задачу — переиспользование, — но по-разному.
Правило простое: **если у блока есть входы, которые хочется называть и
проверять, это компонент; если он просто вынесен, чтобы не мешался, — include.**

Компонент дороже в объявлении и дешевле в использовании: у него есть
собственные умолчания; вход без умолчания нужно передать явно. Он не видит
случайных переменных вызывающего. include наоборот — видит всё, что было в области
вызова, и молча ломается, когда там чего-то нет.

**Компонент с `$attributes` нельзя подключать обычным `@include`.** Директиве неоткуда взять
`$attributes`, будет ошибка про неопределённую переменную. Если блок нужен и
там и там — либо делай его include, либо зови компонент как компонент.

Включение рендерит только Blade, без запуска маршрута или контроллера
включаемой статьи. Стандартные условные варианты Laravel тоже доступны:

```blade
@includeIf('magic::promo')
@includeWhen($showPromo, 'magic::promo', ['item' => $item])
```

#### Компонент

Минимальный пример карточки:

Создайте статью `priceCard`. Выключите `isRoute` и `useController`.

```blade
@props(['title', 'price' => 0])

<article class="price-card">
    <h2>{{ $title }}</h2>
    <strong>{{ number_format($price, 2) }}</strong>
</article>
```

```blade
<x-magic::priceCard title="Basic" :price="$item->price" />
```

Контроллер статьи у анонимного компонента не запускается.

Для списка с настраиваемой карточкой набор входов можно расширить:

```blade
@props(['data' => [], 'card', 'columns' => 4, 'id' => null])
```

Ключ без значения — вход, который вызывающий должен передать; с значением —
вход с умолчанием. `@props` сам по себе не проверяет тип и допустимость значения.

Зовётся так:

```blade
<x-magic::slider_column
  :data="$res['data']"
  card="magic::product_card"
  :columns="5"
/>
```

Двоеточие перед именем значит «дальше выражение», без двоеточия — строка.
`:columns="5"` даёт число, `columns="5"` — строку `"5"`; для сравнений и
арифметики это разные вещи.

**Дефис в атрибуте превращается в камелкейс.** `mobile-width="85"` внутри
компонента доступен как `$mobileWidth`. Объявляйте вход как `mobileWidth`
в `@props` и передавайте его как `mobile-width`. Не рассчитывайте, что
подчёркивание в имени `$mobile_width` автоматически согласуется с таким атрибутом.

**Имя и тип компонента.** В примерах анонимные статьи названы `card` и
`priceCard`, классовая — `PriceBadge`. Сам по себе регистр не переключает
тип: Laravel сначала ищет зарегистрированный класс, затем анонимную view.
Соблюдайте имя статьи и не создавайте конфликтующий класс для анонимной разметки.
[Классовый компонент](use.md#классовый-компонент) требует своего PHP-класса.

**Проброс класса снаружи:**

```blade
<div {{ $attributes->merge(['class' => 'card h-100']) }}>
```

Тогда `<x-magic::card class="mb-3" />` добавит класс, а не затрёт свой.

##### Список: имя карточки вместо слота

Слот компонента рендерится **один раз и в области вызывающего**: `$slot` внутри
— уже готовый html. Поэтому «дай мне разметку одного элемента, а я повторю её
для каждого» слотом не делается — ни обычным, ни именованным.

Делается передачей имени блейда:

```blade
{{-- Caller --}}
<x-magic::slider :data="$items" card="magic::product_card" />

{{-- Component body --}}
@foreach($data as $item)
  <div class="slide">
    <x-dynamic-component :component="$card" :item="$item" />
  </div>
@endforeach
```

`<x-dynamic-component>` принимает имя в переменной и понимает префикс `magic::`.

Договорённость, которая избавляет от разнобоя: **карточка получает ровно один
проп — `item`, один элемент массива.** Всё остальное карточка достаёт из него
сама. Иначе каждый список начинает придумывать свой набор параметров, и
подменить одну карточку другой уже нельзя.

##### Один компонент — много экземпляров

Как только компонент рисует что-то с `id` или собственным css, он обязан
пережить два своих экземпляра на странице.

```blade
@php
  $sliderId = $id ?: 'slider-' . \Illuminate\Support\Str::random(6);
@endphp
```

Дальше все селекторы в стилях и в скрипте — от этого `id`. Проп `id` оставляй:
иногда снаружи нужно за компонент зацепиться.

Никаких глобальных селекторов вроде `.swiper` в скриптах компонента: на странице
может оказаться чужой блок с тем же классом, и вы поломаете друг друга. Это не
теория — так уже было с галереей товара, которая инициализировала все слайдеры
на странице разом.

#### Шаблон

Каркас страницы: `<html>`, шапка, подвал и места, куда страница вставляет своё.
`isRoute` и контроллер выключены.

```blade
<!doctype html>
<html lang="ru">
<head>
    <meta charset="utf-8">
    <title>@yield('title', 'Site')</title>
    @stack('styles')
</head>
<body>
    @yield('content')
    @stack('scriptsBottom')
</body>
</html>
```

`@stack('styles')` и `@stack('scriptsBottom')` — места для стилей и скриптов
страниц и компонентов, см. «Стили и скрипты» ниже.

**Шаблон может требовать переменных.** Если шаблон читает, скажем, `$meta` без
проверки, страница на нём без этой переменной упадёт. Передавай вторым
аргументом: `@extends('magic::шаблон', ['meta' => [...]])`.

#### Страница с контроллером

Когда Blade нужны подготовленные данные, включите `isRoute` и `useController`.
Контракт `MagicController`, полный пример `process()` и вызов общего метода
статьи-helper приведены в [контроллере статьи](use.md#контроллер-статьи).

## Стили и скрипты

Страница отдаёт их шаблону стеками:

```blade
@push('styles')
  <link href="/design/include/thing.css?v=3" rel="stylesheet">
@endpush

@push('scriptsBottom')
  <script src="/design/include/thing.js?v=3"></script>
@endpush
```

Библиотека, которую могут подключить несколько участников страницы, — только
через ключ:

```blade
@pushOnce('scriptsBottom', 'swiper-js')
  <script src="/design/include/vendor/swiper/swiper-bundle.min.js"></script>
@endPushOnce
```

Ключ общий для всех, кто её просит. Иначе на странице с двумя такими блоками
библиотека приедет дважды.

**Порядок в стеке равен порядку отрисовки.** Компонент, который отрисовался
раньше шаблона-владельца библиотеки, положит свой инициализирующий скрипт перед
самой библиотекой и упадёт с `ReferenceError`. Для обычных синхронных `<script>` инициализацию можно отложить
до готовности документа:

```js
const start = () => {
  /* Initialize the component. */
};
if (document.readyState === 'loading') {
  document.addEventListener('DOMContentLoaded', start);
} else {
  start();
}
```

Если библиотека загружается через `async` или динамически, готовность DOM
не означает готовность библиотеки: инициализация должна ждать её загрузки.

**Правил css в блейде должно быть немного.** Инлайновый `<style>` в компоненте
оправдан, когда правила зависят от пропов — ширина слайда, число колонок. Всё
остальное живёт в css-файле сайта.

### Данные в javascript

```blade
<div x-data="widget(@js($items), @js($title))">
```

`@js()` отдаёт значение как безопасный javascript-литерал: кавычки и теги
экранированы, в атрибут ставить можно. Руками через `json_encode` — не надо.

## Ошибки вёрстки

**Собака в комментарии.** Блейд-комментарий вырезается до компиляции, но
директива внутри обычного html-комментария или внутри строки в скрипте —
компилируется. Написанное в пояснении название директивы `push` со знаком
собаки роняет страницу с `Undefined property: …::$startPush`. В комментариях
названия директив пиши словами.

**Не рендерить блейды из консоли.** `view(...)->render()` из tinker под другим
пользователем кладёт скомпилированный файл в `storage/framework/views` с чужим
владельцем; php-fpm потом не может его перезаписать и страница падает с
`touch(): Utime failed`. Проверять — запросом страницы, а не из консоли.

**Версия ассета живёт в статье.** Поправил css или js — подними `?v=` там, где
файл подключён. Иначе у посетителя останется старая копия, и «у меня не
работает» будет правдой.

**Переносы строк.** Файл с CRLF правится с CRLF. Иначе диффом пройдёт весь файл,
и настоящее изменение в нём не найти.

**Экранирование.** `{{ $text }}` экранирует, `{!! $html !!}` — нет. Второе —
только для доверенной или предварительно очищенной разметки. Само хранение
текста в ленте или админке не делает его безопасным. Для всего, что пришло из формы или из внешнего источника, — первое.

## Порядок работы

1. Прочитать статью целиком перед правкой (`get-article`): сохранение
   переписывает тело целиком.
2. Сделать правку.
3. Открыть затронутые страницы и убедиться, что отдают 200. Ошибка в директиве
   видна только при запросе.
4. Если правился файл — проверить, что он отдаётся с новой версией.

## Чего не делать

- Не копировать один и тот же блок css и js в две статьи «пока так, потом
  вынесем». Выносить сразу в компонент, либо честно сказать, что это временно, и
  зачем.
- Проверять [несколько экземпляров компонента](#один-компонент--много-экземпляров)
  при повторном использовании блока.
- Не решать js-ом то, что решается медиазапросом. Если раскладка меняется по
  ширине экрана — это css; javascript нужен, только когда надо что-то
  инициализировать или уничтожить.
