# Картинки: как устроено

Два класса в `src/Image/`. Как звать снаружи — в `use.md`.

| Класс | Отвечает за |
| --- | --- |
| `ImageJob` | одно уменьшение: пути, кеш, замок, ответ |
| `ImageEncoder` | запуск внешних утилит |

Деление такое: `ImageEncoder` про кеш и настройки не знает вовсе, поэтому его
можно звать напрямую, чтобы просто перекодировать файл в файл. Этим и пользуется
кроппер ленты.

## ImageJob

Задание на одно уменьшение. Всё вычисленное вычисляется один раз и лежит в полях
объекта — между методами ходит сам объект, а не шесть аргументов.

Поля разделены на три группы: задание (`source`, `axis`, `size`, `format`,
`quality`), вычисленное (`dir`, `base`, `target`, `path`, `url`, `lockKey`,
`start`) и итог (`width`, `height`, `bytes`, `cmd`, `rotated`, `rotateMs`,
`errorMsg`).

Снаружи два статических входа — `make()` и `clear()`.

### Два шага заполнения

Конструктор берёт то, что известно по одному исходнику: время старта, путь, имя
без расширения и папку кеша. Больше по одному файлу сказать нечего.

`init($axis, $size, $format, $quality)` добавляет то, что зависит от запроса:
формат и качество из настроек, размер, обрезанный по `MAX_RESIZE`, и дальше все
пути с ключом замка.

Разделение не косметическое: `clear()` нужен только первый шаг — папка и имя
исходника. Формат и размер ему безразличны, он сносит всё по маске
`base_*.*`.

### make по шагам

```php
$job = new self($file);
$job->init($axis, $size, $format, $quality);

if (! $job->valid() || $job->fresh()) {
    return $job->toArray();
}

$job->run();

return $job->toArray();
```

`valid()` — исходник существует и это картинка (`getimagesize`), формат из
`ImageEncoder::FORMATS`. `fresh()` — готовый файл есть и он не старше исходника.

### Замок

Кодирование идёт под `Cache::lock($this->lockKey, 30)` с ожиданием `block(5)`.
Ключ — `image:` плюс md5 от целевого пути: замок нужен на конкретный файл, а не
на модуль.

Замок берётся **после** проверки кеша: готовый файл отдаётся без всякой
синхронизации, это самый частый случай. А внутри замка `fresh()` спрашивается
второй раз — пока ждали очереди, файл мог сделать сосед.

Не дождались за 5 секунд — `errorMsg = busy: имя`, наружу уезжает заглушка.
Страница не висит.

### toArray

Размеры читаются из готового файла, а не считаются: вторую сторону вычисляла
утилита, и наша арифметика могла бы разойтись с её округлением.

При ошибке в `url` кладётся svg из настройки `IMAGE_ERROR` как data-uri, а `path`
пустеет. Блейд при этом не меняется — `<img src>` работает в обоих случаях.

Пустой `cmd` в ответе означает, что кодирования не было: файл пришёл из кеша.

## Кеш

### Где лежит

`storage/app/public/magic/images/`, наружу — через symlink `public/storage`.

### Папка по источнику

Метод `place()` кладёт производные не в общую кучу, а в подпапку по тому, где
лежит исходник:

| Буква | Исходник |
| --- | --- |
| `p` | внутри `public` |
| `s` | внутри `storage` |
| `b` | внутри корня проекта |
| `x` | чужой файл, дальше короткий хеш каталога |

Смысл — не переносить абсолютный путь сервера в кеш. Иначе перенос проекта в
другой каталог делает весь кеш мусором, а имена начинают течь наружу в url.

### Имя файла

`имя_ось+размер.формат`: `photo_x800.webp`.

Фактических размеров в имени нет намеренно: имя нужно знать **до** кодирования,
а вторую сторону до него не знает никто.

Отдельный случай — `iwebp`. Метка кодировщика остаётся в имени, а расширение
должно быть настоящим: `photo_x800.iwebp.webp`. Иначе сервер отдаст неизвестный
тип, а два кодировщика одного формата затрут файлы друг друга.

### Годность

Сравнение `filemtime` производной и исходника. Отсюда известная особенность:
поменяли качество в настройках — производные не пересоздадутся, они новее
исходника. Нужен `imageCacheClear()`.

## ImageEncoder

`make()` — тупой диспетчер `match` по формату, на каждый формат свой метод, общий
только `run()`. Лишний массив аргументов дешевле лишнего условия внутри общего
метода: подбирая параметры, лезешь ровно в один метод.

Обе утилиты не умеют stdin и stdout, поэтому работа только через файлы.

### vipsthumbnail: iwebp, avif, jpg, png

Размер задаётся как `800x` или `x800` — пустая сторона означает «без
ограничения». Опции формата идут **в скобках в имени выходного файла**, а сам
формат `vipsthumbnail` выбирает по расширению этого файла. Отсюда требование:
целевой путь обязан иметь правильное расширение, иначе `VipsForeignSave` ругается
на неизвестный формат.

Опции webp для vips вынесены в константу `WEBP_VIPS`
(`preset=photo,effort=6,smart-subsample=true`), чтобы подбирать их не залезая в
метод. У avif свой набор: `effort` 0–9 и `subsample-mode`, но ни `preset`, ни
`smart-subsample` там нет.

Разворот по exif `vipsthumbnail` делает сам.

### cwebp: webp

`-resize` с нулём во второй стороне означает «посчитай сам по пропорциям».
Остальное — `-preset photo -m 6 -af -mt -sharpness 0 -sharp_yuv`.

`cwebp` не разворачивает снимок по exif, поэтому повёрнутый разворачивается
заранее, в `upright()`: gd читает jpeg, крутит по тегу `Orientation` и пишет
временный файл, который после кодирования удаляется в `finally`.

Стоит это дорого — картинка целиком лежит в памяти, 3456 × 3456 это около 48 МБ и
порядка полусекунды. Поэтому время меряется отдельно и уезжает в ответ как
`rotateMs`.

Альтернативу пробовали: отдать cwebp ключ `-metadata exif` вместо разворота через
gd. Результат хуже — блок exif тащит встроенную превьюшку 512 × 512, и файл
вырастает со 102 до 158 КБ. Поэтому метаданные не переносятся вовсе,
`-metadata none` не нужен, он умолчание.

Временный файл берётся от `tempnam()` и пишется **в него же**, без добавления
расширения: иначе в `/tmp` остаётся пустышка на каждый разворот. Формат `cwebp`
определяет по содержимому, расширение ему не нужно.

### run

Аргументы экранируются по одному через `escapeshellarg`: в имени файла может быть
пробел или кавычка.

Ошибка определяется **по коду возврата**, а не по выводу: `vips: not found`
приходит текстом и выглядит как удачный ответ. Та же ловушка была в диагностике
админки.

Ответ всегда одной формы — `error`, `cmd`, `rotated`, `rotateMs`. Последние два
здесь всегда пустые, их перебивает только `webp` через `array_merge`. Именно
`array_merge`, а не `+`: при объединении через `+` побеждает левая сторона, и
умолчания из `run()` затирали бы настоящие значения. Это уже ловили один раз.

## Кроппер ленты

Браузер кадрирует и шлёт голые пиксели в формате `UPLOAD_FORMAT` (png или
jpeg 0.95). Формат спрашивается у сервера командой `uploadFormat`: гадать, что
умеет браузер, дороже, чем спросить.

Дальше `imageCropUpload` в `API_Feeds` зовёт `ImageEncoder::make()` напрямую, мимо
`ImageJob`: кеш и `MAX_RESIZE` тут ни при чём, нужно ровно одно перекодирование
файла в файл. Целевой временный файл создаётся с расширением по формату — по нему
libvips и выбирает кодек.

Обычная загрузка без обрезки идёт командой `imageUpload` и сохраняет файл как
есть. Это две разные команды, а не флаг: одна функция — одно действие.

## Диагностика

Наличие `cwebp` и `vipsthumbnail` проверяется на главной админки, в блоке
«Обработка изображений», по коду возврата. Расширение `gd` там же — оно нужно для
разворота перед cwebp.
