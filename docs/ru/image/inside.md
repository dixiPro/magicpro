# Картинки: как устроено

Документ предназначен для разработчика, который меняет или расширяет модуль
изображений. Публичное использование хелперов описано в `use.md`.

## Границы модуля

Основная реализация находится в `src/Image/`:

| Класс          | Ответственность                                                                          |
| -------------- | ---------------------------------------------------------------------------------------- |
| `ImageJob`     | нормализация задания, размещение производной, кеш, блокировка, очистка и публичный ответ |
| `ImageEncoder` | построение и запуск команд внешних кодировщиков                                          |

Публичные хелперы в `src/Helpers/MproHelper.php` только делегируют вызовы:

```php
imageReduceX()    -> ImageJob::make($file, 'x', ...)
imageReduceY()    -> ImageJob::make($file, 'y', ...)
imageCacheClear() -> ImageJob::clear($file)
imageCacheCleanup() -> ImageJob::cleanup()
```

`ImageEncoder` ничего не знает о кеше, URL, настройках и `MAX_RESIZE`. Он
перекодирует один файл в другой и поэтому используется напрямую кроппером ленты.

У модуля нет таблиц и реестра соответствий. Источник производной кодируется в
пути кеша; состояние модуля — это файлы на диске.

## Публичные контракты

### ImageJob::make

```php
ImageJob::make(
    string $file,
    string $axis,
    int $size,
    ?string $format = null,
    ?int $quality = null,
): array
```

Рабочий контракт предполагает:

- `$file` — абсолютный путь к исходнику;
- `$axis` — `x` или `y`;
- `$format` — `webp`, `iwebp`, `avif`, `jpg` или `png` в нижнем регистре;
- `$quality` — целое значение в шкале выбранного формата.

Публичные хелперы гарантируют `x` или `y`, но сам `ImageJob::make()` ось не
проверяет. Любое значение кроме `x` кодировщик фактически трактует как `y`, при
этом исходное значение остаётся в имени кеша.

### Массив ответа ImageJob

| Ключ       | Тип      | Источник значения                                 |
| ---------- | -------- | ------------------------------------------------- |
| `path`     | `string` | `$url` при успехе, пустая строка при ошибке       |
| `width`    | `int`    | `getimagesize()` готового файла                   |
| `height`   | `int`    | `getimagesize()` готового файла                   |
| `size`     | `int`    | `filesize()` готового файла                       |
| `ms`       | `float`  | время от конструктора до `toArray()`              |
| `rotated`  | `bool`   | ответ `ImageEncoder`                              |
| `rotateMs` | `float`  | ответ `ImageEncoder`                              |
| `cmd`      | `string` | экранированная команда; пусто при попадании в кеш |
| `errorMsg` | `string` | ошибка задания, блокировки или кодировщика        |

Размеры намеренно читаются из результата: вторую сторону и её округление
определяет внешняя утилита.

### Очистка

```php
ImageJob::clear(string $file): int
ImageJob::clearAll(): array // files, bytes
ImageJob::cleanup(): array  // files, bytes, kept, skipped
```

`clear()` удаляет все размеры и форматы одного basename. `clearAll()` удаляет
все файлы и опустевшие подпапки, но сохраняет корень кеша. `cleanup()` удаляет
производные, для которых больше не находится исходник.

## Состояние ImageJob

Поля объекта делятся на три группы:

| Группа      | Поля                                                                 |
| ----------- | -------------------------------------------------------------------- |
| Задание     | `source`, `axis`, `size`, `format`, `quality`                        |
| Вычисленное | `dir`, `base`, `target`, `path`, `url`, `lockKey`, `start`           |
| Результат   | `width`, `height`, `bytes`, `cmd`, `rotated`, `rotateMs`, `errorMsg` |

Конструктор выполняет часть, зависящую только от исходника:

1. сохраняет время старта и переданный путь;
2. получает `base` через `PATHINFO_FILENAME`, без расширения;
3. выбирает ветку кеша методом `place()`.

`init()` добавляет параметры конкретной производной:

1. выбирает формат из аргумента или `RESIZE_FORMAT`;
2. ограничивает размер диапазоном от `1` до `MAX_RESIZE`;
3. выбирает явное качество или `defaultQuality()`;
4. строит относительный путь, абсолютный target, публичный URL и ключ замка.

Разделение нужно для `clear()`: ему известен исходник, но не нужны ось, размер,
формат и качество.

## Последовательность make

```text
new ImageJob($file)
        │
        ▼
init(axis, size, format, quality)
        │
        ▼
valid() ── ошибка ───────────────► toArray()
        │
        ▼
fresh() ── готовый кеш ──────────► toArray()
        │
        ▼
run(): lock → повторный fresh() → mkdir → ImageEncoder::make(temp) → rename(temp, target)
        │
        ▼
toArray()
```

Весь путь от `init()` до `run()` обёрнут в `try/catch` внутри `make()`: любое
исключение — сбой кеша, диска, прав — становится `errorMsg`, наружу не выходит.

Кодировщик пишет не в target, а во временный файл рядом:
`.tmp-<8 hex>-<имя target>`. Расширение то же — vipsthumbnail выбирает формат по
нему. Код возврата 0 и непустой файл — он переезжает на место `rename()`, иначе
удаляется, а в `errorMsg` причина. Поэтому на месте target всегда либо прежний
файл, либо новый целиком. Временный файл, оставшийся после убитого процесса,
уберёт `cleanup()`: исходника с таким именем нет. В `cmd` показывается имя
target, а не временное.

Замок (`Cache::lock`, 30 секунд, ожидание 5) только экономит работу: два
запроса не кодируют одно и то же. Не дождались — `errorMsg = busy: …`. Кеш не
даёт замка вовсе — ресайз идёт без него: испортить файл друг другу два
параллельных запроса уже не могут.

`valid()` проверяет существование обычного файла, успешный `getimagesize()` и
принадлежность формата к `ImageEncoder::FORMATS`.

`fresh()` считает кеш годным, когда target существует и его `filemtime` не
меньше `filemtime` исходника. Формат, размер и ось уже входят в имя файла;
качество и параметры кодировщика — нет.

## Настройки и значения по умолчанию

Настройки находятся в группе `RESIZE` схемы `src/Config/magicSchema.php`:

| Ключ               | Значения схемы               | Значение схемы по умолчанию |
| ------------------ | ---------------------------- | --------------------------- |
| `MAX_RESIZE`       | `10–10000`                   | `10000`                     |
| `RESIZE_FORMAT`    | `webp`, `avif`, `jpg`, `png` | `webp`                      |
| `UPLOAD_FORMAT`    | `png`, `jpeg`                | `png`                       |
| `WEBP_DEF_QUALITY` | `10–100`                     | `82`                        |
| `AVIF_DEF_QUALITY` | `10–100`                     | `50`                        |
| `JPG_DEF_QUALITY`  | `10–100`                     | `70`                        |
| `PNG_COMPRESSION`  | `0–9`                        | `6`                         |
| `IMAGE_ERROR`      | строка SVG                   | SVG-заглушка                |

`IMAGE_ERROR` ресайзер не читает: при ошибке `path` остаётся пустым.

Внутренние fallback-значения применяются только при отсутствии ключа в
`MagicGlobals::$INI`: `RESIZE_FORMAT` — `webp`, `MAX_RESIZE` — `1000`. У
`defaultQuality()` запасное значение своё у каждого ключа — 82, 50, 70 и 6, — и
это важно для png: общее «82 на всех» давало бы ему уровень сжатия вне шкалы
`0–9`.

## Размещение кеша

Корень:

```text
storage/app/public/magic/images/
```

Публичный префикс при наличии `public/storage`:

```text
/storage/magic/images/
```

`place()` проверяет корни именно в таком порядке:

| Префикс | Исходник                | Остаток пути                        |
| ------- | ----------------------- | ----------------------------------- |
| `p`     | внутри `public_path()`  | относительно `public`               |
| `s`     | внутри `storage_path()` | относительно `storage`              |
| `b`     | внутри `base_path()`    | относительно корня Laravel          |
| `x`     | вне этих корней         | первые восемь символов MD5 каталога |

Порядок существенен: `public` и `storage` сами находятся внутри `base`, поэтому
более узкие корни проверяются раньше.

Корень считается своим собственным корнем: у исходника, лежащего
непосредственно в `public`, `dirname()` равен самому корню, и сравнение с
`public/` его бы не пропустило — такой файл уезжал бы в ветку `b/public`.
Поэтому равенство проверяется отдельно, и ветка получается `p`.

Пример для исходника
`public/storage/magicFeed/11/photo.jpg`:

```text
magic/images/p/storage/magicFeed/11/photo_x800.webp
```

Один физический файл, переданный через путь symlink в `public` и через путь его
цели в `storage`, получает разные cache target. Канонизации через `realpath()`
нет.

### Имя производной

Обычный формат:

```text
{base}_{axis}{size}.{format}
photo_x800.webp
```

`iwebp` сохраняет метку кодировщика и настоящее расширение:

```text
photo_x800.iwebp.webp
```

Расширение исходника в target не входит. Поэтому `photo.jpg` и `photo.png` в
одном каталоге делят одну производную. Текущий инвариант: одинаковых basename с
разными расширениями в одном каталоге быть не должно.

## Блокировка и параллельные запросы

Ключ блокировки:

```text
image:{md5 абсолютного target}
```

Параметры текущей реализации:

- срок блокировки — 30 секунд;
- ожидание блокировки — 5 секунд;
- до блокировки выполняется быстрый `fresh()`;
- после получения блокировки `fresh()` выполняется повторно.

Если ожидание закончилось, `run()` записывает `busy: {basename target}` в
`errorMsg` и возвращает пустой `path`.

`clear()`, `clearAll()` и `cleanup()` блокировок не берут. Это намеренное
свойство кеша: очистка может пересечься с записью, а отсутствующая производная
будет создана следующим запросом.

## Очистка одного исходника

`clear()` создаёт объект только с первым шагом и удаляет совпадения:

```text
{cache directory}/{base}_{ось}{размер}.{формат}
```

Формат, ось и размер не выбираются: удаляются все производные этого исходника.
Возвращается количество успешных `unlink`. Пустые каталоги этот метод не удаляет.

Каталог читается `scandir()`, а не `glob()`: имя исходника попадало бы в шаблон
как есть, и `*`, `?` или скобки в нём стали бы метасимволами — свои производные
не нашлись бы, чужие попали бы под удаление. После имени проверяется
`_[xy]\d+\.`, поэтому производные соседа `photo_x800.jpg` (они выглядят как
`photo_x800_x400.avif`) остаются на месте.

## Полная очистка

`clearAll()` обходит кеш через `RecursiveDirectoryIterator` и
`RecursiveIteratorIterator::CHILD_FIRST`:

1. удаляет файлы;
2. суммирует число файлов и их размер;
3. после файлов пытается удалить опустевшие каталоги;
4. оставляет `storage/app/public/magic/images` на месте.

Если корня нет, возвращается `['files' => 0, 'bytes' => 0]`.

## Очистка сирот

`cleanup()` восстанавливает исходник из относительного пути производной. Для
веток `p`, `s` и `b` используются соответственно `public_path()`,
`storage_path()` и `base_path()`.

Имя распознаётся, если заканчивается на суффикс оси и размера, после которого
стоит одно или два расширения из латинских букв и цифр:

```text
_{x|y}{digits}.{format}
_{x|y}{digits}.{marker}.{format}
```

Второе расширение предусмотрено для `iwebp.webp`, но регулярное выражение не
проверяет конкретное значение маркера.

Группа basename жадная, поэтому исходник `photo_x800.jpg` и его производная
`photo_x800_x400.avif` разбираются по последнему суффиксу размера.

Для каждого восстановленного каталога `baseNames()` один раз вызывает
`scandir()` и строит множество имён без расширений. Дальше:

- basename найден — `kept` увеличивается;
- basename не найден — файл удаляется, растут `files` и `bytes`;
- путь нельзя восстановить — растёт `skipped`.

Ветка `x` всегда попадает в `skipped`: хеш каталога нельзя обратить в исходный
путь. Не соответствующие шаблону имена тоже пропускаются. Файл, вручную
положенный в распознаваемую ветку и совпавший с шаблоном ресайзера, будет
обработан как производная независимо от своего происхождения.

Обход диска не отличает удаление исходника от временно непримонтированного или
перенесённого дерева. Поэтому `cleanup()` запускается явно из админки или крона,
а не при отдаче страницы.

## ImageEncoder

### Контракт

```php
ImageEncoder::make(
    string $file,
    string $target,
    string $axis,
    int $size,
    string $format,
    int $quality,
): array
```

Ответ всегда задуман в одной форме:

| Ключ       | Тип      | Значение                                                       |
| ---------- | -------- | -------------------------------------------------------------- |
| `error`    | `string` | пусто при нулевом exit code, иначе stderr/stdout или exit code |
| `cmd`      | `string` | фактически запущенная экранированная команда                   |
| `rotated`  | `bool`   | выполнялся ли предварительный поворот через GD                 |
| `rotateMs` | `float`  | время предварительного поворота                                |

`run()` экранирует каждый аргумент через `escapeshellarg()`, объединяет stderr со
stdout и определяет успех по exit code. Ни `cwebp`, ни `vipsthumbnail` не
используются через stdin/stdout: исходник и target всегда файлы.

### Маршрутизация форматов

| Запрошенный формат | Реализация      | Существенные параметры                                           |
| ------------------ | --------------- | ---------------------------------------------------------------- |
| `webp`             | `cwebp`         | `preset photo`, method 6, auto-filter, multithreading, sharp YUV |
| `iwebp`            | `vipsthumbnail` | `preset=photo`, `effort=6`, `smart-subsample=true`               |
| `avif`             | `vipsthumbnail` | `effort=4`, `subsample-mode=on`                                  |
| `jpg`              | `vipsthumbnail` | `optimize-coding=true`                                           |
| `png`              | `vipsthumbnail` | `compression={quality}`                                          |

`cwebp` используется только для исходников `png`, `jpg`, `jpeg`, `tif`, `tiff`
и `webp`. При другом расширении ветка `webp()` делегирует в `iwebp()`, но target
и внешний формат остаются обычными `.webp`.

`vipsthumbnail` получает размер как `800x` или `x800`. `cwebp` получает ноль для
стороны, которую должен рассчитать по пропорциям.

### Ориентация EXIF

`vipsthumbnail` разворачивает изображение сам. Для `cwebp` JPEG предварительно
обрабатывается в `upright()`:

1. `orientation()` читает EXIF только у JPEG;
2. GD загружает изображение целиком;
3. ориентации `2–8` исправляются поворотом и/или отражением;
4. временный JPEG сохраняется с качеством `95` в файл от `tempnam()`;
5. временный файл удаляется в `finally` после запуска `cwebp`.

Метаданные в WebP не переносятся. `rotateMs` отделяет цену GD от времени внешней
команды.

## Интеграция с кроппером ленты

`API_Feeds::uploadFormat()` сообщает браузеру `UPLOAD_FORMAT`: `png` или `jpeg`.
Браузер кадрирует изображение и отправляет готовые пиксели.

`API_Feeds::imageCropUpload()`:

1. проверяет UploadedFile и MIME `image/*`;
2. выбирает `RESIZE_FORMAT`;
3. создаёт временный target с правильным расширением;
4. читает ширину исходного crop;
5. вызывает `ImageEncoder::make()` напрямую с этой шириной;
6. при успехе заменяет media collection и сохраняет размеры результата.

`ImageJob`, кеш и `MAX_RESIZE` в этом пути не участвуют. Обычная загрузка без
кадрирования идёт другой командой и сохраняет файл в исходном формате.

## Что учитывать при изменении кода

### Новый формат

Нужно согласовать все точки:

1. добавить формат в `ImageEncoder::FORMATS`;
2. добавить ветку диспетчера `ImageEncoder::make()` и метод кодирования;
3. обеспечить правильное расширение target;
4. выбрать настройку в `ImageJob::defaultQuality()`;
5. добавить формат и его настройки в `magicSchema.php`, если он должен быть
   доступен в админке;
6. проверить путь кроппера, если формат допускается как `RESIZE_FORMAT`;
7. обновить диагностику наличия внешней утилиты;
8. очистить старые производные, если изменились параметры уже существующего
   формата.

### Изменение имени кеша

Одновременно должны измениться:

- построение `$path` в `init()`;
- обратный разбор в `sourceBase()`;
- шаблон `clear()`;
- правила для `iwebp`;
- документация и логика очистки сирот.

Путь — единственная связь между исходником и производной. Несогласованное
изменение превращает файлы в вечные `skipped` или позволяет удалить не тот кеш.

### Изменение ответа

Ответ `ImageJob` используют Blade-шаблоны и компоненты. При добавлении или
переименовании ключей нужно синхронно проверить:

- `MproHelper` и его PHPDoc;
- `docs/ru/helpers/use.md`, который генерируется из PHPDoc;
- `x-magic::img` и другие вызывающие шаблоны;
- поведение при успехе, попадании в кеш, `busy` и ошибке кодировщика.

### Известные ограничения

Не сбои, а места, где код может повести себя не так, как обещает публичный
контракт. Оставлены сознательно: цена ошибки — пересозданный кеш, а не потеря
данных. Записаны, чтобы не открывать заново.

**Замок живёт 30 секунд и не продлевается.** Если разворот по EXIF и кодирование
заняли дольше, второй запрос получит замок и закодирует тот же файл ещё раз.
Испортить результат он не может — каждый пишет в свой временный файл, — цена
только в двойной работе. На практике разворот и кодирование даже очень большого
файла укладываются в 30 секунд.

### Проверка после правок

Для изменённых PHP-файлов обязательна проверка синтаксиса через `php -l`.
Фактическую доступность `cwebp`, `vipsthumbnail` и GD показывает блок «Обработка
изображений» на главной странице админки.
