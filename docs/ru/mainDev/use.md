# Как разрабатывать MagicPro

Разработка начинается с конкретного изменения поведения пакета: какой вход
приходит, что система делает сейчас и что должно получаться после изменения.
Для настройки страницы, Blade или контроллера сайта сначала используйте
существующие возможности из [mainUse](../mainUse/use.md).

Здесь описано фактическое устройство ядра: как статья превращается в маршрут,
Blade и PHP-класс, какие данные служат источником истины и какие механизмы
нужно менять вместе. Затем приведён порядок разработки. Анализ сбоев описан
в [поиске ошибок](diagnostics.md).

## Ответственность ядра

Центральный модуль связывает пять видов состояния:

```text
articles в базе
    │
    ├── дерево: parentId, npp, directory, menuOn
    ├── маршрут: name, isRoute, routeParams
    ├── Blade: body → storage/dataMagicPro/view/{name}.blade.php
    ├── PHP: controller → storage/dataMagicPro/controller/{name}.php
    └── история: magicPro_article_versions.data

Laravel request
    → catch-all route
    → DynamicRouteHandler
    → Blade напрямую или MagicController
    → Response
```

MagicPro не реализует свой шаблонизатор, ORM, HTTP-слой или контейнер. Он
регистрирует обычные механизмы Laravel и генерирует для них обычные файлы.

В ядро не входят внутренности:

- лент — `src/Lenta`, `database/Models/Feed*`, `docs/ru/feed/`;
- изображений — `src/Image`, `docs/ru/image/`;
- почты — `src/Mail`, `docs/ru/mail/`;
- MCP — `src/Mcp`;
- расписания — `src/Scheduling`;
- импорта — `src/Import`.

Провайдер ядра подключает эти модули, но их бизнес-правила остаются в их
собственных разделах.

## Как пакет входит в Laravel

`composer.json` объявляет пакет как `laravel-package` и включает auto-discovery:

```json
{
  "extra": {
    "laravel": {
      "providers": ["MagicProSrc\\MagicServiceProvider"]
    }
  }
}
```

Основные PSR-4 пространства:

| Namespace | Каталог |
| --- | --- |
| `MagicProSrc\` | `src/` |
| `MagicProDatabaseModels\` | `database/Models/` |
| `MagicProAdminControllers\` | `admin/controller/` |
| `MagicProAdminMiddleware\` | `admin/middleware/` |
| `MagicProControllers\` | `storage/dataMagicPro/controller/` хост-приложения |

Последнее отображение принципиально: контроллер статьи находится не в пакете, а
в изменяемом `storage` проекта, но загружается как обычный PHP-класс.

## Жизненный цикл провайдера

### register

`MagicServiceProvider::register()` выполняет два действия:

1. `MagicGlobals::register()` читает или впервые создаёт локальный файл
   настроек, затем определяет пути-константы.
2. `MagicLang::loadLocale()` загружает словарь выбранного языка и регистрирует
   `@magic_msg`.

Это происходит рано, до `boot()`. Значит даже обычный запрос или artisan-команда
может создать файл настроек, если его ещё нет.

### boot

Фактический порядок `boot()`:

1. Для `FeedItem` задаётся свой генератор путей Media Library.
2. `MAGIC_VIEW_DIR` регистрируется как пространство Blade `magic`.
3. Через `require_once` подключаются `MproHelper` и два legacy-хелпера.
4. Модели `Feed` и `FeedItem` получают короткие class aliases.
5. Загружаются маршруты MCP. Они намеренно идут раньше catch-all.
6. `admin/web.php` загружается внутри middleware-группы `web`.
7. Подключаются `magicAdmin::` views и миграции пакета.
8. Динамически настраиваются guard `magic`, provider `magic_users`, middleware
   `magic.auth` и директива `@mproauth`.
9. Настраивается Vite админки.
10. Регистрируются анонимные, классовые и Livewire-компоненты статей.
11. Создаётся глобальный alias `API_Auth`.
12. После разрешения `Schedule` подключаются задачи MagicPro.
13. В консоли регистрируются artisan-команды пакета.

Catch-all находится в конце `admin/web.php`; всё, что обязано иметь собственный
маршрут, должно быть зарегистрировано до него либо исключено его регулярным
выражением.

## Настройки и вычисленные пути

Три слоя конфигурации:

| Слой | Назначение |
| --- | --- |
| `src/Config/magicSchema.php` | Допустимые ключи, типы, границы, умолчания и изменяемость |
| `storage/app/private/magic/mproLocalIni.php` | Значения конкретной установки |
| `MagicGlobals::$INI` | Загруженный массив текущего процесса |

При отсутствии локального файла `MagicGlobals` строит полный массив умолчаний и
пишет PHP-файл через `MagicFile`. Затем определяются:

| Константа | Значение |
| --- | --- |
| `MAGIC_DATA_DIR` | `storage/dataMagicPro` |
| `MAGIC_VIEW_DIR` | `storage/dataMagicPro/view` |
| `MAGIC_CONTROLLER_DIR` | `storage/dataMagicPro/controller` |
| `VENDOR_FROM` | `vendor/dixipro/magicpro/readyBundle` |
| `VENDOR_PUBLIC` | `public/vendor/dixipro/magicpro` |
| `STATIC_HTML_CREATE_DIR` | `storage/app/private/magic/html` |
| `MAGIC_INSTALL_FILE` | `storage/app/private/magic/.install` |
| `ART_NAME_404` | `error404` |

`saveIniFile()` сначала проверяет присланные значения по схеме, затем
возвращает немутабельным параметрам умолчания и пишет весь массив через
`var_export`. Неизвестный ключ или неверный тип вызывает исключение.

Группы конфигурации поддерживают один уровень вложенности. В текущей схеме это
`RESIZE`. Для нового параметра недостаточно только добавить чтение в коде:
нужны схема, подписи обоих языков и безопасное умолчание в месте использования.

## Структура данных статьи

Миграция создаёт таблицу `articles`. Модель не переопределяет `$table`, поэтому
Eloquent использует то же имя.

| Колонка | Тип в миграции | Умолчание | Назначение |
| --- | --- | --- | --- |
| `id` | bigint unsigned | auto increment | Первичный ключ |
| `parentId` | integer, index | `0` | Родитель дерева |
| `npp` | integer | `0` | Позиция среди детей |
| `name` | string, index | нет | Уникальное на уровне модели имя |
| `title` | string | `''` | Заголовок |
| `controller` | text nullable | `null` | Исходник PHP |
| `body` | text nullable | `null` | Исходник Blade |
| `templateName` | string | `''` | Не используется и не входит в `$fillable` |
| `directory` | boolean | `false` | Есть ли дети |
| `menuOn` | boolean | `false` | Участие в меню-хелперах |
| `isRoute` | boolean | `false` | Публичность как адреса |
| `routeParams` | text nullable | `null` | JSON, cast модели в array |
| `created_at`, `updated_at` | timestamp nullable | `null` | Время записи, заполняется Eloquent |

`Article::$fillable` допускает все рабочие поля, кроме `id`, `templateName` и
timestamps. `parentId`, `npp` приводятся к integer; три флага — к boolean;
`routeParams` — к array. Mutator полей `name`, `title`, `controller` и `body`
переводит `null` в строку, а `name` ещё и обрезает по краям.

У новой модели `parentId` и `npp` равны `0`; `name`, `title`, `controller`
и `body` — пустые строки; `directory`, `menuOn`, `isRoute` — `false`.
`routeParams` заполняется при `saving`. Это умолчания модели, отличающиеся
от nullable-колонок миграции. Команда `createNew` дополнительно задаёт имя,
заголовок, родителя, позицию и заготовку контроллера, как описано ниже.

Связи модели:

```php
$article->parent();
$article->children();
```

Внешних ключей нет. Целостность дерева обеспечивается прикладным кодом.

### Проверки модели при saving

Модель проверяет:

- у записи `id = 1` имя обязано быть `root`, а `parentId` принудительно `0`;
- статья не может быть своим прямым родителем;
- положительный `parentId` должен существовать;
- имя содержит только латинские буквы, цифры, дефис и подчёркивание;
- другая статья с тем же именем отсутствует.

Уникального ограничения в самой базе нет: проверка имени выполняется запросом
из события модели.

Модель не проверяет косвенные циклы, согласованность `directory`, плотность
`npp`, полный набор routeParams и пригодность имени для PHP-класса. Часть этих
инвариантов поддерживает API и восстанавливает `ArticleCheck`.

## Формат routeParams

Полный объект, он же умолчания — `Article::ROUTE_PARAMS`:

```php
[
    'useController' => false,
    'adminOnly' => false,
    'utmParamsEnable' => true,
    'getEnable' => false,
    'postEnable' => false,
    'bindKeys' => false,
    'keysArr' => [],
]
```

У миграции нет JSON default. Умолчания в одном месте, их берут все:

- модель в `saving` прогоняет поле через `Article::routeParams()` — недостающий
  ключ получает умолчание, присланный приводится к типу, чужие ключи остаются;
- маршрутизатор читает статью через тот же `Article::routeParams()`, поэтому
  старая запись с неполным объектом не падает в 404;
- `Installer::defaultRouteParams()` возвращает `Article::ROUTE_PARAMS`;
- Vue `store.updateRouteParams()` держит те же значения на своей стороне;
- `ArticleCheck`, пункт 1, дописывает недостающие ключи в базу.

`saveById` берёт `routeParams` по ключам: присланное накладывается на
сохранённое (`array_replace`, не рекурсивно — `keysArr` заменяется целиком).

## Рабочие файлы статьи

Для статьи `catalog` создаются:

```text
storage/dataMagicPro/view/catalog.blade.php
storage/dataMagicPro/controller/catalog.php
```

Blade всегда создаётся. Наличие `isRoute` на генерацию не влияет: шаблоны,
include и компоненты без адреса тоже нуждаются в файле.

Контроллер создаётся, когда `routeParams.useController` истинно. Функция
`dataController()` берёт сохранённый текст; если он пуст, подставляет
`default/defaultController.php`. Затем заменяет все вхождения
`Magic_Pro_Name_Controller` на имя статьи.

### MagicProBuilder

`admin/controller/MagicProBuilder.php` подключается через `require_once`, поэтому
его функции находятся в namespace `MagicProAdminControllers`:

- `createMpro(array $article)`;
- `deleteMpro(array $article)`;
- `fileNameView()` и `fileNameController()`;
- `dataController()`;
- файловые вспомогательные функции.

`createMpro()` выполняет операции в таком порядке:

1. Проверяет `id` и непустое имя.
2. Вызывает `deleteMpro()` и удаляет прежний Blade и контроллер по текущему
   имени.
3. Записывает Blade из `body`.
4. Вычисляет текст контроллера.
5. При включённом `useController` записывает PHP-файл.
6. Запускает для созданного контроллера `php -l` через shell.
7. Если ожидаемой строки успеха нет, бросает исключение.

`deleteMpro()` удаляет оба файла через подавленный `unlink`. Ошибка удаления не
проверяется. Запись выполняет `MagicFile::saveToFile()`: каталог создаётся с
правами `0775`, содержимое пишется целиком, затем очищается stat cache.

Генератор не компилирует Blade и не проверяет существование include,
компонентов и layout. Такие ошибки обнаруживаются только при рендеринге.

## Сохранение и операции над деревом

Единая HTTP-точка редактора:

```text
POST /a_dmin/api/articles
```

Она защищена `magic.auth`, исключена из CSRF middleware и передаёт запрос в
`AbstractApiHandler`. Поле `command` выбирает закрытый метод из `$map`.

Ответ успеха:

```json
{
  "status": true,
  "errorMsg": "",
  "data": {},
  "request": {}
}
```

Исключение преобразуется в HTTP JSON с `status: false`; в `errorMsg` попадает
только текст исключения, а файл и строка — в лог `api` (ответ уходит в браузер и
через МСП агенту). То же у файлового менеджера. HTTP-код при этом остаётся стандартным для JSON-ответа,
если middleware не остановил запрос раньше.

`API_ArticlesPostController::run()` позволяет внутреннему коду и MCP вызвать тот
же обработчик без HTTP: он создаёт `Illuminate\Http\Request`, вызывает
`handle()` и превращает JsonResponse обратно в массив.

### saveById

Фактическая последовательность:

1. Берётся `article` и его `id`.
2. Из payload удаляются `parentId`, `npp` и `directory` — их считает дерево.
3. Загружается текущая модель, её состояние запоминается как «до».
   Присланный `routeParams` накладывается на сохранённый по ключам.
4. `$record->update($article)` в транзакции, частично, только присланные поля.
5. **Контроллер проверяется:** сперва имя статьи как имя класса
   (`checkControllerName()`), потом текст — `php -l` во временном файле.
6. Прошёл — если имя изменилось, удаляются файлы прежнего имени, и по новому
   состоянию создаются Blade и контроллер.
7. Не прошёл — файлы не трогаются вовсе, а в ответ добавляется `warning`.
8. Сохранённое состояние добавляется в архив, если отличается от последнего.

Сохранение исходника и публикация файлов — разные этапы. Ошибка имени класса
или PHP-синтаксиса не отменяет уже сохранённый текст: API возвращает `warning`
и пропускает публикацию. Ошибка валидации модели, напротив, прерывает обновление
до обращения к генератору.

При `warning` база и диск намеренно различаются. Если статья переименована,
прежний файл не становится файлом нового класса или новой view. Сохранение
старых файлов не гарантирует работоспособность нового адреса.

Проверка синтаксиса не доказывает наличие нужного класса, наследование от
`MagicController`, существование зависимостей и успешное выполнение `process()`.
Blade до публикации не компилируется.

Ошибка архива записывается в лог `api`, успешный ответ сохранения сохраняется.
Общей транзакции базы и файловой системы нет: отказ диска может оставить
частично опубликованное состояние после успешного обновления модели.

### createNew

В транзакции:

- проверяется существование родителя;
- вычисляется максимальный `npp` его детей;
- создаётся статья `art_<milliseconds>` последней в списке;
- в `controller` кладётся стандартная заготовка;
- родитель получает `directory = true`.

`routeParams` получает `Article::ROUTE_PARAMS` через событие `saving`,
`isRoute` — `false`, `body` — пустым. Рабочие
файлы и версия архива на этом шаге не создаются. Они появятся после сохранения
статьи редактором или `save-article`.

### copyRec

В транзакции блокируется исходная статья и сдвигаются следующие siblings.
Создаётся `replicate()` со следующими изменениями:

- к `name` и `title` добавляется timestamp;
- `npp` становится `source.npp + 1`;
- `directory` принудительно `false`;
- дети не копируются.

После записи создаются рабочие файлы копии. Архивная версия не создаётся.

### move

Параметры:

- `id` — перемещаемая статья;
- `newParentId` — итоговый родитель;
- `idBrotherUp` — sibling, после которого поставить; `0` означает первое место.

В пределах одного родителя API сдвигает диапазон `npp` и сохраняет новую
позицию. Между родителями он:

1. закрывает дыру у старых siblings;
2. открывает позицию у новых;
3. меняет `parentId` и `npp`;
4. снимает `directory` у опустевшего старого родителя;
5. включает `directory` у нового родителя.

Запросы используют `lockForUpdate()` и транзакции. Генерировать файлы не нужно:
иерархия на их содержимое и имена не влияет.

`saveById` отбрасывает `parentId` и `npp`, поэтому позиция должна меняться
только командой `move`.

### deleteById

Корень `id = 1` отклоняется. Остальные статьи удаляются рекурсивно снизу вверх:

1. собираются прямые дети;
2. для каждого вызывается тот же метод;
3. закрывается дыра `npp` у siblings;
4. удаляются рабочие файлы;
5. удаляется запись;
6. при необходимости очищается `directory` родителя.

Вся рекурсия находится в одной транзакции. Удаление статьи само по себе
не удаляет архивные версии; последующая очистка по сроку сохраняет последнюю
версию каждой статьи, включая удалённые.

| `search` | id/title статей, где body или controller содержит текст |
| `regenerateAll` | Пересоздание рабочих файлов всех статей |
| `getDefaultController` | Текст обычной заготовки |
| `getDefaultLiveWareController` | Текст Livewire-заготовки |
| `versions`, `versionGet`, `versionRestore` | Работа с версиями |
| `archiveInfo`, `archivePurgeDeleted` | Состояние и ручная очистка архива |

## Архив статей

Таблица `magicPro_article_versions`:

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `id` | bigint unsigned, auto increment | Первичный ключ версии |
| `userId` | integer, default `0` | Администратор или владелец MCP-токена |
| `articleId` | integer, index, без умолчания | Исходная статья без foreign key |
| `data` | longText, без умолчания | Полная статья в JSON без сжатия |
| `created_at` | timestamp nullable | Время версии |

`updated_at` отсутствует. Foreign key на статью тоже отсутствует, чтобы удаление
статьи не уничтожало последнюю возможность достать её содержимое.

`ArticleArchive::add()`:

- игнорирует состояние без `id`;
- кодирует весь массив с `JSON_UNESCAPED_UNICODE`;
- сравнивает строку с последней версией;
- записывает только изменившееся состояние;
- после записи очищает старые версии этой статьи.

`ARCHIVE_DAYS = 0` отключает временную очистку. При ненулевом сроке самая свежая
версия каждой статьи исключается из удаления независимо от возраста.

`ArticleVersion` заполняет время создания средствами Eloquent. При сохранении
с `warning` в JSON передаётся и этот ключ ответа.

Автор берётся из guard `magic`; без авторизации записывается `0`. MCP
`TokenMiddleware` авторизует владельца токена через тот же guard, поэтому его
изменения получают автора.

Восстановление получает JSON версии, подставляет текущий `articleId` и вызывает
обычный `saveById`. Таким образом, восстановление обновляет базу, генерирует
файлы и само становится новой версией.

## Регистрация Blade

Провайдер регистрирует один каталог тремя способами:

```php
$this->loadViewsFrom(MAGIC_VIEW_DIR, 'magic');
Blade::anonymousComponentPath(MAGIC_VIEW_DIR, 'magic');
Blade::componentNamespace('MagicProControllers', 'magic');
```

Отсюда три разных пути выполнения.

### Именованная view

```blade
@extends('magic::main')
@include('magic::block')
```

Laravel читает сгенерированный Blade. Связанный контроллер статьи не создаётся и
не вызывается.

### Анонимный компонент

```blade
<x-magic::block :item="$item" />
```

Blade ищется в том же `MAGIC_VIEW_DIR`. Внутри работают обычные `@props` и
component attributes. Это не отдельная таблица: компонент является статьёй без
маршрута.

### Классовый компонент

```blade
<x-magic::PriceBadge label="New" />
```

Namespace `magic` отображается в `MagicProControllers`. Класс лежит в
сгенерированном controller-файле и наследует `Illuminate\View\Component`.
Создание такого файла всё равно определяется `routeParams.useController`, а не
`isRoute`.

### Livewire

Провайдер заменяет стандартный `Livewire\Mechanisms\ComponentRegistry` своим
наследником. Он перехватывает только:

- `magic::{name}` → `MagicProControllers\{name}`;
- legacy `magic-pro-controllers.{name}` → тот же класс.

Если класс не найден, управление возвращается стандартному registry, чтобы не
сломать чужие компоненты.

Глобальная подмена registry является интеграционной точкой: при обновлении
Livewire нужно проверять сигнатуру `generateClassFromName()` и создание
родительского registry.

## Выполнение публичного запроса

### Регистрация catch-all

В конце `admin/web.php` строится отрицательное регулярное выражение из
`MagicGlobals::$INI['EXCLUDED_ROUTES']` и регистрируется:

```php
Route::any('{any?}', [DynamicRouteHandler::class, 'handle'])
    ->where('any', $pattern)
    ->withoutMiddleware([$csrf]);
```

Вся группа уже находится под `web`, поэтому доступны session, cookies и guard.
CSRF middleware с catch-all снимается явно.

`EXCLUDED_ROUTES` обрабатывается как набор начальных префиксов строки маршрута.
Значения очищаются только от начального и конечного `/`, затем проходят
`preg_quote`.

### Выбор статьи

`DynamicRouteHandler::checkFirts()`:

1. Получает `$request->segments()`.
2. Для пустого пути выбирает `index`.
3. Иначе первый сегмент становится именем статьи, остальные — параметрами.
4. Если в первом сегменте есть точка, заменяет каждую точку на `___`.
5. Если точки нет, заменяет `___` на точку; последующая проверка отклонит такое
   имя, закрывая прямой URL служебного псевдофайла.
6. Проверяет имя на латинские буквы, цифры, дефис и подчёркивание.
7. Загружает Article по `name`.
8. Проверяет `isRoute`.
9. Проверяет `adminOnly` через `Auth::guard('magic')`.
10. Проверяет HTTP-метод через `checkMethod()`.
11. При `postEnable` проверяет присланный токен и читает тело; иначе разбирает URL-параметры.
12. Собирает окружение и выбирает direct view либо controller.

Родитель статьи в поиске не участвует. Адрес плоский.

### Разбор URL-параметров

`checkRout()` сначала разбирает оставшиеся path segments.

Позиционный режим включён только если одновременно:

```php
! empty($routeParams['keysArr'])
&& $routeParams['bindKeys']
&& $routeParams['getEnable'];
```

Тогда количество сегментов обязано совпасть с количеством ключей, а
`array_combine(keysArr, segments)` строит результат.

Во всех остальных случаях сегменты делятся по чётности на ключи и значения.
Нечётное количество отклоняется. Затем выполняется:

```php
$allQuery = array_merge($request->query(), $segmentParams);
```

Поэтому одноимённый path parameter сильнее query string.

Дальнейшая проверка работает только с ключами:

1. При `utmParamsEnable` из списка неизвестных убираются глобальные
   `ENABLE_URL_PARAMS`.
2. При выключенном `getEnable` после этого не должно остаться ключей.
3. При включённом `getEnable` и пустом `keysArr` принимается всё.
4. При непустом `keysArr` разрешённые ключи вычитаются из неизвестных.
5. Остаток приводит к исключению.

Типы и значения не проверяются. Все принятые данные возвращаются в `$Get`,
включая UTM.

### postEnable

Если `postEnable` истинно, обработчик берёт `$request->post()` и вообще не
вызывает `checkRout()`. Query string и дополнительные сегменты игнорируются.

Метод ограничивает `checkMethod()`: `GET` и `HEAD` — всегда, `POST` — только при
`postEnable`, остальное — 405. Присланный csrf-токен проверяет `checkToken()`,
неверный — 419. Отсутствие токена не отклоняется: это не обязательная
CSRF-защита endpoint.

### Окружение Blade

```php
$env = [
    'name' => $article['name'],
    'title' => $article['title'],
    'artId' => $article['id'],
    'parentId' => $article['parentId'],
    'view' => 'magic::' . $article['name'],
];
```

Если `useController` ложен (после нормализации ключ есть всегда), возвращается:

```php
view($view, [
    'Env' => $env,
    'Get' => $get,
    'Post' => $post,
]);
```

Во всех остальных случаях строится строка класса
`\MagicProControllers\{name}`, объект создаётся оператором `new`, а `$env`
добавляется в `$request->attributes`.

Раньше отсутствие ключа `useController` вело в контроллерную ветку, а файла
класса у такой статьи не было — выходил 404. Теперь отсутствие — это `false`.

### Ошибка маршрутизатора

`handle()` повторно выбрасывает `HttpException`, включая 405 и 419.
Остальные `Throwable`, возникшие внутри вызова обработчика, преобразуются в:

```php
response()->view('magic::' . ART_NAME_404, [
    'message' => $throwable->getMessage(),
    'file' => $throwable->getFile(),
    'line' => $throwable->getLine(),
], 404);
```

Создание `View` и рендеринг — разные этапы. В ветке без контроллера Laravel
может рендерить возвращённую view уже после выхода из `handle()`: такие ошибки
не перехватываются этим блоком. Если ошибка возникнет при рендеринге самого
`error404`, дополнительной защиты вокруг него также нет.

## MagicController

Базовый класс не наследует Laravel Controller. Это небольшой шаблон HTTP-ответа
со следующими protected-свойствами:

```php
protected string $contentType = 'text/html; charset=utf-8';
protected int $status = 200;
protected array $headers = [];
protected ?string $redirect = null;
```

`handle()`:

1. Достаёт request, getParams и postParams.
2. Берёт имя view из `$request->attributes`.
3. Делает `view()->share('Env', attributes->all())`.
4. Делает `view()->share('Get', $getParams)`.
5. Вызывает `process($params)`.
6. При установленном redirect возвращает redirect response.
7. Иначе рендерит view с массивом из `process()`.
8. Заворачивает HTML в response с status, Content-Type и дополнительными
   headers.

`Post` глобально не разделяется. Контроллер должен сам вернуть его в массиве,
если Blade его использует.

Любой `Throwable` внутри этого пути ловится уже `MagicController`, а не внешним
динамическим маршрутизатором. Ответ — HTML с кодом 500 и экранированным message;
trace добавляется только при `config('app.debug')`. Даже `abort(404)`
из `process()` попадёт в этот перехват и станет 500. Чтобы вернуть 404 через
текущий контракт, контроллер задаёт `$this->status = 404` и возвращает данные
для своего Blade.

Абстрактный контракт:

```php
abstract protected function process(array $params): array;
```

Возвращаемый тип исключает прямой возврат JsonResponse, StreamedResponse и
других Laravel response из `process()`. Для JSON-подобного endpoint нужно
рендерить тело через Blade либо использовать отдельный обычный маршрут.

Контроллер динамической страницы создаётся через `new $controllerName()`, так
что constructor injection контейнера не работает. Публичные вспомогательные
методы разработчик может разрешать через `app(Class::class)->method()`, но это
другой путь: `handle()` сам не вызывается.

## Vue-редактор статьи

Точка входа — `/a_dmin/artEditor#<id>`. Hash хранит id статьи и позволяет
открывать несколько редакторов в отдельных вкладках без нового server route.

`store.js`:

- загружает статью через `getById`;
- нормализует routeParams;
- хранит body/controller для двух Ace Editor;
- сохраняет весь текущий объект через `saveById`;
- открывает архив, настройки, файловый менеджер и snippets.

`TreeArticle.vue`:

- получает путь к текущей статье через `makeHeTree`;
- лениво грузит детей через `getChildrens`;
- меняет порядок командой `move`;
- переносит к другому родителю через cut/paste и тот же `move`;
- создаёт, копирует, удаляет и экспортирует через API.

`RouteParam.vue` непосредственно редактирует флаги статьи и routeParams.
`TopMenu.vue` редактирует `name`, `title`, открывает публичный URL и панели.
Оба редактора Ace работают без worker; PHP и Blade анализируются только
клиентским форматированием, а окончательная PHP-проверка происходит в builder.

## Статическая публикация

Статическая генерация разделена между Vue crawler и `API_Setup`.

### Обход в браузере

`Crawler.vue`:

1. Загружает настройки и прошлый отчёт.
2. Нормализует `EXCLUDED_ROUTES` и `RENDER_URL` в абсолютные URL текущей сессии.
3. Удаляет прошлый staging-каталог.
4. Последовательно обходит `RENDER_URL`, затем `/`.
5. Из HTML достаёт все `<a href>` и рекурсивно продолжает обход.
6. Повторно один URL не читает.
7. Внешние URL проверяет, но дальше по ним не идёт.

Сохраняются только same-origin URL без точки в path либо адреса, начинающиеся с
элемента `RENDER_URL`.

### Получение и запись на сервере

`API_Setup::processUrl()` получает абсолютный URL и выполняет server-side GET:

- TLS verification выключена;
- timeout — 3 секунды;
- redirect не следует;
- успехом считается только HTTP 200;
- сохраняется только ответ, чей Content-Type начинается с `text`.

Query string не участвует в имени файла. Path `/` становится `index.html`;
остальные адреса без расширения получают `.html`. Staging находится в
`STATIC_HTML_CREATE_DIR`.

`startHtmlCache()` сначала удаляет каталог, указанный `STATIC_HTML_DIR`, затем
копирует staging целиком. Это публикация файлов, не конфигурация Nginx: правило
`try_files` описано в [настройке nginx](install.md#nginx) и ставится руками. Сохранение и удаление
статьи снимают её файлы из этого каталога — `forgetStaticHtml()` в
`MagicProBuilder.php`, зовётся из `deleteMpro()`. Страницы, куда статья
встроена (меню, списки детей), не снимаются.

## Установка и восстановление согласованности

`Installer` запускается на главной странице `/a_dmin`.

Для ядра важны его действия:

- проверка таблицы `articles`;
- создание `root`, `error404`, `index` при отсутствии;
- создание тестовой статьи и проверка появления Blade/контроллера;
- удаление тестовой статьи и проверка удаления файлов;
- перегенерация всех статей;
- проверка writable-каталогов и ассетов.

Корень создаётся с `id = 1`, `parentId = 0`. `error404` и `index` становятся его
детьми. Только `index` сразу получает `isRoute = true` и разрешённые UTM.

`ArticleCheck` предназначен для уже нарушенного состояния. Он проверяет и чинит родителей, циклы, имена, `npp`, `directory`, системный
root, routeParams и рабочие файлы. Это намеренное исключение из правила работы
через модель: испорченные записи могут не пройти model events.

Cleanup и regenerate не заменяют нормальный путь сохранения; они возвращают
систему в согласованное состояние после сбоя или ручного вмешательства.

## Добавить поле статьи

Проследите поле от хранения до всех способов чтения и записи:

1. Определите тип, допустимые значения, умолчание и поведение старых записей.
2. Для изменения хранения нужна новая миграция; выпущенную миграцию не меняют.
3. Проверьте `$fillable`, `$casts`, `$attributes`, mutator и события модели.
4. Проверьте API статей и интерфейс редактора.
5. Добавьте поле в MCP schema, если агент должен его редактировать.
6. Проверьте импорт, экспорт, `ArticleCheck`, архив и восстановление старых версий.
7. Если поле влияет на файлы, учтите генерацию и удаление прежнего результата.
8. Опишите хранение в разделе «Структура данных статьи» этого руководства,
   а использование — в документации участника.

Архив хранит JSON статьи целиком. Новая колонка архива для каждого нового поля
статьи не нужна, но старые версии не будут содержать новое поле.

## Добавить параметр маршрута

Умолчания PHP находятся в `Article::ROUTE_PARAMS`, нормализация — в
`Article::routeParams()`. Маршрутизатор использует нормализованный объект.
Значения Vue находятся отдельно в `ArtEditor/store.js::updateRouteParams()`,
системные статьи получают их через `Installer::defaultRouteParams()`.

Согласуйте модель, обработку URL, `RouteParam.vue`, MCP `SaveArticleTool`,
создание системных статей и `ArticleCheck`. Обновите описание использования
и выберите соответствующие сценарии из [матрицы проверки](diagnostics.md#матрица-проверки-изменения). Решите, что означает отсутствие
нового ключа в старой статье. Сохранение API объединяет `routeParams` по ключам,
а вложенный `keysArr` заменяет целиком.

## Изменить сохранение

Проверяйте отдельно запись исходника, проверку контроллера, публикацию файлов
и архив. Текущий контракт сохраняет ошибочный PHP-текст и возвращает `warning`,
не публикуя его. Отказ валидации модели работает иначе: запись не обновляется.

Прямые вызовы `createMpro()` не проходят предварительную проверку `saveById`.
Изменение одного пути не меняет автоматически копирование, импорт,
перегенерацию и установку. Найдите все вызовы генератора.

Транзакция базы не откатывает файловую систему. При изменении порядка операций
учтите отказы между записью модели, удалением прежних файлов и созданием новых.
Смена имени затрагивает адрес, Blade, PHP-класс и ссылки из других статей.
Сохраните владение полями положения за операцией дерева. Если меняется
атомарность публикации, продумайте временные файлы, проверку до замены
и восстановление после отказа.

## Изменить допустимое имя


Одновременно участвуют:

- model validation;
- DynamicRouteHandler;
- генератор имён PHP-классов;
- Composer PSR-4 path;
- маршруты с точкой `.` ↔ `___`;
- cleanup имён;
- MCP JSON schema;
- Vue transliteration/validation;
- import.

Нельзя менять регулярное выражение только в одном месте.

## Добавить обычный публичный маршрут Laravel


Маршрут должен регистрироваться раньше catch-all. Если порядок регистрации не
гарантирован, его первый префикс добавляется в `EXCLUDED_ROUTES`, иначе запрос
уйдёт в статью или `error404`.

Для endpoint с записью лучше использовать отдельный Laravel route с явными
middleware, чем расширять `postEnable`: catch-all статьи снимает стандартный CSRF middleware.
Методы уже ограничивает `checkMethod()`, но отсутствие токена `checkToken()`
не отклоняет.

## Изменить классовые или Livewire-компоненты


Проверяются сразу четыре слоя:

- имя статьи и PHP-класса;
- `routeParams.useController`, без которого файла класса нет;
- Blade component namespace или custom Livewire registry;
- view, возвращаемая `render()`.

После обновления Laravel/Livewire обязательно проверяется fallback чужого
обычного компонента, а не только `magic::`.

Анонимный компонент не требует изменения ядра: его Blade публикуется в
`anonymousComponentPath`. Создание описано в [руководстве по вёрстке](../mainUse/layout.md#компонент).

## Развивать отдельный модуль

Бизнес-правила размещаются в модуле, которому принадлежат данные. Редактор
и MCP-инструмент должны вызывать эти правила, а не создавать независимые
варианты одной операции. Текущий пример — `save-article`, вызывающий API статей.

Для лент прочитайте [внутреннее устройство](../feed/inside.md): схема,
слоты, связи, модель и файлы образуют общий контракт. Для нового инструмента —
[устройство МСП](../mcp/inside.md). Новый пользовательский метод `MproHelper`
документируется в PHPDoc с `@ru` и `@en`; `docs/ru/helpers/use.md` создаётся
генератором. Команда генерации:

```bash
php artisan magicpro:docs
```

После разрешённого запуска проверяют `docs/<lang>/helpers/use.md` и страницу
документации в админке. Порядок — в [разработке хелпера](../helpers/inside.md#как-менять-или-добавлять-helper).
`MproHelper` намеренно находится в глобальном namespace: перенос без
совместимого alias сломает существующие статьи.

## Инварианты


При изменении ядра проверяйте следующие условия целостности данных:

- существует `id = 1`, его имя `root`, `parentId = 0`;
- каждый положительный `parentId` существует;
- нет прямых и косвенных циклов;
- у siblings последовательные уникальные `npp`;
- `directory` равен факту наличия детей;
- имя статьи допустимо и уникально;
- routeParams содержит полный ожидаемый набор ключей;
- direct view и controller получают одинаковое базовое `$Env`;
- отдельные Laravel routes не захватываются catch-all;
- статический HTML снимается только у самой статьи; страницы, где она выводится,
  остаются старыми до новой публикации.

Для успешно опубликованной статьи дополнительно проверяют наличие Blade
по текущему имени, соответствие имени класса статье и успешный `php -l`.
Контроллер публикуется только при `useController`. Сразу после `createNew`
файлов ещё нет; после `warning` остаются прежние файлы — это отдельные
состояния, а не гарантия синхронности базы и диска после любого сохранения.

## Проверить конкретное изменение

Выберите сценарий по изменённому контракту из [матрицы проверки](diagnostics.md#матрица-проверки-изменения). Например, для ошибки при сохранении
нужно различить сохранённый текст, ответ API и опубликованные файлы. Успешный
HTTP-ответ сам по себе не подтверждает все три результата.

Изменённый PHP-файл проверяется только на синтаксис:

```bash
php -l packages/dixipro/magicpro/src/MagicController.php
```

Путь в примере заменяется путём реально изменённого файла. Если менялся frontend
админки, сборка запускается из пакета:

```bash
cd packages/dixipro/magicpro
npm run build
```

Эти команды описывают проверки соответствующих изменений. Правка документации
не требует сборки админки или запуска приложения. Запуски приложения, работа
с базой, Composer и Git подчиняются отдельным разрешениям проекта.

После изменения опишите итоговое поведение, изменённые файлы и фактически
проведённую проверку. Не выдавайте предложенный сценарий за выполненный тест.
