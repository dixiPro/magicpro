# Крон: как пользоваться

## Что нужно один раз

Системный крон должен звать планировщик раз в минуту. Настроен он или нет —
видно на главной админки: там либо строка «Крон жив» с временем последней
отметки, либо сообщение с готовой командой для `crontab`.

## Статья под задачу

Задача зовёт **публичный метод** контроллера статьи. От статьи нужно только одно:
включённый тумблер «использовать контроллер» (`useController`) — по нему и
рождается файл класса. Маршрут не нужен: статья может быть без маршрута вовсе,
контроллер всё равно будет на диске. `postEnable` и `adminOnly` крону тоже ни к
чему — он идёт не по адресу и поста не делает.

Метод пишется рядом с `process()` и объявляется публичным:

```php
<?php

namespace MagicProControllers;

use Illuminate\Support\Facades\Cache;
use MagicProSrc\MagicController;
use MagicShop\Api\ApiItems;

class dataCache extends MagicController
{
    // страница: тот же расчёт, но по адресу
    protected function process(array $params): array
    {
        return $this->task($params['postParams'] ?? []);
    }

    // задача крона
    public function task(array $params): array
    {
        $res = Cache::remember(
            'index_product_children',
            600,
            fn () => ApiItems::run('getChildrens', [
                'parent_sku' => $params['parent_sku'],
            ])
        );

        return ['res' => $res];
    }
}
```

`process()` тут не обязателен — он нужен, только если ту же работу хочется
дёргать по ссылке. Метод самостоятелен, и статья под него может быть не
страницей, а просто хранилищем контроллера: маршрут выключен, `useController`
включён.

Метод принимает **один массив** — json задачи, как он записан. Подпись из
нескольких аргументов (`task(string $sku, int $limit)`) кроном не позовётся.
Метод, объявленный вообще без аргументов, работать будет: лишний аргумент php
терпит.

Возвращённое значение крон выбрасывает и тип его не проверяет.

## Завести задачу

`/a_dmin/cron`, кнопка «Добавить задачу».

| Поле | Что писать |
| --- | --- |
| Контроллер | `статья\|метод`, например `dataCache\|task` |
| Название | для человека, в списке |
| Параметры | json-объект, можно пусто |
| Расписание | пять полей, как в системном кроне |
| Активна | выключенная задача не регистрируется вовсе |

Имя метода — с буквы, дальше буквы, цифры и подчёркивание. Магические методы php
(`__construct` и прочие) этим правилом отсекаются сами.

Пример расписания: `0 4 * * *` — каждый день в 4 утра, по времени сервера.

Кнопка с треугольником запускает задачу сразу, мимо расписания. Она же — главная
проверка: **ошибку внутри метода видно прямо на экране**, текстом. Получилось —
покажет, сколько миллисекунд заняло.

При сохранении проверяется только, что статья есть и класс контроллера
существует. Есть метод или нет, подходит ли ему то, что вы прислали, — покажет
кнопка запуска.

Задача, у которой пропала статья, в списке помечена красным. Проверка идёт при
каждом заходе на экран: статью могли переименовать уже после того, как задача
была заведена.

## Что стоит помнить

**Крон не разбирает результат.** Он зовёт метод и выбрасывает ответ. Ни повторов,
ни отключения задачи после ошибки, ни отметки «упало». Ошибка попадёт в лог
текстом — и на этом всё; что с ней делать, решает человек.

**Одна задача не мешает другой.** Падение ловится и уходит в лог, проход
планировщика продолжается. Кривая строка расписания не регистрируется вовсе, и
почта с heartbeat живут дальше.

**Наложение.** Задачам ставится `withoutOverlapping`: пока предыдущий запуск
идёт, следующий по расписанию пропускается. На ручной запуск это не действует —
нажали кнопку во время работы, пойдёт вторым потоком.

**Время серверное**, `config('app.timezone')`. Своей таймзоны у задачи нет.

**Одну статью можно завести несколько раз** — разными методами, с разными
параметрами и расписанием.

**Http вокруг метода нет.** Ни `Request`, ни `Env`, ни `Get`, ни сессии, ни
вошедшего пользователя, вьюха не рендерится. Метод, которому нужен запрос,
задачей работать не будет.

## Лог

`storage/logs/cron.log`, ротация 14 дней.

Беды пишутся всегда: `id`, `name`, `controller`, `method`, `error`, `ms`. Строка
об отработавшей задаче — с `params` вместо `error` — пока включена настройка
`CRON_LOG_SUCCESS` в Setup. По началу включена: полезно видеть, что задачи ходят
и сколько занимают. Дальше можно выключить.
