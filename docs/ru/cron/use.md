# Крон: как пользоваться

MagicPro хранит задачи расписания в админке и в нужную минуту напрямую вызывает
публичный метод контроллера статьи. Задача состоит из названия, ссылки
`статья|метод`, JSON-параметров, cron-выражения и флага активности.

Это расписание, а не очередь: крон не анализирует возвращённое значение, не
повторяет неудачный вызов и не выключает задачу после ошибки.

## Что нужно настроить один раз

Laravel Scheduler должен запускаться системным cron каждую минуту. Команду из
корня Laravel-приложения добавляют так:

```bash
(sudo crontab -u www-data -l 2>/dev/null; echo "* * * * * cd $(pwd) && /usr/bin/php artisan schedule:run >> /dev/null 2>&1") | sort -u | sudo crontab -u www-data -
```

Команда использует текущий каталог, поэтому выполнять её нужно именно в корне
приложения. Пользователь `www-data` должен иметь доступ к приложению, базе,
кешу Laravel и каталогу `storage`.

На главной странице `/a_dmin` установщик показывает:

- «Крон жив» и время последней отметки, если heartbeat моложе 120 секунд;
- готовую команду для `crontab`, если отметки нет или она устарела.

Heartbeat подтверждает только запуск Laravel Scheduler. Он не гарантирует, что
конкретная динамическая задача завершилась успешно.

Планировщик MagicPro не помечен `evenInMaintenanceMode()`. Во время
`php artisan down` не выполняются ни heartbeat, ни динамические задачи, поэтому
отметка станет устаревшей даже при исправном системном cron.

## Подготовка статьи

Задача вызывает класс `MagicProControllers\{имя статьи}`. Подготовьте статью в
редакторе:

1. выберите имя, которое допустимо как имя PHP-класса;
2. включите «Использовать контроллер» (`useController`);
3. добавьте публичный метод задачи;
4. сохраните статью.

Маршрут (`isRoute`) можно оставить выключенным. `postEnable` и `adminOnly` при
запуске по расписанию не используются. MagicPro всё равно создаёт Blade-файл
статьи, но крон его не рендерит.

Обычный контроллер статьи наследует абстрактный `MagicController`, поэтому
`process()` должен присутствовать даже у статьи без маршрута. Если страница не
нужна, достаточно вернуть пустой массив:

```php
<?php

namespace MagicProControllers;

use MagicProSrc\MagicController;

class dataCache extends MagicController
{
    protected function process(array $params): array
    {
        return [];
    }

    public function refresh(array $params): array
    {
        $limit = (int) ($params['limit'] ?? 100);

        // Run the scheduled work here.

        return ['processed' => $limit];
    }
}
```

Если ту же работу нужно вызывать страницей, `process()` может делегировать её
публичному методу:

```php
protected function process(array $params): array
{
    return $this->refresh($params['postParams'] ?? []);
}
```

Сгенерированные файлы в `storage/dataMagicPro/` руками не меняют. Контроллер
правится в статье и сохраняется через редактор MagicPro.

## Контракт метода задачи

Рекомендуемая сигнатура:

```php
public function refresh(array $params): array
```

Правила вызова:

- метод должен быть `public`;
- имя начинается с латинской буквы, затем допустимы латинские буквы, цифры и
  подчёркивание;
- весь JSON задачи передаётся одним массивом;
- внедрение зависимостей в аргументы метода не выполняется;
- сам объект контроллера создаётся через `app()`, поэтому зависимости можно
  получать в конструкторе;
- возвращённое значение полностью игнорируется;
- метод без аргументов сейчас тоже вызывается, но устойчивый контракт — один
  аргумент-массив.

При запуске планировщиком нет маршрута статьи, `MagicController::handle()`,
`process()`, Blade, `$Env`, `$Get`, `$Post`, сессии и вошедшего пользователя.
Пишите задачу так, чтобы она зависела только от переданных параметров и обычных
сервисов приложения.

Кнопка «Выполнить сейчас» работает внутри HTTP-запроса админки. Поэтому глобальный
`request()` и авторизация там технически доступны, а при ночном запуске — нет.
Не используйте их в методе задачи: иначе ручная проверка и расписание будут
вести себя по-разному.

## Создание задачи в админке

Откройте `/a_dmin/cron` и нажмите «Добавить задачу».

| Поле | Что вводить |
| --- | --- |
| Название | понятное человеку имя задачи; пустое значение не принимается |
| Контроллер | `статья|метод`, например `dataCache|refresh` |
| Параметры | JSON-объект или пустое поле |
| Расписание | стандартное cron-выражение из пяти полей |
| Активна | только активные задачи регистрируются в Laravel Scheduler |

### Параметры

Пустое поле и `{}` дают пустой массив. Всё остальное должно быть **json-объектом**:
сломанный json, список `[1,2]`, число или `null` не принимаются, и задача не
сохранится. Раньше сломанный json молча превращался в пустые параметры, и задача
уходила работать без того, что ей нужно. Обычный пример:

```json
{
  "limit": 100,
  "section": "catalog"
}
```

Метод получит его без дополнительной оболочки:

```php
[
    'limit' => 100,
    'section' => 'catalog',
]
```

В параметрах можно использовать вложенные массивы и объекты. Верхний уровень
должен быть объектом ключ-значение; непустой JSON-список не принимается.

Сломанный json, литерал `null`, число и список получают отказ
`params must be a json object`: задача не сохранится, пока строка не станет
объектом.

### Расписание

Пять полей идут в таком порядке:

```text
минута час день-месяца месяц день-недели
```

Примеры:

| Выражение | Когда выполняется |
| --- | --- |
| `* * * * *` | каждую минуту |
| `*/15 * * * *` | каждые 15 минут |
| `0 4 * * *` | ежедневно в 04:00 |
| `0 9 * * 1-5` | по будням в 09:00 |
| `30 2 1 * *` | первого числа каждого месяца в 02:30 |

Используемая библиотека также принимает псевдонимы `@yearly`, `@annually`,
`@monthly`, `@weekly`, `@daily`, `@midnight` и `@hourly`, хотя подсказка формы
говорит только о пяти полях. Для переносимости лучше использовать явные пять
полей.

Время вычисляется в `config('app.schedule_timezone')`, а если эта настройка не
задана — в `config('app.timezone')`. Собственной таймзоны у задачи нет.

## Что проверяется при сохранении

MagicPro не сохраняет задачу, если:

- не заполнено название;
- не заполнено поле `статья|метод`;
- имя метода не соответствует допустимым символам;
- статьи с таким именем нет;
- класс её контроллера не найден;
- параметры распознаны как непустой список или другой неподдерживаемый тип;
- cron-выражение пустое или не принято библиотекой.

На этом проверка заканчивается. Существование самого метода, его видимость,
сигнатура и результат не проверяются при сохранении. Их проверяет фактический
запуск.

Если статью позже переименовали, удалили или выключили её контроллер, задача
остаётся в таблице. При следующем открытии списка рядом появится красное
сообщение о неисправной ссылке.

## Ручной запуск и управление

В строке задачи доступны четыре действия:

- переключатель активности;
- «Выполнить сейчас»;
- редактирование;
- удаление.

«Выполнить сейчас» вызывает метод синхронно и ждёт его завершения. При успехе
интерфейс показывает длительность в миллисекундах, при исключении — текст
ошибки. Долгая задача держит HTTP-запрос и может упереться в таймаут nginx:
тогда экран покажет ошибку, но php доработает задачу до конца, итог — в логе
`cron`.

Ручной запуск:

- работает и для выключенной задачи;
- не учитывает cron-выражение;
- берёт ту же блокировку, что и расписание: пока задача идёт, второй запуск —
  кнопкой или по расписанию — получает «the task is already running».

После создания задачу полезно один раз запустить кнопкой, но такой тест не
доказывает отсутствие зависимости от HTTP-контекста.

## Поле «Последний запуск»

`last_run_at` обновляется перед созданием контроллера и вызовом метода. Поэтому
оно означает «раннер дошёл до попытки вызова», а не успешное завершение.

То же поле обновляет «Выполнить сейчас». Это время последней автоматической или
ручной попытки. Если класс контроллера не найден, отметка не меняется; если
ошибка возникла в конструкторе или методе, отметка уже сохранена.

## Выполнение по расписанию

При каждом новом `schedule:run` MagicPro заново читает из базы активные задачи.
Изменение через админку начинает действовать со следующего запуска системного
cron, без очистки кеша и перезапуска приложения.

Задачи выполняются обычными синхронными callback-событиями Laravel. В одном
процессе длинная задача задерживает следующие события. Системный cron при этом
может запустить новый процесс `schedule:run` в следующую минуту.

Одна задача не идёт дважды одновременно — блокировка стоит в раннере:

- относится только к этой задаче и строится по её `id`;
- общая для расписания и кнопки «Выполнить сейчас»;
- после окончания задачи снимается;
- если процесс убили посреди задачи, живёт 10 минут и уходит сама;
- задача, которая идёт дольше 10 минут, может быть запущена ещё раз поверх себя;
- занятую задачу расписание молча пропускает, в лог это не пишется.

`onOneServer()` не включён. Если Scheduler запущен на нескольких серверах, для
гарантированно единственного вызова нужна отдельная архитектурная защита.

## Ошибки, повторы и результат

Раннер ловит `Throwable` из конструктора и метода и записывает текст ошибки.
После этого проход расписания продолжается. Автоматических повторов нет,
задача остаётся активной, а отдельные поля статуса и последней ошибки не
ведутся.

Возврат `false`, `null`, массива, модели или ответа HTTP не меняет оценку
запуска: результат выбрасывается. Для неуспеха метод должен бросить исключение.

## Лог

Записи создаёт `MproHelper::addLog('cron', ...)`. Фактические файлы имеют дату в
имени:

```text
storage/logs/cron-YYYY-MM-DD.log
```

Хранится не более 14 дневных файлов.

При ошибке метода пишутся `id`, `name`, статья в поле `controller`, отдельное
поле `method`, текст `error` и `ms`. Успешная запись содержит `params` вместо
`error` и создаётся, пока в Setup включён `CRON_LOG_SUCCESS`. По умолчанию эта
настройка включена.

В успешную запись идут **имена параметров, а не значения**: в параметрах задачи
живут токены ботов и ключи, а лог хранится две недели и читается кем угодно, у
кого есть доступ к серверу. Понадобилось значение при разборе — пишите его в
свой лог из самого метода, осознанно.

Ошибка регистрации некорректного cron-выражения имеет другой набор полей:
`stage: register`, `id`, `name`, `error`. Ошибка чтения таблицы при построении
расписания намеренно не логируется.

## API из PHP

Командный класс доступен как `MagicProSrc\Scheduling\API_Cron`:

```php
use MagicProSrc\Scheduling\API_Cron;

$result = API_Cron::run('list');

if (! $result['status']) {
    throw new \RuntimeException($result['errorMsg']);
}

$tasks = $result['data']['list'];
```

`run()` всегда возвращает общую оболочку и сам не бросает ошибку:

```php
[
    'status' => true,
    'errorMsg' => '',
    'data' => [],
    'request' => [],
]
```

При ошибке добавляется `line`, `status` становится `false`, а `data` остаётся
пустым массивом. Если вызывающему нужно исключение, используйте унаследованный
`runOrFail()`:

```php
$data = API_Cron::runOrFail('get', ['id' => 12]);
```

## HTTP API

Точка входа:

```text
POST /a_dmin/api/cron
```

Маршрут защищён `magic.auth`, по умолчанию требует роль `admin` и исключён из
CSRF middleware. Команда передаётся в поле `command`, остальные поля зависят от
неё.

| Команда | Вход | `data` при успехе |
| --- | --- | --- |
| `list` | только `command` | `list` со всеми задачами и `check` у каждой |
| `get` | `id` | `task`, `check` |
| `save` | `id` при обновлении, `name`, `controller`, `params`, `cron`, `enabled` | сохранённая `task` |
| `toggle` | `id` | `id`, новое `enabled` |
| `delete` | `id` | удалённый `id` |
| `runNow` | `id` | `ms` |

Для `enabled` передавайте настоящий JSON boolean. Строка `"false"` в PHP
приводится к `true`.

## Короткая проверка задачи

Перед тем как оставить задачу работать без наблюдения, проверьте:

1. heartbeat на `/a_dmin` свежий;
2. у статьи включён контроллер и контроллер сохранён без синтаксических ошибок;
3. `process()` присутствует, даже если маршрут выключен;
4. метод публичный и принимает один массив;
5. параметры после сохранения отображаются как задумано;
6. расписание рассчитано в нужной таймзоне;
7. «Выполнить сейчас» завершается без ошибки;
8. в датированном cron-логе есть ожидаемая запись.
