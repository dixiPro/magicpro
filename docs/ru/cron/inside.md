# Крон: устройство и сопровождение

Документ предназначен для разработчика, который меняет подсистему расписания
MagicPro. Создание и эксплуатация задач описаны в `use.md`.

## Состав подсистемы

| Часть | Файл | Ответственность |
| --- | --- | --- |
| регистрация расписания | `src/Scheduling/MagicProSchedule.php` | встроенные события и активные задачи из базы |
| проверка ссылки | `src/Scheduling/CronTaskChecker.php` | разбор `статья|метод`, статья и класс контроллера |
| выполнение | `src/Scheduling/CronTaskRunner.php` | отметка запуска, создание контроллера, вызов и лог |
| командный API | `src/Scheduling/API_Cron.php` | список, сохранение, переключение, удаление, ручной запуск |
| модель | `database/Models/MagicProCronTask.php` | casts, fillable и имя таблицы |
| миграция | `database/migrations/create_magicPro_cron_tasks_table.php` | структура `magicPro_cron_tasks` |
| heartbeat | `src/Scheduling/Heartbeat.php` | файловая отметка работы Scheduler |
| диагностика | `src/Install/Installer.php` | проверка возраста heartbeat |
| HTTP-маршруты | `routes/admin.php` | страница и `POST /a_dmin/api/cron` |
| интерфейс | `admin/js/app/cronAdmin/cronAdmin.vue` | форма, список и действия оператора |
| настройка лога | `src/Config/magicSchema.php` | `CRON_LOG_SUCCESS` |
| подключение | `src/MagicServiceProvider.php` | вызов `MagicProSchedule::register()` |

Генерируемый контроллер статьи лежит в
`storage/dataMagicPro/controller/{article}.php`, но этот каталог не является
исходником: его содержимое создаёт `MagicProBuilder` из записи статьи.

## Общий поток

```text
system cron
    -> php artisan schedule:run
        -> Laravel resolves Schedule
            -> MagicServiceProvider
                -> MagicProSchedule::register()
                    -> heartbeat
                    -> mail queue
                    -> AI session cleanup
                    -> active MagicPro cron tasks
                        -> due event
                            -> CronTaskRunner::run()
                                -> app(controller)->method(params)
```

Интерфейс и ручной запуск идут другим путём:

```text
/a_dmin/cron
    -> POST /a_dmin/api/cron
        -> AbstractApi::handle()
            -> API_Cron::run(command, params)
                -> CRUD or CronTaskRunner::run()
```

## Подключение к Laravel Scheduler

`MagicServiceProvider` использует:

```php
$this->callAfterResolving(
    Schedule::class,
    function (Schedule $schedule): void {
        app(MagicProSchedule::class)->register($schedule);
    }
);
```

Так пакет дополняет общий экземпляр `Schedule`, когда его разрешает консольное
ядро Laravel. Таймзона этого экземпляра берётся из
`config('app.schedule_timezone')` с откатом к `config('app.timezone')`.

События не получают `evenInMaintenanceMode()`, `runInBackground()` или
`onOneServer()`.

## Встроенные события

`MagicProSchedule::register()` сначала регистрирует три ежеминутных события:

| Имя события | Callback | Назначение |
| --- | --- | --- |
| `magicpro:heartbeat` | `new Heartbeat()` | отметка живого Scheduler |
| `magicpro:sendQueue` | `API_Mail::run('sendQueue', [])` | обработка очереди писем |
| `magicpro:aiCleanup` | `AiSession::cleanup()` | уборка зависших AI-сеансов |

После них вызывается `registerCronTasks()`. Ошибка одной callback-задачи
обрабатывается Laravel на уровне события и не отменяет обход остальных due
events.

## Регистрация динамических задач

Сначала выполняется одна выборка:

```php
MagicProCronTask::where('enabled', true)->get();
```

Она находится в отдельном `try/catch`. Любой `Throwable` — отсутствующая база,
таблица до миграции или сбой соединения — приводит к тихому `return`. Встроенные
события к этому моменту уже зарегистрированы.

Каждая полученная модель обрабатывается в собственном `try/catch`:

1. `CronExpression::isValidExpression()` проверяет строку;
2. создаётся синхронный callback с `CronTaskRunner::run($task)`;
3. применяется `cron($task->cron)`;
4. событию присваивается имя `magicpro:dynamic:{id}`.

`withoutOverlapping()` не включается: блокировка стоит внутри
`CronTaskRunner::run()`, см. «Блокировка и параллельность».

Проверка выражения до `Event::cron()` тоже обязательна. `cron()` только
сохраняет строку; ошибка без предварительной проверки возникла бы позже при
вычислении due events, уже вне локального `try/catch` регистрации.

Ошибка регистрации пишется в cron-лог с полями `stage: register`, `id`, `name`
и `error`. Задача остаётся включённой, поэтому ошибка повторится при следующем
построении расписания.

Одна и та же жалоба пишется **не чаще раза в час на задачу**: регистрация идёт
каждую минуту, и сломанное расписание залило бы лог сорока тысячами одинаковых
строк в месяц. Задача при этом не отключается — решать, чинить её или убрать,
человеку.

## Cron-выражение

Прямой формат содержит пять полей: минута, час, день месяца, месяц и день
недели. Секундного и годового поля нет.

Текущая `CronExpression` также разворачивает псевдонимы:

- `@yearly`, `@annually`;
- `@monthly`;
- `@weekly`;
- `@daily`, `@midnight`;
- `@hourly`.

И API, и регистрация используют один `CronExpression::isValidExpression()`, а
Laravel при вычислении запуска создаёт `CronExpression` ещё раз.

## Структура данных

Таблица: `magicPro_cron_tasks`.

| Колонка | Тип миграции | Nullable | Умолчание | Назначение |
| --- | --- | --- | --- | --- |
| `id` | unsigned big integer, auto increment | нет | — | первичный ключ |
| `name` | string, обычно `varchar(255)` | нет | — | название в интерфейсе и логе |
| `controller` | string, обычно `varchar(255)` | нет | — | строка `article|method` |
| `params` | json | да | `null` | параметры одного вызова |
| `cron` | string, обычно `varchar(255)` | нет | — | cron-выражение |
| `enabled` | boolean | нет | `true` | участие в расписании |
| `last_run_at` | timestamp | да | `null` | время последней попытки раннера |
| `created_at` | timestamp | да | `null` | создание строки Eloquent |
| `updated_at` | timestamp | да | `null` | последнее сохранение строки Eloquent |

Индексы:

- primary key по `id`;
- обычный индекс по `enabled`.

Внешних ключей и unique-ограничений нет. Связь со статьёй хранится именем, а не
`article_id`, поэтому переименование или удаление статьи не изменяет задачу
автоматически. Одинаковые задачи разрешены.

### Модель

`MagicProCronTask` разрешает mass assignment для `name`, `controller`, `params`,
`cron`, `enabled` и `last_run_at`.

Casts:

| Поле | Cast |
| --- | --- |
| `params` | `array` |
| `enabled` | `boolean` |
| `last_run_at` | `datetime` |

Модель задаёт только одно собственное умолчание: `enabled = true`. Для `params`
умолчания модели нет. Новая задача через API получает `[]`, а строка, созданная
другим кодом без `params`, может хранить `null`; раннер заменит `null` на `[]`.

## Формат controller

`CronTaskChecker::SEPARATOR` равен `|`. `parse()` обрезает пробелы вокруг всей
строки и обеих частей, затем делит только по первому разделителю:

```text
dataCache|refresh
```

Результат:

```php
[
    'article' => 'dataCache',
    'method' => 'refresh',
]
```

Класс строится без чтения отдельного поля:

```php
'\\MagicProControllers\\' . $article
```

Имя статьи должно приводить к существующему классу. Сам checker отдельно не
проверяет синтаксис имени класса: нормальный путь создания контроллера делает
это сохранением статьи и `php -l`.

## CronTaskChecker

`check()` возвращает массив стабильной формы:

```php
[
    'ok' => true,
    'error' => '',
]
```

Проверки идут до первой ошибки:

1. статья не пуста;
2. метод не пуст;
3. метод начинается с латинской буквы и дальше содержит только латинские буквы,
   цифры и подчёркивание;
4. `Article::where('name', $article)->exists()`;
5. `class_exists('\\MagicProControllers\\' . $article)`.

Checker не проверяет:

- `isRoute`, `postEnable`, `adminOnly` и другие свойства маршрута;
- `useController` напрямую — его фактический результат покрывает
  `class_exists()`;
- существование и видимость метода;
- сигнатуру и return type метода;
- наследование класса от `MagicController`;
- пригодность параметров для бизнес-логики.

Он вызывается из `save`, `get`, `list` и `runNow`. В `list` проверка выполняется
заново для каждой задачи, поэтому получается отдельный запрос к таблице статей
на строку списка.

Планировщик весь checker не вызывает — в нём запрос к базе. Раннер повторяет
то, что обходится без базы: непустые части, класс существует, имя метода по
правилу (`CronTaskChecker::methodName()`), метод свой (`ownMethod()`). Поэтому
строка, записанная мимо админки, не вызовет ни `__construct`, ни `handle`.

## API_Cron

Класс наследует `MagicProSrc\Api\AbstractApi` и сопоставляет внешние команды с
защищёнными методами:

| Команда | Метод | Действие |
| --- | --- | --- |
| `list` | `listTasks` | все строки по `id`, плюс `check` у каждой |
| `get` | `getTask` | одна строка и отдельный `check` |
| `save` | `saveTask` | создание или обновление |
| `toggle` | `toggleTask` | инверсия `enabled` |
| `delete` | `deleteTask` | удаление строки |
| `runNow` | `runNow` | синхронный вызов через раннер |

### Общая оболочка

`AbstractApi::run()` добавляет `command` обратно в `request` и возвращает:

```php
[
    'status' => true,
    'errorMsg' => '',
    'data' => $data,
    'request' => $params,
]
```

Ветка ошибки содержит `status = false`, текст в `errorMsg`, пустой `data` и
исходный `request`; путь и строка исключения уходят в лог `api`. `run()` не
бросает. `runOrFail()` проверяет статус, бросает новый `Exception` и возвращает
только `data` при успехе.

HTTP `handle()` берёт `$request->all()`, отделяет `command` и отдаёт JSON.
Маршрут защищён `magic.auth`, исключён из CSRF middleware и по умолчанию доступен
только роли `admin`.

### save

Порядок `saveTask()`:

1. `trim()` для `name`, `controller`, `cron`;
2. проверка обязательного названия и controller;
3. полный `CronTaskChecker::check()`;
4. проверка обязательного и валидного cron-выражения;
5. `findTask()` при непустом `id` или новая модель;
6. нормализация `params`;
7. приведение `enabled` через `(bool)`;
8. `fill()` и `save()`.

Из-за прямого `(bool)` строка `"false"` становится `true`. Vue передаёт boolean,
но внешние клиенты должны соблюдать JSON-типы.

### Нормализация params

`readParams()` принимает строку из формы или массив из PHP:

- пустая строка возвращает `[]`;
- JSON-строка разбирается через `json_decode(..., true)`;
- пустая строка и `{}` возвращают `[]`;
- `json_last_error()` проверяется, и результат разбора обязан быть массивом:
  сломанный json, `null`, число и строка получают
  `params must be a json object`;
- непустой PHP list — тоже отказ: у списка нет имён, а метод задачи получает
  один массив с ключами;
- ассоциативный массив возвращается как есть.

Пустой массив, пришедший из кода, остаётся пустым: там это осмысленное «нет
параметров», в отличие от `null` в форме.

### toggle, delete и get

Все три команды используют `findTask()`: `id` приводится к integer, должен быть
больше нуля, после чего выполняется `MagicProCronTask::find($id)`.

`toggle` не вызывает checker. Поэтому он может включить задачу, ссылка которой
уже сломана; список при этом продолжит показывать её ошибку.

### runNow

Команда:

1. находит задачу;
2. выполняет полный checker;
3. вызывает `CronTaskRunner::run()`;
4. при непустом `error` бросает исключение для общей API-оболочки;
5. при успехе возвращает `ms`.

`enabled` и cron-выражение здесь не учитываются. Mutex планировщика не
используется. Вызов идёт в текущем HTTP-процессе и ждёт завершения метода.

## CronTaskRunner

`run(MagicProCronTask $task)` задуман с ответом:

```php
[
    'ms' => 17,
    'error' => '',
]
```

Фактическая последовательность:

1. запоминается `microtime(true)`;
2. `params = $task->params ?? []`;
3. `CronTaskChecker::parse($task->controller)` вызывается до `try`;
4. внутри `try` проверяются непустые статья и метод, затем существование класса;
5. `last_run_at = now()` сохраняется до создания контроллера;
6. `app(className)` создаёт контроллер через контейнер;
7. `$controller->{$method}($params)` вызывает метод напрямую;
8. значение метода отбрасывается;
9. при включённом `CRON_LOG_SUCCESS` пишется успешный лог;
10. возвращаются миллисекунды и пустая ошибка.

Любой `Throwable` внутри `try` превращается в строку ошибки и логируется. Время
считается от начала раннера до конца метода, но до записи соответствующей строки
лога.

Важные границы:

- вызов метода не идёт через container call, поэтому method injection нет;
- `app()` поддерживает constructor injection;
- `last_run_at` обновляет и автоматический, и ручной запуск;
- сохранение `last_run_at`, создание объекта и сам метод находятся в одном
  `try`;
- `parse()` перед `try` и повторный вызов логгера внутри `catch` не защищены
  этим перехватом.

Callback расписания получает массив раннера. Для Laravel это не `false`, поэтому
само callback-событие имеет успешный exit code даже тогда, когда массив содержит
`error`. Собственная оценка неуспеха существует только в cron-логе и в
`API_Cron::runNow()`.

## Контекст выполнения

Автоматический запуск происходит в консольном приложении. Раннер не создаёт
`Request`, не собирает route params и не вызывает `MagicController::handle()`.

Ручной запуск использует тот же раннер, но сам раннер вызван из HTTP API. В
контейнере уже находится текущий request и пользователь guard. Поэтому код,
который обращается к глобальному HTTP-состоянию, может успешно пройти ручную
проверку и упасть ночью.

Отдельная проверка стоит на имя метода: он должен быть **объявлен самим
контроллером статьи**, публичный и нестатический. `CronTaskChecker::ownMethod()`
смотрит на это рефлексией. Рефлексия называет класс без ведущего `\`, а
`className()` отдаёт его с ним, поэтому сравнение идёт через `ltrim`: без этого
любая задача считалась чужой и отказывала.

Правило появилось из-за `handle`. Имя обычное, проверку букв и цифр проходит, а
метод при этом унаследован от `MagicController`: он возвращает http-ответ и ловит
собственную ошибку внутри. Раннер получал не исключение, а объект ответа,
отбрасывал его и писал в лог **успешный запуск** — задача годами «работала», не
делая ничего.

Та же проверка стоит и в раннере: чекер работает при сохранении, а задачи,
сохранённые до появления правила, лежат в таблице.

## Блокировка и параллельность

Блокировку берёт сам `CronTaskRunner::run()`, поэтому она одна на оба пути —
расписание и `runNow`:

```text
Cache::lock('magicpro:cron:run:{id}', CronTaskRunner::LOCK_SECONDS)   // 600
```

- берётся до всего остального, даже до отметки `last_run_at`;
- занята — `run()` сразу возвращает `error = the task is already running`
  (`CronTaskRunner::ERRORS['running']`), без записи в лог: расписание встречает
  занятую задачу каждую минуту, пока идёт долгая;
- снимается в `finally`;
- убитый процесс снять её не может — она уходит по сроку, через 10 минут.
  Раньше был `withoutOverlapping()` без аргумента, и его mutex в таком случае
  жил 1440 минут, задача всё это время молча пропускалась;
- кеш не отвечает (файловый store чужого пользователя) — задача идёт без
  блокировки: невыполненная задача хуже.

`runNow` вдобавок ставит `ignore_user_abort(true)` и `set_time_limit(0)`:
оборванный nginx-ом или закрытой вкладкой запрос не обрывает задачу.

События — синхронные closures; `CallbackEvent::runInBackground()` для них
недоступен. Внутри одного `schedule:run` они идут последовательно. Следующий
системный cron может поднять ещё один процесс через минуту, поэтому разные
задачи способны выполняться параллельно.

`onOneServer()` не задан. Локальный cache на нескольких узлах не защищает от
дублей: блокировка у каждого узла своя.

## Логирование

`CronTaskRunner::LOG` равен `cron`. `MproHelper::addLog()` создаёт новый Monolog
`RotatingFileHandler` с базовым путём `storage/logs/cron.log`, но стандартный
шаблон обработчика записывает фактически в:

```text
storage/logs/cron-YYYY-MM-DD.log
```

`maxFiles = 14`, уровень `Info`. Массив превращается в многострочный текст;
вложенные массивы и объекты сериализуются в JSON без экранирования Unicode.

Формы записей:

| Событие | Поля |
| --- | --- |
| успех метода | `id`, `name`, `controller`, `method`, `params`, `ms` |
| ошибка раннера | `id`, `name`, `controller`, `method`, `error`, `ms` |
| ошибка регистрации | `stage`, `id`, `name`, `error` |

В этих строках `controller` — только имя статьи, а не сохранённое
`article|method`.

Успех пишется при `MagicGlobals::$INI['CRON_LOG_SUCCESS'] ?? true`. Значение
схемы по умолчанию тоже `true`; `?? true` сохраняет это поведение для старого
`magic.ini`, где ключ ещё отсутствует. Ошибки настройки не учитывают.

Ошибки чтения таблицы при регистрации не логируются. `MproHelper::addLog()`
исключений не бросает, поэтому незаписанный лог не выходит ни из раннера, ни из
регистрации. Жалоба регистрации вдобавок обёрнута в try/catch целиком — из-за
`Cache::add`, который может упасть на файловом кеше чужого пользователя.

## Heartbeat и диагностика

`Heartbeat::__invoke()` каждую минуту:

1. строит `storage_path(Heartbeat::FILE)`;
2. при необходимости создаёт каталог с режимом `0775`;
3. записывает текущую дату `Y-m-d H:i:s`.

Константа:

```text
app/private/magic/heartbeat.txt
```

`Installer::checkCron()` использует только `filemtime`, а текст файла нужен для
чтения человеком. Отметка считается свежей не более 120 секунд. Проверка не
смотрит таблицу задач, их enabled, cron-выражения, `last_run_at` или лог.

Ошибка heartbeat локально не ловится. Laravel обработает её как ошибку одного
scheduled event и продолжит обход, но диагностика останется красной.

## Интерфейс

`cronAdmin.vue` держит список и форму локально. Все запросы проходят через
`apiCron()`; пока один запрос активен, новый вызов сразу возвращается.

Особенности, которые нужно сохранять согласованными с API:

- `params` хранятся в модели как объект/массив, но редактируются JSON-строкой;
- после save, toggle, delete и runNow список загружается заново;
- checker errors показываются рядом с controller;
- `last_run_at` форматируется `formatDate()` в часовом поясе браузера;
- кнопка runNow доступна независимо от `enabled`;
- форма отправляет `enabled` как boolean.

Blade `admin/views/cron.blade.php` подключает Vue только для роли `admin`.
Сам POST API дополнительно защищён middleware.

## Инварианты при изменении кода

### Изменение ссылки на метод

Формат `article|method` одновременно знают:

- `CronTaskChecker::parse()` и `className()`;
- `CronTaskRunner`;
- API-валидация;
- форма, список и переводы админки;
- существующие строки базы;
- документация и примеры.

Смена разделителя или переход на `article_id + method` требует миграции старых
данных, а не только правки parser.

### Изменение params

Нужно синхронно проверить:

1. `API_Cron::readParams()`;
2. JSON cast модели и nullable таблицы;
3. сериализацию формы Vue;
4. аргумент `CronTaskRunner`;
5. успешный лог, куда параметры попадают целиком;
6. существующие методы задач.

Нельзя незаметно заменить один массив несколькими аргументами: dynamic method
call не использует container injection.

### Новое поле задачи

Согласуются миграция, `$fillable`, casts или `$attributes`, `saveTask()`,
`toArray()`/API, пустая форма, форма редактирования, список и документация.
Изменение порядка выполнения может потребовать индекс; сейчас гарантированного
порядка у выборки активных задач нет.

### Изменение проверки

У checker четыре разных потребителя с разными задачами:

- `save` запрещает новую битую ссылку;
- `get` и `list` диагностируют устаревшую строку;
- `runNow` не начинает заведомо недоступный вызов;
- автоматический раннер берёт из него только то, что без базы: `methodName()`
  и `ownMethod()`.

Унаследованные методы запрещены везде, сигнатура не проверяется: метод получает
один массив, и что он с ним делает — его дело.

### Изменение блокировки

Ключ блокировки строится по `id` задачи в `CronTaskRunner::lock()`. При
изменении `LOCK_SECONDS` учитывайте долгие задачи (дольше срока — второй запуск
поверх), аварийное завершение (меньше срок — быстрее оживает) и cache store на
нескольких серверах.

### Изменение обработки ошибок

Сейчас бизнес-результат метода не имеет значения: только брошенный `Throwable`
попадает в `error`. Если появятся статусы, ретраи или автоматическое отключение,
понадобятся новые колонки, переходы состояния, UI и отдельное решение для
идемпотентности.

## Проверка после правок

Минимальный набор проверок для затронутой подсистемы:

1. каждый изменённый PHP-файл проверить через `php -l`;
2. при изменении Vue собрать фронт из корня пакета через `npm run build`;
3. проверить save для новой и существующей задачи;
4. проверить пустые, объектные, списочные и ошибочные `params`;
5. проверить валидное и невалидное cron-выражение;
6. проверить отсутствующую статью, класс, метод и исключение внутри метода;
7. сравнить ручной и автоматический запуск;
8. проверить `last_run_at`, success/error/register записи лога;
9. проверить пропуск наложения и освобождение mutex;
10. проверить heartbeat при обычном и maintenance-режиме.

Выделенных автоматических тестов cron-подсистемы в пакете сейчас нет.
