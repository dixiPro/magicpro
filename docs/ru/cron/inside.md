# Крон: как устроено

Как заводить задачи — в `use.md`. Здесь внутренности.

## Расписание

`MagicProSrc\Scheduling\MagicProSchedule::register()`, зовётся провайдером через
`callAfterResolving(Schedule::class, …)`.

Сперва то, что было всегда: `magicpro:heartbeat` и `magicpro:sendQueue`,
ежеминутно. Ниже — `registerCronTasks()`, задачи из базы.

Защиты две, и обе обязательны.

**Чтение базы в своём `try/catch`.** Расписание собирается при любом
artisan-вызове, в том числе на свежей установке, где таблиц ещё нет. Нет базы,
нет таблицы — метод молча возвращается, и `artisan` работает дальше.

**Каждая задача регистрируется в своём `try/catch`.** Одна кривая строка в базе
не должна унести весь проход планировщика вместе с почтой.

Строка `cron` проверяется до регистрации:

```php
if (! CronExpression::isValidExpression($task->cron)) {
    throw new \Exception('invalid cron expression: ' . $task->cron);
}
```

Без этого беда приходит позже и не туда: `Event::cron()` принимает строку не
глядя, а спотыкается о неё при проверке «пора ли запускать», уже внутри прохода
`schedule:run`. Тот бросок нашим `try/catch` не поймать — он вне регистрации.

Порядок вызовов тоже не случайный:

```php
$schedule
    ->call(fn () => CronTaskRunner::run($task))
    ->cron($task->cron)
    ->name('magicpro:dynamic:' . $task->id)
    ->withoutOverlapping();
```

`name()` обязан стоять до `withoutOverlapping()`: замок берёт имя оттуда, и без
имени `CallbackEvent` бросает `LogicException`.

Список читается заново при каждом проходе, кеша нет намеренно: правка в админке
должна действовать сразу.

## Вызов

`CronTaskRunner::run()` короткий:

1. разбирает `controller` на статью и метод — `CronTaskChecker::parse()`;
2. убеждается, что класс `\MagicProControllers\{статья}` существует;
3. ставит `last_run_at`;
4. `app($class)->{$method}($params)`.

Http вокруг вызова нет вовсе: ни `Request`, ни `Env`, ни рендера вьюхи. Метод —
самостоятельная точка входа, а не страница. Проверок доступа тоже нет: задачу
завёл администратор в админке, это и есть авторизация.

`app()`, а не `new`: контроллер может просить зависимости в конструкторе.

Параметры уезжают **одним массивом** — json задачи как есть. Метод объявляет один
аргумент-массив; объявленный без аргументов тоже сработает, лишний аргумент php
терпит.

`last_run_at` ставится **до** вызова, а не после. Это отметка «планировщик досюда
дошёл и задачу дёрнул», а не «задача отработала».

Возвращённое значение выбрасывается, тип его не проверяется.

Возвращает `run()` пару `['ms' => int, 'error' => string]`. Пустой `error` —
дошло до конца.

### Что с ошибками

`handle()` здесь не участвует, а значит ничто больше не проглатывает исключение
из контроллера: `MagicController::handle()` ловил `\Throwable` и превращал его в
500-страницу, которую крон выбрасывал вместе с текстом беды. Прямой вызов метода
такого щита не имеет — что упало, то и попадёт в лог, и то же самое покажет
кнопка «выполнить сейчас».

`try/catch` внутри `run()` стоит при этом не ради вердикта, а ради соседей: одна
упавшая задача не должна унести проход планировщика. Разбирать результат крон
по-прежнему не берётся — ретраев нет, задача сама себя не выключает, поэтому в
таблице нет ни `last_status`, ни `last_error`.

## Проверка задачи

`CronTaskChecker::check($controller)` возвращает `['ok' => bool, 'error' => string]`.
Список короткий:

1. левая часть строки не пуста;
2. правая часть — имя метода — не пуста;
3. имя метода подходит под `^[A-Za-z][A-Za-z0-9_]*$`. Начинается с буквы, значит
   `__construct` и прочая магия php отсекаются самим правилом, отдельного списка
   запретов не нужно;
4. статья с таким именем есть;
5. класс `\MagicProControllers\{статья}` существует.

Дальше не проверяется ничего: ни `isRoute`, ни `adminOnly`, ни `postEnable` — они
про страницу, а метод не страница. Есть ли сам метод и подойдёт ли ему то, что
прислали, выясняет кнопка «выполнить сейчас», и её ошибка видна на экране.

Маршрут не спрашивается и намеренно: `createMpro()` пишет файл контроллера по
одному `useController`, `isRoute` в этом решении не участвует. Статья без
маршрута с включённым контроллером — законный носитель задачи, и `class_exists`
это увидит.

Первый непройденный пункт и есть `error`.

Зовётся из трёх мест — `save`, `list`, `runNow`. В `list` на каждом заходе:
статью могли переименовать или удалить уже после того, как задача была заведена,
и экран — единственное место, где это станет видно.

Крон чекер не зовёт: он и так в `try/catch`, а лишний запрос к базе каждую минуту
незачем. `class_exists` он проверяет сам, ради внятного текста в логе.

## API

`POST /a_dmin/api/cron`, за `magic.auth`, без CSRF. Класс `API_Cron` наследует
общий `AbstractApi`, форма ответа обычная: `status / errorMsg / data / request`.

| Команда | Что делает |
| --- | --- |
| `list` | все задачи, у каждой поле `check` |
| `get` | одна задача по `id` |
| `save` | создать или обновить (есть `id` — обновить) |
| `toggle` | переключить `enabled` |
| `delete` | удалить по `id` |
| `runNow` | выполнить сейчас, вернуть `ms` |

`save` не сохранит задачу, которая заведомо не отработает: имя, `controller`
через чекер, валидная строка `cron`. `params` принимается строкой из формы или
массивом из кода и обязан быть объектом ключ-значение — метод получает его одним
массивом, список там не разложить.

`runNow` — единственное место, где ошибку задачи видно человеку: непустой `error`
от раннера бросается исключением и уходит в `errorMsg`, то есть на экран.

Замка у `runNow` нет: `withoutOverlapping` стоит на событии планировщика и ручной
запуск не покрывает.

## Модель

`MagicProCronTask`, таблица `magicPro_cron_tasks`.

| Поле | Зачем |
| --- | --- |
| `name` | название для человека |
| `controller` | `статья\|метод`: из левой части собирается класс, правая зовётся |
| `params` | json, уезжает в метод одним массивом |
| `cron` | пять полей, время сервера |
| `enabled` | выключенная не регистрируется |
| `last_run_at` | когда планировщик её дёрнул |

Индекс по `enabled`: выборка активных идёт раз в минуту.

Отдельного поля под метод нет: он живёт в той же строке через `|`. Статуса
последнего запуска нет, см. выше.

## Лог и настройка

`MproHelper::addLog('cron', …)` пишет в `storage/logs/cron.log`, ротация 14 дней.

Беды пишутся всегда. Строка выполнения — под настройкой `CRON_LOG_SUCCESS`
(`src/Config/magicSchema.php`, тип `boolean`, по умолчанию включено). Читается
она как `MagicGlobals::$INI['CRON_LOG_SUCCESS'] ?? true`: в уже существующем
`magic.ini` ключа нет до первого сохранения Setup, и `??` держит поведение по
умолчанию, пока он не появится.

## Диагностика

Живость планировщика проверяет `Installer::checkCron()` на каждом заходе в
`/a_dmin`: смотрит возраст файла `Heartbeat::FILE`. Свежий — строка «Крон жив» с
временем отметки в списке пройденных проверок, старый или отсутствует —
сообщение с командой для `crontab`.

Отдельной проверки задач там нет: задачи видно на своём экране, где каждая
проходит через `CronTaskChecker`.
