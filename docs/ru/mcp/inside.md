# МСП: как устроено

Пакет `laravel/mcp`. Как звать инструменты — в `use.md`.

## Из чего собран

| Где | Что |
| --- | --- |
| `src/Mcp/ai.php` | регистрация сервера |
| `src/Mcp/Servers/MagicProServer.php` | список инструментов |
| `src/Mcp/Tools/*.php` | сами инструменты, по классу на каждый |

Регистрация — одна строка:

```php
Mcp::local('magicpro', MagicProServer::class);
```

`local` означает, что сервер поднимается локально и говорит через stdio: агент
запускает его сам, http и авторизация не участвуют.

## Инструмент

Обычный `Laravel\Mcp\Server\Tool`. Три части: имя, описание, схема параметров.

```php
#[Name('save-file')]
#[Description('Writes one file through the MagicPro file manager api…')]
class SaveFileTool extends Tool
{
    public function schema(JsonSchema $schema): array { … }
    public function handle(Request $request): Response|ResponseFactory { … }
}
```

**Описание — это не комментарий, а часть контракта.** Оно уезжает агенту вместе с
инструментом и остаётся единственным местом, откуда тот узнаёт правила: что
`save-file` заменяет файл целиком, что блейды статей сюда не относятся, что
`parentId` у `create-article` — будущий родитель. Правило, не попавшее в
`Description`, для агента не существует. Поэтому описания длинные, и это
намеренно.

То же и со `schema()`: `description` каждого поля — подсказка на месте
использования, а не документация для человека.

## Тело инструмента

Своей логики у инструментов нет. Каждый собирает запрос и отдаёт его тому же
контроллеру админки, что обслуживает браузер:

```php
$result = (new API_FileManagerPostController())
    ->handle(new HttpRequest([
        'command'  => 'saveFile',
        'fileName' => $request->get('fileName'),
        'fileData' => $request->get('fileData'),
    ]))
    ->getData(true);

if (! $result['status']) {
    return Response::error($result['errorMsg'] ?? 'saveFile failed');
}

return Response::structured($result['data']);
```

Отсюда всё остальное: агент проходит те же проверки, что оператор, файлы
перегенерируются, дерево пересчитывается. Дублировать логику в инструменте нельзя
— она разойдётся с админкой в первый же месяц.

Ответ всегда один из двух: `Response::structured($data)` при удаче,
`Response::error($msg)` при ошибке. Исключения наружу не выпускаются, ошибка API
становится ошибкой инструмента.

## Добавить инструмент

1. Класс в `src/Mcp/Tools/`, унаследовать `Tool`.
2. `#[Name]` и `#[Description]`. В описании — все правила и ограничения, включая
   то, чего делать нельзя.
3. `schema()` с описанием каждого параметра.
4. `handle()` — собрать запрос к существующему API админки, не писать свою логику.
5. **Дописать класс в `MagicProServer::$tools`.** Не дописал — инструмента нет.

## Почему для лент задумана одна точка

`AbstractFeedApi::run()` уже универсальна: команда, массив параметров, ответ
всегда одной формы, исключений не бросает. Инструмент на каждую команду означал
бы полтора десятка классов, которые надо держать в согласии с `$map`.

Поэтому в ТЗ один инструмент поверх `run()`, со списком разрешённых команд внутри:

```
feed-api { command: "itemsList", params: { "feedId": 2 } }
```

Новые команды API появляются в МСП сами, инструмент править не надо. Команда не
из списка — ошибка инструмента, до `run()` дело не доходит.

Разрешены только чтение: `groupsList`, `feedsList`, `feedGet`, `schemaGet`,
`itemsList`, `itemGet`, `itemLinks`, `itemsLookup`. Запись и удаление не входят.

Кода пока нет, ТЗ — `docs/toDo/TZ_mcp.md`.

## Что учесть

- Удаления статей среди инструментов нет намеренно: агент удаляет молча, а
  восстановления нет.
- Инструменты чтения дерева отдают короткие записи. Полное тело статьи берётся
  `get-article`, и незачем тянуть его пачкой.
- Правило, которое агент должен соблюдать, живёт в `#[Description]`, а не в
  документации: документацию он может не открыть.
