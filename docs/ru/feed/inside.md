# Ленты: внутреннее устройство и развитие

Документ для разработчика, который меняет модели, Feed API, схему хранения или
админский интерфейс. Пользовательские рецепты находятся в `use.md`.

## Инварианты модуля

При любой доработке сохраняйте следующие правила:

1. Таблицы общие для всех лент и не меняются из админки.
2. Смысл физического слота задаёт JSON-схема конкретной ленты.
3. Прикладной код работает с логическими именами полей.
4. `__data` доступен на модели, но не переводится в SQL-колонку.
5. Видимость никогда не добавляется к запросу автоматически.
6. Новая запись получает позицию атомарно и начинается скрытой.
7. На занятую ссылками запись действует запрет физического удаления.
8. Одна коллекция изображения соответствует одному коду поля.
9. Изменение схемы должно инвалидировать уже выданные карты полей.

## Таблицы

Миграции идут по порядку `create_magicPro_lenta_0...3`.

### `magicPro_feed_groups`

- `id`, `title`, `position`, timestamps;
- индекс `(position, id)`;
- первая миграция создаёт группу с id `1`;
- `FeedGroup::DEFAULT_ID` запрещает удалить эту группу;
- непустую группу также нельзя удалить.

### `magicPro_feeds`

- `code` — `varchar(255)`, уникален во всей таблице;
- `title`;
- `schema` — JSON без DB default, модель задаёт `EMPTY_SCHEMA`;
- `group_id`, `position`, timestamps;
- индекс `(group_id, position, id)`;
- внешний ключ на группу с `RESTRICT`.

Сохранение или удаление любой ленты очищает статические карты схем и увеличивает
`Feed::$schemaGeneration`.

### `magicPro_feed_items`

| Колонки | Тип и смысл |
| --- | --- |
| `feed_id` | владелец записи, внешний ключ `RESTRICT` |
| `__string_1...5` | nullable string, короткие индексируемые значения |
| `__bigint_1...3` | nullable bigint |
| `__date_1...3` | nullable datetime |
| `__bool_1...3` | boolean, DB default `false` |
| `__link_1...3` | nullable unsigned bigint, без внешнего ключа |
| `__data` | JSON, модель задаёт пустой объект |
| `__slug` | nullable string, адрес записи |
| `__position` | bigint, порядок внутри ленты |
| `__visible` | boolean, DB default `false` |
| timestamps | время создания и изменения |

Число слотов продублировано намеренно: актуальные значения живут в константах
`FeedItem`, а старая миграция остаётся снимком структуры на момент выпуска.

В `magicPro_feed_items` двадцать явно объявленных вторичных индексов, не считая
`PRIMARY`, с учётом отдельной slug-миграции:

- список по ручному порядку — 1;
- список по `created_at` — 1;
- датовые — 3;
- связи — 3;
- флаги — 3;
- строковые — 5;
- целочисленные — 3;
- `UNIQUE (feed_id, __slug)` — 1.

Первые одиннадцать списковых индексов начинаются с
`(feed_id, __visible, ...)`. Строковые и числовые поисковые индексы не содержат
видимость. Проверка входящих ссылок делает `OR` по трём `__link_N` без известного
`feed_id`, поэтому составные индексы связей для неё не подходят.

## Формат схемы

Минимальная схема — `{"version":1,"fields":[]}`. Полная форма выглядит так:

```json
{
  "version": 1,
  "slugFrom": "title",
  "orderBy": "publishedAt",
  "orderDir": "desc",
  "viewArticle": "product",
  "order": ["__string_1", "__data.description"],
  "orderForm": ["__string_1", "__data.description"],
  "fields": [
    {
      "column": "__string_1",
      "code": "title",
      "label": "Название",
      "type": "string",
      "unique": true,
      "showOnList": true,
      "validation": "required|string|max:255"
    },
    {
      "column": "__link_1",
      "code": "category",
      "label": "Категория",
      "type": "link",
      "relation": {
        "feed_id": 3,
        "display_code": "__string_1"
      }
    },
    {
      "column": "__data",
      "code": "data",
      "data": [
        {
          "code": "description",
          "label": "Описание",
          "type": "text",
          "editor": "html"
        },
        {
          "code": "image",
          "label": "Изображение",
          "type": "image"
        }
      ]
    }
  ]
}
```

`API_Feeds::checkSchema()` нормализует верхний уровень и проверяет:

- `fields` — массив, каждый элемент — объект;
- физическая колонка существует и занята не больше одного раза;
- все коды непустые, уникальные, соответствуют
  `^[A-Za-z0-9_-]+$`, не начинаются с `__` и не равны системным именам;
- у отображаемого поля есть `label`;
- тип физического поля совпадает с родом слота;
- тип `__data` входит в `DATA_TYPES`;
- `editor` равен `html`, `markdown` или `plain`;
- `unique` запрещён внутри `__data`;
- `link.relation.feed_id` существует, а `display_code` — занятая физическая
  колонка целевой ленты;
- `slugFrom` ссылается на строковый слот;
- `orderBy` ссылается на строковый или датовый слот.

`order` и `orderForm` не сверяются с фактическими полями. Сервер оставляет в них
строковые элементы, потому что согласованность должен обеспечить frontend.
Неизвестные дополнительные ключи описания поля сохраняются.

Если в ленте есть записи, код занятого физического слота нельзя изменить.
Контейнер `__data` из этой проверки исключён: переименование вложенного кода по
сути создаёт новый ключ, а старые значения остаются в JSON под прежним именем.

## Логические имена на модели

`Feed::schemaMap()` строит пару:

```php
[
    ['title' => '__string_1', 'price' => '__bigint_1'],
    ['description', 'image'],
]
```

`FeedItem::getAttribute()` и `setAttribute()` действуют в следующем порядке:

1. Физическое или системное имя передаётся Eloquent.
2. Код слота переводится в физическую колонку.
3. Код из `__data` читается или меняется внутри JSON с сохранением соседей.
4. Неизвестное имя снова передаётся Eloquent, чтобы продолжали работать
   relations и accessors.

Поле схемы может называться как метод модели: известный схеме код имеет приоритет
над relation/accessor. `fields()` выдаёт логическое представление; `toArray()`
не переопределён и остаётся физическим.

`fill()` сначала устанавливает `feed_id`, независимо от порядка входного
массива. `getFillable()` динамически дополняется логическими кодами. Поэтому
создание поддержано и через `$feed->items()->create()`, и через
`FeedItem::create(['feed_id' => ...])`.

## Логические имена в запросах

`Feed::items()` вызывает `FeedItemBuilder::forFeed($feed)` для существующей
ленты. Builder сохраняет карту и передаёт её прототипу модели, чтобы строки
результата не делали запрос схемы каждая.

Перевод реализован только для:

- `where()` с простым именем, массивом или Closure;
- `whereIn()`, `whereNotIn()`, `whereNull()`, `whereNotNull()`;
- `orderBy()`, `orderByDesc()`;
- `value()`, `pluck()`;
- `update()`.

Незнакомый логический код вызывает `feed_err_field_no_schema`. Код из `__data`
вызывает `feed_err_field_in_data`. Expression, квалифицированная колонка с
точкой и физическое имя проходят без перевода.

Голый `FeedItem::query()` схемы не имеет. Загруженная им модель всё равно
разрешит логическое поле по `feed_id` при чтении, но условия этого запроса нужно
писать физическими именами.

Mass update без полей `__data` выполняется одним SQL. Если среди значений есть
хотя бы одно JSON-поле, builder загружает записи и сохраняет их по одной, чтобы
не затереть остальные ключи контейнера.

Отсюда важная асимметрия: физический mass update обходит события модели и не
пересчитает slug, даже если изменено его поле-источник. Ветка с `__data` вызывает
`save()` для каждой записи и события выполняет. Обе ветки обходят проверки
`validation`, `unique` и `link` из `API_Feeds::itemSave()`. Для данных, где важны
эти инварианты, загружайте модели и меняйте их осознанно либо используйте API.

### Кэш и устаревание

`Feed::schemaMapOf($feedId)` кеширует карту на время PHP-процесса.
`FeedItem` запоминает также номер поколения. После `Feed::save()` или удаления
ленты статический кеш очищается, поколение растёт, а уже созданная модель при
следующем обращении перечитывает карту.

Не обновляйте `magicPro_feeds.schema` в обход модели: карта и живые объекты не
узнают об изменении.

## Slug

Slug применяется в событии `saving`:

- при непустом `slugFrom` модель берёт физическую колонку источника;
- без источника используется присланный `__slug`;
- `MproHelper::translitForUrl()` нормализует оба варианта;
- пустой результат записывается как `NULL`;
- программная проверка даёт понятную ошибку;
- `UNIQUE (feed_id, __slug)` закрывает гонки на уровне базы.

Смена `slugFrom` не пересчитывает существующие строки немедленно. Новый slug
появится при следующем сохранении каждой записи.

## Позиции и блокировки

Перед вставкой `FeedItem::nextPosition()` блокирует строку ленты и считает
`max(__position) + 1`. `FeedItem::save()` сам открывает транзакцию для новой
модели, поэтому блокировка живёт до завершения insert.

`itemSave` также блокирует строку ленты: программная проверка `unique` и запись
выполняются в одной транзакции. Скрытые записи участвуют в уникальности.
Обычный Eloquent `save()` правила `validation`, schema-level `unique` и
корректность link-полей не проверяет: это ответственность Feed API.

`groupMove`, `feedMove` и `itemMove` собирают упорядоченный список id, вставляют
перемещаемый id на целевую позицию и перенумеровывают список от нуля. После
простого удаления позиции не уплотняются; следующая запись всё равно получает
`max + 1`.

## Связи и удаление

Ссылка хранит id `FeedItem`, но внешнего ключа на уровне БД нет. `itemSave`
проверяет существование цели, нужную ленту и отсутствие цикла любой глубины.

`FeedItem::delete()` открывает транзакцию, проверяет все три link-слота всех
записей и лишь затем вызывает родительское удаление. Это важно для Media
Library: файлы нельзя удалить до того, как принято решение удалить строку.

`FeedItemBuilder::deleteEach()` загружает модели по одной, пропускает удерживаемые
и возвращает число удалённых. Обычный builder `delete()` намеренно не
переопределён и обходит защиту — внутренний и прикладной код не должен применять
его к записям лент.

`feedClear` и `feedDelete` вызывают `deleteEach()` проходами. После удаления
держателя на следующем проходе может освободиться его цель. Если записи всё ещё
удерживаются извне, очистка возвращает `false`, а удаление сохраняет и записи, и
саму ленту.

Удаление группы запрещено для id `1` и для любой группы с лентами. Внешние ключи
дополнительно запрещают удалить группу с лентами и ленту с записями.

## Изображения

`FeedItem` реализует `HasMedia` и использует `InteractsWithMedia`.

- коллекция называется кодом image-поля;
- перед новой загрузкой коллекция очищается;
- метаданные `path`, `size`, `mime`, `x`, `y`, `alt` записываются в `__data`;
- устаревший ключ `url` удаляется при следующей загрузке этого поля;
- `imageDelete` сначала очищает коллекцию, затем удаляет ключ из JSON;
- `imageCropUpload` перекодирует временный файл через `ImageEncoder` в
  `RESIZE_FORMAT`;
- `imageUpload` сохраняет присланный файл как есть.

`path` — URL-path без домена. В HTML он используется напрямую, а image helpers
получают `public_path($path)`.

`MagicServiceProvider` регистрирует `FeedPathGenerator` только для модели
`FeedItem` через `PathGeneratorFactory::setCustomPathGenerators()`. Это не
глобальная подмена `media-library.path_generator`.

## Текст записи

`MproHelper::feedText()` делегирует в `FeedText::render()`.

Обработка идёт так:

1. Из `fields()` берётся карта значений.
2. Одиночные теги `<x-magic::... />` или их escaped-вариант разбираются отдельно.
3. Метки в атрибутах подставляются с сохранением типа для bound-атрибута.
4. Компилируется и рендерится только тег компонента.
5. В оставшемся тексте заменяются `#code#` и `#code.key#`.

Blade-синтаксис внутри тега запрещён. Ошибка разрешения компонента пишется в лог
`feed`, вместо тега возвращается `unsupported`. Текст вокруг не компилируется.

Этот механизм не является общим HTML sanitizer. `editor` описывает интерфейс,
но сервер сохраняет присланный HTML. `MproHelper::mdToHtml()` — отдельный
безопасный путь для Markdown оператора.

## API

`AbstractFeedApi` хранит карту `command => method` и предоставляет два входа:

- `API_Feeds::run()` никогда не бросает наружу: формирует
  `status/errorMsg/data/request`, а у `FeedValidationException` добавляет
  `errors`;
- `API_Feeds::runOrFail()` нужен внутреннему коду и сохраняет исходное
  исключение.

HTTP `handle()` берёт `command` из body. Маршрут
`POST /a_dmin/api/feed` зарегистрирован в web-группе, защищён `magic.auth` и
исключён из CSRF middleware пакета.

`itemSave` принимает объект `fields`, запрещает неизвестные коды, собирает
Laravel validation rules из схемы, затем отдельно проверяет `unique` и `link`.
Проверяются только пришедшие поля. `visible` и `slug` находятся на верхнем уровне
параметров.

`itemsList` последовательно применяет фильтры через `AND`, сортирует по заданному
полю и всегда добавляет `id` в том же направлении для стабильной пагинации.
Размер страницы ограничен снизу единицей, верхней границы на сервере нет.

При добавлении команды нужно одновременно:

1. Добавить имя в `$map`.
2. Реализовать protected handler.
3. Добавить сообщения `feed_err_*` во все словари, если появились новые ошибки.
4. Добавить клиентский вызов и обработать точную форму `data`.
5. Обновить документацию и тесты.

## Чек-лист изменения

### Новый физический слот

1. Создать новую миграцию, старую не менять.
2. Обновить константы и `slotColumns()` в `FeedItem`.
3. Добавить cast и нужные статические индексы.
4. Обновить `COLUMN_TYPES` и schema UI.
5. Проверить logical get/set, create, query translation и API presentation.
6. Проверить MySQL/PostgreSQL-совместимые типы и имена индексов.

### Новый тип `__data`

1. Добавить тип в `DATA_TYPES`.
2. Добавить редактор и отображение списка/формы.
3. Определить default, validation и формат API.
4. Не обещать фильтрацию, сортировку или `unique` без отдельной архитектуры.

### Изменение модели или builder

- проверить модель, загруженную через `$feed->items()` и через
  `FeedItem::find()`;
- проверить создание через relation и с явным `feed_id`;
- проверить вложенный `where`, массив условий, `pluck` с key и JSON update;
- проверить инвалидирование уже выданной карты после сохранения схемы;
- не превращать `toArray()` в логическое представление без аудита всех API.

### Изменение удаления или медиа

- проверить прямую и косвенную входящую ссылку;
- проверить запрет цикла;
- проверить одиночное, групповое удаление, очистку и удаление ленты;
- убедиться, что при отказе строка и файлы остаются, а при успехе удаляются оба;
- не заменять модельное удаление массовым builder delete.

## Проверка перед сдачей

- PHP-файлы: `php -l` для каждого изменённого файла.
- Frontend: штатная сборка пакета после согласования с правилами репозитория.
- API: happy path и отрицательные ответы с точной формой envelope.
- Схема: занятый слот, повторный code, неверный тип, link relation,
  `slugFrom`, `orderBy`, code lock на непустой ленте.
- Записи: defaults, visible, slug, validation, unique, relation, cycle,
  пагинация и стабильный второй `orderBy(id)`.
- Не менять напрямую БД, Composer, git и сгенерированные файлы без отдельного
  разрешения по правилам проекта.
