# Ленты: как устроены

Документ для того, кто **правит сам модуль**. Как пользоваться готовыми лентами —
в `use.md`, здесь это не повторяется.

## Хранение

Три таблицы: `magicPro_feed_groups`, `magicPro_feeds`, `magicPro_feed_items`.

### magicPro_feed_groups

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `id` | bigint | первичный ключ |
| `title` | string | название группы |
| `position` | bigint | порядок вывода |
| `created_at`, `updated_at` | datetime | |

Миграция заводит группу по умолчанию: удалить нельзя, в неё попадают новые ленты,
переименовать можно. Лента без группы не существует, а группа с лентами не
удаляется — сперва ленты переносят или удаляют.

### magicPro_feeds

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `id` | bigint | первичный ключ |
| `code` | string, `UNIQUE` | программный код ленты |
| `title` | string | название в админке |
| `schema` | json | описание полей |
| `group_id` | bigint | группа, обязательна |
| `position` | bigint | позиция внутри группы |
| `created_at`, `updated_at` | datetime | |

Версия формата схемы лежит **внутри** json, отдельной колонки нет: схему копируют
и переносят целиком, версия должна ехать вместе с ней. `group_id` — настоящий
внешний ключ, второй рубеж поверх проверок в коде.

### magicPro_feed_items

Записи **всех** лент лежат здесь, набор колонок фиксирован.

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `id` | bigint | первичный ключ |
| `feed_id` | bigint | лента записи |
| `__string_1` … `__string_5` | varchar(255) nullable | строки для поиска и сортировки |
| `__bigint_1` … `__bigint_3` | bigint nullable | целые |
| `__date_1` … `__date_3` | datetime nullable | даты и время |
| `__bool_1` … `__bool_3` | boolean not null, default 0 | флаги |
| `__link_1` … `__link_3` | unsigned bigint nullable | ссылки на другие записи |
| `__data` | json | неиндексируемые данные и тексты |
| `__slug` | varchar(255) nullable | адрес записи для SEO, уникален в ленте |
| `__position` | bigint | позиция внутри ленты |
| `__visible` | boolean, default 0 | видимость |
| `created_at`, `updated_at` | datetime | |

Отдельных текстовых колонок нет: большие тексты живут в `__data`. Внешнего ключа
на `__link_N` тоже нет — «запись, на которую ссылаются, не удаляется» это правило
модуля, а не базы.

Количества слотов вынесены в константы `FeedItem::STRINGS`, `BIGINTS`, `DATES`,
`BOOLS`, `LINKS`. В миграции те же числа выписаны отдельно, и это сделано
намеренно: миграция — снимок того, какой таблица была тогда, и она не должна
менять смысл вслед за константами.

### Умолчания при создании записи

- `__position` = `max(__position) + 1` внутри своей ленты, в транзакции с
  блокировкой строки `magicPro_feeds`.
- `__visible` = `false`. Редактор ставит `true` сам, когда запись готова, иначе на
  сайте появляются пустые заготовки.
- `__bool_N` = `0`. Колонка `not null`, а умолчание стоит на уровне миграции: поля
  может ещё не быть в схеме, а вставка должна пройти.
- Незанятые слоты — `NULL`, а не пустая строка. Два `NULL` считаются разными, две
  пустые строки — одинаковыми, и на этом ломается проверка уникальности.
- У `__data` умолчания в базе нет: mysql не разрешает его на json-колонке, пустой
  объект приходит от модели.
- `__slug` = `NULL`, пока запись не сохранили с непустым источником или с
  введённым руками адресом.
- Остальное берётся из настроек поля в схеме.

### Slug

Адрес записи для SEO и больше ни для чего: `/pesnya` вместо `/id/17`. Колонка
системная, как `__position` и `__visible`, — она есть у записи любой ленты
независимо от схемы, поэтому строковый слот под неё не занимается.

Заполняется в модели, обработчиком `saving`, — то есть при любом способе
сохранения, а не только через админку:

- **источник задан** (`slugFrom` в схеме) — адрес каждый раз считается заново из
  этого поля. Поменяли название — поменялся адрес. Руками не правится;
- **источника нет** — считать не из чего, оператор вводит адрес сам.

Введённое руками проходит ту же транслитерацию: колонка — это кусок URL, и то,
что набрали, должно быть таким же безопасным, как то, что посчитали.

Пусто — это `NULL`, а не пустая строка: два `NULL` в SQL не равны, поэтому
записей без адреса может быть сколько угодно, а пустую строку уникальный индекс
пустил бы только одну. Пустой источник даёт `NULL` — запись без адреса допустима.

Уникальность держат двое. Модель проверяет запросом и бросает исключение с
текстом «Slug не уникален» и самим значением — автоматических суффиксов нет,
оператор правит источник сам. Уникальный индекс `(feed_id, __slug)` — второй
рубеж на случай записи мимо проверки. `itemSave` делает проверку и запись в одной
транзакции с блокировкой строки ленты, поэтому два параллельных сохранения не
пройдут проверку оба.

Смена источника ничего не пересчитывает: у старых записей адрес остаётся
прежним, новое правило работает с их следующего сохранения. По той же причине
выкатка миграции ничего не ломает — существующие записи получают `NULL`.

Транслитерация — `MproHelper::translitForUrl()`, она же переводит русский и
сербский. Таблица закрытая: чего в ней нет, того не будет и в адресе.

### Что куда ложится

Что не влезло в слоты, живёт в `__data`: тексты, картинки, json. Своей колонки у
них нет, поэтому искать и сортировать по ним нельзя.

| Колонка | Допустимые типы |
| --- | --- |
| `__string_N` | `string` |
| `__bigint_N` | `integer` |
| `__date_N` | `datetime` |
| `__bool_N` | `boolean` |
| `__link_N` | `link` |
| `__data` | `string`, `text`, `integer`, `decimal`, `boolean`, `datetime`, `json`, `code`, `image` |

Это `COLUMN_TYPES` и `DATA_TYPES` в `API_Feeds`, проверяется при сохранении схемы.

### Схема

Хранится в `magicPro_feeds.schema` как json и целиком описывает соответствие
«логическое имя → колонка»:

```json
{
  "version": 1,
  "slugFrom": "title",
  "orderBy": "date",
  "orderDir": "desc",
  "viewArticle": "blog",
  "order": ["__string_1", "img", "__date_1"],
  "fields": [
    {
      "column": "__string_1",
      "code": "title",
      "label": "Название",
      "unique": true,
      "validation": "required|string|max:255",
      "showOnList": true
    },
    {
      "column": "__link_1",
      "code": "category",
      "label": "Категория",
      "relation": { "feed_id": 3, "display_code": "__string_1" }
    },
    {
      "column": "__data",
      "code": "content",
      "data": [
        { "code": "img", "label": "Картинка", "type": "image", "minWidth": 600, "ratio": "16/9" },
        { "code": "body", "label": "Текст", "type": "text", "editor": "markdown" }
      ]
    }
  ]
}
```

Правила, которые держит `API_Feeds::checkSchema()`:

- колонка занята ровно одним полем, `code` уникален в пределах ленты;
- `code` — латиница, цифры, дефис, подчёркивание; `id`, `feed_id`, `created_at`,
  `updated_at` зарезервированы;
- тип поля должен соответствовать роду слота (`COLUMN_TYPES`), для `__data` —
  входить в `DATA_TYPES`;
- `editor` — только `html`, `markdown`, `plain`;
- у поля связи обязателен `relation`, целевая лента должна существовать, а
  `display_code` — быть занятой колонкой в ней;
- `unique` нельзя для поля в `__data`;
- переименовать `code` нельзя, если в ленте уже есть записи (`code_locked`);
- `slugFrom` — либо пусто, либо `code` поля, сидящего в строковом слоте: из
  абзаца текста или из даты адрес получится мусорный;
- `orderBy` — либо пусто, либо `code` поля из строкового или датового слота:
  сортирует база, а у поля `__data` своей колонки нет;
- `order` приходит из админки согласованным со схемой и не проверяется.

Неизвестные ключи поля проходят насквозь: админка кладёт туда своё
(`showOnList`, `listFormat`, `minWidth`, `ratio`).

### Ключи админки

Сервер их не проверяет, но смысл у них закреплённый.

**`order`** — плоский массив имён, задаёт порядок колонок в списке записей. Имя,
начинающееся с `__`, — физическая колонка слота, любое другое — `code` поля
внутри `__data`. Двусмысленности нет: `code` не может начинаться с `__`.

**`slugFrom`** — `code` строкового поля, из которого считается адрес записи. На
экране ленты это переключатель в таблице строк: источник один, выбор второго
снимает первый, повторный выбор снимает совсем. Внутри админка держит его
колонкой, а в схему пишет `code`: пока в ленте нет записей, `code` разрешено
менять, и переключатель не должен слетать от переименования поля.

**`orderBy` и `orderDir`** — с какого порядка открывается список записей:
`code` поля и `asc` либо `desc`. Пусто — свой порядок ленты, `__position`, как
было. Задаётся на экране колонок списка отдельным выбором.

Отдельным, а не первой колонкой списка, хотя так не пришлось бы рисовать ничего
нового: колонку двигают ради удобства чтения, и порядок записей от этого ехать
не должен — по той же причине в списке разведены галочка группового режима и
ручка перетаскивания. К тому же сортировать нередко надо по полю, которого в
списке нет вовсе, а первой колонкой чаще всего стоит картинка или связь.

Порядок этот начальный: стрелки в шапке списка работают как работали, и выбор
оператора живёт до перезагрузки экрана. Перетаскивать записи по-прежнему можно
только в своём порядке ленты — в любом другом место строки ничего не значит.

Рядом с заголовком колонки «Видимость» стоит глаз, и это отбор, а не настройка
схемы: все записи, только скрытые, только видимые — по кругу. Скрытые первыми,
их и ищут: заготовка, которую забыли открыть, иначе не находится ничем, кроме
листания.

Иконка показывает не то, что на экране, а то, что даст нажатие: перечёркнутый
глаз — будут скрытые, зелёный — видимые, серый — снова все. Что показано сейчас,
и без иконки видно по строкам. Условие уезжает в тот же `filter`, что и поиск,
отдельным
`{"field": "__visible", "op": "=", "value": false}` — поле системное, и в выборе
полей поиска его нет.

**`viewArticle`** — имя статьи, которой сайт показывает запись. Из него и `slug`
записи собирается её адрес, `/<статья>/<slug>`, и по этому адресу в форме записи
стоит ссылка «Посмотреть». Пусто — ссылки нет, и это умолчание: лента может
вообще не иметь своей страницы.

Хранится имя статьи, а не готовый адрес: адрес считается каждый раз, поэтому
переименование статьи ломает ссылку видимо, а не уводит её в никуда. Ссылки нет
и у записи без `slug` — «Посмотреть», ведущее на статью без записи, хуже, чем
ничего.

Существование статьи не проверяется: лента и статья заводятся в разном порядке,
и запрет мешал бы больше, чем помогал.

**`showOnList`** — показывать ли поле колонкой в списке. Ключа нет — **поле
показывается**, для всех типов, включая тексты и картинки. Из двух зол выбрано
меньшее: лишняя колонка видна, и оператор сам сообразит её убрать, а скрытое по
умолчанию поле просто не появится, и догадаться о нём неоткуда. Выключить можно
все поля сразу — строка списка остаётся рабочей, у неё есть перетаскивание и
карандаш.

**`listFormat`** — маска даты в списке, у слотов `__date_N` и у полей `__data`
типа `datetime`. Буквы взяты у PHP и значат то же самое, поэтому маску можно без
перевода поставить в блейд:

| Буква | Значение |
| --- | --- |
| `d` | день с ведущим нулём |
| `m` | месяц с ведущим нулём |
| `y` | год двумя цифрами |
| `Y` | год четырьмя цифрами |
| `H` | часы, 24-часовые |
| `i` | минуты |
| `s` | секунды |

Остальные символы выводятся как есть. Набор букв ограничен намеренно: полный
список PHP тянет названия дней и месяцев, а они английские. Ключа нет — значение
показывается как лежит в базе, `2028-01-26 13:33:00`. Не разобралось как дата —
показывается как есть, пусть видно, что в поле.

Ни `showOnList`, ни `listFormat` на вывод сайта не влияют: там состав полей и
формат пишет блейд.

### Строковое поле

`admin/js/app/feedAdmin/dataStringField.vue` — textarea вместо однострочного
инпута. Слот держит 255 символов, а в строку столько не видно: конец уезжает за
край, и оператор правит вслепую. Поле растёт под текст (`height: auto`, потом
`scrollHeight` — без сброса высота умеет только расти), прокрутки внутри нет.

Счётчик появляется за тридцать символов до потолка и краснеет вместе с рамкой,
когда потолок пройден. Сохранить при этом дают: обрежет базу, а не форму —
поле varchar(255) и молча отрезает хвост. Запрет здесь означал бы правило,
которого нет ни в схеме, ни на сервере.

`max` нулём счётчик выключает: строка внутри `__data` лежит в json, и потолка у
неё нет.

### Редактор текста

Чем правится текстовое поле, решает ключ `editor`. Все три варианта живут в
`admin/js/app/feedAdmin/dataTextField.vue`:

| `editor` | Что видит оператор |
| --- | --- |
| `plain` | обычная textarea, моноширинный шрифт |
| `markdown` | Ace в режиме markdown, под ним предпросмотр |
| `html` | три вкладки: **result**, **WYSIWYG**, **ace** |

Предпросмотр markdown считает не браузер, а сервер, командой `mdToHtml` — тем же
вызовом, каким запись рендерится на сайте. Предпросмотр, считающий текст сам,
рано или поздно разошёлся бы со страницей.

**Визуальный редактор вынесен в отдельный компонент** `htmlEditor.vue`. Наружу у
него один `v-model` со строкой html — ни настроек движка, ни его событий, ни его
классов. Поменять движок значит переписать этот файл, `dataTextField` и всё
остальное не сдвинется. Вкладки `result` и `ace` от движка не зависят и остались
снаружи.

Внутри — TipTap (ProseMirror). Разрешённая разметка описана схемой редактора, и
она же решает, что переживёт вставку из Word: чего в схеме нет, то при разборе
отваливается само.

| Есть | Нет |
| --- | --- |
| абзац, перенос строки | заголовок `h1` |
| `h2`, `h3` | цвет, фон, шрифт, размер |
| жирный, курсив, зачёркнутый | выравнивание, отступы |
| списки маркированный и нумерованный | подчёркивание |
| цитата | код и блок кода, линейка |
| ссылка | картинка из буфера |

Заголовка первого уровня нет намеренно: на странице он один, и он выше записи.
Вставленный `h1` схема превращает в обычный абзац. Подчёркивание убрано потому,
что в вебе подчёркнутый текст читается как ссылка. Картинка из буфера
выбрасывается: Word кладёт её base64 или ссылкой на свой временный файл — первое
раздувает запись, второе не откроется.

Руками остаётся одна правка вставки, `transformPastedHTML`: Word и Google Docs
ставят неразрывный пробел вместо каждого обычного, а строка из таких пробелов не
переносится и вылезает за край колонки.

Панель своя целиком: движок даёт команды, кнопки нарисованы иконками
FontAwesome. Адрес ссылки вводится строкой под панелью, а не окном браузера:
`prompt` вешает страницу и выглядит чужеродно. Пустой адрес снимает ссылку.

Старые записи чинятся сами: разметка, которой нет в схеме, отваливается при
открытии, и запись сохраняется уже чистой. Обратной стороной — открыл, сохранил,
и часть чужого оформления пропала.

### Текст записи: подстановки и компоненты

`FeedText`, вход из блейда — `MproHelper::feedText($item, 'body')`. Делает две
вещи.

**Подстановки** `#code#` и `#code.key#` — по всему тексту. Нет такого поля —
метка остаётся буквами: решётки пишут и в обычном тексте. Поле есть, а ключа
внутри нет — пусто: `alt` картинки заполняют не всегда, и хеши не должны
вылезать на страницу.

**Теги компонентов** — по одному:

```html
<x-magic::resize_abs_img :file="#img1.path#" width="400" />
```

Атрибут с двоеточием получает php-литерал, поэтому массив приезжает массивом;
без двоеточия — текст. Значение с двойной кавычкой уходит связанным само: иначе
оно оборвало бы атрибут, а сущности Blade внутри не читает. Литерал собирается
`var_export`, кавычки внутри — через `chr(34)`.

В Blade попадает **только тег**. Текст вокруг не компилируется, поэтому `{{ }}` и
`@php`, написанные оператором, остаются буквами, а разница между блейдом и
текстом из админки сохраняется. `{{`, `{!!` или `@буква` внутри самого тега —
тег не рендерится, на его месте `unsupported` и запись в лог.

Порядок такой: сперва `Blade::compileString()`, и только потом `Blade::render()`.
Компиляция разрешает имя компонента, а падение рендера Laravel заканчивает
вызовом `flushState()` — тот чистит секции всей внешней страницы, и она валится
уже на своём `@endsection`. Ошибка компиляции безопасна и даёт `unsupported`.

Белого списка компонентов нет: тегом зовутся blade-компоненты пакета, их набор
пишет разработчик, чужой статьи среди них не бывает.

В визивиге тег хранится экранированным, `&lt;x-magic::… /&gt;` — редактор видит
текст и не трогает его. Сырой тег там писать нельзя: неизвестный тег в html не
самозакрывается, и весь текст после него уехал бы внутрь.

## Слой логических имён

Это главное место модуля, дальше всё крутится вокруг него.

### На записи

`FeedItem::getAttribute()` / `setAttribute()` разбирают имя так:

1. физическое (`__`-имя или уже существующий атрибут) — отдаём Eloquent как есть;
2. есть в карте слотов — читаем/пишем соответствующую колонку;
3. есть среди кодов `__data` — лезем внутрь json, не затирая соседей;
4. иначе — обычный Eloquent (связи, аксессоры).

Имена методов при этом не проверяются намеренно: поле вполне может называться
`feed` или `media`, и схема должна побеждать связь с тем же именем.

Карта берётся из `Feed::schemaMapOf($feedId)` — статический кэш по id ленты.
Иначе страница из сотни записей стоила бы сотню запросов.

### На запросе

`FeedItemBuilder` переводит имена в `where`, `whereIn`, `whereNull`, `orderBy`,
`value`, `pluck`, `update`. Схему он получает от `Feed::items()` через
`forFeed($feed)`; у голого `FeedItem::query()` схемы нет, и там живут только
физические и системные колонки — так работает внутренний код модуля.

Неизвестное имя не уезжает в базу, а бросает исключение: в лучшем случае это была
бы ошибка SQL, в худшем — попадание в чужую колонку.

Вложенный `where(fn ($q) => …)` получает схему отдельно, иначе логические имена
работали бы снаружи скобок и ломались внутри.

### Устаревание карт

Схема меняется — карты, розданные раньше, становятся ложью. Поэтому у `Feed` есть
счётчик `schemaGeneration()`: он растёт на каждом сохранении и удалении ленты, а
запись хранит номер поколения вместе с картой и перечитывает её, когда номера
разошлись. Просто чистить кэш мало: объекты, уже получившие копию, о ней не
узнают.

`newInstance()` и `newFromBuilder()` передают карту дальше **вместе с поколением**
— переставлять его там нельзя, иначе устаревшая карта выглядела бы свежей.

`fill()` первым делом ставит `feed_id`: порядок ключей в массиве ничего не
обещает, а без ленты остальные имена не разрешатся.

## Уникальность, видимость, безопасность

**`unique` проверяется кодом, а не базой.** Уникальных индексов на слоты нет и
быть не может: слот общий для всех лент, и `UNIQUE (feed_id, __string_2)`
заставил бы второй строковый слот быть уникальным везде — а другая лента держит
там название отдела, и двух сотрудников из одного отдела туда уже не запишешь.
Поэтому проверка идёт запросом, в транзакции с блокировкой строки ленты, и
только для полей физических колонок. Скрытые записи в проверку входят:
`__visible = false` означает «не показывать», а не «освободить значение».

Настоящий уникальный индекс во всём модуле один — `magicPro_feeds.code`.

**`__visible` не применяется автоматически.** Модуль его не подставляет ни в один
запрос: владелец должен уметь открыть скрытую запись по адресу и посмотреть, как
она будет выглядеть. Решение о показе принимает блейд или контроллер. Плата —
фильтр можно забыть, и черновик уедет на сайт.

**HTML оператора не чистится.** Значения строковых и текстовых полей сохраняются
ровно так, как введены; автоматической очистки на сервере нет. `editor` (`html`,
`markdown`, `plain`) описывает только интерфейс редактирования, а не правила
безопасности. Визуальный редактор действительно пропускает лишь свою разметку,
но это удобство, а не защита: соседняя вкладка `ace` отправит любой html, и API
примет его без вопросов.
Следствие прямое: вывели введённое через `{!! !!}` — оператор может вставить
`<script>`. Это сознательная ответственность разработчика и доверенного
оператора, модуль в неё не лезет. Исключение — `MproHelper::mdToHtml()`, он режет
html и небезопасные ссылки, потому что рассчитан именно на операторский текст.

## Позиции, транзакции, блокировки

- `__position` считается в `FeedItem::nextPosition()`: строка ленты берётся
  `lockForUpdate()`, затем `max + 1`. Блокировка живёт до конца транзакции, и
  поэтому `save()` новой записи сам заворачивается в транзакцию — иначе гарантии
  нет, а одинаковые позиции ломают пагинацию: одна запись показывается дважды,
  другая нигде.
- `itemMove` перенумеровывает **всю** ленту с нуля, `groupMove` и `feedMove` —
  свои списки. Дырки и повторы визуально ничего не ломают, но после них никто не
  скажет, что значит «позиция 3».
- `itemSave` держит транзакцию с блокировкой строки ленты: две параллельные
  записи иначе обе пройдут проверку уникальности и обе запишут одно значение.

## Удаление

Удаление физическое. Корзины, мягкого удаления и восстановления нет.

**Главное правило: запись, на которую ссылаются через `link`, не удаляется.**
Сначала снимают ссылку, потом удаляют. Проверка — прямой `OR` по всем слотам
связей; отдельных индексов под неё не заводили, операция редкая и скорость её не
важна.

Со стороны оператора это выглядит так: не держит никто — подтверждение и
удаление вместе с файлами; держат — окно со списком держащих, у каждой своя
корзинка. Окно рекурсивное: оператор спускается по цепочке до записей, которые
никто не держит, и разбирает её снизу вверх.

`__position` соседей после удаления не пересчитывается: дырка в нумерации ничего
не ломает, новая запись получает `max + 1`.

Очистка и удаление ленты идут проходами: за проход удаляется всё, что никто не
держит, и проход повторяется, пока удалилась хоть одна запись. Это из-за цепочек
— пока жива C, не удалить B, пока жива B, не удалить A. Остаётся только то, что
держат ссылки из других лент; при удалении ленты в этом случае описание ленты
тоже остаётся.

### Кольца запрещены

Если A ссылается на B, то B не может ссылаться на A — ни напрямую, ни через
цепочку. Проверка идёт при сохранении записи, ошибка `link_cycle` несёт путь
кольца.

Без запрета обе записи становятся вечными: каждая держит другую, ни одна не
удаляется, проходы очистки на них останавливаются, а рекурсивное окно водит
оператора по кругу. Удалить их можно было бы только правкой записи, то есть в
обход всей механики удаления.

### Механика

- `FeedItem::delete()` сначала проверяет входящие ссылки и только потом зовёт
  родителя. Проверка стоит в самом методе, а не в обработчике `deleting`: на то же
  событие подписана медиатека, и порядок подписчиков решал бы, не сотрутся ли
  файлы у записи, которую удалить нельзя.
- `FeedItemBuilder::deleteEach()` — групповое удаление: идёт по одной записи
  через модель, удерживаемые пропускает и возвращает число удалённых. Обычный
  `delete()` builder-а оставлен как есть, иначе удаление модели (`newModelQuery()
->delete()`) звало бы само себя без конца.
- `feedClear` и `feedDelete` крутят `deleteEach()` в цикле: удалённая запись могла
  быть последней, кто держал другую.
- Массовые удаления через query builder события моделей не поднимают — проверки
  придётся повторять руками.
- `FeedGroup` не даёт удалить группу по умолчанию (`DEFAULT_ID = 1`) и непустую
  группу. Оба запрета на модели, а не только в команде API: лента не может жить
  без группы, и это не должно зависеть от того, каким путём пришли к удалению.

## API

`AbstractFeedApi::run()` никогда не бросает: ошибка становится ответом
`status / errorMsg / data / request`. Исключение — `FeedValidationException`: она
несёт разбор по полям, он уезжает в `errors`, а заодно дописывается в `errorMsg`,
потому что клиент показывает тостом именно его.

`runOrFail()` для внутренних вызовов диспетчеризует команду напрямую, минуя
`run()`: так сохраняется исходное исключение вместе с полями.

Тексты ошибок — в словаре пакета, `lang/{locale}/messages.php`, префикс
`feed_err_`, обращение через `API_Feeds::err('feed_not_found')`. Неизвестный ключ
возвращает сам ключ: пропажа перевода должна быть видна.

## Индексы

Все статические, создаются миграцией. Админка никогда не делает `ALTER TABLE`.

`magicPro_feed_items`, 19 штук:

| Индекс | Для чего |
| --- | --- |
| `(feed_id, __visible, __position, id)` | главный список ленты, ручной порядок |
| `(feed_id, __visible, created_at, id)` | список по дате создания |
| `(feed_id, __visible, __date_N, id)` × 3 | список и фильтр по датам |
| `(feed_id, __visible, __link_N, __position, id)` × 3 | записи по связи, по порядку |
| `(feed_id, __visible, __bool_N, __position, id)` × 3 | списки по флагам |
| `(feed_id, __string_N)` × 5 | поиск записи по строке |
| `(feed_id, __bigint_N)` × 3 | поиск записи по числу |
| `(feed_id, __slug)` `UNIQUE` | открыть запись по адресу, он же держит уникальность |

`magicPro_feeds`: `UNIQUE (code)` и `(group_id, position, id)` — второй
обслуживает главный экран админки и заодно покрывает внешний ключ, потому что
стоит первой колонкой. `title` и `schema` не индексируются: по названию не ищут,
схема — json.

`magicPro_feed_groups`: `(position, id)`. Таблица в единицы строк, читается
целиком и всегда по порядку.

### Почему именно так

**Порядок колонок: `feed_id`, потом равенство, потом сортировка, в конце `id`.**
Составной индекс читается слева направо, пропускать колонки нельзя: не задали
`__visible` — до `__date_1` база не дойдёт и пойдёт читать таблицу.

**`id` в хвосте сортировочных — про корректность, не про скорость.** При
одинаковых `__position` порядок строк не определён, и на границе страниц одна
запись покажется дважды, а другая нигде.

**`__visible` стоит только в списковых индексах.** Поиск конкретной записи идёт
без него: запись по адресу берётся независимо от видимости, иначе не работает
предпросмотр черновика. Поставь `__visible` вторым в поисковом индексе — и запрос
без него до `__string_2` не доберётся.

**Флаги и связи — всегда вместе с сортировкой.** Голый
`(feed_id, __visible, __bool_1)` строки отберёт, но сортировать их придётся в
памяти.

**Строковые и числовые — без сортировки.** По ним ищут конкретную запись по
равенству: slug, артикул, номер документа.

**`__data` не индексируется вовсе** — по ней и так запрещены `where` и `orderBy`.

**Проверка «на эту запись ссылаются» индексами 6–8 не пользуется:** они
начинаются с `feed_id`, а ищут по самой колонке, через `OR` по всем слотам, и
ленту при этом не знают.

**Индексы не зависят от схемы.** `__string_2` у блога хранит slug, у сотрудников
— отдел; индекс один и работает для обоих. Поэтому список фиксирован и не растёт
при появлении новых лент.

## Файлы

Медиатека — `spatie/laravel-medialibrary` в `require` пакета, версия `^11.0`. Она
требует, чтобы запись была Eloquent-моделью, — это заложено в архитектуру.

Коллекция называется как `code` поля,
одно поле — одна картинка: перед загрузкой коллекция чистится, старый файл уходит
вместе с ней. Метаданные (`path`, `x`, `y`, `mime`, `size`) пишутся в
`__data` рядом с тем, что ввёл оператор.

`alt` приходит параметром той же команды и ложится туда же, потому что файл
попадает в базу сразу, а запись может остаться несохранённой. Пустой параметр
подпись не трёт: перезалив её переживает.

`path` — адрес без хоста, `/storage/magicFeed/19/1.png`. Он годится и в `src`, и
ресайзеру, который ждёт путь от `public`, а домен в него не входит, поэтому
переезд проекта ничего не ломает.

Полного адреса рядом нет намеренно: он повторял бы то же самое, только с хостом.
Раньше писался ключ `url`; при загрузке он теперь гасится, а из уже сохранённых
записей убран.

`FeedPathGenerator` кладёт файлы в подпапку `magicFeed`, а не в корень диска.
Регистрируется он на модель, в `MagicServiceProvider`:

```php
PathGeneratorFactory::setCustomPathGenerators(
    FeedItem::class,
    FeedPathGenerator::class
);
```

Именно на модель, а не в `media-library.path_generator`. Глобальная настройка одна
на всё приложение, и если её забрать, чужие файлы поедут в наш `magicFeed`.
Проверено на живом проекте: рядом стоял второй пакет с медиатекой, его картинки
лежали под своим префиксом, а ссылки строились с нашим — страница отдавала 403.
Регистрация по модели проверяется раньше глобальной, поэтому каждый пакет отвечает
только за свои файлы, и порядок загрузки провайдеров ничего не решает.

## Что учесть при изменениях

- **Новый слот** — это миграция, константа в `FeedItem` и индексы. Старую миграцию
  не трогать.
- **Смена смысла колонки под живыми записями** ломает данные молча: схема лишь
  переименовывает, никакого переноса значений нет.
- Любое изменение схемы должно проходить через сохранение ленты — только так
  вырастет `schemaGeneration` и разойдутся устаревшие карты.
- Добавляя команду, дописать её и в `$map`, и в словари (если у неё свои ошибки).
- Фронт админки собирается отдельно: `cd packages/dixipro/magicpro && npm run build`.
