# AI-агент: как устроено

## Где что лежит

| Что | Где |
| --- | --- |
| настройки | `src/Ai/AiConfig.php` |
| промпты | `src/Ai/AiPrompts.php` |
| сеанс | `src/Ai/AiSession.php` |
| API админки | `src/Ai/API_Ai.php` |
| страница | `admin/views/mcp.blade.php`, `admin/js/app/mcpAdmin/` |
| маршруты | `admin/web.php`, `magic.mcp` и `/a_dmin/api/mcp` |
| уборка | `src/Scheduling/MagicProSchedule.php`, задача `magicpro:aiCleanup` |

Базы у раздела нет. Всё состояние — один файл на сеанс, сам сеанс `tmux` и имя
сеанса в браузерной сессии.

## Структура данных

### Настройки

`storage/app/private/ai-sessions/configAI.php`, php-файл, возвращающий массив.
Читается один раз на запрос.

Кладёт его установка: `Installer::checkAiConfig()` копирует образец из пакета,
`src/Config/configAI.php`, если своего файла у сайта нет. Проверка идёт на
каждом заходе в админку, а не только при первой установке: файл приезжает с
новой версией пакета, а сайт, поставленный раньше, о нём не знает. Синхронизации
дальше нет — сайт правит свою копию, образец её не догоняет.

Пароль в образце пустой, и это выключатель: `AiConfig::on()` — файл есть и
пароль не пуст. Раздел приходит выключенным, включает его человек.

| Ключ | Тип | Умолчание | Что значит |
| --- | --- | --- | --- |
| `password` | строка | нет | дополнительный пароль запуска; пустой запрещает запуск |
| `agents` | список агентов | `[]` | агенты; один агент можно писать ключом `agent` без списка |
| `poll_interval` | целое, мс | `1000` | как часто браузер просит новый вывод, не меньше `200` |
| `session_timeout` | целое, сек | `600` | молчание браузера, после которого сеанс закрывается |
| `session_kill_timeout` | целое, сек | `720` | молчание браузера, после которого сеанс убивается |

Агент:

| Ключ | Тип | Что значит |
| --- | --- | --- |
| `name` | строка | имя; в имя сеанса идут только латинские буквы и цифры из него |
| `startCommands` | список | чем запускать |
| `exitCommands` | список | чем завершать |
| `cwd` | строка | рабочая папка; пусто — `base_path()` |
| `env` | карта | переменные окружения сеанса |

Имя переменной окружения уходит в командную строку `tmux` как написано, поэтому
пропускается только то, что вообще может быть именем: буква или подчёркивание,
дальше буквы, цифры и подчёркивания. Значение экранируется при сборке команды и
может быть любым.

Команда пишется подписью и командной строкой: `['Заново' => 'codex']`. Список из
таких пар и обычная карта `'Заново' => 'codex'` читаются одинаково — файл
набирают руками, и обе записи выглядят правильными.

Номер команды в списке — то, чем её выбирает браузер. Порядок в файле поэтому
имеет значение: перестановка строк меняет то, что выберется по старому номеру.

### Промпты

`storage/app/private/ai-sessions/commands.json`, список объектов с полями `name`
и `text`. Правится из админки целиком и целиком же перезаписывается.

json, а не php, хотя настройки рядом — php: этот файл пишет браузер, а php-файл,
написанный браузером, сайт потом выполняет. json выполнить нельзя, в этом вся
причина. `configAI.php` остаётся php потому, что его кладут руками через ssh.

Битый json, не тот формат, нет файла — пустой список: раздел обязан открыться,
даже если файл поправили руками в бессмыслицу. При записи выбрасываются строки
без имени или без текста, имя режется по 120 знакам, текст по 20000, список по
200 строкам.

Список общий на сайт: администраторов немного, и удачный промпт полезнее общим,
чем спрятанным.

### Сеанс

Имя сеанса собирается при запуске: имя агента, `id` администратора и `time()`
через дефис — `codex-1-1756400000`. Оно же имя сеанса `tmux` и имя файла,
поэтому на входе в API оно проверяется: латинские буквы, цифры и дефис, не
длиннее 64 знаков. Ничего другого в имени быть не может — оно становится
аргументом shell-команды и именем файла.

Дефисы не для красоты: имя — единственное место, которое знает хозяина сеанса.
Базы нет, а браузерная сессия знает только то, что завела сама. Без
разделителей `codex` + `11` + `788…` и `codex` + `1` + `1788…` — одна и та же
строка.

| Файл | Что в нём |
| --- | --- |
| `storage/app/private/ai-sessions/poll/<сеанс>.log` | время последнего запроса браузера за экраном |

Файл один, и он не про вывод: вывод живёт в самой пане `tmux`, а этот файл
говорит, что за паной ещё смотрят. Он же список сеансов, по которому ходит
уборка. Удаляется вместе с сеансом.

### Браузерная сессия

Имена запущенных сеансов лежат в сессии Ларавела, ключ `magicAiSessions`. Любая
команда, кроме `config` и `start`, требует, чтобы имя было в этом списке.

Пароль так работает не только на запуск: чужое имя сеанса не примут, кто бы его
ни прислал.

## API

`POST /a_dmin/api/mcp`, `magic.auth`, ответ обычной формы `AbstractApi`.

| Команда | Параметры | Ответ |
| --- | --- | --- |
| `config` | — | `ready`, `password`, `path`, `agents`, `pollInterval` |
| | | у агента: `name`, `start`, `exit`, `rules`, `rulesPath` |
| `start` | `agent`, `command_index`, `password` | `instance`, `pollInterval` |
| `output` | `instance` | `output`, `status`, `error` |
| `reread` | `instance` | `output`, `status`, `error` |
| `send` | `instance`, `text` | `ok` |
| `close` | `instance`, `command_index` | `alive` |
| `killAll` | — | `killed` |
| `prompts` | — | `prompts` |
| `promptsSave` | `prompts` | `prompts` — что легло в файл |

`command_index`, а не `command`: слово `command` занято именем самой команды
API.

`prompts` и `promptsSave` не спрашивают ни пароля, ни имени сеанса: это текст для
оператора, а не путь к агенту. Входа администратором хватает.

В `config` уходят только подписи команд, `agents[].start` и `agents[].exit` —
списки строк. Командные строки на экран не попадают, браузер выбирает номером.
Сам пароль тоже не уходит: `password` — это «он задан», а не он.

`status` — `running` или `stopped`. Получив `stopped`, страница показывает
последний экран, прячет управление и оставляет его висеть.

`output` отдаёт экран целиком, а не добавку к прежнему: у агента нет добавки,
он перерисовывает окно. Поэтому и позиции в запросе нет.

## Правила агента

`AGENTS.md` в рабочей папке агента. Нет файла — `start` бросает исключение, и
сеанс не заводится; страница говорит об этом заранее, до нажатия, и прячет
кнопку запуска.

Проверяется только наличие. Что внутри — дело агента и того, кто файл писал:
это правила, а не настройка. Образец — `docs/ru/aiAgent/AGENTS.example.md`, он
не копируется никуда сам: файл принадлежит сайту, и пакет, перезаписывающий его
при обновлении, стёр бы то, ради чего он заведён.

Ищется он в `cwd` агента, то есть там же, где агент его и читает. Переехала
рабочая папка — переезжают и правила.

## Запуск

```
tmux set-option -wg alternate-screen off \; set-option -g history-limit 10000 \
   \; new-session -d -s <сеанс> -c <папка> -e KEY=VAL -x 200 -y 50 \
        /bin/sh -c '<команда>; sleep 1' \
   \; set-option -t <сеанс> remain-on-exit on
```

Всё одним вызовом и в этом порядке. Настройки — до `new-session`, потому что
пана читает их при создании, и отдельным вызовом их не поставить: сервер `tmux`
без сеансов не живёт, и всё, что на него положили, умирает раньше, чем появится
пана.

**`alternate-screen off` — это и есть история.** Агент рисует себя как `vim`:
уходит в альтернативный экран, а у того буфера прокрутки нет вовсе — то, что
ушло за верхний край, не существует нигде, и `capture-pane -S -` отдаёт ровно
тот же экран. Запрет оставляет вывод в обычном экране, откуда он уезжает в
историю на `history-limit` строк.

Агент — программа терминала: ей нужен терминал, она живёт дольше запроса и
обязана дожить от одного опроса браузера до другого. Сеанс `tmux` — это её
жизнь.

**Команда идёт отдельными аргументами, через явный `/bin/sh`.** `default-shell`
у `tmux` берётся из `passwd`, php работает от `www-data`, а у него в `passwd`
стоит `/usr/sbin/nologin`. Отданная одной строкой команда уходит в `nologin` и
не запускается вовсе: `new-session` отвечает успехом, а сеанс умирает в ту же
секунду и без единого слова в файле. Отдельными аргументами `tmux` зовёт
`execvp` и `default-shell` не трогает.

**`remain-on-exit` ставится тем же вызовом.** Агент, падающий на первой строке,
падает раньше, чем до него дошёл бы второй вызов, а с уже включённым параметром
его пана остаётся стоять — с жалобой на ней. Отсюда берётся экран законченного
сеанса.

**После команды стоит `sleep 1`.** `tmux` читает пану в своём цикле и отпускает
её вместе с процессом: агент, сказавший одно слово и вышедший, говорит его в
никуда — пана мертва и пуста. Проверено: `nosuchagent` без ожидания оставляет
пустой экран, с ожиданием — строку `command not found`. Секунды хватает, а
«закончился» страница узнаёт всё равно не раньше следующего опроса.

**Папка и окружение — из настроек, а не из кода.** `-c` и `-e` умеет сам `tmux`
(`-e` — с версии 3.2). Переменная ставится сеансу, а не приписывается к команде:
она достанется и тому, что агент запустит потом, и её не приходится сперва
читать как строку шелла.

Php отдаёт агенту своё окружение, а оно почти пустое: `HOME` от `www-data`,
`PATH` службы. Всё, что агенту нужно другое, пишется в `env` настроек.

Размер терминала задан явно: отсоединённый сеанс `tmux` — 80×24, и агент
переносит по этой ширине, смотрит на него кто-нибудь или нет.

Команда агенту уходит двумя вызовами:

```
tmux send-keys -l -t <сеанс> <текст>
tmux send-keys -t <сеанс> Enter
```

`-l` — буквально: набранное должно дойти как набрано, а без `-l` `tmux` прочёл
бы внутри текста `Enter` или `C-c` как клавиши. `Enter` поэтому отдельно.

## Вывод

```
tmux capture-pane -p -J -S -200 -t <сеанс>   # экран и 200 строк над ним
tmux capture-pane -p -J -S -    -t <сеанс>   # всё, что помнит история
```

Экран спрашивается у `tmux`, а не собирается здесь. Агент не печатает строки: он
двигает курсор и перерисовывает окно, и запись этого потока — не текст, а
указания терминалу. `tmux` и есть терминал, который их выполняет, поэтому
`capture-pane` отдаёт готовую картинку, уже разложенную по строкам.

Так было не сразу: первая версия писала поток трубой (`pipe-pane`) и вырезала из
него управляющие коды. Выходила каша — коды переноса строки там нет, есть
«поставить курсор в строку 12», — и одна и та же шапка повторялась столько раз,
сколько агент перерисовал окно.

`-J` склеивает строку, не влезшую в ширину: это одна строка агента, разбитая
терминалом, и на странице ей нет причины оставаться разбитой.

Хвост пустых строк отрезается: пана высотой в пятьдесят строк, и то, что ниже
последней строки текста, — не молчание агента, а пана. Пустые строки внутри
схлопывает уже страница, там же, где красит вопрос жирным.

Опрос берёт экран не один: ответ длиннее пятидесяти строк уезжает вверх ещё
пока пишется, и на экране остаётся его хвост. Поэтому в живом опросе 200 строк, а
«Перечитать» отдаёт всё, что помнит история, — 10000 строк.

## Закрытие

**Жив ли агент.** Кончиться можно двумя способами, и спрашивается сразу про оба:
`display-message -p '#{pane_dead}'`. Сеанса нет вовсе — `tmux` отвечает ошибкой.
Агент вышел, а пана осталась стоять по `remain-on-exit` — сеанс есть, `pane_dead`
равен `1`, и последний экран ещё можно прочесть.

**Закрыть.** Агент жив — уходит команда из `exitCommands`, и он выходит сам: у
него своё состояние, и убитый процесс бросает его на середине мысли. Агент уже
вышел — сеанс убивается и файл удаляется: пана держалась ради последнего экрана,
а он прочитан.

Отсюда порядок в опросе: сперва спрашивается жизнь, потом снимается экран, и
только потом мёртвый сеанс отпускается.

**Убить.** `tmux kill-session`, файл удаляется. Последнее средство уборки.
Жизнь перед этим спрашивается только ради лога: убивать надо и мёртвую пану — её
держит `remain-on-exit`, — но `kill` в логе должно значить, что прервали живого.

**Убить свои.** `killAll` проходит по всем сеансам администратора и убивает
каждый. Единственная команда без проверки по браузерной сессии — её и просят
тогда, когда та проверка не помогает: вкладка, заведшая сеанс, закрыта, а агент
всё ещё держит свой тред и не пускает в него следующий запуск. Дальше сеансов
этого администратора убийство не достаёт: чужие отсеиваются по `id` в имени, не
наши — по имени агента, которого нет в настройках.

Сеансы ищутся в двух местах сразу, файлы опроса и `tmux list-sessions`: файл
может остаться без сеанса, сеанс без файла. И то и другое — мусор, и убрать надо
и то и другое.

**Уборка.** Задача `magicpro:aiCleanup` раз в минуту смотрит все файлы опроса —
когда браузер в последний раз просил экран. Молчание дольше `session_timeout` —
закрыть, дольше `session_kill_timeout` — убить.

Каждый тронутый сеанс пишется в `storage/logs/aiSession.log`: это единственное
место раздела, где что-то происходит без свидетелей. Строка говорит, что было
сделано и сколько сеанс молчал.

| `stage` | Что случилось |
| --- | --- |
| `close` | агент был жив, ему ушла команда завершения |
| `gone` | агент уже кончился сам, осталась мёртвая пана — её и убрали |
| `kill` | молчал дольше `session_kill_timeout` и был жив: прервали |
| `cleanup` | на этом сеансе вышла ошибка; остальные она не задела |

К `close` и `kill` дописывается хвост экрана — пять последних непустых строк,
одной строкой, до 400 знаков. К `close` ещё и `sent`: что именно ушло агенту.

Это единственное, по чему потом разбирать, почему агент не вышел по-хорошему.
Экран снимается до убийства и до того, как пана исчезнет: после `kill-session`
смотреть уже нечего. Обычные подозреваемые видны сразу — меню, которого агент
ждёт, его собственный вопрос, «unknown command» на нашу команду выхода.

Нет `configAI.php` — уборка молча уходит: без настроек не узнать ни таймаутов,
ни команды завершения.

## Вопросы

- Раздел лежит в `docs/ru/aiAgent/`, а на экране называется `MCP`. Может, назвать
  папку `mcpAgent` — или наоборот, переименовать раздел в админке.
- Сеанс не переживает перезагрузку страницы: имя нигде не хранится. Если хранить
  его в браузерной сессии и отдавать в `config`, вкладку можно было бы вернуть к
  живому агенту.
- Команда завершения не настроена, а сеанс жив — сейчас это ошибка «no exit
  command», и такой сеанс дожидается убийства по таймауту. Может, убивать сразу.
