# Импорт: как устроено

Как пользоваться — `use.md`. Здесь внутренности.

## Три класса

`MagicProSrc\Import\ImportTree` — разбор файла, план и работа.

`MagicProSrc\Import\Snapshots` — сохранённые состояния: запись, список, чтение,
удаление.

`MagicProSrc\Import\API_Import` — точка входа страницы, `POST /a_dmin/api/import`.
Наследник `AbstractApi`: карта команд, метод бросает исключение, форму ответа
собирает родитель.

Команды: `check`, `run`, `snapshots`, `save`, `delete`, `restore`. Скачивание —
отдельным `GET /a_dmin/api/importSnapshot`, потому что это файл, а не json.

## Данные

Своих таблиц у импорта нет: он пишет в `articles` через модель `Article`.

Файл — список записей, каждая запись это статья:

```text
npp          int      номер среди братьев
name         string   имя, оно же ключ переноса
title        string
controller   string
body         string
directory    bool
menuOn       bool
isRoute      bool
routeParams  array
parentName   string   имя родителя, не id
```

Всё, кроме `parentName`, — поля статьи; список полей, которые импорт берёт из
записи, лежит в `ImportTree::FIELDS`. Чего нет в списке, то игнорируется, в том
числе `id`: идентификаторы чужого сайта здесь ничего не значат.

Снимок — файл в `storage/app/private/magic/articles/`. Имя приходит из браузера:
`Snapshots::fileName()` выбрасывает из него всё, кроме латинских букв, цифр,
дефиса и подчёркивания, режет до восьмидесяти знаков и дописывает `.json`. Пустое
имя превращается в `Snapshots::stamp()` — `root_` и дата до минуты, то же, что
страница предлагает по умолчанию.

Маска имени, `Snapshots::MASK`, — единственная проверка пути: имя приходит из
браузера, и ничего, кроме своих файлов, класс не отдаёт и не удаляет. Список
сортируется по времени файла, а не по имени: имена теперь произвольные.

## Два прохода

`check()` и `run()` начинаются одинаково — с `plan()`. Первый на этом
останавливается и отдаёт отчёт, второй повторяет план и делает работу.

Между проходами не хранится ничего: файл живёт в браузере и приезжает в теле
каждого запроса. Тысяча записей считается за секунды, и городить временное
хранилище дороже, чем посчитать дважды.

## План

`plan()` идёт сверху вниз и на первой же беде останавливается:

1. `json_decode`, список ли это, не пустой ли.
2. `readRow()` на каждую запись: массив, есть имя, имя допустимое, имя не
   повторяется. Записи складываются в `$rows`, ключ — имя.
3. Частичный импорт и `root` в файле — отказ.
4. `order()` — порядок и верхушки.
5. `planPartial()` или `planFull()` — строки отчёта.

`order()` сперва собирает верхушки: записи, чьего родителя в файле нет. Дальше
раскладывает остальных слоями, пока раскладывается. Слой, в котором не сдвинулось
ничего, означает кольцо: `a` ждёт `b`, `b` ждёт `a`. Файл отвергается целиком.

Порядок нужен работе: родитель создаётся раньше ребёнка, иначе `parentId`
некуда взять.

`planPartial()` считает, что дуб потеряет: для каждого имени из файла ищется
статья дуба, и в удаление уходит она со всем поддеревом (`subtree()`, обход
слоями с защитой от кольца). Только после этого решается, куда цеплять верхушки:
родитель, попавший в удаление, за родителя не считается.

## Работа

`run()` держит всю базу в одной транзакции:

```php
$gone = DB::transaction(fn () => $mode === self::FULL ? $tree->applyFull() : $tree->applyPartial());
```

`applyPartial()` сносит посчитанное и поднимает берёзу в порядке `order()`.
Родитель ищется по имени: если он из файла — он уже создан, если из дуба — взят
на этапе плана. `npp` берётся из файла всем, кроме верхушек: верхушке ставится
`max + 1` среди детей нового родителя.

`applyFull()` сносит всё, кроме `id = 1`, и поднимает берёзу с номерами из файла:
сталкиваться уже не с чем. Запись `root` не создаётся, а вливается в корень
через `update()` — корень удалить нельзя, и второго корня быть не может.

`wipe()` возвращает имена удалённых. Они нужны потом: файлы удаляются по имени, а
после `delete()` спрашивать уже некого.

## Генерация файлов

`generate()` работает **после** коммита и одним прогоном по всему дереву:
`deleteMpro()` на удалённые имена, `createMpro()` на все существующие статьи.

Так сделано потому, что половина сгенерированных файлов после падения хуже, чем
их отсутствие. Внутри транзакции файлов не касаются вовсе, поэтому откат ничего
за собой не тянет; прогон в `catch` — страховка, а не починка.

`MagicProBuilder.php` подключается `require_once` в шапке файла — тем же
способом, что и в `Installer`.

## Отчёт

Строка отчёта — код и его части, а не текст:

```php
['code' => 'replace', 'params' => ['name' => 'about'], 'error' => false, 'done' => false]
```

Слова берутся в браузере, `t('imp_' . code, params)`: админка говорит на двух
языках, и словарь у неё один — `admin/js/app/CommonCom/translate.js`.

Коды плана: `replace` и `drop` — коллизии, `attach_root` — верхушка приземлилась
не туда, куда сказано в файле, `snapshot` — сохранённое состояние. Всё. Коды
отказа начинаются с `e_`: `e_json`, `e_not_list`, `e_empty`, `e_row`, `e_name`,
`e_name_bad`, `e_dup`, `e_root_partial`, `e_ring`.

Отчёта о том, что создаётся, нет намеренно: «статья поднимается из файла» — это
определение импорта, а не новость. Поэтому `planFull()` пуст: полный импорт сносит
всё и поднимает всё, перечислять там нечего.

После удачного второго прохода всем строкам ставится `done`, и страница пишет
рядом «сделано». Падежей никто не склоняет: строка та же, что была в плане.

## Страница

`admin/js/app/importAdmin/importAdmin.vue`, точка входа `admin/js/importAdmin.js`,
блейд `admin/views/import_tab.blade.php`.

Файл читается `FileReader` в строку и хранится в `ref`. Кнопка «Импорт» заперта,
пока `check` не вернул чистый ответ; смена файла запирает её снова.

## Экспорт

Не трогаем. Снимок — его же вызов:

```php
app(ImportExportController::class)->exportArticle(new Request(['id' => 1]))->getContent();
```

Поэтому снимок и файл экспорта — одно и то же, и импортируется любой из них.
