# Правила работы над MagicPro

Читать перед любой правкой кода. Это приказы, а не пожелания.

## Порядок работы

- Вопрос — это не задача. Спросили — ответь, ничего не делай: ни правок, ни
  чтения файлов, ни проверок. Действуй только по прямому указанию.
- Задача понятна — выполни ровно её, без дополнительных улучшений.
- Задача неоднозначна, не хватает данных или можно понять двояко — задай вопрос.
  Не угадывай и не придумывай недостающее.
- Считаешь, что нужна ещё работа, — сперва спроси, потом делай.
- Одна задача — одно действие. Один тест значит один тест, одна функция значит
  эта функция.
- Не добавляй подготовку, которой не просили: создание данных, вызовы соседних
  команд, лишние тесты и хелперы.
- Перед правкой скажи коротко, что изменишь. После — перечисли файлы и что в них
  поменялось.
- Отвечай по-русски. Код, комментарии и сообщения коммитов — по-английски, как в
  существующем коде.

## Без разрешения не делать

- Не лезть в базу данных. Никаких записей, миграций, `artisan migrate`.
- Не удалять файлы.
- Не делать коммитов и вообще ничего в git.
- Не трогать `vendor/dixipro/magicpro` — это симлинк на пакет.
- Не править сгенерированное в `storage/dataMagicPro/` — перезапишется.
- Не трогать соседний проект `/home/m/mpro3.test`. Читать можно, менять нельзя.
- Не запускать код приложения ради проверки своей правки. Нужно убедиться —
  скажи об этом или посмотри через браузер.

## Где работать

Продукт живёт в `packages/dixipro/magicpro`. Корневое приложение Laravel — только
хост, пакет подключён через симлинк composer.

Не искать логику продукта в корневом `app/` и не править корневой boilerplate,
пока об этом не попросили прямо.

Только Laravel 13, его синтаксис и возможности.

## Проверки

- Изменённые PHP-файлы прогнать через `php -l`. Только синтаксис, стилевые
  фиксеры не запускать.
- Фронт админки собирается из каталога пакета:
  `cd packages/dixipro/magicpro && npm run build`.
- Файлы `* copy.php` и `* copy.js` — устаревшие резервные копии, их не трогать и
  за образец не брать.

## МСП

У проекта свой MCP-сервер, `magicpro`. Задачу, которую можно сделать его
инструментом, делать инструментом, а не правкой файлов руками.

- Статью писать только `save-article`, он перегенерирует блейд и контроллер.
- `parentId` и `npp` менять только `move-article`, иначе задвоятся `npp` и
  сломается флаг `directory` у родителей.
- Статья `id = 1` обязана сохранить имя `root`.
- `read-file` и `save-file` — не для статей: блейды и контроллеры читаются
  `get-article` и пишутся `save-article`.
- `save-file` заменяет файл целиком и не создаёт новых. Сперва `read-file`, потом
  полное содержимое обратно.
- К лентам МСП пока нет, пользоваться моделями и API лент.
- Добавил инструмент — допиши его в `MagicProServer::$tools`, иначе его нет. Все
  правила по нему — в `#[Description]`: агент читает только оттуда.

Подробности — `docs/ru/mcp/`.

## Статьи и маршруты

- В имени статьи допустимы только латинские буквы, цифры, дефис и подчёркивание.
- Статью менять только через `API_ArticlesPostController`
  (`POST /a_dmin/api/articles`). Прямой SQL рассинхронит базу с генерированными
  файлами: сохранение перегенерирует блейд и контроллер и пересчитывает `npp` и
  `directory` в транзакциях.
- Позицией в дереве владеет команда `move`, и только она.
- Маршруты, которые не должны попадать в динамический роутер, добавлять в
  `EXCLUDED_ROUTES`.
- Преобразование `.` ↔ `___` в именах маршрутов не менять, не проверив оба
  направления.

Подробности — `docs/ru/main/`.

## Ленты

- Не писать в `magicPro_feed_items` напрямую SQL: мимо модели не посчитается
  `__position`, не проверятся ссылки и не удалятся файлы.
- Записи создавать через ленту (`$feed->items()->create()`), а не
  `FeedItem::create()`: без ленты новая запись не знает своей схемы.
- Искать и сортировать можно только по слотам. По полям из `__data` нельзя, у них
  нет своей колонки.
- Запись, на которую ссылаются, не удаляется. Кольца связей запрещены.
- Новый слот — это миграция, константа в `FeedItem` и индексы. Старую миграцию не
  трогать.
- Любое изменение схемы проводить через сохранение ленты: иначе не вырастет
  `schemaGeneration` и разойдутся устаревшие карты.

Подробности — `docs/ru/feed/`.

## Картинки

- Оригиналы не трогать, производные живут в кеше и создаются сами.
- Кеш считается годным, пока он новее исходника. Поменяли настройки качества —
  нужен `imageCacheClear()`, сам он не пересоздастся.
- Ресайзер не бросает исключений: битая картинка не должна ронять страницу.

Подробности — `docs/ru/image/`.

## Почта

- `MproHelper::sendMail()` отправляет сразу и исключений не бросает.
- Отложенные письма разбирает крон. Нет крона — письма лежат.
- Методы `API_Mail` работают до первой ошибки и бросают исключение; форму ответа
  собирает родитель, ловить внутри не надо.

Подробности — `docs/ru/mail/`.

## Документация

Папка на модуль, внутри три обязательных файла:

```
docs/ru/main/      центральный модуль
docs/ru/feed/      ленты
docs/ru/image/     ресайзер
docs/ru/mail/      почтовая система
docs/ru/mcp/       MCP-сервер
docs/ru/helpers/   MproHelper
```

- `about.md` — назначение;
- `use.md` — как пользоваться снаружи;
- `inside.md` — как устроено внутри.

Правила деления:

- **Структура данных — самая важная часть описания.** Дока любой подсистемы
  обязана её содержать: все таблицы с колонками и типами, что где хранится,
  умолчания при создании записи, связи между таблицами. Без этого документ
  бесполезен: по нему нельзя ни понять систему, ни изменить её. Нет базы —
  описывается то, что её заменяет: формат файла, ключи ответа, структура json.
- **ТЗ — это что надо сделать. Документация — что сделано.** Не путать и не
  дописывать в ТЗ по факту работ.
- **Ограничения на значения описывать словами, а не регуляркой.** «Латинские
  буквы, цифры, дефис и подчёркивание» вместо `^[A-Za-z0-9_-]+$`. Читателю доки
  надо понять, что можно вводить, а не разбирать выражение. Регулярка уместна
  только там, где речь идёт о самой строке проверки в коде, и то лучше пояснить
  словами рядом.
- Своё решение, о котором не договаривались, в документ не вписывать. Такие вещи
  идут в раздел «Вопросы» в конце файла.
- Задачи и находки — в `docs/toDo/taskAll.md`.
- Команды установки писать в документ или выполнять, а не выкладывать в чат для
  ручного перенабора.
