# ТЗ v9. Модуль «Ленты» (Feeds). Структура данных

Источник истины по структуре данных и удалению. Остальные файлы папки — черновики.

## Назначение

`MagicPro Lenta` — модуль хранения линейных данных небольших сайтов: новости, блог,
рецепты, FAQ, отзывы, сотрудники, вакансии, афиша, справочники, заявки с сайта. Полный
разбор сценариев — в `TZ_cases.md`.

Модуль не является конструктором произвольных баз данных. Структура таблиц фиксирована,
разработчик работает с логическими именами полей, физические колонки скрыты.

Везде, где возможно, используются штатные механизмы Laravel: Eloquent, Query Builder,
casts, paginator, validation, transactions, Spatie Media Library.

## Принцип хранения

Данные делятся на две группы.

**Индексируемые** — те, по которым ищут, фильтруют, сортируют, проверяют уникальность или
строят связи. Лежат в физических колонках: `string_N`, `bigint_N`, `date_N`, `bool_N`,
`link_N`.

**Неиндексируемые** — те, которые только хранят, редактируют и показывают. Лежат в
JSON-колонке `data`. Туда же уходят большие тексты: статьи, описания, программы, код.

Запросы вида `where('data->content', …)` модуль не поддерживает. Это и даёт одинаковое
поведение на SQLite, MySQL и PostgreSQL.

### Код ленты

`code` состоит из латинских букв, цифр, дефиса и подчёркивания. Изменить можно, но тогда придётся поправить вызовы в блейдах. На связи это не влияет —
они ссылаются на ленту по `id`.

## Слоты

Дальше по тексту слоты пишутся как `string_1` … `string_N`. Значение `N` для каждого типа
задаётся здесь и только здесь.

| Слоты                   | Назначение | `N` |
| ----------------------- | ---------- | --- |
| `string_1` … `string_N` | Строки     | 5   |
| `bigint_1` … `bigint_N` | Целые      | 3   |
| `date_1` … `date_N`     | Дата-время | 3   |
| `bool_1` … `bool_N`     | Флаги      | 3   |
| `link_1` … `link_N`     | Связи      | 3   |

Числа взяты из `TZ_cases.md`: тридцать сценариев, ни одному не нужно больше. Изменение
количества — это миграция и новые индексы, из админки слоты не добавляются.

### Правила при создании записи

- **`position` = `max(position) + 1`** внутри своей ленты. Расчёт идёт в транзакции с
  блокировкой строки `feeds`: два параллельных запроса иначе дадут одинаковую позицию, а
  это ломает пагинацию — см. «Индексы `feed_items`».
- **`visible` = `false`.** Редактор ставит `true` сам, когда запись готова, иначе на сайте
  появляются пустые заготовки.
- **`bool_1` … `bool_N` = `0`.** Колонка `not null`, и `DEFAULT 0` стоит на уровне
  миграции: поля может ещё не быть в схеме, а вставка должна проходить.
- **Незанятые слоты = `NULL`, а не пустая строка.** Два `NULL` считаются разными, две
  пустые строки — одинаковыми, и на этом ломается проверка уникальности.
- **Остальные значения по умолчанию** берутся из настроек поля в схеме.

## Формат `schema`

```json
{
  "version": 1,
  "fields": []
}
```

Порядок элементов `fields` определяет порядок полей в форме. Каждое поле — один объект.

## Логическое имя

`code` поля состоит из латинских букв, цифр, дефиса и подчёркивания.

## Валидация

`validation` — строка правил Laravel, как в форм-реквестах:

```json
"validation": "required|string|min:4|max:255"
```

Своего формата у модуля нет: строка уходит в штатный валидатор при сохранении записи через
API. Отдельного ключа `required` нет — это слово в той же строке.

**`unique` правилом Laravel не выражается.** `unique:feed_items,string_2` проверил бы всю
таблицу, а слот общий: у блога там `slug`, у сотрудников — `department`, и два сотрудника
одного отдела перестали бы сохраняться. Поэтому уникальность остаётся отдельным ключом
поля — см. «Уникальность».

## Физические колонки

**`string_1` … `string_N`** — `varchar(255)`. Заголовки, slug, коды, короткие значения,
всё, по чему ищут строкой.

**`bigint_1` … `bigint_N`** — только целые. Деньги в минимальных единицах: `150000` это
1500.00. Координаты — умноженные на миллион: `55.755819` хранится как `55755819`, множитель
одинаков для всех лент. Дробные значения, по которым не ищут, — в `data`.

**`date_1` … `date_N`** — дата и время, cast `datetime`. Тип один: `datetime`. Отдельного
типа «только дата» нет — время либо используется, либо просто остаётся нулевым. Двух дат в сценариях хватало
всегда: начало и конец, выдан и истекает.

**`bool_1` … `bool_N`** — никогда не `NULL`. Отсутствие значения у старой записи означает
`false`.

**`link_1` … `link_N`** — см. «Связи».

## Связи

Каждый `link_N` содержит `feed_items.id`. Связи возможны только между записями модуля
«Ленты»; связи с произвольными таблицами проекта в модуль не входят.

Описание лежит **внутри поля**, а не отдельным массивом:

```json
"relation": {
  "feed_id": 22,
  "display_code": "title"
}
```

`feed_id` — из какой ленты берём запись, `display_code` — `code` её поля, которое
показывается оператору в выпадающем списке.

Лента указывается по `id`, а не по `code`, потому что `code` разрешено менять — при
переименовании ленты все связи на неё остались бы битыми.

При сохранении проверяется: связанная запись существует, принадлежит указанной ленте, и
поле `display_code` есть в схеме той ленты.

**Кольца запрещены.** Если A ссылается на B, то B не может ссылаться на A, ни напрямую, ни
через цепочку — см. «Удаление».

**Связь всегда «одна запись → одна запись».** Если нужно несколько ссылок одного вида —
несколько авторов, теги — оператор заводит обычную ленту-связку с двумя полями `link`.
Движок про неё ничего особенного не знает.

## JSON `data`

Все поля, которым не нужна физическая колонка, описываются одним объектом схемы с
`"column": "data"`. Сами поля лежат в его вложенном массиве `data` и отличаются от обычных
только тем, что вместо `column` у них `type` — см. «Пример описания».

В базе хранится плоский объект: ключ — `code` вложенного поля, значение — его содержимое.

```json
{
  "subTitle": "Подзаголовок",
  "email2": "user@example.com",
  "description": "<p>Текст статьи</p>"
}
```

В `data` запрещены `where`, `orderBy`, `unique` и связи.

### Загрузка

`data` читается вместе с записью, обычным запросом. Ленивой загрузки нет и отдельного
метода подгрузки тоже: в `data` лежат метаданные изображений, а миниатюра нужна как раз в
списке — колонку всё равно пришлось бы тянуть почти всегда.

Плата понятна: список тащит и тексты записей. На объёмах, ради которых делается модуль,
это не имеет значения; если у конкретной ленты тексты большие, а список длинный, поля
такой ленты стоит раскладывать иначе.

## Совместимость «колонка ↔ тип»

Одна физическая колонка используется только одним полем схемы.

| Колонка    | Допустимые типы                                                                        |
| ---------- | -------------------------------------------------------------------------------------- |
| `string_N` | `string`                                                                               |
| `bigint_N` | `integer`                                                                              |
| `date_N`   | `datetime`                                                                             |
| `bool_N`   | `boolean`                                                                              |
| `link_N`   | `link`                                                                                 |
| `data`     | `string`, `text`, `integer`, `decimal`, `boolean`, `datetime`, `json`, `code`, `image` |

Проверяется при сохранении схемы.

## Редакторы

У всех полей, кроме текстовых, редакторы зашиты в модуль и HTML не пропускают — только
простой текст.

Для текстовых полей доступны `html`, `markdown`, `plain`.

Неизвестный редактор — ошибка сохранения схемы.

**`select` и `textSearch` — не редакторы, а способ ввода.** Они не меняют ни тип, ни
формат хранения, а только ограничивают ввод заранее определёнными значениями: вместо
свободного поля оператор выбирает из списка или ищет по нему.

## Форматирование и безопасность

Как выводить — вопрос блейда. Как вводить — вопрос админки.

HTML допустим только в текстовых полях. Во всех остальных он экранируется целиком.

**`plain`** — выводится с HTML-экранированием.

**`html`** — должен почистить джава скрипт, оставить чистый хтмл

**`markdown`** — в `data` хранится исходный Markdown. Как выводить маркдаун дело блейда.

## Видимость

`visible` не применяется автоматически. Владелец должен
открыть скрытую новость по её адресу и увидеть, как она будет выглядеть. Решение о показе
принимает контроллер или блейд.

Плата — фильтр в списке можно забыть, и черновик уедет на сайт.

## Уникальность

`unique: true` объявляется в описании поля и разрешён только для полей физических колонок. Проверка идёт по всем записям
ленты, включая скрытые: `visible = false` означает «не показывать», а не «освободить
значение».

Проверка и запись выполняются в транзакции с блокировкой строки `feeds`.

Уникальных индексов на слоты **нет**: слот общий для всех лент, и `UNIQUE (feed_id,
string_2)` заставил бы быть уникальным второй строковый слот везде — а другая лента держит
там название отдела, и два сотрудника из одного отдела туда уже не запишутся.

Настоящий уникальный индекс есть только у `feeds.code`.

## Индексы `feed_items`

Количество слотов: `string` — 5, `bigint` — 3, `date` — 3, `bool` — 3, `link` — 3, `data` — 1.

Все индексы перечислены явно. Они статические, создаются миграцией, админка никогда не
делает `ALTER TABLE`.

| №   | Индекс                                     | Для чего                               |
| --- | ------------------------------------------ | -------------------------------------- |
| 1   | `(feed_id, visible, position, id)`         | Главный список ленты, ручной порядок   |
| 2   | `(feed_id, visible, created_at, id)`       | Список по дате создания                |
| 3   | `(feed_id, visible, date_1, id)`           | Список и фильтр по первой дате         |
| 4   | `(feed_id, visible, date_2, id)`           | То же по второй дате                   |
| 5   | `(feed_id, visible, date_3, id)`           | То же по третьей дате                  |
| 6   | `(feed_id, visible, link_1, position, id)` | Все записи с первой связью, по порядку |
| 7   | `(feed_id, visible, link_2, position, id)` | То же по второй связи                  |
| 8   | `(feed_id, visible, link_3, position, id)` | То же по третьей связи                 |
| 9   | `(feed_id, visible, bool_1, position, id)` | Список по первому флагу, по порядку    |
| 10  | `(feed_id, visible, bool_2, position, id)` | То же по второму флагу                 |
| 11  | `(feed_id, visible, bool_3, position, id)` | То же по третьему флагу                |
| 12  | `(feed_id, string_1)`                      | Поиск записи по первой строке          |
| 13  | `(feed_id, string_2)`                      | Поиск по второй строке                 |
| 14  | `(feed_id, string_3)`                      | Поиск по третьей строке                |
| 15  | `(feed_id, string_4)`                      | Поиск по четвёртой строке              |
| 16  | `(feed_id, string_5)`                      | Поиск по пятой строке                  |
| 17  | `(feed_id, bigint_1)`                      | Поиск записи по первому числу          |
| 18  | `(feed_id, bigint_2)`                      | Поиск по второму числу                 |
| 19  | `(feed_id, bigint_3)`                      | Поиск по третьему числу                |

Итого 19 индексов.

### Почему именно так

**Порядок колонок: `feed_id`, потом равенство, потом сортировка, в конце `id`.** Составной
индекс читается слева направо, пропускать колонки нельзя: если в индексе
`(feed_id, visible, date_1)` не задать `visible`, до `date_1` база не доберётся и пойдёт
читать таблицу.

**`id` в конце сортировочных — не про скорость, а про корректность.** При одинаковых
значениях `position` или `date_1` порядок строк не определён, и на границе страниц одна
запись покажется дважды, а другая не покажется нигде. `id` делает порядок однозначным.

**`visible` стоит только в списковых индексах (1–11).** Поиск конкретной записи идёт без
него: запись по адресу берётся независимо от видимости, иначе не работает предпросмотр
черновика. Поставь `visible` вторым в поисковом индексе — и при запросе без него база до
`string_2` не дойдёт.

**Булевы и связи — всегда вместе с сортировкой.** Голый `(feed_id, visible, bool_1)`
отберёт строки, но сортировать их придётся в памяти. С `position` следом «первые десять
оплаченных» читаются как десять строк, а не как двести с последующей сортировкой.

**Строковые и числовые индексы — без сортировки.** По ним ищут конкретную запись по
равенству: slug, артикул, номер документа. Сортировать по ним незачем, поэтому `position`
и `id` в них не нужны.

**`data` не индексируется вовсе** — по ней запрещены `where` и `orderBy`.

**По `link_1` … `link_N` идёт проверка «на эту запись ещё ссылаются».** Индексы 6–8 для неё
не годятся: они начинаются с `feed_id`, а ищут по самой колонке, через `OR` по всем трём
слотам, и ленту при этом не знают.

**Индексы не зависят от схемы ленты.** Слот `string_2` у блога хранит `slug`, у сотрудников
— отдел; индекс один и тот же и работает для обоих. Поэтому список фиксирован и не растёт
при появлении новых лент.

## Индексы `feeds`

| №   | Индекс                     | Для чего                                     |
| --- | -------------------------- | -------------------------------------------- |
| 1   | `UNIQUE (code)`            | Поиск ленты по коду и запрет двух одинаковых |
| 2   | `(group_id, position, id)` | Список лент группы по порядку в админке      |

**`UNIQUE (code)`** — единственный настоящий уникальный индекс во всём модуле. По нему
работает обращение к ленте из кода, и он же не даёт завести вторую ленту с тем же кодом.
Проверка в админке остаётся, но последнее слово за базой.

**`(group_id, position, id)`** обслуживает главный экран админки: группы, внутри каждой —
свои ленты в заданном порядке. Он же покрывает внешний ключ `group_id`, потому что стоит
первой колонкой.

`title` и `schema` не индексируются: по названию не ищут, а схема — JSON.

## Индексы `feed_groups`

| №   | Индекс           | Для чего                         |
| --- | ---------------- | -------------------------------- |
| 1   | `(position, id)` | Вывод групп по заданному порядку |

Таблица маленькая — обычно единицы строк, — и других запросов к ней нет: группы всегда
читаются целиком и всегда по порядку. `id` в конце по той же причине, что и везде: при
одинаковых `position` порядок иначе не определён.

Уникального индекса на `title` нет. Две группы с одинаковым названием ничего не ломают,
а запрет — вопрос админки, а не базы.

## Медиа

Файлы хранит Spatie Media Library, количество не ограничено. Она требует, чтобы запись была
Eloquent-моделью — это в архитектуру заложено.

Метаданные файла лежат в `data` под `code` поля: `url`, `size`, `mime`, `x`, `y`, а рядом
то, что заполняет оператор, например `alt`. Само поле описывается в схеме типом `image`.

**Одно поле — одно изображение.** При загрузке коллекция поля очищается, старый файл
удаляется. Галереи нет: нужно десять картинок — заводится десять полей.

**Пока только изображения.** Документы и видео — позже, отдельным типом поля.

**Медиа меняется только через API модуля.** Если файл удалить или заменить мимо него —
через саму Spatie или через медиатеку — метаданные в `data` об этом не узнают и ссылка
останется битой.

Загрузка после создания записи:

```php
/**
 * Загружает изображение в поле записи и сохраняет его метаданные.
 * Существующие пользовательские данные поля, например alt, сохраняются.
 * Обработки ошибок нет, вызов стоит завернуть в try/catch.
 * На этапе ТЗ уточняем только важные моменты.
 */
public function loadImage(string $code, int $id, $file): FeedItem
{
    // Получаем запись ленты.
    $item = FeedItem::findOrFail($id);

    // В поле хранится одно изображение — старое удаляем.
    $item->clearMediaCollection($code);

    // Сохраняем файл в коллекцию с именем поля.
    $media = $item
        ->addMedia($file)
        ->toMediaCollection($code);

    // Получаем размеры изображения.
    [$width, $height] = getimagesize($media->getPath());

    $data = $item->data ?? [];

    // Обновляем только метаданные файла, не затирая alt и другие свойства.
    $data[$code] = array_merge($data[$code] ?? [], [
        'url'  => $media->getUrl(),
        'size' => $media->size,
        'mime' => $media->mime_type,
        'x'    => $width,
        'y'    => $height,
    ]);

    // Сохраняем обновлённый JSON.
    $item->data = $data;
    $item->save();

    return $item;
}
```

## Удаление

Удаление физическое. Корзины, мягкого удаления и восстановления нет. `visible` — это не
удаление, а скрытие.

### Главное правило

**Запись, на которую кто-то ссылается через `link`, не удаляется.** Сначала снимается
ссылка, потом удаляется запись.

Проверка «кто ссылается»:

```sql
SELECT * FROM feed_items
WHERE link_1 = :id OR link_2 = :id OR link_3 = :id
```

### Удалить запись

1. Оператор нажимает корзинку.
2. Проверяем, кто ссылается на запись.
3. Никто — подтверждение, удаляем запись вместе с её файлами.
4. Кто-то ссылается — открывается окно со списком ссылающихся записей, у каждой своя
   корзинка.

Окно рекурсивное: удаление записи из списка идёт по тем же правилам и может открыть
следующий список. Оператор спускается по цепочке до записей, которые никто не держит, и
разбирает её снизу вверх.

`position` соседей не пересчитывается: дырка в нумерации ничего не ломает, новая запись
получает `max(position) + 1`.

### Групповое удаление записей

Рядом с каждой записью чекбокс, есть «выбрать все». После подтверждения удаляются все
отмеченные записи, на которые никто не ссылается.

В конце выводится список тех, кого удалить не удалось, с указанием, кто их держит.

### Очистка ленты

Удаляются данные, описание ленты остаётся.

Проход по записям: удаляем все, на которые никто не ссылается. Проход повторяется, пока за
него удалилась хоть одна запись.

Повтор нужен из-за цепочек: пока жива запись C, нельзя удалить B, которая на неё
ссылается, а пока жива B — нельзя A. Первый проход снимает C, второй B, третий A. Когда
очередной проход не удалил ничего, работа закончена.

В ленте остаётся только то, что держат ссылки из других лент.

### Удаление ленты

То же самое, что очистка, плюс последний шаг:

1. Проходами удаляем все записи, которые никто не держит.
2. Смотрим, осталось ли что-нибудь.
3. Записей нет — удаляем описание ленты, ленты больше не существует.
4. Записи остались — описание остаётся, лента продолжает жить с остатком.

### Файлы

Файлы записи удаляются вместе с ней средствами Spatie Media Library — коллекции чистятся
до удаления строки, иначе на диске останутся файлы, на которые никто не ссылается.

Метаданные лежат в `data` той же строки и исчезают вместе с ней.

### Взаимные ссылки запрещены

**Связи не должны образовывать кольцо.** Если A ссылается на B, то B не может ссылаться на
A — ни напрямую, ни через цепочку C, D и так далее.

Без этого запрета обе записи становятся вечными: каждая держит другую, ни одна не
удаляется, проходы очистки на них останавливаются, и рекурсивное окно водит оператора по
кругу. Удалить их можно было бы только правкой записи, то есть в обход всей механики
удаления.

Проверка выполняется при сохранении записи: если новая связь замыкает кольцо, запись не
сохраняется и оператор получает ошибку с указанием, через какие записи идёт кольцо.

## Чего в модуле нет

Сознательные ограничения, а не пропуски.

- **Мягкого удаления записей** — есть `visible`. Скрыть и удалить это разные намерения,
  и они не должны прятаться за одной кнопкой.
- **Деревьев** — обхода на произвольную глубину модуль не делает.
- **Связей «многие ко многим»** — собираются лентой-связкой.
- **Фильтрации и сортировки по `data`**.
- **Полнотекстового поиска и сложных фильтров.**
- **Галерей** — одно поле хранит одно изображение.
- **Файлов и видео** — на этом этапе только изображения.
- **Мультиязычности данных** — интерфейс да, данные нет.
- **Динамического изменения структуры таблиц.**

## CRUD

Источник истины

CRUD лент использует модели Laravel и Eloquent.

В таблице `feed_items` данные физически хранятся в универсальных колонках:

```text
string_1
string_2
bigint_1
date_1
bool_1
link_1
```

В коде приложения вместо физических названий колонок используются логические имена `code`, заданные в `feeds.schema`.

Например:

```text
name  → string_1
price → bigint_1
date  → date_1
```

## Пример поиска

Найти в ленте `Users` все записи, где поле `name` равно `Вася`:

```php
$feed = Feed::where('code', 'Users')->firstOrFail();

$items = $feed->items()
    ->where('name', 'Вася')
    ->get();
```

Перед выполнением запроса имя `name` автоматически заменяется на физическую колонку `string_1`.

Фактически Eloquent выполняет запрос:

```php
$items = FeedItem::query()
    ->where('feed_id', $feed->id)
    ->where('string_1', 'Вася')
    ->get();
```

## Пример поиска по нескольким полям

Найти товары ленты `Products`, у которых название равно `Мыло`, а цена больше `1000`:

```php
$feed = Feed::where('code', 'Products')->firstOrFail();

$items = $feed->items()
    ->where('name', 'Мыло')
    ->where('price', '>', 1000)
    ->get();
```

Если схема ленты содержит:

```text
name  → string_1
price → bigint_1
```

то запрос преобразуется в:

```php
$items = FeedItem::query()
    ->where('feed_id', $feed->id)
    ->where('string_1', 'Мыло')
    ->where('bigint_1', '>', 1000)
    ->get();
```

## Пример сортировки

Получить записи ленты `Users`, отсортированные по имени:

```php
$feed = Feed::where('code', 'Users')->firstOrFail();

$items = $feed->items()
    ->orderBy('name')
    ->get();
```

Фактически выполняется:

```php
$items = FeedItem::query()
    ->where('feed_id', $feed->id)
    ->orderBy('string_1')
    ->get();
```

## Подключение Builder

Модель `FeedItem` использует собственный Eloquent Builder:

```php
public function newEloquentBuilder($query)
{
    return new FeedItemBuilder($query);
}
```

Класс `FeedItemBuilder`:

- получает массив соответствий `code → физическая колонка`;
- заменяет логические имена полей в Eloquent-запросах;
- передаёт преобразованный запрос стандартному Eloquent Builder.

Пример массива соответствий:

```php
[
    'name'  => 'string_1',
    'price' => 'bigint_1',
]
```

Полный пример исходного запроса:

```php
$feed = Feed::where('code', 'Users')->firstOrFail();

$items = $feed->items()
    ->where('name', 'Вася')
    ->get();
```

После преобразования:

```php
$items = FeedItem::query()
    ->where('feed_id', $feed->id)
    ->where('string_1', 'Вася')
    ->get();
```

Источник массива соответствий не относится к механизму замены. Он может быть получен из `feeds.schema` и передан в `FeedItemBuilder` при создании запроса конкретной ленты.
