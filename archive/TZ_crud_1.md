# ТЗ. Модуль «Ленты» (Feeds). CRUD

Дополнение к `TZ_data_9.md`: что можно делать с данными и по каким правилам. HTTP, команды
и формат ответа — в ТЗ на API.

Разработчик работает логическими именами полей. Физические колонки, `data` и слоты наружу
не торчат нигде.

## Чтение

```php
MproHelper::getFeed('news')
    ->where('mpro.visible', true)
    ->where('category', $categoryId)
    ->orderBy('mpro.position')
    ->paginate(10);
```

Без префикса — логическое поле ленты, с `mpro.` — системная колонка.

Разрешены `where`, `orderBy`, `limit`, `paginate`, `get`, `first`, `find`. Поля из `data`
в `where` и `orderBy` не принимаются — ошибка, а не тихий пропуск.

Обращение к несуществующей ленте и к несуществующему полю — исключение. Опечатка в имени
поля должна падать сразу, а не возвращать `null`.

У записи поля читаются одинаково, независимо от того, где лежат:

```blade
{{ $item->title }}          {{-- string_1 --}}
{{ $item->description }}    {{-- data --}}
{{ $item->category->title }}{{-- link_1, связанная запись --}}
{{ $item->mpro->visible }}  {{-- системная колонка --}}
```

Связь отдаёт саму запись, а не идентификатор. Связанная лента читается отдельным запросом,
одним на всю выборку, а не по записи.

## Создание

На вход — значения логическими именами, только те, что заданы.

Проверки по порядку:

1. Поле есть в схеме ленты.
2. Значение подходит колонке по типу — таблица совместимости.
3. `validation` из описания поля.
4. `unique`, если он есть у поля — по всем записям ленты, включая скрытые.
5. Для связи: запись существует, принадлежит указанной в `relation` ленте, кольца не
   образуются.

Автоматика описана в `TZ_data_9.md`: `position` = `max + 1`, `visible` = `false`, булевы в
`0`, остальное из `default`.

Всё в одной транзакции с блокировкой строки `feeds` — иначе два одновременных сохранения
дадут одинаковый `position` или проскочат мимо проверки `unique`.

## Обновление

Обновление частичное: передаются только те поля, которые меняются. Не переданное поле не
трогается, а `null` — это осмысленное значение «очистить».

Проверки те же, что при создании. `unique` проверяется по всем записям ленты, кроме
обновляемой.

`position` через обновление не меняется — для этого отдельная операция.

## Перемещение

Порядок внутри ленты меняется только целенаправленно: запись ставится на новое место,
соседи сдвигаются, всё в транзакции.

Дырки в нумерации после удалений допустимы и никак не мешают.

## Удаление

Описано в `TZ_data_9.md`, раздел «Удаление». Коротко: запись со ссылками не удаляется,
кольца запрещены, лента исчезает, когда в ней не осталось записей.

## Ленты

Создание ленты: `code`, `title`, `group_id`, схема. Группа обязательна, при отсутствии
берётся группа по умолчанию.

Правка схемы — отдельная операция, не часть обновления ленты. При сохранении схемы
проверяется:

- `code` поля соответствует маске, уникален внутри ленты, не равен `mpro`;
- `column` занята ровно одним полем;
- тип поля совместим с колонкой;
- `relation` ссылается на существующую ленту и на существующее в ней поле.

**`column` у поля с данными не меняется.** Перенос значений между колонками — это миграция
данных, а не правка описания; при смене колонки значения остались бы в старой, и поле
показалось бы пустым.

**Удаление поля из схемы очищает его колонку.** Иначе в слоте остаются значения, которые
никто не видит, но которые продолжают участвовать в проверке `unique` следующего поля,
занявшего эту колонку.

## Группы

Создание и переименование группы, изменение порядка. Группа по умолчанию переименовывается,
но не удаляется.

## Ошибки

Любая неудачная проверка — исключение с текстом, понятным человеку: какое поле, что не так,
какое значение пришло. Слой API превращает его в `errorMsg`, и никакой другой обработки не
требуется.

## Вопросы

**1. Перемещение записи.** «Поставить на позицию N» или «поставить после записи X»? Второе
удобнее для перетаскивания мышью в админке, первое проще для кода.

**2. Очистка колонки при удалении поля.** Делать сразу или спрашивать оператора — данные
теряются безвозвратно, а поле могли удалить по ошибке.
