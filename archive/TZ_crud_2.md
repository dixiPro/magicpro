# ТЗ. Модуль «Ленты» (Feeds). Слой над Eloquent

Дополнение к `TZ_data_9.md`. Своего CRUD модуль не пишет: запись ленты — обычная
Eloquent-модель, а модуль добавляет к ней перевод имён и правила на событиях.

HTTP, команды и формат ответа — в ТЗ на API.

## Что делаем сами

Только две вещи:

1. **Перевод «логическое имя ↔ физическая колонка»** по схеме ленты.
2. **Правила модуля** — значения при создании, валидация, уникальность, связи, удаление.

Всё остальное — выборки, пагинация, коллекции, транзакции, события, касты, медиа — берётся
у Eloquent как есть. Ни одна из этих вещей не переписывается и не оборачивается.

## Модель `FeedItem`

Таблица `feed_items`, одна модель на все ленты.

Касты: `data` → массив, `date_1` … `date_N` → `datetime`, `bool_1` … `bool_N` → `boolean`.

Трейт Spatie `InteractsWithMedia` — он же и требует, чтобы запись была моделью.

Модель знает свой `feed_id`, а значит знает и схему: по ней строится таблица соответствий
для перевода имён. Схема читается один раз и кэшируется на время запроса.

## Перевод имён

Переопределяются `getAttribute` и `setAttribute`. Логическое имя разворачивается в одно из
трёх мест, и снаружи разницы нет:

| Что в схеме             | Куда идёт           | Пример                |
| ----------------------- | ------------------- | --------------------- |
| `"column": "string_1"`  | Физическая колонка  | `$item->title`        |
| Поле внутри `data`      | Ключ JSON-колонки   | `$item->description`  |
| `"column": "link_1"`    | Связанная запись    | `$item->category`     |

Системные колонки доступны через `mpro`: `$item->mpro->visible`, `$item->mpro->position`,
`$item->mpro->id`.

Обращение к имени, которого нет в схеме, — исключение. Опечатка должна падать сразу, а не
возвращать `null` и показывать пустоту в блейде.

## Построитель запросов

Свой класс через `newEloquentBuilder()`. Переопределяются только `where`, `orderBy` и
`find`: логическое имя переводится в колонку, префикс `mpro.` снимается, дальше вызывается
родительский метод.

Отсюда бесплатно работают `paginate`, `simplePaginate`, `chunk`, `first`, `firstOrFail`,
`exists`, `count`, коллекции и всё остальное — переписывать их незачем.

```php
MproHelper::getFeed('news')
    ->where('mpro.visible', true)
    ->where('category', $categoryId)
    ->orderBy('mpro.position')
    ->paginate(10);
```

`getFeed('news')` возвращает построитель с наложенным глобальным скоупом `feed_id` и
подставленной схемой. Обращение к несуществующей ленте — исключение.

Поля из `data` в `where` и `orderBy` не принимаются — исключение, а не тихий пропуск.

## Связи

`link_1` … `link_N` — обычные `belongsTo` на ту же модель. Целевая лента берётся из
`relation` в описании поля.

`$item->category` отдаёт связанную запись целиком, а не идентификатор. Для списка связанные
записи подгружаются одним запросом на всю выборку — штатный eager loading, ничего своего.

## Правила на событиях

**`creating`**

- `position` = `max(position) + 1` внутри своей ленты;
- `visible` = `false`;
- булевы колонки = `0`;
- остальные значения по умолчанию из схемы.

**`saving`**

- валидация штатным `Validator` по строке правил из описания поля;
- совместимость значения с колонкой по таблице типов;
- `unique` — по всем записям ленты, включая скрытые, кроме самой обновляемой;
- связь: запись существует, принадлежит указанной в `relation` ленте, кольца не образуются.

**`deleting`**

- проверка входящих ссылок — запись со ссылками не удаляется;
- очистка медиаколлекций до удаления строки.

Всё это выполняется в транзакции с блокировкой строки `feeds`: без неё два одновременных
сохранения дадут одинаковый `position` или оба проскочат проверку `unique`.

## Обновление

Штатное. Передаются только меняющиеся поля, `null` означает «очистить», непереданное поле
не трогается.

`position` через обновление не меняется: порядок задаётся отдельной операцией, которая
сдвигает соседей в транзакции.

## Схема ленты

Правка схемы — не часть работы с записями и через модель не идёт.

При сохранении схемы проверяется:

- `code` поля соответствует маске, уникален внутри ленты, не равен `mpro`;
- `column` занята ровно одним полем;
- тип поля совместим с колонкой;
- `relation` ссылается на существующую ленту и существующее в ней поле.

**`column` у поля с данными не меняется** — значения остались бы в старой колонке, и поле
выглядело бы пустым. Это миграция данных, а не правка описания.

**Удаление поля из схемы очищает его колонку** — иначе в слоте остаются невидимые значения,
которые продолжат участвовать в проверке `unique` следующего поля, занявшего эту колонку.

## Ошибки

Любая неудачная проверка — исключение с человеческим текстом: какое поле, что не так, какое
значение пришло. Слой API превращает его в `errorMsg`, другой обработки не требуется.

## Вопросы

**1. Перемещение записи.** «Поставить на позицию N» или «поставить после записи X»? Второе
удобнее для перетаскивания в админке, первое проще для кода.

**2. Очистка колонки при удалении поля.** Делать молча или спрашивать оператора — данные
уходят безвозвратно, а поле могли удалить по ошибке.
