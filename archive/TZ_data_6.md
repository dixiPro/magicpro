# ТЗ v6. Модуль «Ленты» (Feeds). Структура данных

Источник истины по структуре данных. Остальные файлы папки — черновики. Удаление вынесено
в отдельное ТЗ и здесь не описано.

## Назначение

`MagicPro Lenta` — модуль хранения линейных данных небольших сайтов: новости, блог,
рецепты, FAQ, отзывы, сотрудники, вакансии, афиша, справочники, заявки с сайта. Полный
разбор сценариев — в `TZ_cases.md`.

Модуль не является конструктором произвольных баз данных. Структура таблиц фиксирована,
разработчик работает с логическими именами полей, физические колонки скрыты.

Везде, где возможно, используются штатные механизмы Laravel: Eloquent, Query Builder,
casts, paginator, validation, transactions, Spatie Media Library.

## Принцип хранения

Данные делятся на две группы.

**Индексируемые** — те, по которым ищут, фильтруют, сортируют, проверяют уникальность или
строят связи. Лежат в физических колонках: `string_N`, `bigint_N`, `date_N`, `bool_N`,
`link_N`.

**Неиндексируемые** — те, которые только хранят, редактируют и показывают. Лежат в
JSON-колонке `data`. Туда же уходят большие тексты: статьи, описания, программы, код.

Запросы вида `where('data->content', …)` модуль не поддерживает. Это и даёт одинаковое
поведение на SQLite, MySQL и PostgreSQL.

| ------------ | -------- | --------------- |

| `title`      | string   | Название группы |

## Таблица `feeds`

| Колонка      | Тип      | Назначение                      |
| ------------ | -------- | ------------------------------- |
| `id`         | bigint   | Первичный ключ                  |
| `code`       | string   | Программный код ленты, `UNIQUE` |
| `title`      | string   | Название в админке              |
| `schema`     | json     | Описание полей                  |
| `lock`       | boolean  | Схема защищена от изменений     |
| `group_id`   | bigint   | Группа, обязательна             |
| `position`   | bigint   | Позиция внутри группы           |
| `created_at` | datetime |                                 |
| `updated_at` | datetime |                                 |

`lock = true` запрещает править схему. Наполнение ленты записями он не ограничивает —
это разные операции и разные команды API.

Версия формата схемы лежит внутри самого JSON (`"version"`), отдельной колонки нет: схема
переносится и копируется целиком, версия должна ехать вместе с ней.

### Код ленты

`code` соответствует `^[a-z][a-z0-9_]*$`, не равен `mpro`, уникален среди всех лент.
Изменить можно, но тогда придётся поправить вызовы в блейдах. На связи это не влияет —
они ссылаются на ленту по `id`.

## Слоты

Дальше по тексту слоты пишутся как `string_1` … `string_N`. Значение `N` для каждого типа
задаётся здесь и только здесь.

| Слоты                   | Назначение | `N` |
| ----------------------- | ---------- | --- |
| `string_1` … `string_N` | Строки     | 5   |
| `bigint_1` … `bigint_N` | Целые      | 3   |
| `date_1` … `date_N`     | Дата-время | 3   |
| `bool_1` … `bool_N`     | Флаги      | 3   |
| `link_1` … `link_N`     | Связи      | 3   |

Числа взяты из `TZ_cases.md`: тридцать сценариев, ни одному не нужно больше. Изменение
количества — это миграция и новые индексы, из админки слоты не добавляются.

## Таблица `feed_items`

| Колонка                 | Тип                   | Назначение                      |
| ----------------------- | --------------------- | ------------------------------- |
| `id`                    | bigint                | Первичный ключ                  |
| `feed_id`               | bigint                | Лента записи                    |
| `string_1` … `string_N` | varchar(255) nullable | Строки для поиска и сортировки  |
| `bigint_1` … `bigint_N` | bigint nullable       | Целые числа                     |
| `date_1` … `date_N`     | datetime nullable     | Даты и время                    |
| `bool_1` … `bool_N`     | boolean not null      | Флаги                           |
| `link_1` … `link_N`     | bigint nullable       | Ссылки на другие `feed_items`   |
| `data`                  | json                  | Неиндексируемые данные и тексты |
| `position`              | bigint                | Позиция внутри ленты            |
| `visible`               | boolean               | Видимость записи                |
| `created_at`            | datetime              |                                 |
| `updated_at`            | datetime              |                                 |

Отдельных текстовых колонок нет. Большие тексты живут в `data` — см. «JSON `data`».

### Правила при создании записи

- **`position` = `max(position) + 1`** внутри своей ленты. Расчёт идёт в транзакции с
  блокировкой строки `feeds`: два параллельных запроса иначе дадут одинаковую позицию, а
  это ломает пагинацию — см. «Индексы `feed_items`».
- **`visible` = `false`.** Редактор ставит `true` сам, когда запись готова, иначе на сайте
  появляются пустые заготовки.
- **`bool_1` … `bool_N` = `0`.** Колонка `not null`, и `DEFAULT 0` стоит на уровне
  миграции: поля может ещё не быть в схеме, а вставка должна проходить.
- **Незанятые слоты = `NULL`, а не пустая строка.** Два `NULL` считаются разными, две
  пустые строки — одинаковыми, и на этом ломается проверка уникальности.
- **Остальные значения по умолчанию** берутся из настроек поля в схеме.

## Логическое имя

`code` поля соответствует `^[a-z][a-z0-9_]*$`, уникален внутри ленты, не равен `mpro`, не
содержит точек и не меняется после появления данных.

Точка запрещена потому, что префикс `mpro.` в запросах разделяет логические поля и
системные колонки — см. «Query Builder».

## Физические колонки

**`string_1` … `string_N`** — `varchar(255)`. Заголовки, slug, коды, короткие значения,
всё, по чему ищут строкой.

**`bigint_1` … `bigint_N`** — только целые. Деньги в минимальных единицах: `150000` это
1500.00. Координаты — умноженные на миллион: `55.755819` хранится как `55755819`, множитель
одинаков для всех лент. Дробные значения, по которым не ищут, — в `data`.

**`date_1` … `date_N`** — дата и время, cast `datetime`. Двух дат в сценариях хватало
всегда: начало и конец, выдан и истекает.

**`bool_1` … `bool_N`** — никогда не `NULL`. Отсутствие значения у старой записи означает
`false`.

**`link_1` … `link_N`** — см. «Связи».

## Связи

Каждый `link_N` содержит `feed_items.id`. Связи возможны только между записями модуля
«Ленты»; связи с произвольными таблицами проекта в модуль не входят.

Описание лежит **внутри поля**, а не отдельным массивом:

```json
"relation": {
  "feed_id": 22,
  "display_code": "title"
}
```

`feed_id` — из какой ленты берём запись, `display_code` — `code` её поля, которое
показывается оператору в выпадающем списке.

Лента указывается по `id`, а не по `code`, потому что `code` разрешено менять — при
переименовании ленты все связи на неё остались бы битыми.

При сохранении проверяется: связанная запись существует, принадлежит указанной ленте, и
поле `display_code` есть в схеме той ленты.

На уровне базы `link_N` — внешний ключ на `feed_items.id` с `ON DELETE SET NULL`. Удалили
категорию — ссылка обнулилась сама, висячих идентификаторов не остаётся и чистить в коде
нечего.

**Связь всегда «одна запись → одна запись».** Если нужно несколько ссылок одного вида —
несколько авторов, теги — оператор заводит обычную ленту-связку с двумя полями `link`.
Движок про неё ничего особенного не знает.

## JSON `data`

Все поля, которым не нужна физическая колонка, описываются одним объектом схемы с
`"column": "data"`. Сами поля лежат в его вложенном массиве `data` и отличаются от обычных
только тем, что вместо `column` у них `type` — см. `TZ_data_example.md`.

В базе хранится плоский объект: ключ — `code` вложенного поля, значение — его содержимое.

```json
{
  "subTitle": "Подзаголовок",
  "email2": "user@example.com",
  "description": "<p>Текст статьи</p>"
}
```

В `data` запрещены `where`, `orderBy`, `unique` и связи.

### Ленивая загрузка

`data` **не выбирается в списочных запросах**. Иначе вывод тридцати заголовков вытащил бы
из базы тридцать тел статей.

Колонка подгружается по обращению к любому JSON-полю записи. Для страницы записи это один
дополнительный запрос, для списка — ни одного.

Именно это делает возможным отказ от отдельных текстовых колонок.

Если блейд обратится к `data` в цикле по списку, запросов будет столько же, сколько
записей. Отдельного метода «подгрузить `data` для всей выборки» модуль не даёт: на
типичных для лент объёмах это незаметно, а автор блейда видит, что он делает.

## Совместимость «колонка ↔ тип»

Одна физическая колонка используется только одним полем схемы.

| Колонка    | Допустимые типы                                                                       |
| ---------- | ------------------------------------------------------------------------------------- |
| `string_N` | `string`                                                                              |
| `bigint_N` | `integer`                                                                             |
| `date_N`   | `datetime`                                                                            |
| `bool_N`   | `boolean`                                                                             |
| `link_N`   | `link`                                                                                |
| `data`     | `string`, `text`, `integer`, `decimal`, `boolean`, `date`, `datetime`, `json`, `code` |

Проверяется при сохранении схемы.

## Редакторы

У всех полей, кроме текстовых, редакторы зашиты в модуль и HTML не пропускают — только
простой текст.

Для текстовых полей доступны `html`, `markdown`, `plain`.

Неизвестный редактор — ошибка сохранения схемы.

## Форматирование и безопасность

Как выводить — вопрос блейда. Как вводить — вопрос админки.

HTML допустим только в текстовых полях. Во всех остальных он экранируется целиком.

**`plain`** — выводится с HTML-экранированием.

**`html`** — должен почистить джава скрипт, оставить чистый хтмл

**`markdown`** — в `data` хранится исходный Markdown. Как выводить маркдаун дело блейда.

## Query Builder

```php
MproHelper::getFeed('news')
    ->where('mpro.visible', true)
    ->where('category', $categoryId)
    ->orderBy('mpro.position')
    ->paginate(10);
```

Правило одно: без префикса — логическое поле ленты, с `mpro.` — системная колонка. Без
него `orderBy('position')` был бы неоднозначным.

Обращение к несуществующей ленте — исключение, а не пустая выборка.

## Видимость

`visible` не применяется автоматически. Списки ставят фильтр явно:

```php
->where('mpro.visible', true)
```

Отдельная запись берётся **без** фильтра — иначе не работает предпросмотр: владелец должен
открыть скрытую новость по её адресу и увидеть, как она будет выглядеть. Решение о показе
принимает контроллер или блейд.

Плата — фильтр в списке можно забыть, и черновик уедет на сайт.

## Уникальность

`unique` разрешён только для полей физических колонок. Проверка идёт по всем записям
ленты, включая скрытые: `visible = false` означает «не показывать», а не «освободить
значение».

Проверка и запись выполняются в транзакции с блокировкой строки `feeds`.

Уникальных индексов на слоты **нет**: слот общий для всех лент, и `UNIQUE (feed_id,
string_2)` заставил бы быть уникальным второй строковый слот везде — а другая лента держит
там название отдела, и два сотрудника из одного отдела туда уже не запишутся.

Настоящий уникальный индекс есть только у `feeds.code`.

## Индексы `feed_items`

Все составные, статические, создаются миграцией. Админка никогда не делает `ALTER TABLE`.

Порядок колонок: `feed_id`, потом равенство, потом сортировка, в конце `id`. Составной
индекс читается слева направо, пропускать колонки нельзя.

`id` в конце сортировочных — не про скорость, а про корректность: при одинаковых
значениях порядок строк иначе не определён, и при пагинации одна запись покажется на двух
страницах, а другая не покажется нигде.

| Индекс                                                | Штук | Для чего                                   |
| ----------------------------------------------------- | ---- | ------------------------------------------ |
| `(feed_id, visible, position, id)`                    | 1    | Главный список ленты                       |
| `(feed_id, visible, created_at, id)`                  | 1    | Список по дате создания                    |
| `(feed_id, visible, date_1, id)` … `date_N`           | 3    | Списки и фильтры по датам                  |
| `(feed_id, visible, link_1, position, id)` … `link_N` | 3    | Все записи с этой связью, сразу по порядку |
| `(feed_id, visible, bool_1, position, id)` … `bool_N` | 3    | Списки по флагу: активные, оплаченные      |
| `(feed_id, string_1)` … `string_N`                    | 5    | Поиск записи по строке                     |
| `(feed_id, bigint_1)` … `bigint_N`                    | 3    | Поиск записи по числу                      |

Итого 19 индексов.

**`visible` только в списковых индексах.** Поиск конкретной записи идёт без него — запись
по адресу берётся независимо от видимости, иначе не работает предпросмотр. Если поставить
`visible` вторым в поисковом индексе, база до `string_2` не доберётся.

**Булевы — только вместе с сортировкой.** Голый `(feed_id, visible, bool_1)` бесполезен: он
отберёт строки, а сортировать всё равно придётся в памяти. С `position` следом работает
«первые десять оплаченных» — при перекосе это разница между чтением десяти строк и двухсот.

`data` не индексируется.

## Индексы служебных таблиц

`feeds` — уникальный индекс по `code` и составной `(group_id, position)` для списка лент в
админке. `feed_groups` — индекс по `position`.

## Медиа

Используем Spatie Media Library, количество файлов не ограничено. Требует, чтобы запись была
Eloquent-моделью — это и заложено в архитектуру.

Информацию о медиа храним в data

После создания записи.

загружаем изображение файл

/\*_
Загружает изображение в поле записи и сохраняет его метаданные.
Существующие пользовательские данные поля, например alt, сохраняются.
Не хватает обработки ошибок, желательно завернуть функцию в try catch
на этапе ТЗ уточнять только важные моменты
_/
public function loadImage(string $code, int $id, $file): FeedItem
{
    // Получаем запись ленты.
    $item = FeedItem::findOrFail($id);

    // В поле хранится одно изображение — старое удаляем.
    $item->clearMediaCollection($code);

    // Сохраняем файл в коллекцию с именем поля.
    $media = $item
        ->addMedia($file)
        ->toMediaCollection($code);

    // Получаем размеры изображения.
    [$width, $height] = getimagesize($media->getPath());

    $data = $item->data ?? [];

    // Обновляем только метаданные файла, не затирая alt и другие свойства.
    $data[$code] = array_merge($data[$code] ?? [], [
        'url'  => $media->getUrl(),
        'size' => $media->size,
        'mime' => $media->mime_type,
        'x'    => $width,
        'y'    => $height,
    ]);

    // Сохраняем обновлённый JSON.
    $item->data = $data;
    $item->save();

    return $item;

}

## Чего в модуле нет

Сознательные ограничения, а не пропуски.

- **Удаление** — отдельное ТЗ.
- **Мягкого удаления записей** — есть `visible`. Скрыть и удалить это разные намерения,
  и они не должны прятаться за одной кнопкой.
- **Деревьев** — обхода на произвольную глубину модуль не делает.
- **Связей «многие ко многим»** — собираются лентой-связкой.
- **Фильтрации и сортировки по `data`**.
- **Полнотекстового поиска и сложных фильтров.**
- **Мультиязычности данных** — интерфейс да, данные нет.
- **Динамического изменения структуры таблиц.**

## Вопросы

**1. Какой формат у `validation`?**

В примере это объект: `{ "type": "string", "min": 4, "max": 255 }` — свой мини-язык, его
придётся описывать и поддерживать.

Свой объект или строка правил Laravel (`"required|string|min:4|max:255"`), которую валидатор
понимает без перевода?

> использовать валидатор Ларавелом, указать это в "unic"

**2. Полный список редакторов.**

В ТЗ названы только `html`, `markdown`, `plain` — и то лишь для текстовых полей. В примере
встречаются `select` и `textSearch`, в разделе «Медиа» — `media`.

> `select` и `textSearch` это не редактор это способ ввода заранее определенных значений, пометить этот факт.

**3. Даты: один тип или два?**

Хранится всегда `datetime`, но редактору нужно знать, показывать календарь с часами или
без: срок годности — без времени, начало эфира — с временем.

> дата эфира это год, месяц, день, час и минута. пока не вижу где нужно именно время

**4. Где объявляется `unique`?**

Раздел «Уникальность» описывает правило, но в примере описания поля такого ключа нет.
Это `"unique": true` в объекте поля?

> смотри в описании поля, исправил пример TZ_data_example.md

## Комментарии к правкам

**1. `unique` правилом Laravel не выражается.** Валидатор умеет `unique:table,column`, но у
нас слот общий: `string_2` — это `slug` у блога и `department` у сотрудников. Правило
проверило бы всю таблицу и запретило двум сотрудникам один отдел. Значит `unique` остаётся
отдельным ключом поля и проверяется кодом внутри своей ленты, как и написано в разделе
«Уникальность». В валидацию он не переезжает.

В примере ключ назван `unic` — похоже на опечатку, ожидается `unique`.

**2. Раз валидация — правила Laravel, пример надо переписать.** Сейчас в
`TZ_data_example.md` объект `{ "type": "string", "min": 4, "max": 255 }`, а по решению
должно быть `"validation": "required|string|min:4|max:255"`. Заодно исчезает `required`
как отдельный ключ — он становится словом в строке правил.

**3. `image` не указан в таблице совместимости.** В примере есть `"type": "image"` внутри
`data`, в разделе «Совместимость колонка ↔ тип» такого типа нет. Нужно добавить, а заодно
решить, есть ли `file` — см. вопросы.

**4. `date` против решения «только datetime».** В ответе сказано, что отдельного времени
нигде не нужно, значит тип один — `datetime`. В примере у `bornDate` стоит `"type": "date"`.

**5. `select` и `textSearch` — способ ввода, а не редактор.** Помечу это в разделе
«Редакторы», как просили, когда будет ответ на вопрос 4 ниже (откуда берутся значения).

## Медиа

**6. Медиа в `data` ломает ленивую загрузку.** Раздел «Ленивая загрузка» строится на том,
что `data` не выбирается в списках. Но миниатюра товара или новости нужна именно в списке,
а её `url` теперь лежит в `data`. Получается, что для любого списка с картинками `data`
всё-таки придётся тянуть — и вместе с ней приедут тела статей, ради чего всё и затевалось.

**7. Два источника истины.** Файл лежит в таблице Spatie, метаданные — в `data`. Если файл
удалить или заменить мимо `loadImage` (через саму Spatie, через админку медиатеки), `data`
об этом не узнает и останется битая ссылка. Нужно правило: медиа меняется только через
API модуля.

**8. «Количество файлов не ограничено» против кода.** Первая строка раздела говорит, что
файлов сколько угодно, а `loadImage` делает `clearMediaCollection($code)` — одно
изображение на поле. Одно из двух надо поправить.

**9. `getimagesize` вызывается всегда.** Для не-изображения он вернёт `false`, и
деструктуризация `[$width, $height]` упадёт с ошибкой. Актуально, если появится тип `file`.

**10. Оформление.** Код `loadImage` вставлен без обрамления в ` ```php `, из-за чего
markdown его не подсвечивает, а комментарий `/\*_ … _/` вместо `/** … */` разъехался.

## Вопросы

**1. Что делать со списками, где нужна картинка?**

Варианты: тянуть `data` в списках всегда и отказаться от ленивой загрузки; держать
метаданные медиа в отдельной колонке рядом с `data`; или брать миниатюру запросом к Spatie
для всей выборки разом.

**2. Одно изображение на поле или несколько?**

Код чистит коллекцию, то есть одно. Галерея — это отдельный тип поля с `multiple` или её
пока нет?

**3. Есть ли тип `file`, кроме `image`?**

PDF, документы, архивы. Если да — `getimagesize` вызывается только для изображений, и в
метаданных вместо `x` / `y` появляется имя файла.

**4. Откуда `select` берёт значения для обычного строкового поля?**

Для `link` понятно — из связанной ленты. А для `string` список вариантов должен где-то
лежать: массив в схеме поля, отдельная лента-справочник или что-то третье?
