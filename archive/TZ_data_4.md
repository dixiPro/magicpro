# ТЗ. Модуль «Ленты» (Feeds). Итоговое

Сведено из `TZ_data_3.md`, `TZ_cases.md` и `TZ_gpt_1.md`. Удаление вынесено в отдельное ТЗ
и здесь не описано.

## 1. Назначение

`MagicPro Lenta` — модуль хранения линейных данных небольших сайтов: новости, блог,
рецепты, FAQ, отзывы, сотрудники, вакансии, афиша, справочники, заявки с сайта. Полный
разбор сценариев — в `TZ_cases.md`.

Модуль не является конструктором произвольных баз данных. Структура таблиц фиксирована,
разработчик работает с логическими именами полей, физические колонки скрыты.

Везде, где возможно, используются штатные механизмы Laravel: Eloquent, Query Builder,
casts, paginator, validation, transactions, Spatie Media Library.

## 2. Принцип хранения

Данные делятся на две группы.

**Индексируемые** — те, по которым ищут, фильтруют, сортируют, проверяют уникальность или
строят связи. Лежат в физических колонках: `string_*`, `bigint_*`, `date_*`, `bool_*`,
`link_*`.

**Неиндексируемые** — те, которые только хранят, редактируют и показывают. Лежат в
JSON-колонке `data`. Туда же уходят большие тексты: статьи, описания, программы, код.

Запросы вида `where('data->content', …)` модуль не поддерживает. Это и даёт одинаковое
поведение на SQLite, MySQL и PostgreSQL.

## 3. Таблица `feed_groups`

| Колонка      | Тип      | Назначение      |
| ------------ | -------- | --------------- |
| `id`         | bigint   | Первичный ключ  |
| `title`      | string   | Название группы |
| `position`   | bigint   | Порядок вывода  |

Миграция создаёт группу по умолчанию. Она не удаляется, используется для новых лент,

## 4. Таблица `feeds`

| Колонка          | Тип      | Назначение                      |
| ---------------- | -------- | ------------------------------- |
| `id`             | bigint   | Первичный ключ                  |
| `code`           | string   | Программный код ленты, `UNIQUE` |
| `title`          | string   | Название в админке              |
| `schema`         | json     | Описание полей                  |
| `schema_version` | integer  | Версия формата схемы            |
| `lock`           | boolean  | Запрет изменения схемы          |
| `group_id`       | bigint   | Группа, обязательна             |
| `position`       | bigint   | Позиция внутри группы           |
| `created_at`     | datetime |                                 |
| `updated_at`     | datetime |                                 |

### 4.1. Код ленты

`code` соответствует `^[a-z][a-z0-9_]*$`, не равен `mpro`, уникален среди всех лент и не
меняется после создания.

```php
MproHelper::feed('news');
```

### 4.2. Блокировка

При `lock = true` запрещено добавлять и удалять поля, менять `code` поля, физическую
колонку, тип и настройки связи. Разрешено менять название ленты, группу, позицию и сами
записи.

## 5. Таблица `feed_items`

| Колонка                 | Тип                   | Назначение                      |
| ----------------------- | --------------------- | ------------------------------- |
| `id`                    | bigint                | Первичный ключ                  |
| `feed_id`               | bigint                | Лента записи                    |
| `string_1` … `string_6` | varchar(255) nullable | Строки для поиска и сортировки  |
| `bigint_1` … `bigint_4` | bigint nullable       | Целые числа                     |
| `date_1` … `date_4`     | datetime nullable     | Даты и время                    |
| `bool_1` … `bool_4`     | boolean not null      | Флаги                           |
| `link_1` … `link_4`     | bigint nullable       | Ссылки на другие `feed_items`   |
| `data`                  | json                  | Неиндексируемые данные и тексты |
| `position`              | bigint                | Позиция внутри ленты            |
| `visible`               | boolean               | Видимость записи                |
| `created_at`            | datetime              |                                 |
| `updated_at`            | datetime              |                                 |

Количество слотов взято не с потолка: в `TZ_cases.md` разобрано тридцать сценариев, ни
один не требует больше пяти строковых, трёх числовых, трёх дат, трёх флагов и трёх связей.
Заложен запас в единицу по каждому типу.

Отдельных текстовых колонок нет. Большие тексты живут в `data` — см. раздел 10.

### 5.1. Значения по умолчанию

При создании записи:

```text
bool_1 … bool_4 = false
visible         = false
data            = {}
position        = max(position) + 1 внутри feed_id
```

Все незанятые колонки, кроме булевых, хранят `NULL`. Пустая строка не подставляется
никогда: два `NULL` не считаются одинаковыми при проверке уникальности, а две пустые
строки — считаются.

`visible = false` при создании потому, что запись сначала наполняют, а потом показывают.

### 5.2. Позиция

Расчёт позиции идёт в транзакции с блокировкой строки `feeds`. Иначе два параллельных
запроса дадут одинаковую позицию, а это ломает пагинацию — см. раздел 19.

## 6. Формат `schema`

```json
{
  "version": 1,
  "fields": []
}
```

Порядок элементов `fields` определяет порядок полей в форме. Каждое поле — один объект.

### 6.1. Пример

```json
{
  "version": 1,
  "fields": [
    {
      "column": "string_1",
      "code": "title",
      "label": "Заголовок",
      "type": "string",
      "editor": "input",
      "required": true
    },
    {
      "column": "string_2",
      "code": "slug",
      "label": "Адрес страницы",
      "type": "string",
      "editor": "input",
      "required": true,
      "unique": true
    },
    {
      "column": "date_1",
      "code": "published_at",
      "label": "Дата публикации",
      "type": "datetime",
      "editor": "datetime"
    },
    {
      "column": "data",
      "code": "content",
      "label": "Текст статьи",
      "type": "text",
      "editor": "html",
      "format": "html",
      "sanitize": true,
      "lines": 20
    },
    {
      "column": "link_1",
      "code": "category",
      "label": "Категория",
      "type": "link",
      "editor": "select",
      "relation": {
        "feed_code": "news_categories",
        "display_code": "title"
      }
    }
  ]
}
```

## 7. Параметры поля

**Обязательные:** `column` (физическая колонка или `data`), `code` (логическое имя),
`label` (подпись в админке), `type` (тип значения).

**Необязательные:**

| Параметр      | По умолчанию | Назначение                        |
| ------------- | ------------ | --------------------------------- |
| `editor`      | по `type`    | Компонент формы                   |
| `required`    | `false`      | Обязательность                    |
| `unique`      | `false`      | Уникальность внутри ленты         |
| `default`     | `null`       | Значение по умолчанию             |
| `placeholder` | `null`       | Подсказка внутри поля             |
| `help`        | `null`       | Текст под полем                   |
| `lines`       | `1`          | Высота многострочного редактора   |
| `format`      | `plain`      | Правило отображения               |
| `sanitize`    | по формату   | Очистка входных данных            |
| `language`    | `null`       | Язык подсветки для редактора кода |
| `readonly`    | `false`      | Запрет ручного редактирования     |

Неизвестные параметры игнорируются — это и позволяет расширять формат, не ломая старые
ленты.

### 7.1. Логическое имя

`code` поля соответствует `^[a-z][a-z0-9_]*$`, уникален внутри ленты, не равен `mpro`, не
содержит точек и не меняется после появления данных.

Точка запрещена потому, что префикс `mpro.` в запросах разделяет логические поля и
системные колонки — см. раздел 15.

## 8. Физические колонки

**`string_1` … `string_6`** — `varchar(255)`. Заголовки, slug, коды, короткие значения,
всё, по чему ищут строкой.

**`bigint_1` … `bigint_4`** — только целые. Деньги в минимальных единицах: `150000` это
1500.00. Координаты — умноженные на миллион: `55.755819` хранится как `55755819`, множитель
одинаков для всех лент. Дробные значения, по которым не ищут, — в `data`.

**`date_1` … `date_4`** — дата и время, cast `datetime`. Двух дат в сценариях хватало
всегда: начало и конец, выдан и истекает.

**`bool_1` … `bool_4`** — никогда не `NULL`. Отсутствие значения у старой записи означает
`false`.

**`link_1` … `link_4`** — см. раздел 9.

## 9. Связи

Каждый `link_*` содержит `feed_items.id`. Связи возможны только между записями модуля
«Ленты»; связи с произвольными таблицами проекта в модуль не входят.

Описание лежит **внутри поля**, а не отдельным массивом:

```json
"relation": {
  "feed_code": "news_categories",
  "display_code": "title"
}
```

`feed_code` — из какой ленты берём запись, `display_code` — какое её поле показывать
оператору в выпадающем списке.

При сохранении проверяется: связанная запись существует, принадлежит указанной ленте, и
поле `display_code` есть в схеме той ленты.

На уровне базы `link_*` — внешний ключ на `feed_items.id` с `ON DELETE SET NULL`. Удалили
категорию — ссылка обнулилась сама, висячих идентификаторов не остаётся и чистить в коде
нечего.

**Связь всегда «одна запись → одна запись».** Если нужно несколько ссылок одного вида —
несколько авторов, теги — оператор заводит обычную ленту-связку с двумя полями `link`.
Движок про неё ничего особенного не знает.

## 10. JSON `data`

Поле с `"column": "data"` хранится в `data` под своим `code`:

```json
{
  "content": "<p>Текст статьи</p>",
  "annotation": "Краткое описание",
  "seo_description": "Описание страницы"
}
```

В `data` запрещены `where`, `orderBy`, `unique` и связи.

### 10.1. Ленивая загрузка

`data` **не выбирается в списочных запросах**. Иначе вывод тридцати заголовков вытащил бы
из базы тридцать тел статей.

Колонка подгружается по обращению к любому JSON-полю записи. Для страницы записи это один
дополнительный запрос, для списка — ни одного.

Именно это делает возможным отказ от отдельных текстовых колонок.

## 11. Совместимость «колонка ↔ тип»

Одна физическая колонка используется только одним полем схемы.

| Колонка    | Допустимые типы                                                                                |
| ---------- | ---------------------------------------------------------------------------------------------- |
| `string_*` | `string`                                                                                       |
| `bigint_*` | `integer`                                                                                      |
| `date_*`   | `date`, `datetime`                                                                             |
| `bool_*`   | `boolean`                                                                                      |
| `link_*`   | `link`                                                                                         |
| `data`     | `string`, `text`, `integer`, `decimal`, `boolean`, `date`, `datetime`, `json`, `code`, `media` |

Проверяется при сохранении схемы.

## 12. Редакторы

`input`, `textarea`, `html`, `markdown`, `code`, `number`, `checkbox`, `date`, `datetime`,
`select`, `json`, `media`.

Неизвестный редактор заменяется стандартным по `type`.

Схема не может содержать PHP-классы, коллбэки, исполняемый JavaScript и имена произвольных
Blade-компонентов. Все значения работают только через белые списки модуля.

## 13. Форматирование и безопасность

Как выводить это вопрос блейда
Как вводить это вопрос редактора.

**`plain`** — выводится с HTML-экранированием.

**`html`** — очищается при сохранении, если `"sanitize": true`. Для вывода используется
отдельный безопасный метод или Blade-компонент; обычное обращение к значению не должно
само выводить сырой HTML.

**`markdown`** — в `data` хранится исходный Markdown. При выводе: преобразование в HTML,
очистка, показ.

**`code`** — не исполняется, не очищается как HTML, всегда выводится с экранированием,
может подсвечиваться по `language`.

## 14. Версионирование схемы

Версия хранится и в `feeds.schema_version`, и внутри JSON.

Правила развития формата: новые параметры добавляются необязательными; для отсутствующих
берутся значения по умолчанию; неизвестные игнорируются; существующие параметры не меняют
смысл; удаление параметра — только отдельной миграцией схемы; структура `feed_items` при
расширении схемы не меняется.

Благодаря этому новые версии модуля добавляют редакторы, правила валидации, подсказки и
настройки медиа без миграции основной таблицы.

## 15. Доступ к данным

Логические поля:

```php
$post->title;
$post->content;
$post->category;
```

Разработчик не работает с `string_1`, `data['content']`, `link_1`.

Системные — через `mpro`:

```php
$post->mpro->id;
$post->mpro->feed_id;
$post->mpro->position;
$post->mpro->visible;
$post->mpro->created_at;
$post->mpro->updated_at;
```

Занято одно слово `mpro`. Имена `id`, `position`, `data` остаются свободными под поля
ленты.

## 16. Query Builder

```php
MproHelper::feed('news')
    ->where('mpro.visible', true)
    ->where('category', $categoryId)
    ->orderBy('mpro.position')
    ->paginate(10);
```

Правило одно: без префикса — логическое поле ленты, с `mpro.` — системная колонка. Без
него `orderBy('position')` был бы неоднозначным.

Обращение к несуществующей ленте — исключение, а не пустая выборка.

Запрос по JSON-полю даёт понятную ошибку:

```text
Field [content] is stored in JSON and cannot be used in where().
```

## 17. Видимость

`visible` не применяется автоматически. Списки ставят фильтр явно:

```php
->where('mpro.visible', true)
```

Отдельная запись берётся **без** фильтра — иначе не работает предпросмотр: владелец должен
открыть скрытую новость по её адресу и увидеть, как она будет выглядеть. Решение о показе
принимает контроллер или блейд.

Плата — фильтр в списке можно забыть, и черновик уедет на сайт.

## 18. Уникальность

`unique` разрешён только для полей физических колонок. Проверка идёт по всем записям
ленты, включая скрытые: `visible = false` означает «не показывать», а не «освободить
значение».

Проверка и запись выполняются в транзакции с блокировкой строки `feeds`.

Уникальных индексов на слоты **нет**: слот общий для всех лент, и `UNIQUE (feed_id,
string_2)` заставил бы быть уникальным второй строковый слот везде — а другая лента держит
там название отдела, и два сотрудника из одного отдела туда уже не запишутся.

Настоящий уникальный индекс есть только у `feeds.code`.

## 19. Индексы `feed_items`

Все составные, статические, создаются миграцией. Админка никогда не делает `ALTER TABLE`.

Порядок колонок: `feed_id`, потом равенство, потом сортировка, в конце `id`. Составной
индекс читается слева направо, пропускать колонки нельзя.

`id` в конце сортировочных — не про скорость, а про корректность: при одинаковых
значениях порядок строк иначе не определён, и при пагинации одна запись покажется на двух
страницах, а другая не покажется нигде.

| Индекс                                                | Штук | Для чего                                   |
| ----------------------------------------------------- | ---- | ------------------------------------------ |
| `(feed_id, visible, position, id)`                    | 1    | Главный список ленты                       |
| `(feed_id, visible, created_at, id)`                  | 1    | Список по дате создания                    |
| `(feed_id, visible, date_1, id)` … `date_4`           | 4    | Списки и фильтры по датам                  |
| `(feed_id, visible, link_1, position, id)` … `link_4` | 4    | Все записи с этой связью, сразу по порядку |
| `(feed_id, visible, bool_1, position, id)` … `bool_4` | 4    | Списки по флагу: активные, оплаченные      |
| `(feed_id, string_1)` … `string_6`                    | 6    | Поиск записи по строке                     |
| `(feed_id, bigint_1)` … `bigint_4`                    | 4    | Поиск записи по числу                      |

Итого 24.

**`visible` только в списковых индексах.** Поиск конкретной записи идёт без него — запись
по адресу берётся независимо от видимости, иначе не работает предпросмотр. Если поставить
`visible` вторым в поисковом индексе, база до `string_2` не доберётся.

**Булевы — только вместе с сортировкой.** Голый `(feed_id, visible, bool_1)` бесполезен: он
отберёт строки, а сортировать всё равно придётся в памяти. С `position` следом работает
«первые десять оплаченных» — при перекосе это разница между чтением десяти строк и двухсот.

`data` не индексируется.

## 20. Индексы служебных таблиц

```text
feeds        UNIQUE(code), (group_id, position, id)
feed_groups  (position, id)
```

## 21. Медиа

Spatie Media Library, количество файлов не ограничено. Требует, чтобы запись была
Eloquent-моделью — это и заложено в архитектуру.

Медиа-поля описываются в схеме и не занимают физических колонок:

```json
{
  "code": "gallery",
  "label": "Галерея",
  "type": "media",
  "editor": "media",
  "multiple": true,
  "collection": "gallery"
}
```

## 22. Чего в модуле нет

Сознательные ограничения, а не пропуски.

- **Удаление** — отдельное ТЗ.
- **Мягкого удаления записей** — есть `visible`. Скрыть и удалить это разные намерения,
  и они не должны прятаться за одной кнопкой.
- **Деревьев** — обхода на произвольную глубину модуль не делает.
- **Связей «многие ко многим»** — собираются лентой-связкой.
- **Фильтрации и сортировки по `data`**.
- **Полнотекстового поиска и сложных фильтров.**
- **Мультиязычности данных** — интерфейс да, данные нет.
- **Динамического изменения структуры таблиц.**

## 23. Итоговая структура

```text
6 string
4 bigint
4 datetime
4 boolean
4 link
1 data JSON
```

Плюс системные: `id`, `feed_id`, `position`, `visible`, `created_at`, `updated_at`.

Колонки выделены только под то, с чем должна работать база. Всё остальное — в `data`, и
расширяется от версии к версии без изменения таблиц.
