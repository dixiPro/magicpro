# Доки через МСП: оглавление и как его отдавать

Дока пакета лежит в `docs/ru/`. Агенту, который работает с сайтом по https, она
недоступна: у него нет ни файлов пакета, ни шелла на сервере. Значит либо сервер
отдаёт доку сам, либо агент её не читает вовсе и работает вслепую.

Отдавать надо двумя способами сразу — ресурсами и инструментами. Ниже почему, а
затем оглавление.

## Ресурсы

`Laravel\Mcp\Server` умеет ресурсы: свойство `$resources` рядом с `$tools`,
методы протокола `resources/list`, `resources/read` и
`resources/templates/list`. Это штатное место для «читаемого материала»:
инструменты что-то делают, ресурсы просто существуют, и клиент может показать
их человеку списком.

Один ресурс на файл доки был бы три десятка классов, поэтому лучше шаблон URI —
`Resource`, реализующий `HasUriTemplate`:

```
magicpro://docs/{path}
```

`resources/list` отдаёт оглавление (то, что ниже), `resources/read` с
`magicpro://docs/ru/main/use.md` — содержимое файла. Имя и описание каждой
записи — та же строка, что в таблице: агент выбирает по ней, не открывая файл.

## Инструменты

Ресурсов мало. Не всякий клиент их показывает модели, а некоторые не
поддерживают вовсе; инструменты видит любой. Поэтому те же данные дублируются
парой:

| Инструмент  | Что делает                                     |
| ----------- | ---------------------------------------------- |
| `list-docs` | оглавление: путь и одна строка про каждый файл |
| `get-doc`   | содержимое одного файла по пути внутри `docs/` |

`get-doc` принимает путь относительно `docs/`, отдаёт файл как есть, без разбора
и обрезки. Путь проверяется: только внутри `docs/`, никаких `..`, только `.md`.
Файла нет — ошибка со списком того, что есть, а не пустой ответ.

Оглавление лучше держать не отдельным файлом, который разойдётся с
действительностью, а собирать обходом каталога, беря описание из первой строки
после заголовка каждого файла. Тогда новая дока попадает в оглавление сама.

## Что писать в описании `list-docs`

Агент не станет читать доку, если не знает, что она отвечает на его вопрос.
Поэтому в описании инструмента — не «returns documentation index», а прямое
указание, когда звать:

> Оглавление документации MagicPro. Позвать перед первой правкой незнакомого
> модуля: лент, картинок, писем, крона, компонентов. Дальше `get-doc` по пути
> из оглавления.

## Оглавление

В каждой папке по три файла: `about.md` — зачем модуль и что умеет, `use.md` —
как пользоваться снаружи, из блейдов и API, `inside.md` — как устроен внутри.

Агенту, который верстает сайт, нужны `use.md`. `inside.md` — когда меняют сам
движок, то есть почти никогда; в оглавлении их держать стоит, но описанием
отделить, чтобы не тянул их без нужды.

## Правила

- **Отдавать как есть.** Не пересказывать и не сокращать на лету: дока живёт и
  обновляется, пересказ протухнет молча.
- **Только чтение.** Инструмента «записать доку» быть не должно: дока правится в
  репозитории пакета, а на сайте лежит копия, приехавшая релизом.
- **Только `docs/`.** Путь наружу — отказ. `get-doc` не должен превращаться во
  второй `read-file`.
- **Оглавление собирать обходом каталога.** Руками поддерживаемый список
  разойдётся с папкой на первом же новом модуле.
- **Ru и только ru.** Появятся переводы — станет `docs/{lang}/{path}`, но пока
  выдумывать раскладку под несуществующие языки не нужно.
