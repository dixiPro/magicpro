# МСП: незакрытые пункты

Из двадцати находок закрыто шесть, и среди них самая дорогая — выход
`read-file` и `save-file` за разрешённый каталог.

Закрыто: корень файлового менеджера (1), токен умирает вместе с правами
владельца (3), `get-doc` уважает пометку `agent` (4), перестановка статьи вниз
внутри родителя (6), `list-docs` на свежей установке (9), сборка мёртвого
`mcpAdmin` (19).

Здесь четырнадцать оставшихся.

| № | Чем аукнется |
| --- | --- |
| 2 | неудачный `save-article` может удалить рабочие файлы статьи |
| 7 | контракт `itemSave` расходится с реализацией, поля-картинки ломаются |
| 8 | подтверждение удаления не привязано к показанному списку |
| 11 | у выдачи токена отключён CSRF |
| 17 | Article и File API отдают абсолютные пути в тексте ошибки |
| 18 | публичный адрес пишет лог, объём которого задаёт чужой |
| 5, 10, 12, 13, 14, 16, 20 | инструкции, ошибки записи файла, снимок, журнал, счёт инструментов, имя сервера, тесты |

### 2. Неудачный `save-article` может удалить рабочие generated files

Где: `admin/controller/API_ArticlesPostController.php`, `saveById()`.

Текущий порядок:

```text
deleteMpro(old article)
record->update(new fields)
createMpro(new article)
ArticleArchive::add(...)
```

Старые Blade/controller удаляются **до** валидации модели при `update()`. На
duplicate `name` или другом исключении запись остаётся прежней, но её
сгенерированные файлы уже удалены. MCP-схема проверяет формат имени, но не его
уникальность, поэтому этот сценарий доступен обычным вызовом `save-article`.

Поток также не транзакционный. Внутри `createMpro()` controller сначала пишется
в рабочий `.php` и лишь затем проверяется через `php -l`. При lint error MCP
вернёт ошибку, но база, новый Blade и невалидный PHP уже могут остаться на
месте, то есть tool error не означает rollback. Нужны предварительная
валидация, безопасная генерация через временные файлы и определённая стратегия
rollback/regeneration.

## Высокий приоритет

### 5. Канонический файл server instructions отсутствует

Где: `src/Mcp/Servers/MagicProServer.php`.

Сервер читает `docs/ru/agentSetup/mcpInstructions.md` и извлекает текст между
двумя строками `---`. Каталога `docs/ru/agentSetup/` в пакете нет. Черновик
лежит в `toDo/temp3/mcpInstructions.md`, но runtime его не читает.

Оба транспорта всегда получают короткий fallback вместо задуманного порядка
работы. Одновременно `MproHelper::getDoc()` пишет `file not found` в doc log при
каждом создании сервера. `CHANGELOG.md` ошибочно сообщает, что инструкции уже
читаются из существующего файла.

### 7. Контракт `itemSave` противоречит реализации и ломает работу с image-полями

Где:

- `src/Mcp/Tools/FeedApiWriteTool.php`, `Description`;
- `src/Lenta/API_Feeds.php`, `itemSave()` и `checkValues()`;
- `docs/ru/mcp/use.md`.

Description и существующая документация утверждают: запись сохраняется целиком,
отсутствующие в `fields` значения очищаются. Реальный код меняет только
переданные ключи; остальные сохраняются. Валидация тоже строится только для
переданных ключей.

Следствия:

- агент принимает решение на ложном описании;
- `required` из схемы не проверяется для отсутствующего поля;
- после `itemCreate` можно сделать запись видимой, не заполнив обязательные
  поля;
- совет «отправить itemGet целиком» несовместим с другим правилом Tool: любое
  переданное поле типа `image` вызывает отказ, даже если значение не менялось.

Нужно выбрать частичный или полный контракт. Для текущей архитектуры с
картинками фактическое частичное обновление выглядит согласованнее, но решение
должно быть явным. После него синхронно меняются Tool Description, проверки API,
документация и тесты.

### 8. Подтверждение удаления статьи не привязано к preview

Где: `src/Mcp/Tools/DeleteArticleTool.php`.

Первый и второй вызовы независимы. Если между ними под статьёй появился новый
ребёнок, `confirm=true` удалит и его, хотя человек его не видел. Нет revision,
hash списка или повторной сверки.

Дополнительно `subtree()` молча продолжает обход, если внутренний
`getChildrens` вернул ошибку. Preview может быть неполным, а рекурсивный
`deleteById` затем всё равно удалит фактическое дерево. У обхода нет `seen`,
поэтому повреждённая циклическая иерархия не завершится.

Preview должен либо выдавать одноразовый подтверждающий fingerprint текущего
поддерева, либо при confirm строить список заново и отказывать, если он
изменился. Ошибка обхода должна останавливать операцию.

## Средний приоритет

### 10. Выпуск токена не проверяет ошибки файловой системы

Где: `src/Mcp/Token.php`, `write()`.

Ошибки `mkdir()` и `chmod()` подавлены, а результат `file_put_contents()` не
проверяется явно. Код полагается на то, что runtime превратит warning записи в
исключение. При неуспешном `chmod()` файл останется с правами, заданными umask.

Запись с `LOCK_EX` также не атомарна для `include`-читателя: `read()` не берёт
shared lock и параллельный запрос теоретически может увидеть PHP-файл между
truncate и завершением записи. Нужно проверять обязательные операции и писать
состояние во временный файл с атомарным `rename()`.

### 11. State-changing token endpoint исключён из CSRF

Где: `admin/web.php`.

`POST /a_dmin/api/mcpToken` использует cookie-сессию guard `magic`, но явно
снимает CSRF middleware. В зависимости от SameSite cookie и расположения
атакующей страницы это позволяет принудительно выполнить `issue` или `revoke`.
Прочитать выданный токен cross-origin обычно нельзя, но можно сбить работающего
агента повторной выдачей или отзывом.

Endpoint вызывается собственным Vue-клиентом в группе `web`; ему следует
передавать CSRF token, а не снимать проверку.

### 12. Снимок рядом с MCP-токеном не возвращает все изменения агента

Где:

- `admin/js/app/mcpToken/mcpToken.vue`;
- `admin/js/app/CommonCom/Snapshots.vue`;
- `src/Import/Snapshots.php`.

Текст UI обещает: «восстановление вернёт сайт к этому состоянию». На деле
snapshot — экспорт дерева статей. Он не содержит ленты, media и файлы,
изменённые `save-file`. Размещение блока рядом с токеном создаёт впечатление
общего rollback для всех MCP-инструментов.

Нужно явно подписать область снимка как «статьи» и отдельно описать резервное
копирование лент и файлов.

### 13. MCP-журнал фиксирует запрос до результата и только для HTTP

Где: `src/Mcp/TokenMiddleware.php`, `src/Mcp/McpLog.php`.

Событие `call` пишется до выполнения Tool. По нему нельзя определить, успешно
ли закончилось сохранение или удаление. Локальный stdio transport middleware не
проходит и не логируется вовсе.

Поэтому фраза существующего `use.md` «всё, что агент звал, лежит в
`storage/logs/mcp.log`» требует двух уточнений:

- только HTTP MCP;
- записан факт входящего вызова, не результат.

Кроме того, фактический `RotatingFileHandler` создаёт
`storage/logs/mcp-YYYY-MM-DD.log`, а не постоянный файл `mcp.log`.

### 14. В документации и changelog устарело число инструментов

`MagicProServer::$tools` содержит 18 классов. `docs/ru/mcp/about.md` и
`CHANGELOG.md` говорят о пятнадцати. Такое число быстро устаревает при ручном
подсчёте; его нужно либо обновлять вместе с registry, либо не обещать в
маркетинговом тексте.

### 15. Документация Codex содержит устаревшее предупреждение об experimental flag

Где: `docs/ru/mcp/use.md`.

Текст советует искать `experimental_use_rmcp_client = true`. Текущая Codex CLI
имеет штатные `codex mcp add --url` и `--bearer-token-env-var`, а официальная
документация описывает Streamable HTTP без такого флага:
[Model Context Protocol](https://learn.chatgpt.com/docs/extend/mcp).

Устаревшая оговорка усложняет настройку и может побудить пользователя включать
несуществующий feature.

### 16. Сервер представляется общим именем и фиктивной версией библиотеки

Где: `src/Mcp/Servers/MagicProServer.php`.

Класс не задаёт name/version, поэтому initialize сообщает `Laravel MCP Server`
и `0.0.1`. Это мешает отличить MagicPro от другого Laravel MCP и сопоставить
ошибку с релизом пакета. Нужны стабильное имя и версия MagicPro.

### 17. Article и File API отдают абсолютные пути и строки исходника в error text

Где:

- `admin/controller/AbstractApiHandler.php`;
- `admin/controller/API_FileManagerPostController.php`.

При исключении `errorMsg` дополняется `getFile()` и `getLine()`. MCP Tool
возвращает этот текст удалённому клиенту. Токен и так административный, но
раскрытие структуры filesystem не требуется для рабочего сообщения и
увеличивает ущерб при утечке токена. Подробность должна идти в server log, а
клиенту — безопасное сообщение.

### 18. Публичный endpoint пишет неограниченный и частично управляемый отказом лог

Где: `src/Mcp/McpLog.php`, `TokenMiddleware::handle()`.

Даже запрос без токена сначала попадает в `McpLog::denied()`. На endpoint нет
видимого rate limiter. Поля JSON-RPC `method` и `params.name` берутся из body без
ограничения длины и очистки переводов строк, поэтому повторными запросами можно
раздувать дневной лог и подделывать его визуальную структуру.

Если вместо строки прислать массив, явное `(string)` вызывает PHP warning; при
обычной обработке ошибок Laravel это может превратить штатный 401 в 500 уже во
время записи отказа. Нужны проверка типа/длины, нормализация одной строки и rate
limit, причём ошибка аудита не должна менять ответ авторизации.

## Низкий приоритет и технический долг

### 20. Нет специальных автоматических тестов MCP

В `src/test` не найдены тесты server registry, tool schemas, токенов,
документации, HTTP middleware или двухфазных удалений. Именно в этих местах уже
есть расхождения между Description и кодом.

При исправлении нельзя ограничиваться happy path. Минимальная матрица приведена
в `inside-codex.md`, раздел «Что проверить после правок».
