# МСП: как устроено

Пакет `laravel/mcp`. Как звать инструменты — в `use.md`.

## Из чего собран

| Где | Что |
| --- | --- |
| `src/Mcp/ai.php` | регистрация сервера, обе точки входа |
| `src/Mcp/Servers/MagicProServer.php` | список инструментов |
| `src/Mcp/Tools/*.php` | сами инструменты, по классу на каждый |
| `src/Mcp/Token.php` | токен: выдача, проверка, продление |
| `src/Mcp/TokenMiddleware.php` | единственные ворота http-входа |
| `src/Mcp/McpLog.php` | лог вызовов |
| `src/Mcp/API_McpToken.php` | выдача токена из админки |

Регистрация — две строки:

```php
Mcp::local('magicpro', MagicProServer::class);
Mcp::web('/mcp/magicpro', MagicProServer::class)->middleware(TokenMiddleware::class);
```

`local` — сервер поднимается на той же машине и говорит через stdio: агент
запускает его сам, http и авторизация не участвуют. `web` — тот же класс сервера
поверх http, и всё, что решает, кого пускать, стоит в middleware.

Маршрут регистрируется вне группы `web`, поэтому ни сессии, ни csrf на нём нет:
единственное, что отвечает за доступ, — токен.

## Токен

### Где лежит

Файл на пользователя: `storage/app/private/magic/mcpTokens/<user_id>.php`, права
`0600`, каталог `0700`. Ни таблицы, ни миграции — имя файла и есть `user_id`.

```php
return [
    'hash'         => 'sha256 от токена',
    'ip'           => 'адрес, с которого выдан',
    'created_at'   => 1757260000,
    'last_used_at' => 1757260000,
];
```

Хранится хеш, а не токен: то, что показали один раз в админке, дальше живёт
только в памяти процесса агента, и копия каталога сайта ничего не даёт.

Один пользователь — один живой токен. Выдали новый — старый затёрт, и это же
кнопка «отозвать».

### Проверка

Токен устроен так: `<user_id>___<64 шестнадцатеричных символа>`. Номер
пользователя в открытую — не секрет: у кого токен, у того и так всё, зато файл
открывается сразу, без перебора каталога.

Порядок в `Token::verify()`:

1. токен пуст или не той формы — отказ;
2. файла нет или хеш не сошёлся — отказ. Сравнение через `hash_equals`: обычное
   `==` подсказывает таймингом, сколько символов совпало;
3. адрес не тот, с которого выдан, — отказ;
4. с последнего вызова прошёл час — отказ;
5. с выдачи прошли сутки — отказ.

Прошло — `last_used_at = now()`, и вызов идёт дальше. Значит **каждый вызов
инструмента стоит одной записи в файл**; это цена скользящего часа.

Адрес берётся из `request()->ip()`. Сайт за прокси, который не отдаёт настоящий
адрес клиента (тот же Cloudflare), увидит адрес прокси и у выдачи, и у вызовов —
проверка пройдёт, но защищать перестанет. Нужен настоящий адрес — настраивается
`TrustProxies` приложения, это дело сайта, а не пакета.

Причина отказа уходит в ответе как есть. Агент — не злоумышленник у формы
входа, а программа, которой надо понять, брать новый токен или остановиться.

### opcache

Файл переписывается на каждом вызове, и php его кеширует. Поэтому `Token::write()`
зовёт `opcache_invalidate()`: иначе выданный секунду назад токен пару секунд
считался бы неизвестным.

## Лог

`storage/logs/mcp.log`, четырнадцать дней, через тот же `MproHelper::addLog()`,
что и остальные логи пакета. Пишутся и принятые вызовы, и отказы: кто, откуда,
какой метод, какой инструмент.

Аргументы не пишутся — в них едут целые блейды, и лог, который съедает каждое
сохранение, никто читать не будет. Токен не пишется тоже, даже кусками: лог
читают больше людей, чем файл настроек.

## Инструмент

Обычный `Laravel\Mcp\Server\Tool`. Три части: имя, описание, схема параметров.

```php
#[Name('save-file')]
#[Description('Writes one file through the MagicPro file manager api…')]
class SaveFileTool extends Tool
{
    public function schema(JsonSchema $schema): array { … }
    public function handle(Request $request): Response|ResponseFactory { … }
}
```

**Описание — это не комментарий, а часть контракта.** Оно уезжает агенту вместе с
инструментом и остаётся единственным местом, откуда тот узнаёт правила: что
`save-file` заменяет файл целиком, что блейды статей сюда не относятся, что
`parentId` у `create-article` — будущий родитель. Правило, не попавшее в
`Description`, для агента не существует. Поэтому описания длинные, и это
намеренно.

То же и со `schema()`: `description` каждого поля — подсказка на месте
использования, а не документация для человека.

## Тело инструмента

Своей логики у инструментов нет. Каждый собирает запрос и отдаёт его тому же
контроллеру админки, что обслуживает браузер:

```php
$result = (new API_FileManagerPostController())
    ->handle(new HttpRequest([
        'command'  => 'saveFile',
        'fileName' => $request->get('fileName'),
        'fileData' => $request->get('fileData'),
    ]))
    ->getData(true);

if (! $result['status']) {
    return Response::error($result['errorMsg'] ?? 'saveFile failed');
}

return Response::structured($result['data']);
```

Отсюда всё остальное: агент проходит те же проверки, что оператор, файлы
перегенерируются, дерево пересчитывается. Дублировать логику в инструменте нельзя
— она разойдётся с админкой в первый же месяц.

Ответ всегда один из двух: `Response::structured($data)` при удаче,
`Response::error($msg)` при ошибке. Исключения наружу не выпускаются, ошибка API
становится ошибкой инструмента.

## Добавить инструмент

1. Класс в `src/Mcp/Tools/`, унаследовать `Tool`.
2. `#[Name]` и `#[Description]`. В описании — все правила и ограничения, включая
   то, чего делать нельзя.
3. `schema()` с описанием каждого параметра.
4. `handle()` — собрать запрос к существующему API админки, не писать свою логику.
5. **Дописать класс в `MagicProServer::$tools`.** Не дописал — инструмента нет.

## Почему у лент одна точка

`AbstractFeedApi::run()` уже универсальна: команда, массив параметров, ответ
всегда одной формы, исключений не бросает. Инструмент на каждую команду означал
бы полтора десятка классов, которые надо держать в согласии с `$map`.

Поэтому инструмент — один вызов поверх `run()`, со списком разрешённых команд
внутри:

```
feed-api { command: "itemsList", params: { "feedId": 2 } }
```

Команда не из списка — ошибка инструмента, до `run()` дело не доходит.

Инструментов при этом два, `FeedApiTool` и `FeedApiWriteTool`, и списки у них не
пересекаются: первый читает, второй пишет. Разделение сделано ради права, а не
ради удобства — разрешение писать это подключённый инструмент, а не флаг в
параметрах. Не подключили — писать нечем.

Ответ приводится к объекту (`FeedApiTool::wrap()`): `Response::structured()` не
принимает пустой массив, а список от `feedsList` структурой не годится.

Своей логики у инструментов нет, кроме двух мест, и оба намеренные:

- `itemDelete` без `confirm` ничего не удаляет, а показывает запись и держателей
  ссылок. Держателей инструмент добирает сам через `itemLinks`: API отвечает на
  такое удаление голым `false`, и агенту оно ничего не говорит.
- `itemSave` отказывает, если в `fields` пришло поле-картинка. Какие поля
  картиночные, знает только схема, поэтому инструмент спрашивает `itemGet` и
  `feedGet` — сам API такую запись пропустил бы в `__data`.

Наружу `itemLinks` при этом не выставляется: она нужна инструменту, а не агенту.

Что не входит и почему — `docs/toDo/TZ_Lenta_mcp_write.md`.

## Что учесть

- Удаление статей идёт в два шага: без `confirm` инструмент показывает статью и
  всю ветку под ней, а удаляет только повторный вызов. Обход дерева для этого
  списка — единственная своя логика внутри инструмента: API отвечает детьми
  одного уровня, а агенту нужен весь список.
- Инструменты чтения дерева отдают короткие записи. Полное тело статьи берётся
  `get-article`, и незачем тянуть его пачкой.
- Правило, которое агент должен соблюдать, живёт в `#[Description]`, а не в
  документации: документацию он может не открыть.
