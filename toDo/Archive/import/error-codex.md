# Импорт статей: найденные ошибки и риски

Файл составлен по текущему коду import/export, модели и миграции `articles`, frontend, routes,
генератору рабочих файлов, cleanup и архиву версий. Исходный код и существующая документация не
изменялись.

Обозначения:

- **ошибка** — реализация нарушает собственный контракт или оставляет неконсистентный результат;
- **риск** — опасный отказ, доверительная граница или незащищённый крайний случай;
- **документация** — заявленное поведение шире фактического;
- **покрытие** — поведение не закреплено автоматическими тестами.

## Критические

### 1. После проверки можно переключить partial на full и импортировать без нового preview

Статус: **ошибка интерфейса**.

Где:

- `admin/js/app/importAdmin/importAdmin.vue`.

`ready` сбрасывается при выборе файла и после run, но не при изменении `mode`. Сценарий:

1. администратор проверяет файл в partial mode;
2. `ready` становится `true`;
3. переключает radio на full;
4. кнопка «Импорт» остаётся доступной;
5. run отправляет уже `mode=full` и удаляет всё не-root дерево.

Сервер повторно выполняет технические проверки, но full plan намеренно не показывает список
потерь. Пользователь не видит новый preview для выбранного режима. Generic confirmation «Сайт
изменится» не сообщает о смене partial на full.

Желаемое направление: привязать readiness к hash файла и mode либо сбрасывать `ready/report` при
каждом изменении mode. Run должен подтверждать mode явно.

### 2. Генерация файлов после DB commit неатомарна и может оставить сайт в смешанном состоянии

Статус: **ошибка отказоустойчивости**.

Где:

- `src/Import/ImportTree.php`, `run()` и `generate()`;
- `admin/controller/MagicProBuilder.php`;
- `src/MagicFile.php`.

DB transaction заканчивается до `generate($gone)`. Генератор:

1. удаляет файлы исчезнувших статей;
2. последовательно пересоздаёт все статьи;
3. для controller сначала пишет PHP-файл и лишь затем запускает `php -l`;
4. останавливается на первом exception.

При ошибке база уже содержит новое дерево и не откатывается. Часть файлов может быть новой,
часть старой, часть удалённой. Синтаксически неверный controller остаётся записанным. API при этом
возвращает ошибку, что способно побудить пользователя повторить уже применённый импорт.

Существующая формулировка, что «упало на середине — не изменилось ничего», верна только для
ошибки внутри DB transaction и только применительно к таблице. Для операции целиком она неверна.

Желаемое направление: строить все файлы в staging, lint/compile до публикации, затем выполнять
контролируемое atomic переключение и иметь recovery по зафиксированному DB revision.

### 3. Проверка принимает имя статьи, с которым controller не может быть PHP-классом

Статус: **ошибка валидации с post-commit отказом**.

Где:

- `src/Import/ImportTree.php`, `readRow()`;
- `admin/controller/MagicProBuilder.php`;
- dynamic routing/controller naming.

Import validation разрешает дефис и цифру первым символом для любого `name`. Это допустимо для
Blade-only статьи, но controller class строится из имени статьи. Например:

```text
order-form
2026report
```

не являются допустимыми PHP class names. При `routeParams.useController=true` check будет
зелёным, DB commit пройдёт, затем generator запишет controller и `php -l` завершится ошибкой.

То же относится к любому синтаксически неверному тексту `controller`: первый проход его не
проверяет.

Желаемое направление: plan должен проверять conditional PHP-class contract и lint всех будущих
controllers до DB mutation.

### 4. Автоматические снимки молча перезаписываются в пределах одной минуты

Статус: **ошибка резервного копирования**.

Где:

- `src/Import/Snapshots.php`, `stamp()`/`save()`;
- `src/Import/ImportTree.php`, pre-import snapshot;
- `src/Cleanup/ArticleCheck.php`.

Автоматическое имя имеет точность до минуты:

```text
root_YYYY-MM-DD_HH-MM.json
cleanup_YYYY-MM-DD_HH-MM.json
```

`save()` пишет с overwrite и не проверяет существование. Два импорта в одну минуту заменяют
первый recovery point вторым без вопроса. Два cleanup-run в одну минуту имеют ту же проблему в
своём namespace.

После второго импорта файл с именем минуты содержит состояние непосредственно перед вторым
импортом, а не перед первым. Откат к исходному состоянию становится невозможен, если отдельной
копии нет.

Желаемое направление: уникальность до микросекунд/случайный suffix или exclusive create с
повторным выбором имени; automatic snapshots никогда не должны overwrite.

### 5. Подтверждение ручной перезаписи сравнивает ненормализованное имя

Статус: **ошибка резервного копирования**.

Где:

- `admin/js/app/CommonCom/Snapshots.vue`;
- `src/Import/Snapshots.php`, `fileName()`.

Frontend проверяет:

```text
existing.file === trimmedInput + ".json"
```

Затем backend:

- снимает уже введённое `.json` без учёта регистра;
- удаляет пробелы и все недопустимые символы;
- обрезает основу до 80 символов;
- может заменить пустой результат timestamp.

Примеры, при которых существующий файл может быть перезаписан без вопроса:

```text
input: before shop   existing: beforeshop.json
input: state.json    existing: state.json
input: state.JSON    existing: state.json
input: first 81+ chars whose normalized prefix already exists
```

Желаемое направление: backend сначала возвращает canonical filename и атомарно требует явный
overwrite flag для уже существующего файла. Frontend-проверка может быть только подсказкой.

### 6. Full import не требует `index` и `error404`

Статус: **риск разрушения системного дерева**.

Где:

- `src/Import/ImportTree.php`, full validation/apply.

В partial запрещён `root`, но в full нет проверки обязательных системных статей. Файл экспорта
обычного поддерева может быть выбран для full:

- текущие `index` и `error404` будут удалены;
- новые появятся только если присутствуют в файле;
- root останется старым;
- full report для корректного JSON будет пустым.

Главная страница и обработка 404 могут исчезнуть либо позже быть воссозданы Installer с default
content, но исходное содержимое уже потеряно.

Желаемое направление: определить поддерживаемые варианты full-файла и проверять обязательные
system articles либо показывать явный destructive report.

### 7. Импортируемый JSON содержит исполняемый код, но пользовательская документация этого не предупреждает

Статус: **риск безопасности документации**.

Поля `body` и `controller` становятся Blade и PHP-файлами. Администратор MagicPro и так имеет
право редактировать код статей, однако импорт файла из внешнего источника превращается в
установку чужого кода. `accept=.json` не является проверкой доверия или типа.

После импорта код может выполняться через route, Blade include/component или cron controller.

Желаемое направление: явное предупреждение перед выбором/подтверждением файла, просмотр diff
исполняемых полей и запрет считать JSON обычными данными.

## Высокий приоритет

### 8. «Проверить» не валидирует структуру и типы полей статьи

Статус: **ошибка полноты проверки**.

`readRow()` проверяет только row и `name`. Не проверяются:

- тип/длина `title`, `controller`, `body`;
- boolean fields;
- object shape `routeParams`;
- integer/range `npp`;
- `directory` относительно детей;
- длина `name` относительно DB/filesystem;
- PHP/Blade syntax;
- ожидаемая форма `parentName`.

Часть значений молча приводится PHP/Eloquent/DB, часть падает во время transaction, часть ломает
runtime уже после успешного импорта. Поэтому UI-сообщение «Файл годится» сильнее фактического
контракта.

Желаемое направление: versioned schema файла и полная validation до plan/report.

### 9. `directory` не поддерживается по фактической структуре

Статус: **ошибка целостности дерева**.

Импорт принимает `directory` из JSON как обычный boolean и не пересчитывает его.

Подтверждённые сценарии:

- новая top-статья присоединяется к существующему leaf-parent, но parent остаётся
  `directory=false`;
- удаление collision subtree может оставить старого parent с `directory=true`, хотя детей больше
  нет;
- JSON может заявить leaf как directory или parent как leaf;
- full без строки root может добавить root детей, сохранив прежний неверный flag.

Обычный API дерева специально поддерживает flag при move/create/delete, а ImportTree этот
инвариант обходит.

Желаемое направление: вычислять `directory` из результата дерева внутри transaction, не доверять
полю файла как источнику истины.

### 10. `npp` не проверяется и не нормализуется

Статус: **ошибка целостности дерева**.

Для внутренних imported siblings `npp` приводится к integer и пишется как есть. Разрешены ноль,
отрицательные значения, дубли и разрывы. Existing siblings не перенумеровываются.

Только top, присоединяемый к существующему parent, получает `max + 1`. В результате import может
создать одинаковые позиции, хотя обычный tree API управляет ими централизованно.

Желаемое направление: валидировать sibling positions или нормализовать весь итоговый sibling set
по детерминированному правилу.

### 11. `routeParams` может пройти импорт в форме, которая ломает маршрутизатор

Статус: **ошибка валидации**.

Модель имеет cast `array`, но не проверяет обязательные ключи и их типы. Import принимает null,
list, строку, неполный object и произвольные значения. DynamicRouteHandler читает часть ключей без
`??`, поэтому проблема проявляется при запросе страницы после успешного импорта.

Желаемое направление: единый normalizer/schema, используемый editor, ordinary API, import,
Installer, Cleanup и MCP.

### 12. Пробелы в `parentName` не обрезаются и молча меняют место статьи

Статус: **ошибка нормализации**.

`name` проходит trim, `parentName` — только string cast. Значение `" root "` не совпадает с
`"root"`:

- внутри файла ребёнок становится top;
- в partial oak parent не находится;
- статья уходит к root;
- в full внешний parent также заменяется root.

В partial появится `attach_root`, но причина не объясняет невидимые пробелы. В full report пуст.

Желаемое направление: одинаковая canonical normalization для name references до построения
графа.

### 13. Plan и применение не защищены от параллельных изменений

Статус: **риск гонки**.

Есть два окна:

- между отдельными HTTP `check` и `run`;
- между `plan()` внутри `run` и началом `DB::transaction()`.

Partial plan заранее вычисляет collision IDs, subtree, hooks и будущие parents без locks/revision.
Другой администратор или importer может изменить дерево после вычисления. Run повторяет plan
относительно check, но не фиксирует состояние между своим plan и apply.

Возможны отличный от preview report, rollback по исчезнувшему parent, collision во время save и
непредсказуемое `max(npp)+1`.

Желаемое направление: revision/hash дерева, transaction-level plan с подходящими locks или
single-writer import lock.

### 14. Снимок — не полный и не точный state сайта

Статус: **документация / риск восстановления**.

Snapshot равен export subtree от `id=1`. Он не содержит:

- numeric IDs non-root статей;
- timestamps;
- `templateName`;
- article version archive;
- другие таблицы/конфигурацию/файлы сайта;
- orphan/ring-компоненты, недостижимые от root.

При restore non-root статьи получают новые IDs и timestamps. Старые rows архива версий остаются
отдельно и не становятся версиями новых статей.

Фраза «снимок всего дерева, из которого сайт можно поднять обратно» допустима лишь для
согласованного дерева и экспортируемого логического содержимого, но не для состояния базы/сайта
в целом.

### 15. Cleanup делает снимок, который может не сохранить именно повреждённые данные

Статус: **ошибка recovery-контракта между модулями**.

`ArticleCheck::run()` вызывает `Snapshots::save()` до ремонта. Но exporter идёт только от root:

- orphan rows не попадут в JSON;
- ring и их descendants также недостижимы;
- invalid names попадут в файл, который ImportTree затем отвергнет;
- duplicate names попадут в файл, который restore отвергнет.

То есть pre-cleanup snapshot может быть неполным или невосстановимым именно тогда, когда cleanup
нужен больше всего.

Желаемое направление: аварийный снимок cleanup должен сохранять сырые строки независимо от
целостности дерева либо иметь отдельный восстановитель повреждённого формата.

### 16. Snapshot write и permissions не проверяются надёжно

Статус: **риск ложного резервного копирования**.

`Snapshots::save()`:

- пишет через `file_put_contents` без явной проверки return value;
- не использует `LOCK_EX`, exclusive create или atomic rename;
- применяет `chmod(0640)` после записи;
- подавляет и не проверяет ошибку chmod;
- возвращает имя как доказательство успеха.

Laravel error handler может превратить часть warnings в exception, но класс сам не гарантирует
полную запись и нужные permissions. При permissive umask между create и chmod существует окно с
более широкими правами.

Snapshot способен содержать закрытый контент и hard-coded данные из controllers/Blade.

### 17. Удаление исчезнувших generated files подавляет ошибки

Статус: **ошибка диагностики**.

`MagicProBuilder::delete_file()` вызывает `@unlink` и не проверяет результат. Если файл старой
статьи нельзя удалить, импорт продолжит работу и сообщит успех. На диске остаётся stale Blade или
controller без соответствующей статьи.

Желаемое направление: проверять удаление и включать leftover в recoverable generation report.

### 18. DB failure всё равно запускает перегенерацию файлов и может скрыть исходную ошибку

Статус: **ошибка обработки исключений**.

Catch вокруг transaction вызывает `generate([])`, затем повторно бросает original exception.
Однако `generate([])` само может упасть:

- оно переписывает файлы уже откатившегося старого дерева;
- failure генерации заменит original DB exception;
- несмотря на комментарий «no file was touched», catch намеренно трогает все существующие файлы.

Желаемое направление: сохранять primary exception, отдельно протоколировать recovery failure и
не обещать отсутствие файловых изменений.

### 19. Full report ничего не сообщает о фактически удаляемых статьях

Статус: **риск UX / осознанное ограничение**.

`planFull()` пуст. Для любого технически допустимого файла проверка показывает отсутствие
ошибок, независимо от количества удаляемых статей и отсутствия system articles.

Это задуманное сокращение отчёта, но оно делает первый проход слабой защитой перед destructive
операцией. Особенно опасно вместе с ошибкой смены mode.

Желаемое направление: хотя бы итоговые counts, системные потери и крупные категории; подробный
список можно сделать сворачиваемым.

## Средний приоритет

### 20. Источник файла не сохраняется и check не связан с run

Статус: **ограничение протокола**.

Сервер не выдаёт plan token/hash. Run можно вызвать напрямую; он не знает, был ли check показан
пользователю. Это нормально для внутреннего `plan()` перед применением, но внешнее обещание
обязательных «двух проходов» обеспечивает только Vue-state.

Direct API caller способен сразу выполнить full run. При усилении нельзя полагаться только на
disabled button.

### 21. Нет ограничений размера, числа строк и глубины

Статус: **риск доступности**.

Файл целиком читается FileReader, передаётся строкой внутри JSON, декодируется в массив и во время
API обработки существует в нескольких копиях. `order()` в глубокой цепочке имеет worst case
O(N²); partial добавляет запросы по именам/уровням, generate пишет всё итоговое дерево.

Реальные пределы наступают в browser memory, reverse proxy, web server, PHP body/time/memory и
DB. Timeout после DB commit особенно опасен из-за отдельной генерации файлов.

Желаемое направление: явные лимиты до decode/apply, оценка complexity и background job для
крупных импортов.

### 22. FileReader callbacks не привязаны к последнему выбранному файлу

Статус: **гонка интерфейса**.

Если быстро выбрать два файла, оба асинхронных reader callbacks могут завершиться в другом
порядке. Старый callback без проверки присвоит `text`, хотя `fileName` уже показывает новый файл.

Выбор каждого файла сбрасывает `ready`, поэтому старый проверенный plan не сохраняется, но
пользователь способен проверить содержимое не того файла, имя которого видит.

Желаемое направление: request/read generation ID либо abort предыдущего FileReader.

### 23. Snapshot `read()` и `delete()` не проверяют результат операции

Статус: **ошибка диагностики**.

После `path()`:

- `read()` приводит `file_get_contents()` к string без явной проверки false;
- `delete()` вызывает `unlink()` и игнорирует boolean result.

В Laravel warnings часто становятся exceptions, но класс не определяет собственный надёжный
контракт. При изменённом error handler read может превратиться в пустой JSON, а delete — показать
обновлённый список без ясной причины отказа.

### 24. Снимки не удаляются автоматически

Статус: **операционный риск, заявленное поведение**.

Каждый manual import/cleanup создаёт файлы в private storage, retention/size quota отсутствуют.
Кроме заполнения диска, snapshots накапливают прежний Blade/PHP content, который может содержать
чувствительные данные.

Нужны документированная retention policy, мониторинг свободного места и осознанное удаление.

### 25. Restore не создаёт снимок заменяемого состояния

Статус: **destructive contract, не скрытая ошибка**.

`snapshotRestore()` намеренно вызывает `ImportTree::run(..., FULL, false)`. UI спрашивает одно
подтверждение. Ошибка пользователя или устаревший snapshot не оставляют автоматической точки
возврата к состоянию перед restore.

Текущее решение заявлено в комментариях как осознанное, но безопасный пользовательский процесс
должен требовать отдельный manual snapshot/download перед восстановлением.

### 26. Import не записывает архив версий, а старые версии остаются по прежним ID

Статус: **ограничение интеграции**.

Обычное сохранение через articles API вызывает `ArticleArchive::add()`. Import создаёт/обновляет
модель напрямую и bulk-удаляет старые статьи. История:

- не фиксирует состояние статьи непосредственно перед заменой;
- не получает версии импортированных строк;
- сохраняет старые versions удалённых numeric IDs как orphan archive rows;
- не восстанавливается из snapshot.

Это согласуется с CHANGELOG, но должно быть явно известно разработчику и администратору.

### 27. Импорт не синхронизирует зависимые cron-задачи

Статус: **ограничение интеграции**.

Cron хранит `article|method` по имени. Строки cron при full import не меняются:

- задача продолжит работать, если импорт вернул совместимый controller;
- станет broken, если article/method исчез;
- может начать выполнять другой код при повторном использовании того же имени.

Cron UI обнаруживает часть проблем при list/check, но import report о них не сообщает.

### 28. Snapshot path защищён именем, но не запрещает filesystem symlink

Статус: **defense-in-depth риск**.

Строгий mask исключает slash/path traversal через HTTP. Но `is_file()` и filesystem functions
следуют symbolic links. Процесс или пользователь с правом записи в snapshot directory может
создать link с допустимым `.json` именем:

- download/read пойдут к target;
- save с тем же именем может записать target;
- delete удалит сам link.

Удалённый неавторизованный пользователь создать такой link не может; риск требует отдельного
filesystem доступа. Для private backup directory всё равно полезны `lstat`/regular-file policy и
безопасные ownership/permissions.

### 29. Даты снимков смешивают timezone браузера и сервера

Статус: **UX / операционный риск**.

Default manual name формирует browser JavaScript, автоматический stamp и колонку `date` — PHP
server. При разных timezone имя и показанное время могут расходиться, что затрудняет выбор точки
восстановления.

Нужна явная timezone в UI/metadata либо единый server-generated timestamp.

### 30. Страница доступна любому вошедшему guard-user, API — только admin

Статус: **UX / authorization consistency**.

Route страницы не использует `magic.auth`; template показывает body любому пользователю,
прошедшему `@mproauth`. API middleware без ролей по умолчанию требует `admin`. Не-admin видит
destructive controls, но получает 403 при запросах.

Это не даёт операции без прав, но вводит в заблуждение и раскрывает ненужный интерфейс.

### 31. Для destructive POST API явно отключён CSRF middleware

Статус: **риск безопасности**.

`POST /a_dmin/api/import` защищён session-based `magic.auth`, но исключён из CSRF middleware.
Browser SameSite/CORS и JSON content type уменьшают часть cross-site сценариев, однако endpoint
сам не требует CSRF token, а принимает и не-JSON request parameters через `$request->all()`.

Full import, restore и delete snapshot не имеют дополнительного server-side confirmation token.
Нужно пересмотреть защиту в контексте общей архитектуры admin API, не ломая прямых клиентов.

### 32. Ошибка API раскрывает абсолютный путь и строку сервера

Статус: **низкий риск information disclosure**.

`AbstractApi` возвращает поле:

```json
{"line":"/absolute/path/File.php 123"}
```

Import endpoint доступен admin, поэтому это не публичная утечка. Но frontend не нуждается в
absolute filesystem layout; такие данные лучше оставлять в server log с correlation ID.

### 33. Возможна зависимость duplicate-name проверки от collation базы

Статус: **риск переносимости**.

Массив `$rows` различает регистр PHP-ключей, поэтому `About` и `about` считаются разными. Запрос
`Article::where('name', ...)` и model uniqueness зависят от collation БД и могут считать их
одинаковыми. DB unique constraint отсутствует.

На case-insensitive collation check способен пропустить конфликт внутри файла, а apply упадёт
во время model save. Нужен явно выбранный case contract, одинаковый в PHP и DB.

### 34. Список снимков не требует regular file до чтения metadata

Статус: **низкий риск диагностики**.

`Snapshots::all()` фильтрует только имя. Directory или специальный filesystem entry с допустимым
именем может попасть в `filesize/filemtime` и UI, тогда `path()` позднее отклонит его через
`is_file()`. Следует фильтровать type до metadata.

## Покрытие

### 35. Автоматических тестов import/snapshot не найдено

Статус: **покрытие**.

В `src/test` найдены только mail tests и вспомогательный user seeder. Тестов для следующих
контрактов нет:

- parser/order/report codes;
- partial/full apply;
- collision subtree;
- root semantics;
- DB rollback и post-commit generation failure;
- snapshot naming/overwrite/I/O;
- restore/delete/download;
- frontend readiness и mode change;
- authorization/CSRF;
- archive/cron interactions.

Из-за destructive поведения и двухсистемной границы DB/filesystem отсутствие failure-injection
tests является существенным риском.

## Приоритет исправления

Предлагаемая последовательность независимых изменений:

1. Сбрасывать preview при смене mode и показывать явный full summary/system-article validation.
2. Валидировать полный versioned JSON contract и все будущие controllers до DB mutation.
3. Исправить atomic publication generated files и recovery после post-commit failure.
4. Пересчитывать tree invariants `directory` и `npp` внутри transaction.
5. Сделать snapshots collision-free, атомарными и проверяемыми; исправить canonical overwrite.
6. Отделить логический export от аварийного raw backup cleanup.
7. Связать plan с revision/lock и исключить параллельных writers.
8. Зафиксировать contracts archive, cron, IDs и system articles.
9. Пересмотреть CSRF/role consistency и filesystem hardening.
10. Покрыть parser, apply и все точки отказа тестами до дальнейшего расширения формата.
