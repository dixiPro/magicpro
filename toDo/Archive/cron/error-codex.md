# Найденные ошибки и расхождения cron-подсистемы

Файл составлен при сверке `Readme.md`, `CHANGELOG.md`, `docs/ru/cron/`, почти
готовой документации `docs/ru/image/`, классов расписания, модели, миграции,
генератора статей, маршрутов и интерфейса. Код и существующие документы не
исправлялись.

## Подтверждённые расхождения

### 1. process() объявлен необязательным, но требуется базовым классом

`docs/ru/cron/use.md` говорит, что `process()` для cron-статьи не обязателен.
`MagicController` при этом абстрактный и объявляет:

```php
abstract protected function process(array $params): array;
```

Обычный контроллер статьи наследует `MagicController`, поэтому без реализации
`process()` класс останется абстрактным или не пройдёт загрузку. Для статьи без
маршрута метод может только возвращать `[]`, но удалить его нельзя.

### 2. PHPDoc MagicProBuilder связывает контроллер с isRoute вопреки коду

PHPDoc `admin/controller/MagicProBuilder.php` говорит, что при `isRoute=false`
контроллер удаляется.

Реализация `createMpro()` не использует `isRoute` при решении о контроллере. Она
записывает его, когда текст непустой и включён `routeParams.useController`.
Именно это позволяет статье без маршрута быть носителем cron-задачи. Комментарий
противоречит и коду, и назначению подсистемы.

### 3. Невалидный JSON параметров молча превращается в пустой массив

`API_Cron::readParams()` декодирует строку через `json_decode($params, true)`, но
не проверяет `json_last_error()` и не использует `JSON_THROW_ON_ERROR`.

При синтаксической ошибке `json_decode()` возвращает `null`, после чего следующая
ветка принимает `null` как пустые параметры. Например, строка с пропущенной
кавычкой будет сохранена как `[]`, хотя API содержит специальную ошибку
`params must be a json object`.

Непустой литерал `null` проходит тем же путём. В результате оператор видит
успешное сохранение и может запустить задачу без требуемых параметров.

### 4. Комментарии называют params POST-параметрами, хотя HTTP-вызова нет

Комментарий колонки `params` в миграции говорит `always sent as POST`, а PHPDoc
`API_Cron::readParams()` — `it goes into the request as post`.

`CronTaskRunner` фактически вызывает метод напрямую:

```php
$controller->{$method}($params);
```

Массив не становится POST, не помещается в Request и не получает оболочку
`postParams`.

### 5. last_run_at обновляет не только планировщик

`docs/ru/cron/inside.md`, модель и `CHANGELOG.md` описывают `last_run_at` как
отметку того, что Scheduler дошёл до задачи.

Кнопка `runNow` использует тот же `CronTaskRunner::run()`, который безусловно
сохраняет `last_run_at` перед вызовом. Поэтому поле отражает последнюю ручную
или автоматическую попытку, а не только работу Scheduler.

### 6. Документированное имя cron.log не совпадает с реальным файлом

`docs/ru/cron/use.md`, `inside.md` и PHPDoc `CronTaskRunner::LOG` называют
`storage/logs/cron.log`.

`MproHelper::addLog()` передаёт этот путь в Monolog `RotatingFileHandler` со
стандартным шаблоном `{filename}-{date}`. Реальная дневная запись идёт в:

```text
storage/logs/cron-YYYY-MM-DD.log
```

Базовый `cron.log` служит только входным именем для handler и сам не является
текущим файлом лога.

### 7. Не все ошибки лога имеют обещанные поля

`docs/ru/cron/use.md` говорит, что беды всегда содержат `id`, `name`,
`controller`, `method`, `error`, `ms`.

Ошибка регистрации cron-выражения пишется из `MagicProSchedule` в другой форме:

```text
stage, id, name, error
```

В ней нет `controller`, `method` и `ms`. Ошибка чтения таблицы активных задач
вообще проглатывается без записи. Обещание «всегда» неверно.

### 8. Таймзона расписания описана не полностью

`docs/ru/cron/use.md` называет временем задачи `config('app.timezone')`.

Laravel создаёт `Schedule` с
`config('app.schedule_timezone', config('app.timezone'))`. Если
`app.schedule_timezone` задан отдельно, задача вычисляется в нём, а не в
`app.timezone` и не обязательно в системной таймзоне сервера.

### 9. У runNow есть HTTP-контекст, несмотря на общее утверждение документации

`docs/ru/cron/use.md` без оговорки говорит, что вокруг метода нет Request,
сессии и вошедшего пользователя.

Для автоматического запуска это верно. `runNow` вызывается из защищённого HTTP
API, поэтому текущий Request, сессия и guard уже находятся в приложении. Метод,
завязанный на них, способен успешно пройти кнопку и упасть при запуске из
консоли.

### 10. В описании MagicProSchedule пропущена уборка AI-сеансов

`docs/ru/cron/inside.md` перечисляет heartbeat и почтовую очередь перед
динамическими задачами.

Текущий `MagicProSchedule::register()` между почтой и динамическими задачами
также ежеминутно регистрирует `magicpro:aiCleanup` с `AiSession::cleanup()`.
Внутреннее описание порядка регистрации устарело.

### 11. CHANGELOG ссылается на отсутствующий MagicController::run()

Запись от 2026-08-25 утверждает, что `MagicController::run()` позволяет
использовать контроллеры как сервисы.

У текущего `MagicController` публичен только `handle()`; метода `run()` нет.
Прямой сервисный вызов реализован в `CronTaskRunner`, а не в базовом
контроллере.

### 12. article|handle принимается и способен замаскировать ошибку как успех

Checker запрещает PHP magic methods правилом имени, но разрешает строку
`article|handle`. `handle()` — публичный inherited-метод `MagicController`.

Раннер вызовет его с обычными cron-параметрами. Внутри `handle()` ожидается ключ
`request`, однако собственный `try/catch` метода превращает возникшую ошибку в
HTTP response 500. `CronTaskRunner` этот response выбрасывает, не видит
исключения и пишет успешный запуск.

Это противоречит утверждению документации и CHANGELOG, что `handle()` больше не
участвует и исключения cron-метода не проглатываются.

### 13. Гость получает 500 на странице /a_dmin/cron

Маршрут страницы не защищён `magic.auth`. В дочернем Blade до решения шаблона об
авторизации вычисляется:

```php
Auth::guard('magic')->user()->role
```

У гостя `user()` равен `null`, поэтому прямое открытие `/a_dmin/cron` приводит к
ошибке вместо формы входа. POST API защищён корректно. Эта проблема уже отмечена
в `toDo/tail_&_idea/2026-08-29-audit.md`, но в коде остаётся.

## Риски реализации

Ниже перечислены свойства, которые следуют из текущего кода. Некоторые из них
могут быть допустимым решением, но программисту нужно учитывать их при
изменениях.

### 14. Автоматический путь не повторяет валидацию имени метода

`save`, `list` и `runNow` используют полный `CronTaskChecker`. Планировщик его
не вызывает: раннер проверяет только непустые части и наличие класса.

Старая или созданная вне API строка с `__construct`, `handle` либо другим
непредусмотренным публичным методом может быть вызвана автоматически, хотя
текущий UI такую новую строку не сохранит.

### 15. Ошибка логгера может выйти из CronTaskRunner

Успешный `self::log()` находится внутри основного `try`, но после его ошибки
ветка `catch` вызывает тот же логгер повторно без дополнительного перехвата.
Логирование обычной ошибки задачи устроено так же.

Если каталог логов недоступен или handler бросает исключение, `run()` не
вернёт обещанный массив `ms/error`. Laravel поймает ошибку scheduled event на
своём уровне, но в cron-логе записи не будет; HTTP `runNow` получит внешнее
исключение.

Та же граница есть в `MagicProSchedule`: логирование невалидного cron-выражения
выполняется уже внутри `catch` и не защищено повторным перехватом. Ошибка
логгера выйдет из регистрации и способна сорвать построение всего расписания,
включая ранее добавленные heartbeat, почту и AI cleanup.

### 16. Успешный лог сохраняет все параметры

При включённом `CRON_LOG_SUCCESS` массив `params` сериализуется целиком. Токены,
пароли и персональные данные из параметров задачи окажутся в дневных логах и
будут храниться до ротации.

### 17. withoutOverlapping не гарантирует единственный запуск на кластере

Динамические события не используют `onOneServer()`. На нескольких серверах с
локальными cache stores одна задача выполняется на каждом узле.

Даже при общем cache `withoutOverlapping()` решает наложение по времени, а не
полную семантику единственного исполнителя для распределённой системы. После
освобождения mutex другой due-процесс может выполнить тот же callback.

### 18. Аварийный mutex может блокировать задачу сутки

`withoutOverlapping()` вызван без аргумента, поэтому expiry Laravel равен 1440
минутам. После штатного завершения lock снимается, но после жёсткого завершения
процесса задача может пропускаться до 24 часов.

### 19. Невалидное расписание создаёт запись в лог каждую минуту

API не позволяет сохранить новую неправильную строку, но устаревшие или
изменённые вне API данные возможны. Такая enabled-задача остаётся в таблице, и
каждый новый `schedule:run` снова пишет ошибку `stage: register`. Автоматического
отключения и подавления повторов нет.

### 20. Ручной запуск не имеет mutex и держит HTTP-запрос

`runNow` не смотрит `enabled`, не получает lock и выполняется синхронно. Двойной
клик частично ограничивает локальный `apiActive` одной вкладки, но другой
браузер, вкладка или прямой API-запрос может запустить ту же работу параллельно
с расписанием.

Для долгой задачи добавляется риск таймаута веб-сервера или PHP, которого нет у
обычного консольного запуска.

### 21. Для cron-подсистемы нет выделенных автоматических тестов

В пакете не найдено тестов для `API_Cron`, `CronTaskChecker`,
`CronTaskRunner`, динамической регистрации, mutex и heartbeat. Ошибки на
границах ручного и автоматического путей сейчас обнаруживаются только чтением
кода или ручной проверкой.
