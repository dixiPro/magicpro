# ТЗ v4: регистрация и вход на сайте

Четвёртая версия. Основа — `tzAuth3.md` (решения владельца) и примеры писем
`authLetter.md`. Предыдущие: `tzAuth.md` (разбор Alpine-формы из другого
проекта), `tzAuth2.md` (коды `situation` для нынешнего `API_Auth`).

## Сценарии

**Email не зарегистрирован.** Ввёл email → «Зарегистрировать?»
ушло письмо `authLetter` со ссылкой → переход по ссылке → ввод пароля → регистрация, вход, письмо `postLetter`, переход на `postUrl`.

**Email зарегистрирован.** Ввёл email → ввёл пароль → вход, переход на `postUrl`.

**Забыл пароль.** «Забыли пароль?» → ушло письмо `resetPasswordLetter` со
ссылкой → переход по ссылке → страница с полем нового пароля → смена пароля,
вход, переход на `postUrl`.

## Принцип: регистрация без записей в базе

До перехода по ссылке в базе ничего не создаётся — ни заявки на регистрацию, ни
токена. Всё, что нужно, лежит в самой ссылке, зашифрованное ключом приложения.

Почему: человек отправил письмо дважды, получил оба и нажал на первое. С
таблицей заявок первое письмо было бы уже недействительным — «идите и делайте всё
заново». Здесь любой ещё не просроченный токен работает, клиента не теряем. И
хранить нечего.

```php
// идея, не окончательный код
$token = crypt([$email, $password, $postUrl, time()]);
$authLinkUrl = $authUrl . '/mode/regByToken/token/' . $token;

// registerUserByToken
$data = decrypt($token);
// $data[3] моложе суток → регистрируем
```

Так уже устроена нынешняя регистрация письмом в пакете (`cryptEmailPass` /
`decryptEmailPass` в `API_Auth`): email, пароль, время и адрес возврата,
`Crypt::encryptString`, срок 24 часа.

## Настройки

Задаются в админке, на странице модуля:

| Ключ                  | Что это                                           |
| --------------------- | ------------------------------------------------- |
| `authUrl`             | страница регистрации и входа сайта — одна на сайт |
| `postUrl`             | куда вести после регистрации или входа            |
| `authLetter`          | блейд письма подтверждения email                  |
| `postLetter`          | блейд письма после регистрации                    |
| `resetPasswordLetter` | блейд письма смены пароля                         |

## API `apiAuth`

Одна точка `POST`, как во всём пакете: `command` и параметры. Ответ — формат
пакета: `status`, `errorMsg`, `data`.

| Команда                   | Параметры                | В `data` при успехе             |
| ------------------------- | ------------------------ | ------------------------------- |
| `checkEmail`              | `email`, `gToken`        | `emailToken`, `emailActive`     |
| `sendRegisterEmail`       | `emailToken`, `password` | —                               |
| `auth`                    | `emailToken`, `password` | — (дальше переход на `postUrl`) |
| `sendChangePasswordEmail` | `emailToken`             | —                               |
| `registerUserByToken`     | `token`                  | — (вход, `postLetter`)          |
| `changePassword`          | `token`, `password`      | — (вход)                        |

- **`checkEmail`** — проверяет email на валидность и есть ли он в базе.
  `emailToken` — зашифрованный email и время создания. `emailActive` — есть ли пользователь с таким email.
- **`sendRegisterEmail`** — отправляет `authLetter` со ссылкой регистрации.
- **`auth`** — вход по email из `emailToken` и паролю.
- **`sendChangePasswordEmail`** — отправляет `resetPasswordLetter` со ссылкой смены пароля.
- **`registerUserByToken`** — регистрирует по токену из ссылки, входит, отправляет `postLetter`.
- **`changePassword`** — по токену из ссылки меняет пароль, входит.

При ошибке в `data` — `errorCode`, код ошибки; страница выбирает текст по нему.

## Страница регистрации (`authUrl`)

Одна статья, режим задаётся параметрами адреса парами `ключ/значение`:

| Адрес                                     | Режим                                                                                             |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `/auth`                                   | форма: email → пароль или регистрация, «забыли пароль»                                            |
| `/auth/mode/regByToken/token/<token>`     | запрашивает пароль, зовёт `registerUserByToken`; успех — вход, `postLetter`, переход на `postUrl` |
| `/auth/mode/changePassword/token/<token>` | поле нового пароля; `changePassword`; успех — вход, переход на `postUrl`                          |

Параметры маршрута статьи: `getEnable: true`, `keysArr: ["mode", "token"]`,
`bindKeys: false` — тогда `/auth` без параметров тоже открывается. (С
`bindKeys: true` число сегментов должно точно совпадать с числом ключей, и
голый `/auth` дал бы 404.)

Фронт — Alpine.js.

## Письма

Блейды писем — статьи сайта, их имена в настройках. Переменные подставляет API:

| Письмо                | Переменные                                    |
| --------------------- | --------------------------------------------- |
| `authLetter`          | `$authLinkUrl` — ссылка регистрации           |
| `postLetter`          | `$userEmail`, `$userPassword`                 |
| `resetPasswordLetter` | `$authResetPasswordUrl` — ссылка смены пароля |

Примеры — `authLetter.md`.

или товар, всё без переходов. `postUrl` можно задать в самой форме.

## Вопросы

1. **Формат ответа.** В `tzAuth3.md` в примерах `status: "1"` строкой и поля
   `errorCode`, `emailToken`, `emailActive` на верхнем уровне, а рядом — «как во
   всём пакете». В пакете ответ `status` (true/false), `errorMsg`, `data`. Здесь
   поля положены в `data` — так?

   > Как в прошлых апи

2. **Куда ведёт ссылка из письма.** В `tzAuth3.md` — на страницу `authUrl` с
   `mode/regByToken`, страница зовёт API. В `authLetter.md` — «клиент тыкает на
   ссылку, попадает на АПИ… если нет — улетает на `authUrl`», то есть ссылка
   ведёт прямо в API. Какой вариант?

   > Ссылка из письма ведет на страницу authUrl, если ее нет, то всё, приплыли.

3. **Пароль открытым текстом в `postLetter`** (`$userPassword`). Письма хранятся
   в ящике годами и пересылаются. Оставляем?

   > Да, и вот почему. Можно не указыать в шаблоне. А написать, пароль указанный при регистрации. Проблема решена, но пусть будет.

4. **Ссылка смены пароля без записи в базе** живёт весь срок, даже после смены
   пароля: по ней можно сменить пароль ещё раз. Устраивает, или токен должен
   переставать работать после смены (например, в токен кладётся отпечаток
   текущего хеша пароля — запись в базе не нужна)?

   > добавить три поля в админку сколько живут токены

5. **Двойной переход по ссылке регистрации.** Пользователь уже создан первым
   кликом. Второй клик — вход (как сейчас в `processNewUser`), или ошибка «уже
   зарегистрирован»?

   > Просто авторизуем тихо.

6. **Срок `emailToken`** и нужен ли `gToken` (reCAPTCHA) кроме `checkEmail` —
   например, на `sendRegisterEmail` и `sendChangePasswordEmail`, чтобы письма не
   рассылались ботом. Сейчас повтор письма на тот же адрес — не чаще раза в 10
   минут; оставляем?

   > Да

7. **`checkEmail` говорит, есть ли email в базе** — по нему можно проверять,
   зарегистрирован ли человек на сайте. Для сценария это нужно; принимаем?
